## 1. 当前结论与本版目标

当前项目不是“从零开始”，也没有全部完成。冻结基线为：269 条可判定要求中，132 条完成、90 条部分完成、42 条未做、5 条不适用；42 条未做可归并为 25 组功能缺口。主体链路已经能从事件进入 Landing，经 Hive/Spark 形成 ODS、DWD、DWS、ADS，并发布到指标库供页面、AI 和决策读取，但仍存在“有表无数据、有算法未接线、有接口无页面”和证据不足的问题。

V2.1 不推翻已完成链路，重点完成四件事：

1. 将现有“两程序”改成三个可独立构建、部署、停止和替换的程序：分析平台、参考商城、模拟数据生成器。
2. 建立真正可更换商城的数据源连接器与字段映射层，清除 `mock-mall` 等硬编码。
3. 把剩余 25 组缺口拆成开发 Agent 可直接执行、可单独验收的小任务。
4. 使用分层测试、固定小数据和并行泳道提高开发速度；大规模数据只在里程碑运行。

### 1.1 当前阶段不做的事

- 不撰写论文正文、摘要、结论、答辩稿，不为了论文包装未完成能力。
- 可以记录真实的架构决策、缺陷根因、修复过程、前后数据和测试证据。
- 未在相同环境、相同数据和相同口径下测量的“提升百分比”不得填写。
- ClickHouse 只保留接口和能力矩阵，状态为 `DEFERRED`；第一阶段不实现。
- 100 万条数据不进入日常回归，只在最终性能里程碑执行。

### 2.2 执行状态

执行任务只允许使用 `TODO / READY / IN_PROGRESS / BLOCKED / REVIEW / DONE_LIMITED / DONE / REGRESSED / DEFERRED / N/A`。代码、表、接口或页面单独存在不等于完成；普通功能至少需要 E2 自动化证据，数据链需要 E3 本地真实链证据，集群能力需要 E4，普通员工可用的页面路径需要 E5。

### 2.3 反馈要求

- 开工前在看板登记任务 ID、Owner、允许修改范围和下次反馈时间。
- 最长 30 分钟更新一次；失败、阻塞或范围变化立即更新。
- 代码写完只能进入 `REVIEW`；通过目标测试并附证据后才能标 `DONE`。
- 开发 Agent 只执行分配的任务 ID，不得自行设计新模块或顺手改其他模块。
- 总控负责契约、热点文件、合并、跨模块测试与最终状态确认。

## 3. 三程序架构裁决

### 3.1 最终边界

| 程序 | 建议名称/端口 | 唯一职责 | 明确禁止 |
|---|---|---|---|
| 分析平台 | `analytics-platform` / 8091 | 数据源配置、采集编排、标准化、Landing、Hive 数仓、Spark 作业、质量、指标发布、看板、AI、决策、运维 | 商城业务增删改；随机造订单；依赖商城数据库或 Java 包 |
| 参考商城 | `reference-mall` / 8090 | 用户、商品、分类、库存、购物车、订单、支付、退款、Outbox 事件 | 分析任务、Spark/Hive、生成场景、直接写分析平台 |
| 模拟数据生成器 | `synthetic-data-generator` / 8092 或 CLI | 固定 seed 的场景生成、负载控制、脏数据策略、运行报告 | 直接操作商城数据库；依赖商城内部 Service/Mapper；写平台业务库；触发平台流水线 |

另外建立中立的 `contract-specs`，保存版本化 JSON Schema、OpenAPI 和清单 Schema。三个程序可以分别根据契约生成或校验数据，但不得通过共享 Java 实体、Mapper 或 Maven 业务依赖耦合。

### 3.2 唯一正常业务路径

```text
模拟数据生成器 --公开 HTTP API--> 参考商城 --Outbox/事件文件--> 数据源连接器
真实商城 -----------------------------------------------> 数据源连接器
数据源连接器 -> HDFS/本地 Landing -> 标准化 -> Hive ODS/DWD/DWS/ADS
             -> 质量门 -> MySQL ACTIVE 指标快照 -> 页面/AI/决策
```

这条路径表达两个关键事实：

- 参考商城只是可替换的数据提供者和演示样例，不是分析平台的一部分。
- 模拟数据生成器只是测试客户端。没有生成器、没有参考商城时，分析平台仍必须能连接其他商城并读取历史 ACTIVE 快照。

### 3.3 生成器的两种模式

#### A. `MALL_API` 模式

用于完整演示。生成器通过 `MallTargetAdapter` 调用商城公开接口完成注册、浏览、加购、下单、支付、取消、退款等行为。禁止调用商城内部类、直接连接商城数据库或修改库存表。

脏数据不得在此模式中绕过商城校验直接写库；需要验证平台隔离能力时，使用 B 模式。

#### B. `CANONICAL_EVENT_FILE` 模式

用于采集、质量、数仓和性能测试。生成器直接输出符合指定契约版本的 JSONL、manifest 和可选脏样本，写入独立测试目录。该模式必须显示 `synthetic=true`，不能被描述为商城端到端测试，也不得直接写 ODS/DWD/ADS/指标库或自动触发流水线。

### 3.4 独立验收

1. 三个程序有独立构建产物、配置、端口、日志和启动命令。
2. 商城工程中不存在 `generator` 包、`GeneratorController` 或生成器页面。
3. 生成器工程不引用商城实体、Mapper、Service、数据源配置，也不能访问商城 JDBC。
4. 分析平台不引用商城/生成器 Java 包、商城表或 `mall.*` 配置键。
5. 分别停止三者：其余程序不会因类加载或数据库依赖崩溃；停止数据源时平台明确显示采集不可用，但历史指标仍可读。
6. 可以用第二个 `MallTargetAdapter` 或一份不同字段的夹具证明平台不是为 `mock-mall` 写死。

## 4. 模拟数据生成器详细设计

### 4.1 核心接口

```java
interface MallTargetAdapter {
    TargetCheckResult test(TargetConfig config);
    TargetCapabilities capabilities();
    ProductPage listProducts(ProductQuery query);
    ExternalUser createSyntheticUser(UserCommand command);
    void emitBehavior(BehaviorCommand command);
    ExternalOrder createOrder(OrderCommand command);
    ExternalOrder pay(PayCommand command);
    ExternalOrder cancel(CancelCommand command);
    ExternalRefund refund(RefundCommand command);
}

interface EventSink {
    void write(CanonicalEvent event);
    Optional<Artifact> rotateIfNeeded();
    void flush();
    Manifest closeAndBuildManifest();
}
```

第一版实现 `ReferenceMallHttpAdapter` 与 `JsonlEventSink`。扩展其他商城时新增 Adapter，不修改场景引擎。

### 4.2 数据结构

| 对象/表 | 关键字段 | 约束与用途 |
|---|---|---|
| `generator_target` | id、name、adapter_type、base_url、credential_ref、config_json、config_version、status、test_environment、capabilities | 凭据只存引用；每次运行冻结版本 |
| `generation_plan` | plan_id、mode、target_id、scenario、seed、start/end、event_count、rate_per_second、dirty_profile、output_uri、version | 运行只引用不可变版本 |
| `generation_run` | run_id、plan_version、target_version、status、started/finished、success_count、failed_count、checksum、error、cancel_requested | 异步运行，可查询和取消 |
| `generation_artifact` | run_id、uri、checksum、bytes、record_count、min/max_event_time、schema_version | 用于可复现和对账 |
| `generation_event_stat` | run_id、event_type、count、amount | 验证各事件类型和金额分布 |

状态机：`PENDING -> RUNNING -> SUCCESS/FAILED/CANCELLED`。相同 `plan_version + seed + time_window` 应可复现；运行中修改计划不会影响已启动任务。

### 4.3 场景和算法

- 商品抽样：类别先按目标权重抽样，类别内采用 Zipf/长尾分布，避免所有商品热度相同。
- 用户分层：新客、活跃、沉睡、高价值、价格敏感等分群使用可配置比例。
- 时间分布：工作日/周末、小时段和活动峰值使用分段权重；不能简单均匀随机。
- 行为链：浏览→收藏/加购→下单→支付→退款使用条件概率，且订单必须引用已存在用户与商品。
- 金额：使用 `BigDecimal`；商品价格、数量、优惠、实付和退款遵守商城公式。
- 库存：MALL_API 模式只通过商城接口变化；失败必须记入运行报告，不能绕过业务规则。
- 可复现：所有随机源由一个根 seed 派生；并行线程也使用确定性子 seed。
- 异常样本：仅在文件模式注入缺字段、未知枚举、重复 eventId、非法金额、迟到事件和非法状态跳转，并在 manifest 中记录期望隔离数。

### 4.4 对外 API

- `POST /api/v1/generation-runs`：按 plan/version 异步启动，返回 runId。
- `GET /api/v1/generation-runs/{id}`：状态、进度、计数、失败摘要。
- `POST /api/v1/generation-runs/{id}/cancel`：幂等取消。
- `GET /api/v1/generation-runs/{id}/artifacts`：文件、checksum、清单。
- `GET /api/v1/scenarios`：场景定义和输入约束。
- `POST/PUT/GET /api/v1/targets` 与 `POST /targets/{id}/test`：目标商城配置和连通性检查。

### 4.5 页面

生成器拥有自己的简洁页面或 CLI，不再出现在 `mall-frontend`：目标商城、场景计划、运行列表、实时进度、失败明细、产物下载。商城页面只面向购物者和商城管理者；分析平台页面只面向分析与运营人员。

## 5. 可更换商城的数据源与连接器

### 5.1 平台统一标识

外部商城不能自行决定平台主键。平台创建 `source_instance_id`，它从 Landing manifest 传播到 ODS、DWD、DWS、ADS、指标快照和页面筛选。跨商城去重键为 `(source_instance_id, event_id)`，不能只按 `event_id` 去重。

第一阶段可限制“一次流水线只处理一个 source instance”，但任何表、Java/Scala 常量、配置键和页面不得写死 `mock-mall`。

### 5.2 元数据结构

| 表 | 关键字段 | 说明 |
|---|---|---|
| `source_instance` | id、tenant_id、code、name、business_type、timezone、currency、status、created_at | 表示一个具体商城/租户 |
| `source_connector` | id、source_instance_id、type、config_json、credential_ref、version、status、capability_json、last_test_result | 表示采集方式和版本 |
| `schema_mapping` | id、source_schema_version、target_contract_version、event_type_map、field_mapping_json、enum_mapping_json、timezone、amount_unit、transform_policy、status、version | 把源字段映射为平台契约 |
| `source_manifest` | batch_id、source_instance_id、connector_version、mapping_version、uri、checksum、record_count、min/max_event_time、event_type_counts、contract_version | 批次溯源与对账 |
| `ingestion_batch_file` | batch_id、file_uri、start/end_offset、checksum、accepted、quarantined、parse_errors | 文件级证据 |
| `file_checkpoint` | connector_id、file_identity、offset、updated_at | 断点必须绑定连接器 |

### 5.3 连接器接口

```java
interface SourceConnector {
    ConnectorType type();
    CapabilitySet capabilities();
    ConnectorTestResult test(ConnectorContext context);
    DiscoveryResult discover(Checkpoint checkpoint);
    FetchResult fetch(SourceObject object, LandingStorage storage);
    Checkpoint commitAfterSuccess(FetchResult result);
}
```

首期：`LocalFileConnector` 和 `FlumeLandingConnector`。Flume 已负责投递到 Landing 时，连接器不重复搬运数据，而是管理配置、心跳、目标 URI、批次发现和 manifest。DataX/Kafka 只登记类型、配置 Schema 和 `NOT_IMPLEMENTED/DEFERRED` 能力，不能显示为可用。

### 5.4 标准化与映射

采集只负责可靠移动和断点；`EventNormalizer` 负责源事件到 canonical event 的转换：事件类型映射、JSONPath 字段提取、枚举映射、时区转换、金额单位转换和允许的纯函数变换。禁止在映射表达式中执行任意脚本或 SQL。

未知源版本、没有 ACTIVE mapping、必填字段缺失和不允许的转换全部进入 quarantine，并保存 source instance、mapping version、reason code 和原始位置。映射激活必须先用样本 dry-run，并输出接受/隔离/错误计数。

### 5.5 数据源页面

普通员工在分析平台中看到“数据源”，而不是填写 `runtimeProfileId`。页面包括：商城名称、连接器类型、状态、最后心跳、最近批次、映射版本、测试连接、启停和查看错误。运行环境档案属于管理员配置；数据源选择使用可读名称。

## 6. 集群、HDFS、Hive 与 Spark 运行方案

### 6.1 不绑定 node01–03，运行能力必须正交配置

node01–03 是一个可选运行环境，不是代码常量。不能再仅凭 `LOCAL / SINGLE_NODE / REMOTE_CLUSTER` 推断所有行为，因为“平台部署在哪里”“Landing 存在哪里”“Spark 由谁提交”“Spark 使用哪种集群管理器”是四个相互独立的维度。例如，平台部署在 node01 时可以由本地进程提交 YARN；平台部署在 Windows 时才需要先 SSH 到提交网关。

`RuntimeProfile` 至少显式区分：

- `platformPlacement`：WINDOWS_LOCAL / LINUX_LOCAL / CLUSTER_GATEWAY，仅用于说明部署位置。
- `landingStoreType`：LOCAL / HDFS。
- `sparkSubmitterType`：LOCAL_PROCESS / SSH。
- `clusterManager`：LOCAL / YARN / STANDALONE。
- `hiveMetastoreUris`：`thrift://host:9083`，供 Spark/Hive catalog 使用。
- `hiveJdbcUrl`：`jdbc:hive2://host:10000/...`，只供 HiveServer2 连通与查询；不得填入 `hive.metastore.uris`。
- `sshCredentialRef`、`hiveCredentialRef`、`hadoopConfRef`：职责分开的凭据/配置引用。
- `remoteLogRoot`、`jobJarUri` 和 jar SHA-256。

旧 `profileType` 可保留为展示标签，但不能继续作为提交方式和存储方式的唯一判断条件。每个档案激活前运行真实环境检查。

### 6.2 推荐集群数据流

```text
参考商城 Outbox/事件文件
    ├─ 商城在 node01：Flume Taildir/Spooling + FileChannel -> HDFS Sink
    └─ 商城在本机/Windows：SFTP/HTTP 网关/明确共享目录 -> node01 spool
                                                        -> Flume -> HDFS
HDFS /graduation/landing/{source_instance_id}/dt=yyyyMMdd/hour=HH/
    -> 平台发现 manifest -> SSH 提交 spark-submit 到 YARN/standalone
    -> Hive warehouse -> ADS -> MySQL 指标快照 -> 页面/AI/决策
```

Flume 不能跨机器直接 tail 一个不存在于 agent 主机的本地文件。商城若不在集群节点上，必须明确传输到 node01 spool 的协议；开发 Agent 不得凭空假设 Windows 路径可被 Linux Flume 读取。

### 6.3 RuntimeProfile 关键字段

- `profileType`：LOCAL/SINGLE_NODE/REMOTE_CLUSTER。
- `landingType` 与 `landingUri`：LOCAL_FILE/HDFS，以及完整 URI。
- `hdfsDefaultFs`、`warehouseUri`、`hiveJdbcUrl` 或 `metastoreUri`。
- `sparkMaster`、`deployMode`、`queue`、`sparkSubmitPath`、`jobJarUri`。
- `submitHost`、`sshPort`、`sshUser`、`sshCredentialRef`。
- `kerberosEnabled`、principal 与 keytab 的凭据引用。
- `metricStoreType` 与 metric read/publish 数据源引用。
- `configVersion`、`status`、`lastCheckAt`、`lastCheckReport`。

敏感值不写数据库明文、YAML、命令日志或页面；只保存环境变量、密钥文件或密钥服务引用。

### 6.4 集群预检顺序

1. 主机名、IP、端口、DNS、时间同步和 Java/Spark/Hadoop/Hive 版本。
2. HDFS 临时文件创建、写入、读取、删除。
3. Hive 临时库/表创建、写入、查询、删除。
4. 提交最小 Spark count 作业，取得 externalJobId、最终状态和日志。
5. Flume 投递一个小文件到目标 HDFS 目录，校验 checksum。
6. 用 55 条黄金数据跑集群小链。
7. 用固定 seed 的 1,000 条数据跑集群链。
8. 对同一输入比较本地与集群的核心指标同值。

任何一步失败都必须返回“检查项、目标、结果、错误摘要和修复建议”，不能只返回激活失败。

### 6.4.1 当前代码在接入集群前必须先修的缺口

以下均为当前实读代码结论，不能把“类已存在”写成“集群已支持”：

1. 生产采集仍有把 `landingUri` 转成 `java.nio.Path` 并使用 `Files.*` 的路径；`hdfs://` 会被误当成本地路径。必须让生产入口实际经过 `LandingStorage`/连接器抽象。
2. `HdfsLandingStorage` 的健康检查不得只列根目录，必须在授权的 `<base>/_health/<uuid>` 中完成 create/write/read/rename/delete，且只清理自己创建的探针。
3. 现有 Flume 配置使用 `%{eventType}` 路径，但 Taildir 没有产生该 header；首版改为按 source + 采集时间写 raw，并启用本地采集时间。业务 `event_type/event_time` 由 ODS 解析后分区。
4. SSH 提交目前可能等待远端 spark-submit 完成并返回伪造 `ssh-*` ID。目标协议是 1–2 秒返回 launcher reference，随后提取真实 YARN `application_...`；伪 ID 不能冒充 externalJobId。
5. 远端命令只允许调用固定 wrapper 和白名单参数，禁止直接拼接 UI 输入；SSH 必须校验 known_hosts，禁止 `StrictHostKeyChecking=no`。
6. 第一版远程执行优先 `master=yarn, deployMode=client`，便于从 node01 网关收集 driver 日志；确认 YARN 日志聚合后再支持 cluster deploy。
7. 版本化 jar 放到 `/apps/graduation/spark-jobs/<gitCommit>/...jar` 并保存 SHA-256，不能只引用可变的 `latest`。
8. Flume 是 at-least-once；平台只能通过 checkpoint、manifest 和 `(source_instance_id,event_id)` 去重提供幂等结果，不得宣称 exactly-once。

### 6.5 需要用户提供的信息

以下内容登记为 `USER-INPUT` 阻塞项，不得由 Agent 猜测：

- node01、node02、node03 的主机名/IP和 NameNode、DataNode、ResourceManager、NodeManager、Hive、Spark 等角色。
- HDFS NameNode URI/端口、允许写入的根目录、warehouse 路径和服务用户权限。
- Spark 是 YARN client、YARN cluster 还是 standalone，队列名称和提交命令路径。
- HiveServer2 JDBC 或 Metastore URI、数据库名前缀。
- SSH 主机、端口、用户、密钥/凭据引用、是否经过跳板机。
- Hadoop/Spark/Hive/Java 版本与安装目录；作业 jar 位于提交节点还是 HDFS。
- 是否启用 Kerberos，以及 principal/keytab 的安全提供方式。
- Flume agent 运行位置，商城事件到 agent spool 的传输方式和监听目录。
- 平台、商城、MySQL 与集群之间实际开放的端口。

## 7. 数仓、算法与剩余实现规格

### 7.1 DIM 与交易 DWD

- `dim_date`：由可配置日期区间生成日期、周、月、季度、工作日和节假日标志；生成任务幂等。
- `dim_region`：版本化地区字典，至少覆盖来源商城实际地区；未知值落 `-1/unknown` 并计数。
- `dim_metric`：由 MySQL `metric_definition` 同步，记录 metric_code、名称、单位、聚合方式和口径版本。
- 订单状态机：Java 与 Scala 共享同一份中立契约；非法转换写 `dwd_reject_record`，不能静默接受。
- 订单行校验：`SUM(quantity * unit_price - line_discount) = order_amount`，误差绝对值小于 0.01。
- 退款：按 `refund_id + event_time + ingest_time + event_id` 取最新；累计退款不得超过实付。
- 去重排序：同一业务键按 event_time、ingest_time、event_id 确定唯一结果，保证重跑稳定。

### 7.2 DWS/ADS 与算法

- 漏斗增加渠道和分类粒度。若后阶段人数大于前阶段，保留真实数值并输出“非严格同 cohort 漏斗”说明，禁止用 `min` 截断伪造单调性。
- 新增 `ads_category_sale` 与 `ads_region_sale`；地区指标至少有 sale_amount、net_sale_amount、order_count、buyer_count。
- `ads_sale_trend` 增加 net_sale_amount；repeat_rate 必须实际落表并发布。
- RFM：宽表保存 recency_days、frequency、monetary_amount、R/F/M score、segment、rule_version。M 的时间范围、退款口径和评分方向必须冻结；小样本标为“仅演示”。
- 排行和 NTILE 增加稳定次序键，避免同值重跑漂移。
- 异常检测：至少 14 个历史点才计算；第一版可采用滚动中位数/MAD 或滚动均值/z-score。结果表保存 metric_code、source_instance_id、window、actual、baseline、deviation、threshold、algorithm_version、snapshot_id。算法类必须接入生产指标链，不允许只有孤立类。

### 7.3 质量规则

建立 `quality_rule_definition` 和版本/生效区间，严重度行为如下：BLOCKING/ERROR 阻断发布，WARN/INFO 持久化并展示但不阻断。至少分别实现和验收：

1. Landing JSON 可解析率。
2. ODS event_id 非空和 schema version 支持。
3. DWD 行为字段/枚举合法。
4. 订单行金额公式误差 < 0.01。
5. 退款额 ≤ 实付额。
6. 非法状态跳转。
7. DWS 与 DWD 金额对账。
8. ADS 的 GMV ≥ 净销售 ≥ 0。
9. ADS 的 UV ≤ PV。
10. 支付用户 ≤ 浏览用户；不满足时必须给出口径说明。
11. `ingest_time - event_time` P95 和迟到率。
12. 发布行数一致性与抽样 checksum。

每条 BLOCKING 规则必须有一条“构造失败→流水线失败→不产生新 ACTIVE→旧 ACTIVE 可读”的负向验收。

### 7.4 指标存储

第一版 Hive 全程存在：ODS/DWD/DWS/ADS 均在 Hive。MySQL 不是数仓替代品，而是将常用 ADS 指标发布为 ACTIVE 快照的低延迟服务库。页面、AI 和决策只通过 MetricStore 读取同一快照。

建立 `MetricStoreFactory` 按 `metric_store_type` 选择实现：MySQL 为默认并完成；Hive 为管理员显式降级查询路径，不由系统按数据量随机切换；Doris 为第二阶段首选；ClickHouse 仅接口和能力矩阵，标记 DEFERRED。

普通用户只能读 ACTIVE 快照。必须提供当前 ACTIVE 元信息接口，包含 snapshotId、sourceInstanceId、businessDate、version、createdAt 和口径版本。

## 8. 页面、AI、决策和安全

### 8.1 面向普通员工的页面

必须补齐：数据源管理、流水线 stage/job/externalJobId/log/error、总览环比、行为渠道/分类构成、商品库存覆盖天数、销售分类/地区、RFM 金额、决策截止日期、表格分页和稳定排序。页面用业务名称，不暴露 runtimeProfileId、Hive 表名或 Spark 参数。

### 8.2 AI

AI 不是独立摆设，而是复用同一证据包辅助问数、异常解释和决策草稿：

- 语义目录补活跃、RFM、质量表并版本化。
- 模板、Mock LLM、真实 LLM 三种路径共享 AST 白名单、EXPLAIN、行数/时间限制和证据包。
- 真实调用记录 traceId、provider/model、输入输出 token、耗时、状态、错误类型和费用估算；traceId 幂等避免重复计费。
- 实现连接/读取/总超时、有限重试、熔断和每日预算。
- AI 只能生成 DRAFT，不能自动审批或执行经营动作。
- Hive、MySQL、API、DOM、AI 必须在同一 snapshotId 下进行五处同值断言。

### 8.3 决策

完成五个模板：流量下降、漏斗流失、商品转化、库存风险、用户召回。每个模板包含发现、量化证据、适用前提、建议动作、目标指标、观察窗口、截止日期和风险。效果评估使用等长前后窗口聚合，不得只比较两个端点快照。

必须生成并保存 EFFECTIVE、PARTIAL、INEFFECTIVE、INSUFFICIENT_DATA 四类可达样本。人工草稿来源为 `human`；AI 草稿来源记录模型和证据版本。

### 8.4 安全与审计

- 增加 data_dev 测试角色；前端路由和后端 API 双层鉴权。
- 删除可用默认口令；生产可关闭种子账号并要求首次登录改密。
- Hive/SSH/LLM 凭据统一使用 credential_ref，日志脱敏 password、token、Authorization、key。
- 分开“启动流水线”和“重试”权限。
- 审计环境激活、流水线启动/重试、质量强制处理、快照激活和归档快照读取。

## 9. 并行开发和测试提速

### 9.1 并行泳道

在四个并发槽位下采用“一总控 + 三开发泳道”：

- A：三程序拆分、连接器、集群。
- B：数仓、ADS、质量、指标发布。
- C：页面、AI、决策、安全。
- 总控：冻结契约、分任务、控制热点文件、集成和验收。

`PipelineService`、迁移版本号、统一事件契约、前端 router、主配置属于热点文件，同一时间只允许一个 Owner 修改。任何跨泳道字段变化先由总控登记契约任务，其他 Agent 等待契约冻结。

### 9.2 测试分层

| 层级 | 内容 | 执行时机 |
|---|---|---|
| T0 | 受影响类的单测、静态检查、编译 | 每个小任务提交前 |
| T1 | 当前 Maven/Vue/Scala 模块测试，使用内存或 20–100 条数据 | 每个泳道交付前 |
| T2 | 55 条黄金链，真实本地 MySQL/Spark/Hive | 一批并行任务合并后一次 |
| T3 | 固定 seed 1,000 条集群链 | 连接器/集群里程碑一次 |
| T4 | 10 万/100 万条性能 | 性能里程碑/最终验收，不做日常回归 |

不删除已有测试，只把重测试移动到里程碑门。以下变化必须运行 T2：事件契约、分区、金额口径、流水线阶段、发布事务、质量阻断。纯页面样式或单一 DTO 变化不应反复启动全 Spark 链。

开发阶段优先使用固定 seed、覆盖所有事件类型和失败分支的小数据；“缩数据量”不能缩业务场景。每个失败只复跑受影响层，修复后再过当前里程碑门。

## 11. 实施顺序

1. M1 冻结三程序边界、契约和独立构建；这是后续并行的前提。
2. M2 建立 source instance、connector 和 mapping；同时收集集群参数。

### 12.2 下一主线选择

下一主线选择 **A：分析平台商城无关化 P1–P5**。商城功能与美化不进入当前关键路径；C 类互不依赖的小收尾可以并行，但不得占用公共契约、数据库迁移号、`PipelineService` 或 P1–P5 热点文件。

理由不是商城“不重要”，而是本项目的产品主体是分析工具。参考商城只需提供稳定、可审计的数据源；等平台能用异构源证明“可替换”后，再决定是否接入一个成熟开源商城。任何开源商城都通过 Adapter/Profile 接入，禁止为了适配它修改平台核心 SQL、事件常量或表结构。

### 12.3 P1–P5 五项默认决策

1. **P5 先用纯文件异构 fixture。** 它便宜、可复现、能验证字段/枚举/UUID/多余字段差异。接真实开源商城是 P5 后的加分项，不作为当前主线依赖。
2. **ODS v2 允许对演示数据重建。** 重建前必须备份对应 warehouse 目录、记录表数/行数/checksum，并由显式的 `INIT_SCHEMA` 审计步骤执行；不得静默 DROP，也不得影响其他 source namespace。
3. **新增 `source_registry`，不折叠进 `runtime_profile`。** source 表示长期业务身份；profile 表示可变化的运行参数，两者生命周期不同。
4. **P4 先做单源切换器。** 同屏跨源比较推迟到 P5 之后；第一版 API 未传 source 时返回当前激活源，并在响应中显式带 sourceCode。
5. **数据源管理不能永久只有 API。** P1/P2 可先交付 API 以解锁后端；P4 出口必须有最小管理员页面，至少支持列表、查看状态、测试连接、启停、选择当前源和查看画像校验结果。可视化拖拽字段映射后续再做。

### 12.4 契约严格度与 synthetic 标识裁决

- `canonical-event.v1.schema.json` 表示目标严格契约；当前旧夹具和旧校验器登记为 `mock-mall-legacy-v1` 兼容来源，不能把 26/55 校验通过伪写成契约已完全冻结。
- P1 不改变黄金指标；P2/P3 由新生成器重建符合严格契约的 golden-55，再逐步移除兼容规则。兼容规则必须按 source profile/version 生效，不能成为全局放宽。
- `synthetic=true` 放在 generation run、artifact manifest 和验收元数据中，不加入 8 字段事件信封。真实与模拟事件保持相同业务契约，避免下游根据 synthetic 分叉业务逻辑。

### 12.5 `newFileCount` 口径裁决

接受现实现的业务口径：“当前目录中至少含一条可采集完整记录的文件数”，而不是“最近新创建的文件数”。文档和页面统一显示为“可采集文件数”。API 为兼容可暂时保留 `newFileCount`，但需在 DTO/OpenAPI 标记 deprecated，并新增语义准确的 `consumableFileCount`；过渡期两者同值，前端只读新字段。
