# 第六章 智能分析模型设计实现（初稿）

> 对应实现：`analytics-server/ai-decision/`（业务语义层、四层校验 `SqlSafetyValidator`、
> 执行器 `SqlExecutor`、证据包与解释模板 `EvidenceTemplates`、审计）；审计表
> `ai_query_history`、`ai_call_log`。
> 证据：**安全与拦截**以 `.verify/r8-accept-report.json`（攻击集与安全问数，实测通过）为准；
> **可用性基线**为 `experiments/ai-eval-*.json`（可编程 Mock 模型，非真实大模型实测）。

## 6.1 设计原则

智能分析模型遵循六条基线（§8.1）：

1. 大模型只查询 ADS 白名单（物化指标宽表），不直接扫描 ODS/DWD 明细；
2. 指标含义来自语义层（表/字段/别名/少样本），不由模型临时猜测；
3. SQL 必须先解析和校验（四层），通过后才执行；
4. 查询结果是回答的唯一数据证据，结论不得引用结果之外的数值；
5. 推测与事实分开表达（possibleCauses 与 facts 分栏）；
6. 失败过程可重试、可记录、可人工检查（至多一次修复 + 全链路审计）。

## 6.2 业务语义层

语义层是可查询 Schema 的唯一事实来源，其内容以冻结契约为准
（`docs/contracts/r8-evidence-security-decision.md` v1，2026-09-11 冻结；当前登记 5 张已发布
ADS 物化表）：

- 每张 ADS 表声明字段级业务含义、单位与口径（如 sale_amount：仅统计有效支付订单、
  单位元、可求和、不可用平均替代客单价）；
- 中文别名表（销售额/GMV/收入→sale_amount；净销售额→net_sale_amount）用于问题匹配；
- 每表提供 2–3 条正确问答少样本（问句→SQL），引导模型按口径书写；
- Schema 选择采用轻量关键词映射（1–3 张表），不依赖向量库（记为可选实验）。

## 6.3 受控 Text-to-SQL 流程

问题先经**问句层安全判定**（越权/注入意图 → 直接拒绝并记审计，错误码
`SQL_QUESTION_UNSAFE`，不产生任何数据库访问），再进入
"规范化→主题与指标识别→Schema 与少样本选择→LLM 生成结构化 JSON
（intent/metrics/dimensions/time_range/sql/assumptions）→四层校验→失败反馈
至多一次修复→EXPLAIN 级保护→只读执行"，最终返回真实结果。模型输出限定 JSON；
问题未给时间范围时默认近 30 天并写入 assumptions，避免无界查询。

Prompt 内嵌约束：只输出一个只读 SELECT；只使用给定表字段；必须包含时间条件；
明细自动限行；不确定返回 clarification_needed 而非编造。SQL 生成温度 0，
解释温度 0.2（§8.10）。

## 6.4 四层 SQL 安全校验

| 层 | 手段 | 说明 |
|---|---|---|
| 〇（前置） | 问句层意图判定 | 越权/注入意图在生成 SQL 之前拒绝，错误码 `SQL_QUESTION_UNSAFE`，被拒问句同样落审计表 |
| 一 | 字符串预检 | 多语句、注释逃逸、INSERT/UPDATE/DELETE/DROP 等 DML/DDL、UNION 拼接、系统库关键词 |
| 二 | JSqlParser 语法树 | 根必须为只读 Select/With；函数白名单（聚合/日期/数学子集）；禁止文件/网络管理函数 |
| 三 | 表白名单与字段 | 表 ∈ ADS 物化白名单；SELECT 字段必须存在于语义层；**校验阶段强制单表**（旧版"最多 3 表"已收紧） |
| 四 | 快照与资源约束 | 快照钉住 + 日期字面量范围（WHERE 必须引用 dt）；无 LIMIT 自动补 200、>200 强制改写为 200；执行 30 秒超时；QueryCostGuard 以 EXPLAIN 预估扫描行数，超阈值（默认 50 万行）直接拒绝 |

即使应用层校验失效，MySQL 侧只读账号（`metric_read`，`setReadOnly(true)`）构成最终防线（纵深防御）。

## 6.5 一次受控修复

当 SQL 在校验阶段失败时，把"错误类型（脱敏）+ 原问题 + 相关 Schema"回送模型，
允许修复一次；修复结果必须重新经历全部校验。超过次数或修复失败返回明确错误，
不循环调用。可用性基线评测（Mock 模型）中 58 次修复均成功转化为合法 SQL
（关联/窗口类查询的合法化）；真实模型下的修复效果待配置 API Key 后验证。

## 6.6 证据约束解释（§8.8）

执行后构造版本化证据包（`templateVersion=evidence_v1`）：{证据 ID、快照 ID、口径版本、
原问题、SQL、涉及表、返回行数、耗时、当前窗与对照窗时间范围、维度、数据质量、血缘、告警}，
每条事实带 `evidenceId`。解释结果固定为六个章节，顺序与标题由模板固化：

| 章节 | 标题 | 内容 |
|---|---|---|
| 1 | 发生了什么 | 关键指标数值与事实（每条关联 evidenceId） |
| 2 | 与上期相比 | 与对照窗的对比（显式声明非因果推断） |
| 3 | 维度贡献 | 按 product/category/region/channel 等维度的贡献拆分 |
| 4 | 数据质量可信度 | 质量规则通过情况与数据可信度提示 |
| 5 | 核查行动 | 建议动作（可带 targetMetricCode 一键创建决策草稿） |
| 6 | 限制 | 口径、样本与推断边界说明 |

结论只能引用证据包内的字段与数值，推测与事实分栏。模型不可用时自动降级为规则化摘要
（`providerUsed=template`，页面标注"规则回退模式"），固定看板与数据处理不受影响。

## 6.7 审计

每次问答落 ai_query_history（问题、SQL、表、状态、行数、耗时、反馈；**被拒绝的问句也写入**，
便于安全复核），每次真实模型调用落 ai_call_log（用例、供应商、模型、令牌、耗时、状态；
当前未配置模型 API Key，该表为空）。流水线/快照/决策均带 trace 关联，
运行中心可从一个异常指标追溯到输入批次与模型调用。
敏感信息（密钥）仅存在于环境变量，错误信息不回显连接细节。

## 6.8 与决策闭环的联动

解释结果中的建议（带 targetMetricCode 与证据快照）经用户确认后创建决策草稿
（AI 只能创建 DRAFT）；人工审核时从当前活跃快照锁定目标指标基线；执行完成后
按目标方向计算改善率并评价（EFFECTIVE/PARTIAL/INEFFECTIVE/INSUFFICIENT_DATA，
状态集合由常量类显式定义的 12 态状态机管理），评价记录显式声明"前后对比，非因果推断"。
由此，智能分析从"问答"延伸到"行动与复盘"，并以审计数据支撑论文的量化讨论。
