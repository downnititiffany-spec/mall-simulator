## 2.1 大数据基础平台

Hadoop 生态提供分布式存储（HDFS）与资源管理（YARN）；Hive 以 SQL 方式定义数仓表
（本文四层 29 张表全部以版本化 DDL 管理），并将查询翻译为分布式执行计划；
Spark SQL 作为计算引擎，通过 Catalyst 优化器与 Tungsten 执行器完成自定义清洗与聚合
（本文作业链共 6 个 Scala 作业，统一入口契约，见第五章）。Flume 用于日志采集
（Taildir 断点语义），本文在 LOCAL 环境下以等价位实现（文件级断点 + 契约校验）验证
"暂停→恢复→不丢不重"，集群迁入时切换为 Flume 配置（`ingestion/flume/flume-taildir.conf`）。

技术选型结论（问题驱动）：分析场景为 T+1 级离线批处理，Spark SQL 在吞吐与开发效率
上优于 MapReduce；数据规模目标为百万至亿级，首版以单机/单节点验证链路正确性，
集群参数（executor/分区数/广播）可通过统一提交脚本切换，不写死任何节点地址。

## 2.2 Java 企业级开发栈

Spring Boot 3.2 + JDK 17 提供模块化单体底座（按功能边界分包而非微服务拆分）；
MyBatis-Plus 负责业务库访问；Flyway 管理 MySQL 迁移（V1~V5 共五版，指标发布、
流水线、AI 审计、决策等元数据全部受版本管理）；HikariCP 连接池 + 只读连接执行器
支撑 AI 查询的纵深防御。前端采用 Vue 3 + Vite + ECharts + axios：
固定看板（大盘/漏斗/商品/销售）与演示控制台（流水线/生成器）以 `/api/v1` 单向依赖后端。

## 2.3 Text-to-SQL 相关技术

Text-to-SQL 主流路线包括：序列到序列模型的直接生成（以 Spider 等基准评测）、
Schema Linking 与检索增强（减少无关表干扰）、以及"受约束生成 + 解析校验"的防御式架构。
结合生产安全性要求，本文采用第三条路线并作出如下取舍：

- 用业务语义层（表/字段/别名/少样本）替代向量检索完成 Schema 选择，避免引入向量库
  等额外依赖（向量检索列为可选实验，用于后续对照）；
- 以 Json 结构化输出 + JSqlParser 语法树校验保证 SQL 结构安全；
- 以 ADS 物化白名单从数据范围上杜绝明细越权；
- 以"至多一次修复"平衡生成质量与调用成本，失败即终止并记录审计。

本文同时研究"证据约束"对结论可信度的影响：解释必须引用查询结果的字段与数值，
推测单独成栏，从机制上降低大模型幻觉对业务解读的污染。

## 2.4 相关技术小结

本章技术组合覆盖"采集（Flume/Taildir 语义）→存储与计算（HDFS/Hive/Spark SQL）→
服务（Spring Boot/MySQL）→展示（Vue/ECharts）→智能（受控 Text-to-SQL）"全链路，
版本与兼容性矩阵见 `docs/compatibility-matrix.md`（随实际环境更新）。
