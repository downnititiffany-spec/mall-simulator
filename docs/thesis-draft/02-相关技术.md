# 第二章 相关技术（初稿）

## 2.1 大数据基础平台

Hadoop 生态提供分布式存储（HDFS）与资源管理（YARN）；Hive 以 SQL 方式定义数仓表
（本文四层数仓的设计 DDL 共 29 张，全部以版本化 DDL 管理；本地真实链由建表作业实建
32 张，其中含 8 张 `__staging` 孪生表，见 5.1），并将查询翻译为分布式执行计划；
Spark SQL 作为计算引擎，通过 Catalyst 优化器与 Tungsten 执行器完成自定义清洗与聚合
（本文作业链共 11 个 Scala 作业：建表 sci、ODS 装载 odl、DWD 清洗 bdw、维表 dim、
主题/指标聚合 tdw/usw/fna、质量 dqc、发布 pub 等，统一入口契约，见第五章）。Flume 用于日志采集
（Taildir 断点语义），本文在 LOCAL 环境下以等价实现（文件级断点 + 契约校验）验证
"暂停→恢复→不丢不重"，集群迁入时切换为 Flume 配置（配置文件
`ingestion/flume/flume-taildir.conf` 已交付；Flume→HDFS 的断点恢复实录待环境，不作为实测结论）。

技术选型结论（问题驱动）：分析场景为 T+1 级离线批处理，Spark SQL 在吞吐与开发效率
上优于 MapReduce；数据规模目标为百万至亿级，首版以单机/单节点验证链路正确性，
集群参数（executor/分区数/广播）不写死任何节点地址；集群分档与广播/并行度对照实验待
集群环境执行（现有 `scripts/run-spark-chain.ps1` 为本地遗留脚本，仅覆盖部分作业，
集群提交以平台流水线提交器为准）。

## 2.2 Java 企业级开发栈

Spring Boot 3.2 + JDK 17 提供模块化单体底座（按功能边界分包而非微服务拆分）；
MyBatis-Plus 负责业务库访问；Flyway 管理 MySQL 迁移（`db/meta` 为 V1–V15 共 14 个版本
（无 V6），`db/metric` V1–V3，`db/business` V1，`db/migration` V1/V7；指标发布、流水线、
AI 审计、决策等元数据全部受版本管理，配置中 `spring.flyway.enabled=false`、由应用内
初始化器触发迁移）；HikariCP 连接池 + 只读连接执行器支撑 AI 查询的纵深防御。
前端采用 Vue 3 + Vite + ECharts + axios：分析平台看板（大盘/漏斗/商品/销售/RFM/流水线/
运维/决策/AI 共 9 个业务页）以 `/api/v1` 单向依赖平台后端（dev 代理 → 8091）；
商城与演示控制台页面位于独立前端 `mall-frontend/`（8090），两者为两个独立产品，
无 Maven 依赖关系。

## 2.3 Text-to-SQL 相关技术

Text-to-SQL 主流路线包括：序列到序列模型的直接生成（以 Spider 等基准评测）、
Schema Linking 与检索增强（减少无关表干扰）、以及"受约束生成 + 解析校验"的防御式架构。
结合生产安全性要求，本文采用第三条路线并作出如下取舍：

- 用业务语义层（表/字段/别名/少样本）替代向量检索完成 Schema 选择，避免引入向量库
  等额外依赖（向量检索列为可选实验，用于后续对照）；
- 以 Json 结构化输出 + JSqlParser 语法树校验保证 SQL 结构安全；
- 以 ADS 物化白名单从数据范围上杜绝明细越权；
- 以"至多一次修复"平衡生成质量与调用成本，失败即终止并记录审计。

本文同时研究"证据约束"对结论可信度的影响：解释必须引用查询结果的字段与数值，
推测单独成栏，从机制上降低大模型幻觉对业务解读的污染。

## 2.4 相关技术小结

本章技术组合覆盖"采集（Flume/Taildir 语义）→存储与计算（HDFS/Hive/Spark SQL）→
服务（Spring Boot/MySQL）→展示（Vue/ECharts）→智能（受控 Text-to-SQL）"全链路，
版本与兼容性矩阵见 `docs/compatibility-matrix.md`（随实际环境更新）。
