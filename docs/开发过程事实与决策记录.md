## 2. 决策记录

### D-001 三程序架构裁决（转写 V2.1 §3，作为实施依据）

- **背景**：现状是"平台 + 商城"两程序，且商城内含数据生成器（`generator` 包、`GeneratorController`、`Generator.vue`），平台侧还残留商城配置键。
- **选定**：① `analytics-platform`(:8091) 不含任何商城业务 CRUD／随机造数／商城库与 Java 依赖；② `reference-mall`(:8090) 保留真实商城行为；③ 新增 `synthetic-data-generator`(:8092 或 CLI)，只经公开 API（`MALL_API`）或产出规范事件文件（`CANONICAL_EVENT_FILE`）；④ 中立契约目录 `contract-specs`；⑤ 三程序不得共享 Java 实体/Mapper/Maven 业务依赖。
- **执行顺序（本记录追加的工程决策）**：**先建 M1-4 新生成器并验收，再执行 M1-7 拆除商城生成器**。理由：反过来做会出现"造数能力真空期"，本地唯一可用数据链会断，导致 T2 黄金链无法复跑。
- **代价**：一段时间内仓库同时存在新旧两套造数代码（允许的过渡态，但必须在看板上可见）。

### D-002 Landing 根的唯一来源 = ACTIVE `RuntimeProfile.landingUri`（退役声明）

- **新唯一来源**：`analytics_meta.runtime_profile` 中 `status='ACTIVE'` 行的 `landing_uri`，由 `RuntimeProfileServiceImpl.findActive()` 读取；写入侧不变（激活流程）。
- **必须删除的旧路径**：`IngestionService.status()` 中的 `environment.getProperty("mall.landing.path", "./landing")`
  ——它既是商城侧配置键（违反 V2.1 §3.4-4"平台不得引用 `mall.*` 配置键"），又与 `runOne()` 使用的档案路径可能不一致（同一份采集状态可能来自两个不同目录）。
- **禁止保留兜底**：删除后**不得**再添加任何"没有 ACTIVE 环境就用默认目录"的分支。无 ACTIVE 时如实报告 `profileState=NO_ACTIVE`。
- **验证计划**：单元测试 `IngestionServiceStatusTest`（有/无 ACTIVE 两条路径 + 最近批次回显）；源码级守卫 `PlatformMallBoundarySourcePolicyTest`（禁止 `mall.*` 键复活）；真实进程烟测（重建 jar → 重启 8091 → `GET /api/v1/ingestion/status`）。
- **破坏性确认**：无需（只改读取来源，不删数据、不删文件）。

### D-003 无 ACTIVE 环境时的行为 = 显式降级报告，而不是"再找一条路"

- **背景**：旧代码在没有 ACTIVE 档案时仍能给出 `eventsDir`（来自配置键默认值），看起来"更健壮"。
- **选定**：返回 `profileState=NO_ACTIVE` + `runtimeProfileId=null` + `landingUri=null` + `eventsDir=null` + `pendingFiles=0`；`latestBatch`/`checkpointFiles` 仍照常返回（历史事实与该环境无关）。
- **理由**：这是一条**显式错误报告分支**，不是第二数据源。若在此回退到默认路径，会出现"报表读 A 目录、采集读 B 目录"的静默错位——正是 D-002 要消除的缺陷。
- **代价**：无 ACTIVE 环境时前端看到"采集不可用"，需要先走激活流程（V2.1 §8.3 的预期行为）。

### D-004 死文件 `db/business/V1__init_mall.sql` 的处置（确认前置）

- **事实**：`analytics-server/platform-app/src/main/resources/db/business/V1__init_mall.sql`（9637 字节）内含 `CREATE TABLE mall_user`（:7）与 `CREATE TABLE mall_order`（:61）；Flyway 只加载 `classpath:db/meta` 与 `classpath:db/metric`，**该文件从不被执行**。
- **风险**：不执行的 DDL 也会被人工/工具误读为"平台拥有商城表"，与 V2.1 §3.4-4 冲突；同时它是平台上唯一残留的商城表字面量。
- **选定**：物理删除（代码退役类操作）。
- **破坏性确认**：**需要**。虽然它不参与运行，但属于"合同承载型残留"（见 §3 反熵声明），必须由用户显式确认删除范围后才执行；确认前看板任务 M1-3 保持 `BLOCKED`，并由 `PlatformMallBoundarySourcePolicyTest` 把它钉在"未被加载"状态（而不是静默忽略）。

### D-008 Landing URI 解析收敛为唯一实现 `LandingUri`

- **背景（缺陷驱动）**：M1-1 写单元测试时发现同一段 `file://` 截断逻辑有三份拷贝
  （`IngestionService`、`PipelineService`、`LocalLandingStorage`），三份都把标准写法
  `file:///D:/landing` 截成 `/D:/landing`：Windows 上 `Paths.get` 直接抛
  `InvalidPathException: Illegal char <:> at index 2`，Linux 上得到一个形如 `/D:/landing` 的错误目录；
  `hdfs://namenode:8020/landing` 会被**静默**当成相对目录 `hdfs:/namenode:8020/landing`（比报错更危险）。
  三份实现 = 三种错法，且都以"看起来支持"的注释写着 `file:///D:/...`。
- **选定**：新增 `platform-common` 的 `com.graduation.analytics.common.LandingUri.resolve(String)` 作为唯一实现：
  标准 `file:///D:/x`、`file:///data/x`、`file://D:/x`、历史 `file://./x` 与裸路径均支持；
  空值、主机名形式 `file://host/share`、非 file 协议一律抛 `MallBizException`（**不返回默认目录**）。
  三个调用点改为调用它，并删除两份重复实现（`PipelineService.parseLandingRoot` 包装方法一并删除）。
- **配置边界的例外（显式声明）**：`LocalLandingStorage` 的构造参数是**配置项** `platform.landing.local-root`
  （默认值已在 `@Value` 里声明为 `./landing`），故仅在配置为空时才兜底 `./landing`——这个默认值属于配置声明，
  不属于"环境档案的第二来源"，解析本身仍走唯一实现。
- **代价**：`platform-common` 过去没有任何测试类，本次新增 test 作用域依赖 `spring-boot-starter-test` 与
  `LandingUriTest`（4 个用例）。
- **验证**：`LandingUriTest`（标准写法/历史写法/盘符写法/非法写法）+ `IngestionServiceStatusTest`（标准写法经 profile 生效）
  + 真实的 `POST /api/v1/ingestion/runs` 一轮采集（产出 `manifestPath=file:///D:/...`，正是曾经会崩的形态）。

### D-009 启动脚本的调用方式（环境事实）

- **事实**：`pwsh -File scripts/start-all.ps1 -PlatformOnly` 在**前台管道**里调用（`... | Select-Object -Last 6`）会挂住不返回：
  脚本自身已成功启动服务并通过探活（日志有完整启动记录、端口在监听），但外层管道等不到结束，5 分钟超时。
- **结论**：启动脚本**只用后台作业方式**调用（`run_in_background`）或直接 `Start-Process java -jar`；
  探活与业务调用分开执行。这条是工具使用约定，不是脚本缺陷（脚本作为后台作业运行时 100% 正常）。

### D-010 中立契约目录 `contract-specs`（M1-5）

- **决策**：新建仓库顶层中立目录 `contract-specs/`，承载三个程序共享的机器可读契约；**权威顺序不变**：
  `docs/contracts/*.md`（语义冻结源）＞ `contract-specs/**`（机器可读表达）＞ 各程序实现。
  目录内 6 个文件：`README.md`、`VERSION`（`contract-specs 1.0.0`）、`schemas/canonical-event.v1.schema.json`、
  `schemas/ingestion-manifest.v1.schema.json`、`schemas/generation-artifact-manifest.v1.schema.json`、
  `openapi/generator-api.v1.yaml`。
- **依据**：V2.1 §3.1 要求"中立契约"；§3.4 六项独立验收需要一份不属于任何单个程序的契约载体。
- **实测证据（E1/E2）**：
  - 3 个 JSON 通过 JSON Schema draft 2020-12 `check_schema` 元校验；真实的 `landing/manifests/30.json`
    按 `ingestion-manifest.v1.schema.json` 校验 **VALID**；OpenAPI 解析出 7 路径 / 11 schema / 17 个本地 `$ref` 全部可解析。
  - 防漂移测试 `CanonicalEventSchemaParityTest`（`platform-common`）：**5/5 绿**
    （`mvn -o test -f analytics-server/pom.xml "-Dtest=CanonicalEventSchemaParityTest" "-Dsurefire.failIfNoSpecifiedTests=false"`）——
    对齐信封 8 字段名与 `required`、`event_type` 12 类枚举、`schema_version.const="1.0"`、`source_system.const="mock-mall"`、
    金额正则、`allOf` 对 12 类 payload 的路由完整性。**该测试不含 payload 必填集**（见下条分歧）。
- **同时发现的真实分歧（不修，登记 B-06）**：按 `EventContractValidator` 全部规则复刻回放夹具 55 行 = 接受 51 / 隔离 4，
  与批次 30 清单 `acceptedRecords=51 / quarantinedRecords=4` **完全一致**；而按本次契约 schema 的 payload 必填集校验同一文件
  = 26 通过 / 29 不通过。即**采集层现今接受的 51 行里约 25 行按契约文本属脏数据**（缺 `status`/`created_at`/`paid_at`/

  两条修法都会改动既有口径（补校验器→黄金数据大批转隔离；放宽契约→契约失去约束力），**属必须由人裁决的项，AI 不自行决定**。

  刻意让 §4.3 "期望隔离数" 在字段未定前报错而非被静默接受），未把猜测伪装成冻结契约。

### D-012 生成器独立元数据库与 S1 骨架（M1-4 S1）

- **决策 1（独立库自举，不碰既有初始化脚本）**：生成器使用自有库 `generator_meta`，连接串带 `createDatabaseIfNotExist=true`，首次启动即自举建库，Flyway location 为 `classpath:db/generator`。
  - **理由**：§3.4-1 要求"独立配置"；若改为往仓库既有的三库初始化脚本里加第四个库，就把生成器的独立性重新绑到平台/商城的部署步骤上。自举后 **B-05 的库名裁决只需改 `application.yml` 一行**，无需改代码、无需改 `scripts/`。
  - **实测（2026-09-11 12:53）**：`Current version of schema 'generator_meta': << Empty Schema >>` → `Migrating schema 'generator_meta' to version "1 - generator meta"` → `Successfully applied 1 migration`；`information_schema` 核实 6 张表（五契约表 + `flyway_schema_history`），全部 InnoDB / utf8mb4。
- **决策 2（五表 DDL 按 §4.2 关键字段落地，字段名与契约一致）**：`generator_target`(12 列) / `generation_plan`(14) / `generation_run`(16) / `generation_artifact`(11) / `generation_event_stat`(5)。
  - 与 §4.2 的对应关系用**列**明确写出，不靠命名猜测：§4.2 的 `count` 落为 `event_count`（`count` 在 SQL 中是函数名，可读性差，DDL 注释已标注对应关系）；§4.2 的 `start/end`、`min/max_event_time` 同理展开为 `start_time`/`end_time`、`min_event_time`/`max_event_time`。
  - `generation_run` 额外落 `error_code`（失败码与摘要分离，与平台 `pipeline_run` 风格一致）；`generation_artifact` 额外落 `kind`（`EVENT_JSONL`/`MANIFEST`/`DIRTY_SAMPLE`），因为 §3.3 B 要求脏样本与期望隔离数进 manifest，产物必须能区分类型。
  - **未冻结处如实标注**：`generation_artifact.checksum` 的注释写明"算法与编码由契约冻结前不得默认与采集侧相同"（采集侧现用某具体算法，尚未升为契约条款）。
- **决策 3（配置命名空间 + 端口 + 日志/产物目录全部自有）**：`generator.*` 键、端口 8092、日志 `./logs/generator.log`、产物 `./generator-output`；`application.yml` 中**不存在** `mall.*` 或 `platform.*` 键。
- **决策 4（边界守卫用源码级负向断言，可用例数少但常驻）**：`GeneratorBoundarySourcePolicyTest` 4 用例——① Java 源码禁 `com.graduation.mall`/`com.graduation.analytics`/`mall_*`/`mall_simulator`/`analytics_meta`/`analytics_metric`/`mall.*` 键/平台 8090-8091 地址；② 配置禁 `mall.*`/`platform.*` 键并**正断言** 8092、`generator_meta`、`generator-output` 存在（防止守卫空跑）；③ 迁移脚本只建 `generator_*`/`generation_*` 表，`mall_*`/`ods_*`/`dwd_*`/`dws_*`/`ads_*`/`metric_*` 一律违规；④ `pom.xml` 不得依赖商城或平台任何构件、不得是 `<modules>` reactor。
  - **实测**：`mvn -o test -f synthetic-data-generator/pom.xml` → BUILD SUCCESS，2.9 秒，**4 用例 0 失败**（离线仓库解析成功，无需联网）。
- **决策 5（"独立启动"用端口 + 日志 + 库三类真实证据，不新增自造端点）**：§4.4 未定义健康检查路径，故**不自造** `/health`；启动证据取 `Started GeneratorApplication in 3.71 s`（日志文件）+ `Get-NetTCPConnection -LocalPort 8092` 监听 + Flyway 迁移记录。
- **S1 明确未完成的部分（不得读作 M1-4 完成）**：两接口（`MallTargetAdapter`/`EventSink`）、`JsonlEventSink`、`ReferenceMallHttpAdapter`、§4.4 端点、状态机、页面/CLI **均未实现**；当前 `src/main/java` 只有 1 个入口类。M1-4 状态为 `IN_PROGRESS`，S2 起继续。

## 6. 缺陷与运行环境异常台账

### DEF-01 T2 实测卡死：Spark 本地模式依赖拉取（Netty `fetchFile`）

- **现象**：run 31 的 `BUILD_DWD-tdw` 作业提交后无日志文件、无进度；`landing/logs/pipeline-31-BUILD_DWD-tdw-*.log` **从未创建**，`%TEMP%\spark-*\userFiles-*\spark-jobs-0.1.0-SNAPSHOT.jar` 只有前 4 个阶段的 4 份（215,866 字节/份），第 5 份不存在。
- **证据（`jstack` 卡死进程）**：

  ```text
  "main" ... Thread.State: RUNNABLE   elapsed=217s
    at org.apache.spark.rpc.netty.NettyRpcEnv$FileDownloadChannel.read(NettyRpcEnv.scala:420)
    at org.apache.spark.util.Utils$.copyStream(Utils.scala:279)
    at org.apache.spark.util.Utils$.fetchFile(Utils.scala:467)
    at org.apache.spark.executor.Executor.updateDependencies(Executor.scala:1155)
    at org.apache.spark.scheduler.local.LocalSchedulerBackend.start(LocalSchedulerBackend.scala:132)
    at org.apache.spark.SparkContext.<init>(SparkContext.scala:604)
  ```

  即：卡在 **SparkContext 创建**时的作业 jar 分发，尚未进入任何本项目代码。
- **归因**：Spark 3.5.1 + Windows 本地模式（`local[*]`）+ 每阶段新建 driver 反复拉取同一 jar 的已知脆弱点；同一次 run 的前 4 个阶段用**同一份 jar、同一机制**成功，故非本批次代码引入。相关噪声：`WARN SparkEnv: Exception while deleting Spark temp dir ... spark-jobs-0.1.0-SNAPSHOT.jar`（Windows 文件锁导致临时 jar 删不掉）。
- **放大效应（→ M1-11）**：平台侧 `LocalProcessSparkSubmitter.status()` 恒为 `SUBMITTED`，因此进程死亡/卡死**完全不可被感知**，只能等满 `platform.spark.job-timeout-ms`（默认 900000 ms）；`cancel()` 亦无 `Process` 句柄可杀。
- **本次处置**：手工终止卡死 driver（PID 46652）以释放资源，如实记录 run 31 = `FAILED`（超时），不改代码（M1-11 已登记）。

### DEF-02 采集批次 29 的全量回填（事实记录，非缺陷）

- 触发批次 30 之前的 `POST /api/v1/ingestion/runs` 把 `landing/events` 下**从未采集过的 47 个文件**一次性采集（869,148 条 → `accepted/29`，manifest 29 `READY`）。原因：断点只对**已采集过**的文件生效，而那 47 个文件此前只有 3 个进过批次。
- 影响：流水线按「最新 `READY` manifest」取数，若当时直接触发流水线会聚合 869k 行（**大规模**）；本次先用 55 行夹具产生批次 30，使 run 31 只处理 51 行，符合"小规模真实链"的提速口径。
- 待办提示：`landing/events` 的存量文件是演示/压测素材，后续若要做 T4 性能里程碑，正是天然的数据源（1,000,000 行量级）。
