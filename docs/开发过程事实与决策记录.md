## 2. 决策记录

### D-001 三程序架构裁决（转写 V2.1 §3，作为实施依据）

- **背景**：现状是"平台 + 商城"两程序，且商城内含数据生成器（`generator` 包、`GeneratorController`、`Generator.vue`），平台侧还残留商城配置键。
- **选定**：① `analytics-platform`(:8091) 不含任何商城业务 CRUD／随机造数／商城库与 Java 依赖；② `reference-mall`(:8090) 保留真实商城行为；③ 新增 `synthetic-data-generator`(:8092 或 CLI)，只经公开 API（`MALL_API`）或产出规范事件文件（`CANONICAL_EVENT_FILE`）；④ 中立契约目录 `contract-specs`；⑤ 三程序不得共享 Java 实体/Mapper/Maven 业务依赖。
- **执行顺序（本记录追加的工程决策）**：**先建 M1-4 新生成器并验收，再执行 M1-7 拆除商城生成器**。理由：反过来做会出现"造数能力真空期"，本地唯一可用数据链会断，导致 T2 黄金链无法复跑。
- **代价**：一段时间内仓库同时存在新旧两套造数代码（允许的过渡态，但必须在看板上可见）。

### D-002 Landing 根的唯一来源 = ACTIVE `RuntimeProfile.landingUri`（退役声明）

- **新唯一来源**：`analytics_meta.runtime_profile` 中 `status='ACTIVE'` 行的 `landing_uri`，由 `RuntimeProfileServiceImpl.findActive()` 读取；写入侧不变（激活流程）。
- **必须删除的旧路径**：`IngestionService.status()` 中的 `environment.getProperty("mall.landing.path", "./landing")`
  ——它既是商城侧配置键（违反 V2.1 §3.4-4"平台不得引用 `mall.*` 配置键"），又与 `runOne()` 使用的档案路径可能不一致（同一份采集状态可能来自两个不同目录）。
- **禁止保留兜底**：删除后**不得**再添加任何"没有 ACTIVE 环境就用默认目录"的分支。无 ACTIVE 时如实报告 `profileState=NO_ACTIVE`。
- **验证计划**：单元测试 `IngestionServiceStatusTest`（有/无 ACTIVE 两条路径 + 最近批次回显）；源码级守卫 `PlatformMallBoundarySourcePolicyTest`（禁止 `mall.*` 键复活）；真实进程烟测（重建 jar → 重启 8091 → `GET /api/v1/ingestion/status`）。
- **破坏性确认**：无需（只改读取来源，不删数据、不删文件）。

### D-003 无 ACTIVE 环境时的行为 = 显式降级报告，而不是"再找一条路"

- **背景**：旧代码在没有 ACTIVE 档案时仍能给出 `eventsDir`（来自配置键默认值），看起来"更健壮"。
- **选定**：返回 `profileState=NO_ACTIVE` + `runtimeProfileId=null` + `landingUri=null` + `eventsDir=null` + `pendingFiles=0`；`latestBatch` 仍照常返回（历史事实与该环境无关）。`checkpointFiles` **在 D-024（M1-12）后不再照常返回**：它已收口为"当前环境 events 目录中已建立断点的文件数"，没有 ACTIVE 环境时如实为 `0`——该字段现在与 `pendingFiles` 同量纲、同样依赖"当前环境"，不再是环境无关的库级历史事实。
- **理由**：这是一条**显式错误报告分支**，不是第二数据源。若在此回退到默认路径，会出现"报表读 A 目录、采集读 B 目录"的静默错位——正是 D-002 要消除的缺陷。
- **代价**：无 ACTIVE 环境时前端看到"采集不可用"，需要先走激活流程（V2.1 §8.3 的预期行为）。

### D-008 Landing URI 解析收敛为唯一实现 `LandingUri`

- **背景（缺陷驱动）**：M1-1 写单元测试时发现同一段 `file://` 截断逻辑有三份拷贝
  （`IngestionService`、`PipelineService`、`LocalLandingStorage`），三份都把标准写法
  `file:///D:/landing` 截成 `/D:/landing`：Windows 上 `Paths.get` 直接抛
  `InvalidPathException: Illegal char <:> at index 2`，Linux 上得到一个形如 `/D:/landing` 的错误目录；
  `hdfs://namenode:8020/landing` 会被**静默**当成相对目录 `hdfs:/namenode:8020/landing`（比报错更危险）。
  三份实现 = 三种错法，且都以"看起来支持"的注释写着 `file:///D:/...`。
- **选定**：新增 `platform-common` 的 `com.graduation.analytics.common.LandingUri.resolve(String)` 作为唯一实现：
  标准 `file:///D:/x`、`file:///data/x`、`file://D:/x`、历史 `file://./x` 与裸路径均支持；
  空值、主机名形式 `file://host/share`、非 file 协议一律抛 `MallBizException`（**不返回默认目录**）。
  三个调用点改为调用它，并删除两份重复实现（`PipelineService.parseLandingRoot` 包装方法一并删除）。
- **配置边界的例外（显式声明）**：`LocalLandingStorage` 的构造参数是**配置项** `platform.landing.local-root`
  （默认值已在 `@Value` 里声明为 `./landing`），故仅在配置为空时才兜底 `./landing`——这个默认值属于配置声明，
  不属于"环境档案的第二来源"，解析本身仍走唯一实现。
- **代价**：`platform-common` 过去没有任何测试类，本次新增 test 作用域依赖 `spring-boot-starter-test` 与
  `LandingUriTest`（4 个用例）。
- **验证**：`LandingUriTest`（标准写法/历史写法/盘符写法/非法写法）+ `IngestionServiceStatusTest`（标准写法经 profile 生效）
  + 真实的 `POST /api/v1/ingestion/runs` 一轮采集（产出 `manifestPath=file:///D:/...`，正是曾经会崩的形态）。

### D-012 生成器独立元数据库与 S1 骨架（M1-4 S1）

- **决策 1（独立库自举，不碰既有初始化脚本）**：生成器使用自有库 `generator_meta`，连接串带 `createDatabaseIfNotExist=true`，首次启动即自举建库，Flyway location 为 `classpath:db/generator`。
  - **理由**：§3.4-1 要求"独立配置"；若改为往仓库既有的三库初始化脚本里加第四个库，就把生成器的独立性重新绑到平台/商城的部署步骤上。自举后 **B-05 的库名裁决只需改 `application.yml` 一行**，无需改代码、无需改 `scripts/`。
  - **实测（2026-09-11 12:53）**：`Current version of schema 'generator_meta': << Empty Schema >>` → `Migrating schema 'generator_meta' to version "1 - generator meta"` → `Successfully applied 1 migration`；`information_schema` 核实 6 张表（五契约表 + `flyway_schema_history`），全部 InnoDB / utf8mb4。
- **决策 2（五表 DDL 按 §4.2 关键字段落地，字段名与契约一致）**：`generator_target`(12 列) / `generation_plan`(14) / `generation_run`(16) / `generation_artifact`(11) / `generation_event_stat`(5)。
  - 与 §4.2 的对应关系用**列**明确写出，不靠命名猜测：§4.2 的 `count` 落为 `event_count`（`count` 在 SQL 中是函数名，可读性差，DDL 注释已标注对应关系）；§4.2 的 `start/end`、`min/max_event_time` 同理展开为 `start_time`/`end_time`、`min_event_time`/`max_event_time`。

  - **未冻结处如实标注**：`generation_artifact.checksum` 的注释写明"算法与编码由契约冻结前不得默认与采集侧相同"（采集侧现用某具体算法，尚未升为契约条款）。

### D-014 运行状态机允许 `PENDING → CANCELLED`（M1-4 S3a）

- **决策**：§4.2 列出的状态机为 `PENDING → RUNNING → SUCCESS/FAILED/CANCELLED`；实现额外允许 `PENDING → CANCELLED`，且**只允许这一条额外边**。
  - **理由**：§4.4 要求 `POST /generation-runs/{id}/cancel` **幂等**。若严格按 §4.2，排队中（尚未 `RUNNING`）的取消请求将无处落地：要么返回失败（违反幂等语义），要么强制先置 `RUNNING` 再立刻 `CANCELLED`（伪造状态迁移，污染运行历史）。允许该边是**受控扩展**，且方向单一、不引入回退边。
  - **边界**：`RUNNING → PENDING`、`SUCCESS → FAILED`、`CANCELLED → RUNNING`、终态的任何出边一律拒绝；`fromDb` 对未知/空串严格抛错（不使用 valueOf 的静默回退）。
  - **证据**：`RunStatusTest` 4 用例（含上述非法迁移全拒与 `fromDb` 严格性）；`GeneratorMetaStoreTest` 在真实 MySQL 上验证"终态保护"（对已终态运行再 `finishRun`/`markRunning` 均不生效）与"取消幂等"（第二次请求返回 `false`）。
- **另一处时间处理决策（同片）**：JDBC 时间统一用 `LocalDateTime` + `java.sql.Timestamp` **之外的** `setObject`，并按 `ContractFormat.BUSINESS_ZONE`（Asia/Shanghai）显式换算。
  - **理由**：用 `Timestamp` 会让落库的 `DATETIME(3)` 字面量随 JVM 默认时区漂移（`-Duser.timezone` 一变，同一 `Instant` 写成不同文本）；显式按业务时区换算后，运行时间在库里可读且与产物的 `+08:00` 时间戳同一口径。
  - **证据**：集成测试断言毫秒往返一致（`2026-09-01T02:00:00.123Z` 写入读回同值）。

### D-015 API 层三处"契约未冻结、实现必须先给出形状"的临时口径（M1-4 S3b）

- **背景**：冻结契约 `contract-specs/openapi/generator-api.v1.yaml` 只冻结了路径、方法与成功码，多处明确写着"形状未冻结、本契约不造结构"。实现不能因此停摆，但也不能把临时形状说成契约。
- **决策（四处，等契约冻结后必须回头对齐）**：
  1. **`ScenarioView` / `TargetCheckView` 的字段**：契约里 `Scenario` 与 `TargetCheckResult` 都是**无属性**模型。实现按 §4.4 的意图补了最小必要字段：场景返回 `{code,label,expected_directions}`，连通性检查返回 `{target_id,reachable,detail}`。**只补语义必需项**，不把实现细节（如内部类名、线程数）写回去。
  2. **计划版本只能由 CLI 创建**：契约七个端点里**没有**创建计划的入口，且 `GenerationRunStartRequest` 严格只承载 `{plan_id, version}`（`additionalProperties:false`）。因此"写入不可变计划版本"由 `GeneratorCli plan-append` 承担，API 只读计划并启动运行。这不是遗漏，是契约边界。
  3. **`PUT /api/v1/targets` 用集合路径**：契约把更新写成集合路径并注明"是否应改为 `/targets/{id}` 未冻结"。实现照抄集合路径，用请求体 `id` 定位；**不擅自新增** `PUT /targets/{id}`，避免在冻结前造出第二套语义。
  4. **错误响应体 `{error,detail,timestamp}` 与状态码 400/404/501/500**：契约对错误体未建模。501 专用于"模式未实现"（`MALL_API`），目的是让未实现的能力**显式失败**，而不是静默换模式。
- **脏数据档位词汇**：`none|light|heavy`（对应脏数据率 0/1%/5%），契约与指导书均未冻结词表，属实现自定。
- **派生量规则**：用户数 = clamp(event_count/12, 3, 5000)、商品池 = clamp(event_count/20, 4, 2000)、分类数 = clamp(商品数/4, 3, 24)、品牌 8 个（按商品序号分摊）。理由：事件预算固定时，用户/商品规模必须由预算派生，否则"先造 10 万用户再发 1000 条事件"会产出几乎全是注册事件的废数据。这些都是**实现自定规则**，不是契约或指导书要求。

### D-016 期望隔离数写在运行报告，不写进清单（M1-4 S3b）

### D-017 `event_id` 以种子为界：可复现优先于跨运行唯一（M1-4 S3b）

- **决策**：`event_id = "E" + hex(seed 低 32 位) + 8 位序号`，`trace_id = "T" + 同前缀 + 序号`。
- **理由**：`EngineOutcome` 要求同一 `reproducibilityKey()`（= plan_version+seed+time_window，**不含 runId**）必得逐字节相同产物。若把 `runId` 编进 ID，同一计划版本重跑就不再可复现——直接违反 §4.2。
- **代价（必须如实记录）**：**跨运行的 `event_id` 会重复**（同一计划版本重跑、或不同计划恰好同种子同窗口）。当前用 ID 前缀携带种子，使"同种子重跑"与"不同种子"在数据上可区分，便于排查；但若下游要求全局唯一主键，正确做法是**重跑前轮换 seed 或换 plan_version**，而不是破坏可复现性。
- **同片另一条**：`ingest_time = event_time`。文件模式没有真实采集链路，取墙上时钟会立刻破坏可复现；这条差异已在运行报告 `notes` 里逐次声明。

### D-018 异常样本与主事件流分离（M1-4 S3b）

### D-019 提交器状态可见性（M1-11）：**已实施**真实进程态 + 进程树终止（2026-09-11 14:30）

- **原状（实测）**：`LocalProcessSparkSubmitter.status()` 恒返回 `SUBMITTED`；平台判定阶段结束**只依赖日志里能否解析出 JobResult 行**（`SparkStageExecutor` 轮询 + `JobResultParser`）。因此"作业进程已死"与"作业仍在正常跑"**不可区分**，任何观测面缺陷都只会表现为"空等到 `maxWaitMs`（实测 900 s）"——DEF-01（jar 拉取阻塞）与 DEF-03（结果行被日志窗口截断）两次事故都是这个形状。旁证：`spark_job_run.log_uri` 只在阶段判定结束时才写，故 `log_uri IS NULL` = "平台尚未判定该阶段完成"。
- **已实施修复**（`connection-ingestion/.../runtime/submit/LocalProcessSparkSubmitter.java`）：
  1. `submit()` 登记存活句柄（`LIVE[jobId]=Process`），`onExit` 回调登记退出码（`EXIT_CODES`，有界 LRU 256 条，避免平台长跑内存增长）；
  2. `status()` 返回**真实进程态**：`CANCELLED`（被本进程取消）→ `RUNNING`（存活）→ `SUCCESS`/`FAILED`（按 `exitValue()`）→ 无句柄时回落 `SUBMITTED`（平台重启后查询历史作业，保持"由日志 JobResult 行判定"的旧语义，不产生新行为差异）；
  3. `cancel()` 由"只打一条 warn"改为真实终止**进程树**（先 `descendants()` 子进程、再父进程，5 s 宽限后 `destroyForcibly`），并置 `CANCELLED`。
- **实施前必做项（已核对源码）**：`SparkStageExecutor` 轮询只把 `CANCELLED/FAILED/SUCCESS` 当终结，`RUNNING`/`SUBMITTED` 继续轮询；终结后 `CANCELLED` → "外部任务被取消"、`FAILED` → 按退出码非 0 判失败、`SUCCESS` 但日志无结果行 → `JobResultParser.resolve(0, empty)` = **FAILED「未找到 JobResult 结果行」**（§13.2 不冒充成功，无假成功分支）。
- **计数口径未变**：输入/输出/拒绝计数仍**只能**来自 JobResult（§15.3 R6-12 不放松）；进程态只回答"死没死"，不产出任何数字。
- **E2 证据**：`LocalProcessSparkSubmitterProcessTest`（4 条，真实 `cmd /c` 子进程）+ 既有 `LocalProcessSparkSubmitterLogTest`（5 条）= **9/9 GREEN**，`mvn -o -f analytics-server/pom.xml -pl connection-ingestion -am test -Dtest=LocalProcessSparkSubmitter*Test`，2026-09-11 14:31 BUILD SUCCESS。覆盖 RUNNING→cancel→CANCELLED、退出码 0→SUCCESS、退出码 3→FAILED、未知 jobId→SUBMITTED。
- **未做/遗留（不掩饰）**：① 未在真实 Spark 链路上验证"driver 中途死亡 → 阶段秒级判失败"（本轮 Spark 链路未制造进程异常，归 T2 复跑）；② 平台**没有**流水线取消路由（`PipelineController` 只有 `POST /`、`GET /{id}`、`POST /{id}/retry`、`GET /`），故 `cancel()` 目前只有测试与未来接线可用，前端也无 cancel 调用（`analytics-web/src` 全文无 `cancel` 字样）——取消能力的 API/状态机口径未立项。

### D-021 跨程序身份语义：规范事件用字符串 id，数仓用 BIGINT（**用户裁决 B-07 → 候选②，2026-09-11 已实施并取证**）

- **三个候选口径**：
  1. **数仓 id 全面改 STRING**（ODS/DWD/DWS/ADS/dim + 指标键 + 页面展示）：与冻结契约完全一致，语义最纯；代价是跨 5 层表结构 + 所有 join/聚合/指标键 + 已发布快照的迁移，属大改，须在 T2/T3 单独排期。
  2. **在 ODS→DWD 边界做一次性 id 归一化**（推荐作为 M1 解阻）：统一表达式把 `^[A-Za-z]+` 前缀剥掉再转数字，例如 `CAST(REGEXP_REPLACE(payload_user_id, '^[A-Za-z]+', '') AS BIGINT)`；数仓模型、指标、页面、已发布快照**都不用动**，改动集 = `DwdSql`(2 处 + 2 join) + `DimSql`(3 处) + `TradeDwdJob`(3 处)。风险：引入"规范 id → 数仓代理键"的**显式映射规则**，必须在契约文档与论文里写明（不得当成隐式兜底）。
  3. **生成器改成输出数字 id**：改动最小，但**违反冻结契约**（契约是权威顺序第 1 位），且把问题推给参考实现，不建议。
- **我的建议**：M1 采候选 2 解阻（并在文档中显式声明该映射规则），把候选 1 登记为 T3 的架构项；候选 3 不采纳。
- **用户裁决（2026-09-11）**：采**候选 2**——"ODS→DWD 边界一次性 id 归一化"。

### D-024 采集断点的"路径字符串"必须由键的所有者归一：规范形式单一所有者 + 状态计数同量纲（M1-12，2026-09-11 16:30 已实施并取证）

- **问题（DEF-13/B-11）**：checkpoint 的物理键是 `runtime_profile_id + file_path + file_identity`，而 `file_path` 是**字符串**——同一个物理文件写两种绝对路径（`…\.\landing\events\x.jsonl` 与 `…\landing\events\x.jsonl`）就是两条互不相认的键。实测后果：50 个文件 100 行、状态计数 101 对 `pendingFiles=51`、换写法时该文件被当作"从未采集"从头重读。
- **裁决 1（键的规范形式只有一个所有者）**：`LocalFileIngestor.checkpointKey(Path)` = `canonical(file.toAbsolutePath().toString())`，读写两侧（`ingestFile` 的写键、`findCheckpoint` 的查键）**只准走它**；`canonical` 只做 `Paths.get(...).normalize()`。**不引入 `toRealPath()`**：它要碰文件系统（文件被移动/删除时会抛异常），而键必须在"文件刚出现、刚消失、正在被写"三种时刻都能算出来；`normalize()` 是纯字符串运算，足以消除 `\.\`、`..`、重复分隔符这些**写法差异**（真正的别名问题——符号链接/短名——当前环境不存在：landing 目录是本机固定路径，无链接）。
- **裁决 2（读数端承认同一规范形式，不先删数据）**：`checkpointKeys(runtimeProfileId)` 把库里已有的行按同一个 `canonical` 归一成集合，状态计数用它；因此**历史遗留写法不再放大计数，且一行数据都不用动**。这条是关键取舍：先让"读数正确"，把不可逆的数据合并留给用户确认（见守卫卡）——反过来（先删 50 行再改代码）会在代码还没修好时先破坏现场。
- **裁决 3（`checkpointFiles` 的口径从"全表行数"改为"当前环境 events 目录中已建立断点的文件数"）**：旧口径回答的问题（整个库有多少行）与读者的问题（当前环境还有多少文件没采完 / 已建断点）不是同一个问题，`101 对 51` 就是这种错位的症状。新口径与 `pendingFiles` 在**同一次目录扫描**内计算，天然同量纲、同分母。这是**有意的口径变更**，因此：① 旧验收记录里的 100/101 保留原文并标注为旧口径（证据不可改写）；② 门禁加结构不变量 `checkpointFiles <= pendingFiles`（这条不变量与"是否已排空"无关，永远成立）。

### DEF-14 测试环境：Mockito 内联 mock maker 无法 self-attach → 用到 `mock()` 的测试类整体报错（2026-09-11 16:04 实测并固化，**已修复**）

- **现场**：M1-6 期间按"改完跑全反应堆"跑 `mvn -o -f analytics-server/pom.xml test`，`metric-analysis` 三个类（`AnalysisServiceTest` / `RfmServiceTest` / `MetricAdsDaoTest`）**23 个用例全部报错**，而代码没动过、编译正常：
  ```text
  Could not initialize plugin: interface org.mockito.plugins.MockMaker (alternate: null)
    Caused by: MockitoInitializationException: Could not initialize inline Byte Buddy mock maker.
               It appears as if your JDK does not supply a working agent attachment mechanism.
      Caused by: IllegalStateException: Could not self-attach to current VM using external process
  ```

- **根因**：Mockito 5 默认内联 mock maker（ByteBuddy）在 JDK 9+ 需要先把 agent attach 到当前 JVM；它先试**借外部 java 进程**attach（`net.bytebuddy.agent.attacher`），这条路在本机受限执行环境（管道/子进程受限）下失败，于是**任何**用到 `mock()`/`mockStatic()` 的测试类在类初始化阶段就整体报错——错误信息完全不提"环境"，极易被误读成代码回归（本轮就先怀疑了自己的改动）。

### DEF-16 两个源码策略测试依赖 surefire fork 的工作目录 → `-DforkCount=0`（本机内存受限时的可用配置）下必然失败（2026-09-11 18:28 实测，**非代码缺陷，测试基础设施脆弱点**；**2026-09-11 19:3x 已由 `P1-07` 修复，见文末"修复"**）

- **现场**：`mvn -o test -f analytics-server/pom.xml -DforkCount=0` 全反应堆时

## 7. 商城无关化实施裁决（2026-09-11，M1-12 后）

### D-025 主线选择：先做分析平台 P1–P5，商城保持参考数据源

- **背景**：三程序已能独立启停，但平台的事件词汇、字段、ID 形状、库名和发布闸门仍与 `mock-mall` 存在硬耦合。继续先美化商城不能证明分析工具可复用。

- **成功判据**：异构源 B 仅新增 profile/登记/fixture/验收，不修改核心 Java/Scala；源 A 指标不变。
- **限定**：这不是放弃当前参考商城，它继续提供可控的演示数据和 MALL_API 目标。

### D-026 五个默认值

1. P5 先用纯文件异构 fixture；真实开源商城排在 P5 后。

### D-027 B-06 契约兼容与 synthetic 标识

- **问题**：旧夹具按当前 validator 为 51/4，但按严格 JSON Schema 只有 26/55 通过。立即收紧会改变黄金口径；放宽 Schema 又会污染未来多商城契约。
- **决定**：严格 Schema 保持目标契约；旧输入标记为 `mock-mall-legacy-v1`，兼容只按 source/version 生效并记录命中数。P2/P3 用独立生成器重建严格 golden-55 后移除兼容。
- **决定**：`synthetic=true` 放在 generation run、artifact manifest 和验收元数据，不加入 8 字段业务事件信封。
- **原因**：真实和模拟数据应遵循同一业务契约；下游不得因 synthetic 字段分叉指标逻辑。

### D-028 B-08 字段语义

### D-029 M1-12 历史 checkpoint 副本处置

- **问题**：ODS→ADS 五层库名（`dw_ods`…`dw_ads`）此前硬编码在 Java（命令构造、AI 血缘）、Scala（SQL 模板、37 条建表 DDL、29 个 producer）与 `warehouse/ddl/*.sql` 里，是**多处所有者**；`runtime_profile.hive_database_prefix` 是死字段。多商城接入要求"两个源的数据落在不同库、互不干扰"，硬编码做不到。

### D-033 目标商城适配器 SPI（M1-4 S4a）：能力三态、凭据只存引用、"参考商城全路由要 Bearer"的实测（2026-09-11 19:4x 已实施并取证）

- **问题**：原"目标连通性检查"把 TCP 端口探活与本地目录可写判断写死在 `TargetProbeService` 的一个 `if` 分支里（旧代码自述"本次未验证"），既回答不了"这台商城到底有没有商品/订单/退款接口"，也无法在换商城时"只增不改"；而指导书 §3.4-6 要求用第二个 `MallTargetAdapter` 或不同字段夹具证明平台不是为 `mock-mall` 写死。用户固定指令同时要求：商城与分析系统解耦、数据种类不得写死。
- **裁决 1（SPI 先落两项，名字逐字对齐 §4.1）**：`MallTargetAdapter` 只声明 `String adapterType()` 与 `TargetCheckResult test(TargetConfig)`。指导书 §4.1 的方法名本就是 `test`、返回类型本就是 `TargetCheckResult`，所以这里**不另起名字**（早先把方法叫 `probe`、类型叫 `TargetCheck`，本轮已改回 §4.1 的字面名，避免以后为了改名再动一遍所有调用点）。§4.1 的其余七项（`capabilities/listProducts/createSyntheticUser/emitBehavior/createOrder/pay/cancel/refund`）属 **S4b**，届时按 §4.1 逐字实现。
- **裁决 2（`adapter_type` 是唯一定位键；未知类型响亮失败，绝不静默回退）**：`MallTargetAdapterRegistry` 按 `adapter_type` 派发（大小写与首尾空白不敏感）；同一类型重复注册在**启动时**就 `IllegalStateException`（"一个类型只允许一个所有者"）；未注册类型在 `POST /targets/{id}/test` 回 **400 `INVALID_ARGUMENT`** 并在 detail 里列出已注册类型。**允许"先登记后实现"**：创建目标不做类型校验（登记是意图），但任何检查/运行都不得降级成默认实现。
- **裁决 3（能力是三态，缺省即"未测出"）**：`CapabilityVerdict ∈ {SUPPORTED, ABSENT, UNDETERMINED}`；2xx→SUPPORTED、404→ABSENT、401/403/其它状态码/无应答→UNDETERMINED。两态表会把"商城没有这个接口"和"我没测出来"混为一谈，所以不可达时**一律 UNDETERMINED**，绝不写成 ABSENT。
- **裁决 4（实测不写回声明）**：探测结果是**实测**，`generator_target.capabilities` 那一列是**运营方声明**；两者不互相覆写（`TargetCheckResult` 永不回写 DB）。不一致时应以实测为准并让人看见差异。
- **裁决 5（只发安全方法）**：探测只发 `OPTIONS`（绝不为了"检查"在他方商城下单、退款、改库存），由测试 `probeUsesOnlySafeMethodsAndNeverWrites` 逐条核对服务端记录到的请求方法。
- **现场实测发现（这条推翻了一个假设）**：2026-09-11 对 8090 实测——**匿名** `OPTIONS` 连公开路由 `/api/v1/mall/products|users|orders|orders/0/pay|cancel|refunds` 也回 **401**（参考商城的 `AuthInterceptor` 对 `/api/v1/**` 一律要求 Bearer，`/api/v1/admin` 另加 admin 角色）。第一版适配器"只给 `/admin` 附凭据"，于是同一次带凭据探测里公开能力全被判 `UNDETERMINED`；改为**能取到凭据就对所有代表路由附带头**后，同一目标实测 `product/user/order/refund/admin = SUPPORTED`。⇒ 对 S4b 的直接约束：`MALL_API` 引擎的**每一次**调用都必须带凭据，不能假设"公开接口免认证"。
- **凭据只存引用**：`credential_ref` 是环境变量名，适配器按引用取值当 Bearer；取不到就匿名探测、判 UNDETERMINED，并在 detail 里点名缺哪个变量；**凭据值永不进 detail、永不入库**（E2 有专门断言，E3 实测 detail 不含令牌）。
- **未冻结的路径不猜**：公开行为埋点接口（B-04：参考商城尚无）与受保护重置接口的路径都未冻结，只能由 `config_json.behavior_path` / `reset_path` 声明；未声明 → UNDETERMINED，声明了就去实测（声明 `/api/v1/mall/behaviors` 实测 404 ⇒ `behavior=ABSENT`，即"这台商城确实没有该接口"的机器可读结论）。
- **包名不与构建产物约定相撞（现场发现）**：SPI 最初放在 `com.graduation.generator.target` 包，结果 **10 个源文件对 git 完全不可见**——`synthetic-data-generator/.gitignore:2` 的 `target/`（Maven 构建产物约定、无前导斜杠 ⇒ 任意层级匹配）命中了 `…/generator/target/*.java`，`git check-ignore -v` 直接证实，`git status` 里这批文件根本不出现（测试全绿也提交不上去）。裁决：**不往 `.gitignore` 加例外**（父目录被排除时对文件的反选无效，且会长期留下"包名与构建产物目录同名"的坑），改名 `adapter`（内容本就是"目标商城适配器 + 其配置/结论类型"）。⇒ 通用规则：包名/目录名撞上 `target/`、`dist/`、`build/` 一类约定时**选改名**；交付前用 `git status --short <模块>` 核对新文件确实出现在待提交列表，不能只看测试绿。

### D-035 P1-03 源登记 API 语义裁决：「当前激活源」的唯一所有者是 ACTIVE `runtime_profile.source_id`——不新增列、不新增表、不需要 V17（2026-09-11 20:0x，**实施前**裁决；本行时间原写作 `20:1x`，与含它的提交 `34bc544`（20:07:58）矛盾，20:17 核时钟后改正）

- **问题**：P1-03 的 DoD 要求"并发激活只有一个当前源"，但 V16 只落了 `source_registry.status` 与 `runtime_profile.source_id` 两处状态，**没有**"当前源"这个概念的显式载体。若实施者各自发明（新增 `is_current` 列 / 新增 `current_source` 单行表 / 靠"唯一 ACTIVE 源行"），就会出现第二个所有者：既与设计 §4.1 的分工冲突，也会把 P4-04 的"源切换"与 P4-02 的"按源隔离"分裂成两套真相。因此在实施开始前先把语义钉死。
- **裁决 1（`status` 是源自身的生命周期，不是当前源指针）**：`source_registry.status ∈ {DRAFT, ACTIVE, PAUSED, DISABLED}`，含义为该源**自身**能否被使用：`DRAFT` 已登记未验证 / `ACTIVE` 可用于采集与分析 / `PAUSED` 暂停使用（保留画像与数据）/ `DISABLED` 停用不可再选。**允许多个源同时 `ACTIVE`**——这是 P5"源 B 全链 + 源 A 回归"能并存的前提；把 `ACTIVE` 当"唯一当前源"会让 P5 只能靠反复停启来表达，语义被压扁。**枚举来源与写路径约束**：设计 §4.1 的 `status` 列只简写 `ACTIVE`/`PAUSED`，实施计划 §3.1 给的是并集 `DRAFT/ACTIVE/PAUSED/DISABLED`，V16 已按并集建列（`VARCHAR(16)`、无 CHECK 约束）⇒ **存储与读取层接受并集**（读到 `DRAFT`/`DISABLED` 不得报错，这是 D-034「并集不删减」口径的延续），而 **P1-03 是唯一写入口、本轮只写三个值**：`create`→`DRAFT`（或显式 `PAUSED`）、`activate`→`ACTIVE`、`pause`→`PAUSED`；`DISABLED`（退役）本轮**不实现**，留给 P4 之后再定义。
- **裁决 2（「当前激活源」= 当前唯一 ACTIVE `runtime_profile` 行绑定的源）**：设计 §4.1 对两处状态的分工是逐字的——"`source_registry` 管**这个源是谁、词汇表在哪**；`runtime_profile` 继续管**这次运行用什么参数**"。当前源属于"这次运行"，不属于"源是谁"⇒ 复用 V16 已经落好的 `runtime_profile.source_id`，**不新增列、不新增表、不需要 V17**（迁移号无需再动）。副产品：设计风险表与计划 §7 P4-03 要求的"`/metrics` 省略 source 时按当前激活源返回"不用再造概念，直接派生自 ACTIVE profile 的绑定。
- **裁决 3（"只有一个当前源"是结构性事实，不是并发技巧）**：`runtime_profile` 的 ACTIVE 行由既有 `RuntimeProfileServiceImpl.activate`（§8.3：旧 ACTIVE → DISABLED，`@Transactional`）维持唯一；当前源是"唯一 ACTIVE 环境的**绑定列**"，不是标志位 ⇒ **两个当前源在数据结构上不可表示**。并发激活的正确性目标因此不是"防止出现两个当前源"，而是：① 不出现两个 ACTIVE 环境；② 每次成功变更都有审计、不静默丢写；③ 每个请求有可判定结果（成功 / 冲突 / 幂等）。这三点必须用**真实并发测试**取证（多线程/多请求），不允许用"想当然是原子的"代替。
- **裁决 4（`activate` 的语义与顺序）**：`POST /sources/{id}/activate`，单事务：① 画像校验（文件存在 + JSON 合法 + 文件里的 `sourceCode`/`profileVersion` 与登记行一致）→ 不合法 `SOURCE_PROFILE_INVALID`；② 该源 `status` 置 `ACTIVE`；③ 把当前 ACTIVE `runtime_profile.source_id` 绑定到该源。**幂等**：该源已是当前源时返回成功，且**不重复写"绑定"审计**（是否写一条 no-op 审计由实施者定，但必须有测试固化所选行为）。
- **裁决 5（`pause` 不能暂停当前源）**：`POST /sources/{id}/pause` 置 `PAUSED`；**若该源正是当前绑定源 → `SOURCE_IN_USE` 拒绝**（先切换当前源）。理由：当前源被暂停是自相矛盾状态，宁可拒绝也不要写进去。

### D-037 P1-05 实施前语义裁决：断点键加源维度（含唯一键重建）、manifest 加源身份四字段、`ingestion_batch.source` 的既有语义不许复用（2026-09-11 20:0x–20:1x，实施前登记）
