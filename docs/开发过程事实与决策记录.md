## 2. 决策记录

### D-001 三程序架构裁决（转写 V2.1 §3，作为实施依据）

- **背景**：现状是"平台 + 商城"两程序，且商城内含数据生成器（`generator` 包、`GeneratorController`、`Generator.vue`），平台侧还残留商城配置键。
- **选定**：① `analytics-platform`(:8091) 不含任何商城业务 CRUD／随机造数／商城库与 Java 依赖；② `reference-mall`(:8090) 保留真实商城行为；③ 新增 `synthetic-data-generator`(:8092 或 CLI)，只经公开 API（`MALL_API`）或产出规范事件文件（`CANONICAL_EVENT_FILE`）；④ 中立契约目录 `contract-specs`；⑤ 三程序不得共享 Java 实体/Mapper/Maven 业务依赖。
- **执行顺序（本记录追加的工程决策）**：**先建 M1-4 新生成器并验收，再执行 M1-7 拆除商城生成器**。理由：反过来做会出现"造数能力真空期"，本地唯一可用数据链会断，导致 T2 黄金链无法复跑。
- **代价**：一段时间内仓库同时存在新旧两套造数代码（允许的过渡态，但必须在看板上可见）。

### D-002 Landing 根的唯一来源 = ACTIVE `RuntimeProfile.landingUri`（退役声明）

- **新唯一来源**：`analytics_meta.runtime_profile` 中 `status='ACTIVE'` 行的 `landing_uri`，由 `RuntimeProfileServiceImpl.findActive()` 读取；写入侧不变（激活流程）。
- **必须删除的旧路径**：`IngestionService.status()` 中的 `environment.getProperty("mall.landing.path", "./landing")`
  ——它既是商城侧配置键（违反 V2.1 §3.4-4"平台不得引用 `mall.*` 配置键"），又与 `runOne()` 使用的档案路径可能不一致（同一份采集状态可能来自两个不同目录）。
- **禁止保留兜底**：删除后**不得**再添加任何"没有 ACTIVE 环境就用默认目录"的分支。无 ACTIVE 时如实报告 `profileState=NO_ACTIVE`。
- **验证计划**：单元测试 `IngestionServiceStatusTest`（有/无 ACTIVE 两条路径 + 最近批次回显）；源码级守卫 `PlatformMallBoundarySourcePolicyTest`（禁止 `mall.*` 键复活）；真实进程烟测（重建 jar → 重启 8091 → `GET /api/v1/ingestion/status`）。
- **破坏性确认**：无需（只改读取来源，不删数据、不删文件）。

### D-003 无 ACTIVE 环境时的行为 = 显式降级报告，而不是"再找一条路"

- **背景**：旧代码在没有 ACTIVE 档案时仍能给出 `eventsDir`（来自配置键默认值），看起来"更健壮"。
- **选定**：返回 `profileState=NO_ACTIVE` + `runtimeProfileId=null` + `landingUri=null` + `eventsDir=null` + `pendingFiles=0`；`latestBatch`/`checkpointFiles` 仍照常返回（历史事实与该环境无关）。
- **理由**：这是一条**显式错误报告分支**，不是第二数据源。若在此回退到默认路径，会出现"报表读 A 目录、采集读 B 目录"的静默错位——正是 D-002 要消除的缺陷。
- **代价**：无 ACTIVE 环境时前端看到"采集不可用"，需要先走激活流程（V2.1 §8.3 的预期行为）。

### D-004 死文件 `db/business/V1__init_mall.sql` 的处置（确认前置）

- **事实**：`analytics-server/platform-app/src/main/resources/db/business/V1__init_mall.sql`（9637 字节）内含 `CREATE TABLE mall_user`（:7）与 `CREATE TABLE mall_order`（:61）；Flyway 只加载 `classpath:db/meta` 与 `classpath:db/metric`，**该文件从不被执行**。
- **风险**：不执行的 DDL 也会被人工/工具误读为"平台拥有商城表"，与 V2.1 §3.4-4 冲突；同时它是平台上唯一残留的商城表字面量。
- **选定**：物理删除（代码退役类操作）。
- **破坏性确认**：**需要**。虽然它不参与运行，但属于"合同承载型残留"（见 §3 反熵声明），必须由用户显式确认删除范围后才执行；确认前看板任务 M1-3 保持 `BLOCKED`，并由 `PlatformMallBoundarySourcePolicyTest` 把它钉在"未被加载"状态（而不是静默忽略）。

### D-008 Landing URI 解析收敛为唯一实现 `LandingUri`

- **背景（缺陷驱动）**：M1-1 写单元测试时发现同一段 `file://` 截断逻辑有三份拷贝
  （`IngestionService`、`PipelineService`、`LocalLandingStorage`），三份都把标准写法
  `file:///D:/landing` 截成 `/D:/landing`：Windows 上 `Paths.get` 直接抛
  `InvalidPathException: Illegal char <:> at index 2`，Linux 上得到一个形如 `/D:/landing` 的错误目录；
  `hdfs://namenode:8020/landing` 会被**静默**当成相对目录 `hdfs:/namenode:8020/landing`（比报错更危险）。
  三份实现 = 三种错法，且都以"看起来支持"的注释写着 `file:///D:/...`。
- **选定**：新增 `platform-common` 的 `com.graduation.analytics.common.LandingUri.resolve(String)` 作为唯一实现：
  标准 `file:///D:/x`、`file:///data/x`、`file://D:/x`、历史 `file://./x` 与裸路径均支持；
  空值、主机名形式 `file://host/share`、非 file 协议一律抛 `MallBizException`（**不返回默认目录**）。
  三个调用点改为调用它，并删除两份重复实现（`PipelineService.parseLandingRoot` 包装方法一并删除）。
- **配置边界的例外（显式声明）**：`LocalLandingStorage` 的构造参数是**配置项** `platform.landing.local-root`
  （默认值已在 `@Value` 里声明为 `./landing`），故仅在配置为空时才兜底 `./landing`——这个默认值属于配置声明，
  不属于"环境档案的第二来源"，解析本身仍走唯一实现。
- **代价**：`platform-common` 过去没有任何测试类，本次新增 test 作用域依赖 `spring-boot-starter-test` 与
  `LandingUriTest`（4 个用例）。
- **验证**：`LandingUriTest`（标准写法/历史写法/盘符写法/非法写法）+ `IngestionServiceStatusTest`（标准写法经 profile 生效）
  + 真实的 `POST /api/v1/ingestion/runs` 一轮采集（产出 `manifestPath=file:///D:/...`，正是曾经会崩的形态）。

### D-009 启动脚本的调用方式（环境事实）

- **事实**：`pwsh -File scripts/start-all.ps1 -PlatformOnly` 在**前台管道**里调用（`... | Select-Object -Last 6`）会挂住不返回：
  脚本自身已成功启动服务并通过探活（日志有完整启动记录、端口在监听），但外层管道等不到结束，5 分钟超时。

  探活与业务调用分开执行。这条是工具使用约定，不是脚本缺陷（脚本作为后台作业运行时 100% 正常）。

### D-012 生成器独立元数据库与 S1 骨架（M1-4 S1）

- **决策 1（独立库自举，不碰既有初始化脚本）**：生成器使用自有库 `generator_meta`，连接串带 `createDatabaseIfNotExist=true`，首次启动即自举建库，Flyway location 为 `classpath:db/generator`。

- **决策 2（五表 DDL 按 §4.2 关键字段落地，字段名与契约一致）**：`generator_target`(12 列) / `generation_plan`(14) / `generation_run`(16) / `generation_artifact`(11) / `generation_event_stat`(5)。

  - **理由**：`contract-specs/schemas/generation-artifact-manifest.v1.schema.json` 已把该文档的属性名冻结为 `artifact_*`（`artifact_uri`/`artifact_checksum`/`artifact_bytes`/`artifact_record_count`），而项目里另有"采集清单"（`ingestion-manifest.v1.schema.json`）也叫 manifest。若类名只叫 `Manifest`，`analytics-server` 的采集侧同名概念会产生歧义。**接口方法名与字段名严格照 §4.1/schema 不动，只动 Java 类名**，故不构成契约偏离。
  - **验证**：`GeneratorContractParityTest` 断言磁盘清单恰好 9 个字段且与 schema 属性逐一对应，类名不参与契约。
- **决策 2（制品类补 `min/max_event_time`）**：`Artifact` 由 `(uri, kind, checksum, bytes, recordCount)` 扩为再加 `(minEventTime, maxEventTime)`。
  - **理由**：§4.2 的 `generation_artifact` 有 `min_event_time`/`max_event_time` 两列，不带上就写不进去；两值在写入过程中顺带即可算出（解析 `event_time` 取极值），无额外成本。
  - **约束**：构造器拒绝"非空制品缺 min/max"，避免出现无法对账的行；空制品（0 行）允许为空。
- **决策 3（轮转即写清单）**：`rotateIfNeeded()` 在关闭当前文件后**立即**写该文件的同名清单，而不是只在最终关账时写一次。

### D-014 运行状态机允许 `PENDING → CANCELLED`（M1-4 S3a）

- **决策**：§4.2 列出的状态机为 `PENDING → RUNNING → SUCCESS/FAILED/CANCELLED`；实现额外允许 `PENDING → CANCELLED`，且**只允许这一条额外边**。
  - **理由**：§4.4 要求 `POST /generation-runs/{id}/cancel` **幂等**。若严格按 §4.2，排队中（尚未 `RUNNING`）的取消请求将无处落地：要么返回失败（违反幂等语义），要么强制先置 `RUNNING` 再立刻 `CANCELLED`（伪造状态迁移，污染运行历史）。允许该边是**受控扩展**，且方向单一、不引入回退边。
  - **边界**：`RUNNING → PENDING`、`SUCCESS → FAILED`、`CANCELLED → RUNNING`、终态的任何出边一律拒绝；`fromDb` 对未知/空串严格抛错（不使用 valueOf 的静默回退）。
  - **证据**：`RunStatusTest` 4 用例（含上述非法迁移全拒与 `fromDb` 严格性）；`GeneratorMetaStoreTest` 在真实 MySQL 上验证"终态保护"（对已终态运行再 `finishRun`/`markRunning` 均不生效）与"取消幂等"（第二次请求返回 `false`）。
- **另一处时间处理决策（同片）**：JDBC 时间统一用 `LocalDateTime` + `java.sql.Timestamp` **之外的** `setObject`，并按 `ContractFormat.BUSINESS_ZONE`（Asia/Shanghai）显式换算。
  - **理由**：用 `Timestamp` 会让落库的 `DATETIME(3)` 字面量随 JVM 默认时区漂移（`-Duser.timezone` 一变，同一 `Instant` 写成不同文本）；显式按业务时区换算后，运行时间在库里可读且与产物的 `+08:00` 时间戳同一口径。
  - **证据**：集成测试断言毫秒往返一致（`2026-09-01T02:00:00.123Z` 写入读回同值）。

### D-015 API 层三处"契约未冻结、实现必须先给出形状"的临时口径（M1-4 S3b）

- **背景**：冻结契约 `contract-specs/openapi/generator-api.v1.yaml` 只冻结了路径、方法与成功码，多处明确写着"形状未冻结、本契约不造结构"。实现不能因此停摆，但也不能把临时形状说成契约。
- **决策（四处，等契约冻结后必须回头对齐）**：
  1. **`ScenarioView` / `TargetCheckView` 的字段**：契约里 `Scenario` 与 `TargetCheckResult` 都是**无属性**模型。实现按 §4.4 的意图补了最小必要字段：场景返回 `{code,label,expected_directions}`，连通性检查返回 `{target_id,reachable,detail}`。**只补语义必需项**，不把实现细节（如内部类名、线程数）写回去。
  2. **计划版本只能由 CLI 创建**：契约七个端点里**没有**创建计划的入口，且 `GenerationRunStartRequest` 严格只承载 `{plan_id, version}`（`additionalProperties:false`）。因此"写入不可变计划版本"由 `GeneratorCli plan-append` 承担，API 只读计划并启动运行。这不是遗漏，是契约边界。
  3. **`PUT /api/v1/targets` 用集合路径**：契约把更新写成集合路径并注明"是否应改为 `/targets/{id}` 未冻结"。实现照抄集合路径，用请求体 `id` 定位；**不擅自新增** `PUT /targets/{id}`，避免在冻结前造出第二套语义。
  4. **错误响应体 `{error,detail,timestamp}` 与状态码 400/404/501/500**：契约对错误体未建模。501 专用于"模式未实现"（`MALL_API`），目的是让未实现的能力**显式失败**，而不是静默换模式。
- **脏数据档位词汇**：`none|light|heavy`（对应脏数据率 0/1%/5%），契约与指导书均未冻结词表，属实现自定。
- **派生量规则**：用户数 = clamp(event_count/12, 3, 5000)、商品池 = clamp(event_count/20, 4, 2000)、分类数 = clamp(商品数/4, 3, 24)、品牌 8 个（按商品序号分摊）。理由：事件预算固定时，用户/商品规模必须由预算派生，否则"先造 10 万用户再发 1000 条事件"会产出几乎全是注册事件的废数据。这些都是**实现自定规则**，不是契约或指导书要求。

### D-016 期望隔离数写在运行报告，不写进清单（M1-4 S3b）

- **决策**：`expected_quarantine_counts`（脏样本类型 → 期望隔离条数）落在 `<runDir>/run-report.json`，**不**写进 `events-*.manifest.json`。

### D-017 `event_id` 以种子为界：可复现优先于跨运行唯一（M1-4 S3b）

- **决策**：`event_id = "E" + hex(seed 低 32 位) + 8 位序号`，`trace_id = "T" + 同前缀 + 序号`。
- **理由**：`EngineOutcome` 要求同一 `reproducibilityKey()`（= plan_version+seed+time_window，**不含 runId**）必得逐字节相同产物。若把 `runId` 编进 ID，同一计划版本重跑就不再可复现——直接违反 §4.2。
- **代价（必须如实记录）**：**跨运行的 `event_id` 会重复**（同一计划版本重跑、或不同计划恰好同种子同窗口）。当前用 ID 前缀携带种子，使"同种子重跑"与"不同种子"在数据上可区分，便于排查；但若下游要求全局唯一主键，正确做法是**重跑前轮换 seed 或换 plan_version**，而不是破坏可复现性。
- **同片另一条**：`ingest_time = event_time`。文件模式没有真实采集链路，取墙上时钟会立刻破坏可复现；这条差异已在运行报告 `notes` 里逐次声明。

### D-018 异常样本与主事件流分离（M1-4 S3b）

- **决策**：脏样本**不进**主事件流，由引擎以 `EngineOutcome.dirtySamples()` 返回，运行服务写成独立制品 `<runDir>/dirty-samples.jsonl`（`kind=DIRTY_SAMPLE`），逐类型的期望隔离数进运行报告。
- **理由**：主事件流必须**100% 契约有效**，才能被 §3.4 的独立验收项真正验证；把脏行混进主流会让"契约符合性"这一项永远说不清。分离后两个目标同时成立：主流可全量校验，脏数据仍可按期望条数对账。

- **`Artifact` 不变量相应收窄**：非空制品必须带 min/max `event_time` 的约束**只对 `KIND_EVENT_JSONL` 生效**。原因：脏样本按定义就包含非法事件时间与截断 JSON，无法给出合法 min/max；强行填计划窗口会伪造"真实时间范围"。

### D-019 提交器状态可见性（M1-11）：**已实施**真实进程态 + 进程树终止（2026-09-11 14:30）

- **原状（实测）**：`LocalProcessSparkSubmitter.status()` 恒返回 `SUBMITTED`；平台判定阶段结束**只依赖日志里能否解析出 JobResult 行**（`SparkStageExecutor` 轮询 + `JobResultParser`）。因此"作业进程已死"与"作业仍在正常跑"**不可区分**，任何观测面缺陷都只会表现为"空等到 `maxWaitMs`（实测 900 s）"——DEF-01（jar 拉取阻塞）与 DEF-03（结果行被日志窗口截断）两次事故都是这个形状。旁证：`spark_job_run.log_uri` 只在阶段判定结束时才写，故 `log_uri IS NULL` = "平台尚未判定该阶段完成"。
- **已实施修复**（`connection-ingestion/.../runtime/submit/LocalProcessSparkSubmitter.java`）：
  1. `submit()` 登记存活句柄（`LIVE[jobId]=Process`），`onExit` 回调登记退出码（`EXIT_CODES`，有界 LRU 256 条，避免平台长跑内存增长）；
  2. `status()` 返回**真实进程态**：`CANCELLED`（被本进程取消）→ `RUNNING`（存活）→ `SUCCESS`/`FAILED`（按 `exitValue()`）→ 无句柄时回落 `SUBMITTED`（平台重启后查询历史作业，保持"由日志 JobResult 行判定"的旧语义，不产生新行为差异）；
  3. `cancel()` 由"只打一条 warn"改为真实终止**进程树**（先 `descendants()` 子进程、再父进程，5 s 宽限后 `destroyForcibly`），并置 `CANCELLED`。
- **实施前必做项（已核对源码）**：`SparkStageExecutor` 轮询只把 `CANCELLED/FAILED/SUCCESS` 当终结，`RUNNING`/`SUBMITTED` 继续轮询；终结后 `CANCELLED` → "外部任务被取消"、`FAILED` → 按退出码非 0 判失败、`SUCCESS` 但日志无结果行 → `JobResultParser.resolve(0, empty)` = **FAILED「未找到 JobResult 结果行」**（§13.2 不冒充成功，无假成功分支）。
- **计数口径未变**：输入/输出/拒绝计数仍**只能**来自 JobResult（§15.3 R6-12 不放松）；进程态只回答"死没死"，不产出任何数字。
- **E2 证据**：`LocalProcessSparkSubmitterProcessTest`（4 条，真实 `cmd /c` 子进程）+ 既有 `LocalProcessSparkSubmitterLogTest`（5 条）= **9/9 GREEN**，`mvn -o -f analytics-server/pom.xml -pl connection-ingestion -am test -Dtest=LocalProcessSparkSubmitter*Test`，2026-09-11 14:31 BUILD SUCCESS。覆盖 RUNNING→cancel→CANCELLED、退出码 0→SUCCESS、退出码 3→FAILED、未知 jobId→SUBMITTED。
- **未做/遗留（不掩饰）**：① 未在真实 Spark 链路上验证"driver 中途死亡 → 阶段秒级判失败"（本轮 Spark 链路未制造进程异常，归 T2 复跑）；② 平台**没有**流水线取消路由（`PipelineController` 只有 `POST /`、`GET /{id}`、`POST /{id}/retry`、`GET /`），故 `cancel()` 目前只有测试与未来接线可用，前端也无 cancel 调用（`analytics-web/src` 全文无 `cancel` 字样）——取消能力的 API/状态机口径未立项。

### DEF-08 热门商品名在维度缺失时为空 → BLOCKING 空关键列把整条发布拦死（2026-09-11 14:51 实测，15:0x **已修复**，E2+E3 待 run 38/39 复核）

- **现象**：run 37（DEF-05 修复后的第一次真实链路）所有 Spark 阶段 SUCCESS、`QUALITY_CHECK/dqc` 仍 FAILED，**只剩一条** BLOCKING：`ADS_STAGING_KEY_NOT_NULL` check 30 / error 9，detail=`空关键列: dw_ads.ads_hot_product__staging=9`。`PUB_DQ_BLOCKING_RULES` 已 passed。
- **实测证据（spark-sql 直读暂存分区）**：`ads_hot_product__staging`（`dt=20260901 AND snapshot_id=S20260901_37`）→ `rows=9, null_pid=0, null_name=9`；同层 `dws_product_behavior_day/dt=20260901` → 9 个商品；而 **`dw_dim.dim_product/dt=20260901` → 0 行**。
- **根因**：`dim_product` 是**按业务日的快照**（只含当日 `product_created/product_updated` 事件）。当日没有商品事件时该分区为空，而 `AdsSql.hotProduct` 用 `LEFT JOIN dw_dim.dim_product p ON p.product_id = t.product_id AND p.dt = '$dt'` 取商品名 → 9 行商品名全部 NULL → 撞上"关键列非空"的 BLOCKING 规则。**这不是 id 问题**（`product_id` 归一化后非空），是**维度覆盖度**问题：跨日商品的维度行不在当日分区里。
- **为什么这条规则必须保留严格**：`ADS_STAGING_KEY_NOT_NULL` 是发布前最后一道"不留空关键列"闸门，宽松化会把"商品名空白"直接放进面向员工的热门商品榜；正确做法是让上游给出**显式的 unknown 值**，而不是让规则放行 NULL。
- **已实施修复**：`AdsSql.hotProduct` 的商品名改为维度表既有 unknown 约定兜底 `COALESCE(p.product_name, 'UNKNOWN') AS product_name`（与 `DimSql.productSnapshot` 写 `COALESCE(payload_product_name,'UNKNOWN')` 一致），并在方法注释里写明 DEF-08 的实测数字。改动 1 文件 1 行 + 注释。
- **E2 证据**：`SqlTemplateSpec`「DEF-08：热门商品名取维度兜底…」断言 `coalesce(p.product_name, 'unknown') as product_name` 存在、裸 `t.product_id, p.product_name,` 不存在；`mvn -o -f spark-jobs/pom.xml package` → **Tests 54 succeeded / 0 failed / BUILD SUCCESS**（2026-09-11 15:0x），jar 已重建。
- **遗留（需要口径裁决，登记 B-09）**：兜底只保证"不空"，不保证"名字真实"。要让热门商品榜显示真实商品名，得让维度覆盖跨日商品，两条路线：① 维度改为**全量滚动快照**（`dim_product` 取 `dt <= 业务日` 的最新状态，标准缓慢变化维做法，改动在 `DimSql` + 维度分区语义）；② ADS 侧改为**维度的最新可用分区下推**（读 `dim_product` 的最大分区，语义更隐晦）。当前实现按"当日快照"语义工作，故 run 38 的热门商品名会是 `UNKNOWN`——这是**已知且如实标注**的表现。
- **同批暴露的维度缺口（事实记录）**：`dim_user/dt=20260901` 只有 8 行（当日注册用户），而 DWS 当日活跃用户 10 → 用户维度属性（城市等级）同样存在跨日缺失；`dwd_user_behavior_detail.category_id` 因 `dim_product` 为空而全部落到 `-1` 哨兵。这些都属同一根因（**维度单日快照 ≠ 全量状态**），登记 B-09 一起裁决。

### DEF-10 用户画像 ADS 的 NOT NULL 列产出 NULL → 发布阶段整条失败（2026-09-11 15:01 实测，15:0x **已修复**，E2 已取证）

- **现象**：run 38（DEF-05 + DEF-08 修复后）**8 个阶段全部推进到 `PUBLISH_METRIC`**，`QUALITY_CHECK` 判 SUCCESS（`ADS_STAGING_KEY_NOT_NULL` passed 30/0），但发布失败：阶段 `PUBLISH_METRIC` = `FAILED / RUN_METRIC_PUBLISH_FAILED`，`evidence` 为空（失败发生在写 evidence 之前），目标快照 `metric_value` **0 行**。

### DEF-11 商城 `GET /api/v1/mall/outbox/status` 在"还没有滚动文件"时 500（2026-09-11 15:1x 实测，**已修复**，E2 已取证）
