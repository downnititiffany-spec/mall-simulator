# 基于 Spark 大数据平台和智能分析模型的电商用户行为分析系统设计与实现

## 项目设计文稿 V2.1

## 版本说明

本文稿在 V2.0 的基础上根据技术能力和系统完整性要求调整为 Java 技术路线。系统后端统一使用 Spring Boot，SQL 解析使用 JSqlParser，数据源由 Java 模拟商城程序持续生成，业务表通过 DataX 周期同步，用户行为日志通过 Flume 自动采集。项目仍以 Hadoop、Hive、Spark 和数据仓库为主体，大语言模型只是智能交互与分析增强模块，不把系统扩展为复杂 Agent、推荐平台或微服务集群。

本版本的核心结论是：毕业设计的创新性不应只表述为“接入大模型 API”，而应体现为一套可实现、可验证、可对比的智能分析方法，即以业务语义层提高 SQL 生成准确率，以多级校验和自动纠错保证查询安全与可用性，以查询证据链降低分析结果不可追溯的问题。围绕这三项设计，可以形成完整的系统实现、对照实验、消融实验和性能测试，论文内容具有足够的技术深度。

# 1 项目概述

## 1.1 项目名称

基于 Spark 大数据平台和智能分析模型的电商用户行为分析系统设计与实现。

## 1.2 项目定位

本项目面向电商运营分析场景，建设从原始数据进入 HDFS、Hive 数仓分层、Spark 离线计算、指标数据服务、可视化展示到大模型辅助分析的完整链路。系统主要解决以下问题：

1. 海量用户行为日志难以直接使用关系数据库高效处理；
2. 原始业务数据口径不统一，难以直接形成稳定指标；
3. 普通运营人员不熟悉 Hive SQL，数据查询门槛较高；
4. 传统报表只给出数值，缺乏对趋势、异常和业务含义的解释；
5. 大模型生成 SQL 存在字段幻觉、口径错误和安全风险。

系统采用“离线数仓计算为主、智能分析为辅”的总体定位：

```text
大数据平台与数仓建设约占 80%
智能分析与自然语言交互约占 20%
```

Spark 和 Hive 负责可信计算，大模型不直接创造业务数据，只负责理解问题、生成受约束 SQL、解释真实查询结果和形成结构化报告。

## 1.3 建设目标

### 1.3.1 工程目标

- 建立“Java 模拟商城数据源、DataX 业务数据同步、Flume 行为日志采集、手动文件导入备用”的多通道数据接入流程；
- 建立 ODS、DWD、DWS、ADS 四层 Hive 数据仓库；
- 使用 Spark SQL 完成清洗、聚合、漏斗分析、用户分层和应用指标生成；
- 建立可视化 Web 系统，展示用户、商品、交易和画像主题指标；
- 建立自然语言到 Hive SQL、查询结果到分析报告的智能分析链路；
- 对任务运行、SQL 查询和大模型调用进行日志记录和审计。

### 1.3.2 研究目标

- 研究业务语义信息对 Text-to-SQL 准确率的影响；
- 研究“生成、校验、执行反馈、修复”闭环对 SQL 执行成功率的影响；
- 研究证据约束对大模型分析结论可信度的影响；
- 验证 Spark 分区、缓存、广播连接等策略对离线任务性能的改善效果。

## 1.4 目标用户与使用场景

| 用户角色 | 主要需求 | 典型操作 |
|---|---|---|
| 系统管理员 | 管理数据、任务、配置和权限 | 导入文件、执行任务、查看运行日志、维护指标口径 |
| 数据分析人员 | 查看指标并进行自助查询 | 查看大盘、筛选时间、查看 SQL、导出结果 |
| 电商运营人员 | 快速理解经营变化 | 查询销售趋势、转化漏斗、热门商品、用户分层 |
| 答辩评审人员 | 验证系统完整性与创新性 | 查看全链路、性能对比、AI 准确率与安全测试 |

## 1.5 项目边界

### 必须实现

- Hadoop、HDFS、YARN、Hive、Spark SQL；
- ODS、DWD、DWS、ADS 四层数仓；
- 数据导入、任务运行、质量检查、分析看板；
- 用户行为、转化漏斗、商品、销售、用户画像五类分析；
- 大模型 API、业务语义层、Text-to-SQL、SQL 安全校验、结果解释；
- Java 模拟商城数据生成器、DataX 批量同步和 Flume 日志采集；
- Spring Boot 后端、Vue 3 管理界面和 ECharts 可视化；
- 查询日志、模型调用日志、实验数据和测试报告。

### 可选增强

- 使用 Spark MLlib KMeans 对 RFM 特征进行用户聚类；
- 使用轻量级关键词或向量检索选择相关表结构；
- Docker Compose 统一部署 Web、MySQL 和 Spring Boot 服务；
- Kafka 与 Structured Streaming 实现实时指标演示。

### 本期不做

- 自训练大语言模型；
- 复杂 Agent 自主规划；
- Spring Cloud 微服务体系；
- 实时个性化推荐和在线特征平台；
- 生产级高可用集群和全量数据治理平台。

# 2 需求分析

## 2.1 功能需求

系统划分为八个一级模块：系统与权限、数据接入、数仓与任务、数据质量、用户行为分析、商品与销售分析、用户画像、智能分析。八个模块共同覆盖“数据进入、数据加工、指标形成、结果展示、自然语言查询、过程审计”的完整闭环。

## 2.2 非功能需求

| 类别 | 设计要求 | 验收方式 |
|---|---|---|
| 可用性 | 核心页面结构清晰，查询过程有状态反馈，错误信息可理解 | 功能测试和用户任务测试 |
| 性能 | 百万级至亿级行为数据可由 Spark 分布式处理，常用 ADS 查询优先在 3 秒内返回 | 不同数据规模压测 |
| 安全 | AI 查询只读、表字段白名单、行数限制、超时控制、敏感字段脱敏 | 恶意提示和危险 SQL 测试 |
| 正确性 | 指标有统一口径，数仓层间记录数和金额可核对 | 数据质量规则和人工基准 SQL |
| 可追溯性 | 每次 AI 回答保存问题、SQL、表、条件、耗时和模型信息 | 查询详情页和审计表 |
| 可扩展性 | 数据源、指标、模型供应商和展示图表通过配置扩展 | 模块接口与配置检查 |
| 可复现性 | 数据集版本、任务参数、提示词版本和实验结果可保存 | 实验记录与版本表 |

## 2.3 核心业务指标定义

| 指标 | 计算口径 | 主要来源 |
|---|---|---|
| PV | 浏览行为记录数 | dwd_user_behavior_detail |
| UV | 发生浏览行为的去重用户数 | dwd_user_behavior_detail |
| DAU | 当日发生任一有效行为的去重用户数 | dwd_user_behavior_detail |
| 加购率 | 加购用户数 ÷ 浏览用户数 | dws_behavior_funnel_day |
| 购买转化率 | 购买用户数 ÷ 浏览用户数 | dws_behavior_funnel_day |
| 客单价 | 支付金额 ÷ 支付订单数 | dws_trade_day |
| 复购率 | 观察期内购买次数不小于 2 的用户数 ÷ 购买用户数 | dws_user_trade_period |
| 商品热度 | 浏览、收藏、加购、购买的加权得分 | dws_product_behavior_day |
| 用户价值 | 最近购买间隔、购买频次、消费金额综合结果 | ads_user_profile |

所有指标必须明确时间范围、过滤条件和统计粒度。AI 模块只允许引用指标字典中已有口径，避免同一问题出现不同计算方式。

# 3 总体架构设计

## 3.1 逻辑架构

```text
┌──────────────────────────────────────────────────────────────┐
│                    Vue 3 + ECharts 展示层                    │
│ 数据生成  采集监控  任务中心  质量中心  分析看板  AI 助手    │
└────────────────────────────┬─────────────────────────────────┘
                             │ REST API
┌────────────────────────────▼─────────────────────────────────┐
│                      Spring Boot 服务层                      │
│ 登录权限  数据生成控制  采集控制  Spark任务  指标查询        │
│ 数据质量  AI调用  JSqlParser校验  审计日志                   │
└──────────────┬───────────────┬──────────────┬────────────────┘
               │               │              │ HTTPS
               │               │              ▼
               │               │          大模型 API
               │               │
┌──────────────▼──────┐  ┌─────▼──────────────────────────────┐
│ Java 模拟商城数据源 │  │              数据采集层             │
│ MySQL业务表+行为日志│  │ DataX: MySQL -> HDFS  Flume: 日志 -> HDFS│
└──────────────┬──────┘  └─────┬──────────────────────────────┘
               └───────────────┤
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ HDFS Landing -> Hive ODS -> Hive DWD -> Hive DWS -> Hive ADS│
│             Spark SQL 清洗 聚合 漏斗 RFM 指标计算             │
└────────────────────────────┬─────────────────────────────────┘
                             │ HiveServer2 JDBC
                             ▼
                  Spring Boot 指标服务与 AI 查询
```

## 3.2 数据流

```text
Java 模拟商城
├─ 用户、商品、订单写入 MySQL -> DataX 定时同步 -> HDFS -> Hive ODS
└─ 浏览、收藏、加购日志写入文件 -> Flume 持续采集 -> HDFS -> Hive ODS

Hive ODS -> Spark 清洗 -> Hive DWD -> Spark 主题聚合 -> Hive DWS
         -> Spark 应用加工 -> Hive ADS -> Spring Boot REST API
         -> Vue/ECharts 看板或 AI 受控查询 -> 可视化结果与分析报告
```

## 3.3 部署拓扑

毕业设计实验环境建议采用 3 节点虚拟机集群：

| 节点 | Hadoop 角色 | Spark 角色 | 其他服务 |
|---|---|---|---|
| node01 | NameNode、ResourceManager | History Server、客户端 | HiveServer2、Metastore、Web 服务 |
| node02 | DataNode、NodeManager | Executor | - |
| node03 | DataNode、NodeManager | Executor | MySQL 可独立部署或位于 node01 |

本地开发环境可使用单机伪分布式模式，最终演示使用 3 节点环境，并保存 YARN 与 Spark UI 截图作为论文中的实现证据。

## 3.4 系统运行机制

系统不是由使用者登录虚拟机手工运行脚本，而是由 Spring Boot 作为统一控制中心，前端页面作为统一操作入口。运行机制分为自动运行、页面手动触发和普通用户查询三种模式。

### 3.4.1 自动运行模式

```text
1 Java 数据生成器按照设定速率产生用户、商品、行为和订单
2 业务数据写入 MySQL，行为事件写入滚动日志文件
3 Flume 持续监听日志目录并把行为日志写入 HDFS Landing
4 Spring 定时任务调用 DataX，把 MySQL 增量业务表同步到 HDFS Landing
5 到达每日调度时间后，Spring Boot 创建 ETL 运行实例
6 后端调用 spark-submit 提交 ODS 到 DWD 清洗任务
7 清洗成功后依次执行 DWS 聚合、画像和 ADS 指标任务
8 数据质量规则核对记录数、主键、金额和异常波动
9 质量检查通过后发布新的 ADS 分区
10 前端看板自动读取最新成功分区并刷新图表
```

### 3.4.2 页面一键演示模式

管理员在“演示控制台”选择数据日期、用户数、商品数、订单量和异常比例，点击“生成并分析”。系统依次执行数据生成、DataX 同步、Flume 采集确认、Spark 全链路任务、质量检查和 ADS 发布。页面用步骤条显示每个阶段的状态、记录数和耗时，失败时可以查看日志并从失败节点重试。

### 3.4.3 普通用户使用模式

普通运营人员不需要理解 HDFS、Hive 或 Spark。用户登录后可以直接选择日期和分类查看图表，也可以输入“最近七天哪些商品浏览高但购买低”。Spring Boot 从 ADS 查询结果；只有自然语言查询需要先调用大模型生成受控 SQL。用户最终看到指标、图表、结论和统计口径，而不是集群命令。

### 3.4.4 AI 查询运行模式

```text
自然语言问题 -> Spring Boot 读取指标语义 -> 调用大模型生成 SQL
             -> JSqlParser 解析与白名单校验 -> Hive EXPLAIN
             -> HiveServer2 执行 -> 获得真实结果
             -> 再次调用大模型解释 -> 返回结论、图表数据和查询证据
```

### 3.4.5 系统降级机制

大模型 API 不可用时，固定分析看板、数据采集、Spark 任务、用户画像和指标查询仍可正常使用；智能助手提示暂时不可用。这样 AI 是增强能力，而不是整个系统的单点依赖。

## 4.4 技术选型约束

1. Spark 主任务使用 Scala，Web、任务控制和 AI 调用统一使用 Java Spring Boot；
2. 前端固定采用 Vue 3，不再同时维护 React；
3. 不引入 LangChain 和 LangGraph，使用 Java HTTP 客户端直接调用兼容接口；
4. sqlglot 是 Python SQL 解析库，本项目不再使用，改用 Java 的 JSqlParser；
5. JSqlParser 对部分 Hive 特有语法的支持可能有限，因此 AI 只生成受控的标准 SELECT 子集，并在 AST 校验后继续执行 Hive EXPLAIN；
6. 向量数据库不是必选项。表数量较少时，使用关键词匹配和业务主题映射选择 Schema；
7. MySQL 同时承担模拟商城业务库和系统元数据库，但使用不同数据库或表前缀隔离；海量行为事实数据最终进入 HDFS 和 Hive；
8. 论文中技术栈版本、节点配置和资源参数均以最终实测环境为准。

# 5 系统功能模块详细设计

系统并不只有 AI 智能辅助。按实现工作量估算，AI 模块约占总代码和设计工作的 15% 至 20%，其余内容由模拟业务源、采集、数仓、Spark 任务、数据质量、Java 后端、前端看板和系统管理组成。最终比例以实际代码统计为准。

| 子系统 | 主要实现内容 | 建议工作量占比 |
|---|---|---:|
| 模拟商城数据源 | 用户、商品、行为、订单生成及场景控制 | 10% |

## 5.2 数据接入与管理模块

### 5.2.1 功能内容

- 在页面配置模拟商城的数据规模、时间范围、生成速度和异常比例；
- 启动或停止 Java 数据生成器，形成用户、商品、订单和行为数据；
- 通过 DataX 把 MySQL 中的用户、商品、订单增量同步到 HDFS；
- 通过 Flume 持续采集用户行为滚动日志并写入 HDFS；
- 保留 CSV 或 JSON 手动上传作为小数据测试和故障备用方式；
- 校验字段数量、数据类型、必要字段、文件时间和采集批次；
- 创建或刷新 ODS 外部表分区；
- 查看采集批次、来源、数据量、延迟、状态和错误样例；
- 对失败批次执行重新采集或重新导入。

### 5.2.2 Java 模拟商城数据生成器

数据生成器不是简单地随机拼接几列数据，而是模拟一个最小商城业务源。程序使用 Java 编写，可以作为独立 Spring Boot 模块或单独的命令行程序运行。

生成内容包括：

- 用户：注册时间、性别、年龄段、城市和会员等级；
- 商品：分类、价格、上下架状态和库存；
- 行为：pv、fav、cart、buy，写入按小时滚动的 JSON 日志；
- 订单：订单项、数量、金额、状态和时间，写入 MySQL；
- 业务关联：行为引用已存在的用户和商品，购买行为可以按设定概率生成订单。

生成器应支持以下参数：

| 参数 | 示例 | 作用 |
|---|---:|---|
| userCount | 10000 | 初始用户数量 |
| productCount | 5000 | 商品数量 |
| eventsPerSecond | 100 | 每秒行为事件数量 |
| buyProbability | 0.02 | 浏览后形成购买的基础概率 |
| startTime、endTime | 指定日期范围 | 生成历史测试数据 |
| randomSeed | 20260905 | 保证同一配置可以复现 |
| dirtyDataRate | 0.001 | 生成少量空值、重复或非法记录用于质量测试 |
| scenario | normal、promotion、decline | 正常、促销峰值、销量下降等演示场景 |

为了让数据更接近真实业务，生成规则需要体现长尾商品分布、用户活跃度差异、周末和晚间流量变化、浏览到购买的转化路径，而不是让所有用户和商品等概率出现。

### 5.2.3 数据采集方案

| 数据类型 | 源端 | 采集工具 | 目标位置 | 原因 |
|---|---|---|---|---|
| 用户、商品 | MySQL | DataX 全量加增量 | HDFS Landing | 低频变化的结构化业务表 |
| 订单、订单项 | MySQL | DataX 按更新时间增量 | HDFS Landing | 保证交易数据一致性和批次可追踪 |
| 浏览、收藏、加购行为 | JSON 滚动日志 | Flume Taildir Source | HDFS Landing | 持续产生、吞吐量较高的日志数据 |
| 小规模验证文件 | CSV 或 JSON | Spring Boot 上传 | HDFS Landing | 方便单元测试和故障备用 |

DataX 适合关系数据库到 HDFS 的批量离线同步；Flume 适合持续监听并采集日志。二者职责不同，可以同时存在，不构成重复堆砌。

### 5.2.4 支持的数据主题

| 数据主题 | 必要字段 | 建议数据源 |
|---|---|---|
| 用户信息 | user_id、gender、age、city、register_time | 模拟数据或脱敏公开数据 |
| 商品信息 | product_id、category_id、price、status | 公开商品数据或模拟数据 |
| 用户行为 | user_id、product_id、behavior_type、behavior_time | 淘宝用户行为公开数据集 |
| 订单信息 | order_id、user_id、product_id、quantity、amount、order_time、status | 模拟生成并与行为数据关联 |

### 5.2.5 数据批次状态

```text
GENERATED -> COLLECTING -> LANDED -> VALIDATING -> ODS_LOADED -> SUCCESS
                 └-> FAILED             └-> QUARANTINED
```

### 5.2.6 增量采集设定

- 用户和商品表按 update_time 进行增量抽取；
- 订单表按 update_time 和主键联合确定增量范围，避免相同时间戳丢数；
- DataX 任务每 5 分钟执行一次，毕业设计演示时可由页面立即触发；
- Flume 持续运行，并按业务日期和小时写入 HDFS 目录；
- 所有采集任务保存 start_offset、end_offset、批次号和记录数；
- 重跑时使用批次目录或分区覆盖，避免重复计入指标；
- 正式 Spark 任务只读取已标记完成的采集批次。

### 5.2.7 验收标准

能从页面启动数据生成器，观察 MySQL 业务数据和行为日志增长；DataX 与 Flume 可以把两类数据自动写入 HDFS；系统完成批次校验、ODS 分区加载和数量核对；错误数据不会进入正式分区；失败原因可以在页面查看并重试。

## 5.4 数据质量模块

### 5.4.1 质量规则

| 规则类型 | 示例 | 处理方式 |
|---|---|---|
| 完整性 | user_id、product_id、behavior_time 不为空 | 隔离错误记录 |
| 唯一性 | behavior_id、order_id 不重复 | 按主键和时间去重 |
| 合法性 | behavior_type 属于 pv、fav、cart、buy | 标记非法枚举 |
| 范围性 | price、amount、quantity 大于等于 0 | 异常记录进入错误表 |
| 一致性 | 订单商品必须存在于商品维表 | 记录无效外键 |
| 波动性 | 当日记录数较近 7 日均值偏离过大 | 触发告警而不直接删除 |
| 对账性 | DWD 支付金额与 DWS 汇总金额一致 | 阻断 ADS 更新 |

### 5.4.2 默认阈值

- 必要字段空值率不超过 0.1%；
- 主键重复率不超过 0.05%；
- 非法行为类型比例为 0；
- 层间金额误差小于 0.01；
- 当日数据量相对近 7 日均值波动超过 50% 时标记异常。

阈值应保存在配置表中并允许管理员修改，论文实验使用固定阈值并记录版本。

# 6 数据仓库详细设计

## 6.1 分层原则

| 层级 | 作用 | 数据特点 | 主要使用者 |
|---|---|---|---|
| ODS | 保存原始数据 | 尽量保持源格式，按批次和日期分区 | 数据接入、问题追溯 |
| DWD | 形成统一业务明细 | 清洗、去重、维度补充、字段标准化 | Spark 主题计算 |
| DWS | 按业务主题汇总 | 用户、商品、交易等公共粒度 | 多个应用指标复用 |
| ADS | 面向页面和 AI 查询 | 高度聚合、口径固定、字段易理解 | API、可视化、AI 助手 |

## 6.2 ODS 层

ODS 原始数据层已经包含在四层数仓中，并且是所有 Spark 清洗任务的唯一正式入口。此前架构图把 HDFS 和 Hive ODS 写在同一条链路上，容易造成 ODS 被省略的误解。二者的区别是：HDFS Landing 是采集文件的物理落地区，ODS 是在原始文件之上建立的 Hive 表和分区。数据不会从 DataX 或 Flume 直接进入 DWD。

```text
MySQL业务表 -> DataX -> HDFS Landing/mysql/{table}/dt=...
行为日志   -> Flume -> HDFS Landing/logs/behavior/dt=.../hour=...
手动文件   -> 上传  -> HDFS Landing/upload/{batchId}/...
                         ↓ 校验与分区发布
                     Hive ODS 原始层
                         ↓ Spark清洗
                     Hive DWD 明细层
```

ODS 原则上保留源数据字段，只增加 source_system、source_file、ingest_batch_id、ingest_time、dt 等审计字段。错误数据可以先进入 ODS 暂存分区或隔离目录，但只有通过批次校验的数据才允许被下游 DWD 任务读取。

| 表名 | 粒度 | 关键字段 | 分区 |
|---|---|---|---|
| ods_user_info | 一名用户一条记录 | user_id、gender、age、city、register_time | dt |
| ods_product_info | 一个商品一条记录 | product_id、category_id、price、status | dt |
| ods_user_behavior | 一次行为一条记录 | behavior_id、user_id、product_id、behavior_type、behavior_time | dt |
| ods_order_info | 一个订单商品项一条记录 | order_id、user_id、product_id、quantity、amount、order_time、status | dt |

ODS 表建议采用外部表并保留 source_file、ingest_batch_id、ingest_time 等审计字段。

### 6.2.1 ODS 加载方式

- ods_user_info、ods_product_info、ods_order_info 由 DataX 落地文件映射或加载；
- ods_user_behavior 由 Flume 日志目录映射或由加载任务统一转换；
- 每个 ODS 分区保存对应批次号和业务日期；
- ODS 数据不进行复杂业务聚合，主要承担原始留存和问题追溯；
- 对源端字段变化进行 Schema 校验，变化未确认前不自动发布分区。

## 6.3 DWD 层

### 6.3.1 dwd_user_behavior_detail

关键字段：behavior_id、user_id、product_id、category_id、behavior_type、event_time、event_date、event_hour、city、source_batch_id、dt。

处理规则：时间统一、枚举映射、空值过滤、重复事件去重、用户与商品维度补充、异常数据进入 dwd_reject_record。

### 6.3.2 dwd_order_detail

关键字段：order_id、user_id、product_id、category_id、quantity、unit_price、pay_amount、order_status、order_time、order_date、city、dt。

处理规则：只把状态符合业务定义的订单计入销售额；退款或取消订单保留明细，但在指标计算时按口径过滤。

### 6.3.3 维度表

- dim_user：用户稳定属性；
- dim_product：商品、分类、价格带和状态；
- dim_date：日期、星期、月份、季度、是否周末；
- dim_region：城市与区域映射；
- dim_metric：指标名称、业务定义、公式、默认时间字段和允许维度。

## 6.4 DWS 层

| 表名 | 粒度 | 核心指标 |
|---|---|---|
| dws_user_behavior_day | 用户和日期 | pv、fav、cart、buy、active_hours |
| dws_behavior_funnel_day | 日期和可选分类 | 各阶段用户数、阶段转化率 |
| dws_product_behavior_day | 商品和日期 | pv、uv、fav、cart、buy、heat_score |
| dws_product_sale_day | 商品和日期 | sale_count、sale_amount、buyer_count |
| dws_trade_day | 日期 | order_count、buyer_count、sale_amount、avg_order_value |
| dws_user_trade_period | 用户和统计周期 | last_buy_date、order_count、sale_amount |
| dws_region_sale_day | 地区和日期 | buyer_count、order_count、sale_amount |

## 7.8 Spark 优化方案

| 优化点 | 实施方式 | 对照实验指标 |
|---|---|---|
| 分区裁剪 | 查询和任务强制使用 dt 条件 | 扫描数据量、任务耗时 |
| 列式存储 | Parquet 与 Snappy | 存储空间、读取耗时 |
| 广播连接 | 对小维表使用 broadcast hint | Shuffle Read、任务耗时 |
| 缓存复用 | 重复使用的数据集 cache 后及时释放 | 重算次数、任务耗时 |

| 小文件治理 | 合理 repartition 或 coalesce | 输出文件数、后续查询耗时 |
| 倾斜处理 | 热点键识别、预聚合或加盐 | 最大 Task 耗时与中位数比值 |

## 7.9 运行参数记录

每次性能实验应保存 executor 数、executor cores、executor memory、driver memory、shuffle partitions、输入记录数、输入文件数、输出文件数、总耗时和失败次数。只有记录这些参数，论文中的性能对比才具有可复现性。

# 8 智能分析模型设计

## 8.1 设计原则

1. 大模型只查询 ADS 白名单，不直接扫描 ODS 和 DWD；
2. 指标含义来自语义层，不由模型临时猜测；
3. SQL 必须先解析和校验，再执行；
4. 查询结果是回答的唯一数据证据；
5. 推测和事实分开表达；
6. 失败过程可重试、可记录、可人工检查。

## 8.2 业务语义层

语义层是本项目 AI 创新的基础。每个可查询表和字段包含：

- 中文名称和业务说明；
- 数据类型和单位；
- 可用聚合方式；
- 默认时间字段；
- 常见中文别名；
- 允许关联的表和关联键；
- 指标计算公式与过滤条件；
- 正确和错误用法示例。

例如 sale_amount 不只描述为“销售额”，还需注明“仅统计有效支付订单，单位为元，可求和，不可直接平均替代客单价”。这种业务语义比单纯提供建表语句更能减少口径错误。

## 8.3 Schema 选择

基础方案不引入向量数据库，使用以下轻量流程：

1. 将问题中的“销售、用户、商品、转化、地区”等词映射到业务主题；
2. 根据主题选择 1 至 3 张 ADS 表；
3. 根据指标别名选择指标定义；
4. 只把相关表、字段、关联关系和示例放入 Prompt。

可选实验增加 Embedding 检索，与“全量 Schema”和“关键词选择”进行准确率、耗时和令牌消耗对比，但不作为一期上线依赖。

## 8.4 Text-to-SQL 流程

```text
用户问题
  -> 问题规范化
  -> 主题和指标识别
  -> 相关 Schema 与指标定义选择
  -> 少样本示例选择
  -> LLM 生成结构化结果
  -> SQL AST 解析
  -> 表字段和函数白名单校验
  -> EXPLAIN 或小范围试执行
  -> 正式执行
  -> 失败反馈与最多一次修复
  -> 结果解释与证据展示
```

模型输出建议使用 JSON：

```json
{
  "intent": "查询最近7天商品销售排行",
  "metrics": ["sale_amount"],
  "dimensions": ["product_name"],
  "time_range": "最近7天",
  "sql": "SELECT ...",
  "assumptions": []
}
```

## 8.5 Prompt 设计

SQL 生成 Prompt 至少包含角色、任务、方言、数据范围、语义层、指标口径、允许关联、少样本示例、输出格式和安全规则。核心限制如下：

- 只输出一个查询语句；
- 只允许 SELECT 或 WITH 开头的只读查询；
- 只使用给出的表和字段；
- 必须包含时间条件，问题没有时间范围时采用默认近 30 天并写入 assumptions；
- 明细查询自动限制返回行数；
- 不确定时返回 clarification_needed，而不是编造字段；
- 不允许把推测写入 SQL 结果。

## 8.6 SQL 安全校验

### 第一级 字符串预检

拒绝多语句、注释逃逸和明显的 INSERT、UPDATE、DELETE、DROP、ALTER、TRUNCATE、CREATE、LOAD、EXPORT 等关键词。

### 第二级 AST 语法树校验

- 根节点必须为 Select 或只读 With；
- 表必须属于 ADS 白名单；
- 字段必须存在；
- 禁止文件、网络和管理函数；
- 禁止笛卡尔积；
- 禁止访问系统库；
- 强制或重写 LIMIT。

### 第三级 数据库权限

Hive 使用只读账号，账号只拥有 ADS 查询权限。即使前两级校验失效，数据库权限仍阻止数据修改和底层表访问。

### 第四级 资源限制

- 默认最大返回 500 行；
- 绝对最大返回 1000 行；
- 默认查询超时 30 秒；
- 单次查询最多关联 3 张表；
- 查询结果发送给模型前最多保留 200 行，并进行字段脱敏和长度截断。

## 8.7 SQL 自动纠错

SQL 在解析、EXPLAIN 或执行阶段失败时，系统将“原问题、相关 Schema、原 SQL、经过脱敏的错误类型”重新发送给模型，允许最多修复一次。修复后的 SQL 必须重新经过全部安全校验。超过次数后返回明确错误和建议问题，不进行无限循环。

## 8.8 结果解释与证据约束

模型收到的数据包括问题、指标口径、SQL、列名、查询结果、时间范围和总行数。Prompt 明确要求：

- 不得引用结果中不存在的数值；
- 比例和增幅需要给出计算依据；
- 不能仅根据相关性声称因果关系；
- 数据不足时说明不足；
- 将推测放入“可能原因”，将事实放入“数据发现”；
- 每条主要结论关联至少一个结果字段或数值。

## 8.9 多轮上下文边界

一期只支持有限上下文：保存上一轮问题、已确认时间范围和筛选条件，不让模型自主调用任意工具。用户说“再按城市拆分”时，系统将其与上一轮完整问题合并后重新执行标准流程。

## 8.10 AI 配置设定

|---|---:|---|
| generation_temperature | 0 | SQL 生成尽量稳定 |
| explanation_temperature | 0.2 | 允许有限语言组织变化 |
| max_schema_tables | 3 | 控制上下文噪声 |
| sql_repair_count | 1 | 防止循环调用 |

## 8.11 Java 调用大模型 API 示例

调用大模型本质上是 Spring Boot 向模型服务发送一次 HTTPS POST 请求。请求头携带 API Key，请求体包含模型、系统提示词和用户问题，响应体中返回模型生成的文本。该部分不要求 Python，也不要求 LangChain。

以下代码用于说明核心调用方式，正式实现时应把 baseUrl、model 和 apiKey 放在 application.yml 或环境变量中，并定义请求响应 DTO 代替 Map：

```java
@Service
public class LlmClient {
    private final WebClient client;
    private final String model;

    public LlmClient(
            @Value("${llm.base-url}") String baseUrl,
            @Value("${llm.api-key}") String apiKey,
            @Value("${llm.model}") String model) {
        this.model = model;
        this.client = WebClient.builder()
                .baseUrl(baseUrl)
                .defaultHeader("Authorization", "Bearer " + apiKey)
                .defaultHeader("Content-Type", "application/json")
                .build();
    }

    public String generateSql(String schema, String question) {
        String systemPrompt = "你是Hive SQL助手，只能生成SELECT查询。"
                + "只能使用以下表和字段：\n" + schema;

        Map<String, Object> request = Map.of(
                "model", model,
                "temperature", 0,
                "messages", List.of(
                        Map.of("role", "system", "content", systemPrompt),
                        Map.of("role", "user", "content", question)
                )
        );

        Map<?, ?> response = client.post()
                .uri("/v1/chat/completions")
                .bodyValue(request)
                .retrieve()
                .bodyToMono(Map.class)
                .block(Duration.ofSeconds(30));

        List<?> choices = (List<?>) response.get("choices");
        Map<?, ?> first = (Map<?, ?>) choices.get(0);
        Map<?, ?> message = (Map<?, ?>) first.get("message");
        return String.valueOf(message.get("content"));
    }
}
```

实际业务调用过程为：Controller 接收问题，SemanticService 提供相关指标和表结构，LlmClient 生成 SQL，SqlSafetyService 校验 SQL，HiveQueryService 执行 SQL，最后再次调用 LlmClient 生成解释。调用接口的代码量不大，主要难点和论文价值在其前后的语义组织、安全约束、执行反馈和结果核对。

## 8.12 JSqlParser 的作用与示例

JSqlParser 是一个 Java SQL 解析库。它把 SQL 字符串转换为抽象语法树，也就是把“SELECT 哪些字段、FROM 哪些表、WHERE 有什么条件、是否存在 DELETE”等结构拆出来。系统因此不必只靠字符串包含关系判断 SQL 是否安全。

本项目只需要掌握三个用途：判断是否为 SELECT、提取访问表名、检查或补充 LIMIT。概念上类似 Java 编译器先把源代码解析成语法结构，再进行规则检查。

```java
public void validateSql(String sql) throws Exception {
    Statement statement = CCJSqlParserUtil.parse(sql);

    if (!(statement instanceof Select)) {
        throw new IllegalArgumentException("只允许SELECT查询");
    }

    String normalized = statement.toString().toLowerCase(Locale.ROOT);
    Set<String> forbidden = Set.of(
            "insert ", "update ", "delete ", "drop ",
            "alter ", "truncate ", "load ", "create "
    );
    if (forbidden.stream().anyMatch(normalized::contains)) {
        throw new IllegalArgumentException("SQL包含禁止操作");
    }

    // 正式实现继续遍历AST中的Table节点，检查是否都属于ADS白名单。
    // 通过本地校验后，再向Hive执行EXPLAIN进行方言和字段检查。
}
```

JSqlParser 不是本项目的研究重点，只是 SQL 安全模块的一个工具。若其不能解析少量 Hive 特有语法，系统应拒绝该语句或交由 Hive EXPLAIN 检查，而不是绕过安全流程。

# 9 创新性设计

## 9.1 创新点一 面向电商数仓语义的 Text-to-SQL

传统做法通常只向大模型提供表结构，模型容易生成不存在的字段或采用错误指标口径。本系统增加业务语义层和指标字典，以主题选择的方式只提供相关 Schema，并加入真实的指标含义、时间字段、允许关联和少样本示例。

可验证内容：比较“仅表结构”“表结构加语义层”“语义层加少样本”三种方案的 SQL 执行正确率和指标口径正确率。

## 9.2 创新点二 多级校验与执行反馈驱动的 SQL 修复

系统不直接执行模型输出，而是使用字符串预检、AST 校验、数据库只读权限、资源限制四层防护，并利用解析或执行错误驱动一次受控修复。

可验证内容：统计危险 SQL 拦截率、首次执行成功率、修复后执行成功率和错误类型分布。

## 9.3 创新点三 带证据链的可信分析报告

系统不仅返回自然语言结论，还展示查询 SQL、指标定义、数据范围、使用表、返回行数和耗时；模型被要求区分数据事实、可能原因和建议。这使回答可以复核，而不是生成无法验证的“正确语气”。

可验证内容：构建事实一致性评分，统计回答中数值与查询结果一致的比例，并通过人工评分比较普通总结 Prompt 与证据约束 Prompt。

## 9.4 创新点四 大数据处理与智能交互的分层解耦

Spark 负责重计算，ADS 负责稳定口径，大模型只进行受控查询和解释。与让大模型直接访问原始明细相比，该结构减少扫描量、控制提示词规模、提高查询稳定性，也体现大数据工程与生成式 AI 的合理分工。

可验证内容：比较查询 DWD 与查询 ADS 时的平均扫描量、平均耗时和 SQL 复杂度。

## 9.5 创新点表述边界

论文中不应声称发明新的大模型算法或推荐算法。更准确的表述是“提出并实现了一种面向电商分层数仓的受控智能分析方法”，创新属于系统方法、约束机制和工程验证层面。

# 10 实验与评价方案

## 10.1 数据集设计

主数据集可选淘宝用户行为公开数据，并补充与用户、商品和订单主题一致的模拟维度数据。实验需记录：

- 原始记录数和清洗后记录数；
- 用户数、商品数、分类数和日期范围；
- 各行为类型数量及比例；
- 数据生成或关联规则；
- 训练示例、开发问题和测试问题的隔离方式。

AI 测试问题建议不少于 100 条，覆盖简单筛选、聚合、排序、时间比较、多维分组、两表关联、窗口计算、歧义问题和越权问题。

## 10.2 Spark 性能实验

### 实验一 数据规模扩展

使用 100 万、1000 万、5000 万和可行时的 1 亿条记录运行相同任务，记录总耗时、吞吐量和资源占用，验证系统处理规模扩大后的变化趋势。

### 实验二 优化策略对比

依次比较基础方案、增加分区裁剪、增加 Parquet、增加广播连接、调整并行度后的任务耗时。每组至少运行 3 次，报告平均值和标准差。

### 实验三 单机与集群对比

在相同数据规模下比较本地模式和 YARN 集群模式，说明小数据下集群启动开销和大数据下并行计算优势。

## 10.3 Text-to-SQL 对照实验

| 方案 | Schema | 语义层 | 少样本 | 自动修复 |
|---|---|---|---|---|
| Baseline A | 全量基础表结构 | 无 | 无 | 无 |
| Baseline B | 主题选择表结构 | 无 | 无 | 无 |
| Proposed C | 主题选择 | 有 | 有 | 无 |
| Proposed D | 主题选择 | 有 | 有 | 有一次 |

评价指标：

- Valid SQL：语法可解析比例；
- Execution Accuracy：SQL 可成功执行且结果正确的比例；
- Exact Set Match：结果集合与标准答案一致的比例；
- Metric Accuracy：指标口径正确的比例；
- Safety Pass Rate：危险请求被正确阻止的比例；
- Average Latency：端到端平均耗时；
- Token Cost：平均输入输出令牌数或估算调用成本。

## 10.4 结果解释实验

选择 30 至 50 组查询结果，由人工按照以下维度评分，每项 1 至 5 分：

- 数值事实一致性；
- 统计口径正确性；
- 结论完整性；
- 推测边界清晰度；
- 建议与数据相关性；
- 表达可读性。

比较普通结果总结和证据约束总结，必要时由两名评价者独立评分并计算一致性。

## 10.5 安全测试

测试集至少包括：数据修改、删除表、读取系统表、多语句注入、SQL 注释绕过、超大结果、无时间范围、请求敏感字段、提示词注入和不存在字段等场景。预期所有危险请求被阻止，正常只读查询不被误拦截。

## 10.6 建议验收目标

| 指标 | 建议目标 |
|---|---:|
| 核心 Spark 任务成功率 | 100% |
| DWD 与 DWS 金额对账误差 | 小于 0.01 |
| AI 测试集 SQL 可执行率 | 不低于 90% |
| AI 测试集结果正确率 | 不低于 80% |
| 危险 SQL 拦截率 | 100% |
| 回答数值事实一致率 | 不低于 95% |
| 常用 ADS 查询 P95 | 不高于 3 秒，按实验环境说明 |

这些数值是项目目标，不是预先写好的实验结果。论文必须以实测值替换，并如实分析未达标原因。

# 12 安全与隐私设计

## 12.1 数据安全

- 用户标识在展示和发送给模型前进行脱敏；
- 不保存真实姓名、手机号、身份证和精确地址；
- API 密钥使用环境变量或密钥文件，不写入代码库；
- Hive AI 账号只拥有 ADS SELECT 权限；
- 数据导出记录操作人、查询条件和时间；
- 日志不记录完整密钥和敏感字段值。

## 12.2 大模型安全

- 系统 Prompt 与用户输入分离；
- 用户输入只能作为问题，不能覆盖安全规则；
- SQL 不从 Markdown 文本中直接截取执行，而从结构化字段读取；
- 模型输出即使声称“已经校验”也必须经过本地校验；
- 错误信息只返回必要内容，避免泄露连接信息和服务器路径；
- 模型供应商、模型名称和调用时间进入审计日志。

## 13.1 测试层次

1. 单元测试：指标公式、时间范围解析、SQL 规则、标签规则；

7. 用户验收测试：管理员、分析员、运营人员完成典型任务。

| 编号 | 场景 | 预期结果 |
|---|---|---|
| T01 | 导入缺少 user_id 的行为文件 | 批次失败，错误样例可查看 |

# 16 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| Hadoop、Hive、Spark 版本不兼容 | 环境无法稳定运行 | 先固定版本矩阵并完成最小链路测试 |
| 数据集只有行为、缺少金额 | 销售分析无法验证 | 使用公开订单数据或按规则生成可追溯模拟订单 |
| 功能过多导致延期 | 核心链路未完成 | 先完成必须项，可选聚类和实时计算最后实施 |
| AI SQL 准确率不稳定 | 演示失败 | 建立固定问题集、低温度、语义层和允许一次修复 |
| AI 费用或网络不可用 | 无法现场演示 | 缓存典型结果，提供可切换兼容模型和降级提示 |
| 分析结论出现幻觉 | 降低可信度 | 证据约束、数值核对、SQL 和口径可见 |
| 参考代码与自主成果边界不清 | 学术规范风险 | 记录来源，重构实现，论文中如实说明借鉴内容 |
| 指标口径前后不一致 | 实验结论无效 | 指标字典作为唯一来源，版本化管理 |

# 18 项目最终定位

本项目最终形成一套以 HDFS 为分布式存储基础、以 Hive 四层数据仓库为数据组织方式、以 Spark 为离线计算引擎、以 Web 可视化为业务入口、以大语言模型为自然语言分析增强能力的电商用户行为分析系统。

系统创新不依赖训练新模型，而体现在面向电商指标语义的 SQL 生成、多级安全校验与自动修复、可追溯分析证据链，以及对这些方法进行可复现的对照实验。该定位与大数据开发和数仓方向一致，同时具备明确的 AI 特征、工程实现价值和论文研究内容。
