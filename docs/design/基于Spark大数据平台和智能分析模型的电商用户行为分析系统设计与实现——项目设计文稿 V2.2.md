# 基于 Spark 大数据平台和智能分析模型的电商用户行为分析系统设计与实现

## 项目设计文稿 V2.2

## 版本说明

V2.2 在 V2.1 基础上将项目从“集群实验案例”进一步明确为“普通员工可使用、运行环境可切换、数据链路可扩展的电商分析与决策支持程序”。本版本不直接进入编码，而是先固定产品边界、模块职责、数据模型、运行状态、接口契约、算法口径、异常恢复和分阶段路线，为后续开发提供可验收的依据。

首版采用 Java 技术路线：Spring Boot 模块化单体后端、Vue 3 前端、Java 模拟商城、Flume 事件采集、Hive 四层数仓、Spark SQL 离线计算、MySQL 指标服务库和大模型兼容 API。Hive 全程作为权威数仓；MySQL 只承载已经发布且高频访问的 ADS 指标快照，不替代数仓。第二阶段优先接入 DataX、Doris、Livy 和 DolphinScheduler；ClickHouse、Kafka、SeaTunnel 与流式计算只保留扩展接口。

AI 被设计为跨模块的辅助能力，而不是孤立的“自然语言转 SQL”页面。它可以在经营概览、销售、商品、用户、转化、库存、订单、质量、报告和决策模块中生成基于真实指标的解释与建议，但只能形成草稿，不能自动改价、补货、取消订单或写回商城业务数据。即使模型服务不可用，采集、数仓、计算、固定看板、报表和人工决策流程仍能运行。

### V2.2 变更摘要

- 增加 LOCAL、SINGLE_NODE、REMOTE_CLUSTER 三类运行环境及可切换连接配置；
- 明确首版“Flume 全事件接入”，DataX 延后至第二阶段；
- 增加最小商城、事务 Outbox、场景化自动数据生成器和事件版本机制；
- 明确 Hive、MySQL、Doris、ClickHouse 的职责及指标快照发布机制；
- 增加模块化单体代码边界、关键 Java 接口、REST API、错误码和幂等规则；
- 增加指标算法、异常检测、RFM、漏斗、留存、复购、库存和决策效果算法；
- 增加 AI 跨模块协作、证据约束、结构化输出、人工审核与决策闭环；
- 增加调度恢复、迟到数据、Schema 隔离、安全、测试、监控和分阶段验收设计。

# 1 项目概述

## 1.1 项目名称

基于 Spark 大数据平台和智能分析模型的电商用户行为分析系统设计与实现。

## 1.2 项目定位

本项目面向电商运营分析场景，建设从原始数据进入 HDFS、Hive 数仓分层、Spark 离线计算、指标数据服务、可视化展示到大模型辅助分析的完整链路。系统主要解决以下问题：

1. 海量用户行为日志难以直接使用关系数据库高效处理；
2. 原始业务数据口径不统一，难以直接形成稳定指标；
3. 普通运营人员不熟悉 Hive SQL，数据查询门槛较高；
4. 传统报表只给出数值，缺乏对趋势、异常和业务含义的解释；
5. 大模型生成 SQL 存在字段幻觉、口径错误和安全风险。

系统采用“数据工程为可信基础、业务应用为主要入口、AI 为横向增强能力”的总体定位。下列比例只是首版工作量规划，不是论文结论：

```text
模拟商城、采集、数仓与计算约占 50%
后端、前端、指标服务与运行管理约占 30%
AI 分析、可信查询与决策辅助约占 20%
```

Spark 和 Hive 负责可信计算，大模型不直接创造业务数据，只负责理解问题、生成受约束 SQL、解释真实查询结果和形成结构化报告。

## 1.3 建设目标

### 1.3.1 工程目标

- 建立“Java 模拟商城 + 事务 Outbox + JSON 事件日志 + Flume”的首版可靠采集链路，并预留 DataX、Kafka 和 SeaTunnel 适配器；
- 建立 ODS、DWD、DWS、ADS 四层 Hive 数据仓库；
- 使用 Spark SQL 完成清洗、聚合、漏斗分析、用户分层和应用指标生成；
- 建立面向普通员工的可视化 Web 系统，展示经营、用户、商品、交易、库存、转化、画像和决策效果；
- 建立“固定指标查询 + 自然语言查询 + 结果解释 + 决策草稿 + 人工审核 + 效果追踪”的智能分析链路；
- 支持本地、单节点和远程集群环境切换，禁止把 node01 至 node03 写死在业务代码中；
- 对任务运行、SQL 查询和大模型调用进行日志记录和审计。

### 1.3.2 研究目标

- 研究业务语义信息对 Text-to-SQL 准确率的影响；
- 研究“生成、校验、执行反馈、修复”闭环对 SQL 执行成功率的影响；
- 研究证据约束对大模型分析结论可信度的影响；
- 验证 Spark 分区、缓存、广播连接等策略对离线任务性能的改善效果。

## 1.4 目标用户与使用场景

| 用户角色 | 主要需求 | 典型操作 |
|---|---|---|
| 系统管理员 | 管理环境、凭据、权限和发布策略 | 配置运行环境、启停系统、处理安全事件 |
| 数据工程人员 | 管理采集、任务、数仓和质量 | 查看批次、重跑任务、处理隔离数据、维护指标口径 |
| 数据分析人员 | 查看指标并进行自助查询 | 查看大盘、筛选时间、复核 SQL、导出报告 |
| 电商运营人员 | 快速理解经营变化 | 查询销售趋势、转化漏斗、热门商品、用户分层 |
| 答辩评审人员 | 验证系统完整性与创新性 | 查看全链路、性能对比、AI 准确率与安全测试 |

## 1.5 项目边界

### 必须实现

- Hadoop、HDFS、YARN、Hive、Spark SQL；
- ODS、DWD、DWS、ADS 四层数仓；
- 数据导入、任务运行、质量检查、分析看板；
- 用户行为、转化漏斗、商品、销售、用户画像五类分析；
- 大模型 API、业务语义层、Text-to-SQL、SQL 安全校验、结果解释；
- Java 最小商城、场景化自动数据生成器、事务 Outbox 和 Flume 日志采集；
- LOCAL、SINGLE_NODE、REMOTE_CLUSTER 三类运行配置；
- Hive ADS 快照发布、MySQL 指标服务和人工控制的 Hive 应急查询；
- AI 跨分析模块辅助、决策建议审核与效果评价；
- Spring Boot 后端、Vue 3 管理界面和 ECharts 可视化；
- 查询日志、模型调用日志、实验数据和测试报告。

### 可选增强

- 使用 Spark MLlib KMeans 对 RFM 特征进行用户聚类；
- 使用轻量级关键词或向量检索选择相关表结构；
- DataX 同步结构化业务表、Doris 指标服务、Livy 提交和 DolphinScheduler 调度；
- Docker Compose 统一部署 Web、MySQL 和 Spring Boot 服务。

### 本期不做

- 自训练大语言模型；
- 复杂 Agent 自主规划；
- Spring Cloud 微服务体系；
- 首版 DataX、Doris、Livy 和 DolphinScheduler；
- ClickHouse 实际适配、Kafka、SeaTunnel、实时计算和在线特征平台；
- 生产级高可用集群和全量数据治理平台。

# 2 需求分析

## 2.1 功能需求

系统划分为十二个一级模块：模拟商城、数据生成、连接与环境、数据接入、数仓流水线、数据质量、指标服务、经营分析、用户与商品专题、AI 辅助、决策中心、系统与权限。模块共同覆盖“业务发生、事件采集、分层加工、质量校验、指标发布、业务理解、人工决策、效果复盘”的完整闭环。

## 2.2 非功能需求

| 类别 | 设计要求 | 验收方式 |
|---|---|---|
| 可用性 | 核心页面结构清晰，查询过程有状态反馈，错误信息可理解 | 功能测试和用户任务测试 |
| 性能 | 本地支持 10 万至 100 万、单节点支持 100 万至 1000 万、集群验证 1000 万至 1 亿；普通看板 P95 目标不高于 2 秒 | 分档数据规模压测，记录真实结果 |
| 安全 | AI 查询只读、表字段白名单、行数限制、超时控制、敏感字段脱敏 | 恶意提示和危险 SQL 测试 |
| 正确性 | 指标有统一口径，数仓层间记录数和金额可核对 | 数据质量规则和人工基准 SQL |
| 可追溯性 | 每次 AI 回答保存问题、SQL、表、条件、耗时和模型信息 | 查询详情页和审计表 |
| 可扩展性 | 数据源、运行环境、指标库、任务提交器、模型供应商和图表通过接口扩展 | 适配器替换和模块依赖检查 |
| 可复现性 | 数据集版本、任务参数、提示词版本和实验结果可保存 | 实验记录与版本表 |

## 2.3 核心业务指标定义

| 指标 | 计算口径 | 主要来源 |
|---|---|---|
| PV | 浏览行为记录数 | dwd_user_behavior_detail |
| UV | 发生浏览行为的去重用户数 | dwd_user_behavior_detail |
| DAU | 当日发生任一有效行为的去重用户数 | dwd_user_behavior_detail |
| 加购率 | 加购用户数 ÷ 浏览用户数 | dws_behavior_funnel_day |
| 购买转化率 | 购买用户数 ÷ 浏览用户数 | dws_behavior_funnel_day |
| 客单价 | 支付金额 ÷ 支付订单数 | dws_trade_day |
| 复购率 | 观察期内购买次数不小于 2 的用户数 ÷ 购买用户数 | dws_user_trade_period |
| 商品热度 | 浏览、收藏、加购、购买的加权得分 | dws_product_behavior_day |
| 用户价值 | 最近购买间隔、购买频次、消费金额综合结果 | ads_user_profile |

所有指标必须明确时间范围、过滤条件和统计粒度。AI 模块只允许引用指标字典中已有口径，避免同一问题出现不同计算方式。

# 3 总体架构设计

## 3.1 逻辑架构

```text
普通员工：经营首页 / 专题分析 / AI解释 / 报告 / 决策中心
数据人员：环境配置 / 采集监控 / 流水线 / 质量 / 指标发布
                         │ Vue 3 + ECharts
                         ▼
┌────────────────────────────────────────────────────────────┐
│ Spring Boot 模块化单体（控制面与业务服务面）               │
│ 权限 │ 环境 │ 采集 │ 调度 │ 质量 │ 指标 │ AI │ 决策 │ 审计 │
└──────┬───────────────┬───────────────────┬─────────────────┘
       │               │                   │ HTTPS
       │               │                   ▼
       │               │              大模型兼容 API
       │               │
       ▼               ▼
模拟商城 App       可替换基础设施适配器
MySQL + Outbox     JobSubmitter / MetricStore / EventIngestor
       │               │
       └─JSON日志─Flume┤
                       ▼
 Landing/HDFS或本地文件 → Hive ODS → DWD → DWS → ADS
                                      Spark SQL 批处理
                       │                         │
                       └─权威历史与复杂分析─────┘
                                      │ 质量校验后发布
                                      ▼
                    MySQL 指标服务（首版默认）
                    Doris（第二阶段）/ ClickHouse（预留）
```

架构分为控制面和数据面。控制面负责配置、权限、任务状态、发布、AI 与页面接口；数据面负责事件采集、文件存储、Hive 分层与 Spark 计算。二者通过稳定接口连接，使运行环境或指标服务发生变化时，不需要重写业务页面。

## 3.2 数据流

```text
人工操作或自动生成器
  → 调用同一商城业务 Service
  → MySQL 业务事务同时写 event_outbox
  → OutboxPublisher 将事件写入滚动 JSON 日志
  → Flume 断点采集到 Landing 区
  → ODS 原样落表并保存 schema_version
  → DWD 清洗、标准化、去重和关联维度
  → DWS 按日、用户、商品、分类、渠道进行主题汇总
  → ADS 形成看板、报告和决策所需指标快照
  → 数据质量通过后发布快照
  → 首版同步到 MySQL 指标服务库
  → 固定看板查询指标；AI 读取相同证据并生成解释或建议草稿
  → 员工审核建议、指定负责人和截止时间
  → 后续快照评价目标指标变化，形成决策闭环
```

首版为了把采集链路做完整，用户、商品、库存、订单、支付、退款和行为统一转换为版本化 JSON 事件并交给 Flume。第二阶段才增加 DataX，将结构化业务表直接按增量字段同步到 ODS；它是新增接入方式，不会取消 Flume 事件链路。

## 3.3 部署拓扑

系统不能与 node01 至 node03 强绑定。运行环境以 `RuntimeProfile` 保存，首版允许保存多个环境，但同一时刻只激活一个，以避免同一流水线向多个数仓误写。三种模式如下：

| 模式 | 适用场景 | 文件与数仓 | Spark 提交 | 建议数据量 |
|---|---|---|---|
| LOCAL | 开发、单机演示 | 本地文件 + 本地/容器 Hive，也可简化为单机 Hadoop | `spark-submit --master local[*]` | 10 万至 100 万事件 |
| SINGLE_NODE | 一台服务器上的完整大数据环境 | 单节点 HDFS + Hive | 本机或 SSH 提交 | 100 万至 1000 万事件 |
| REMOTE_CLUSTER | node01 至 node03、未来服务器或云端集群 | 远程 HDFS + Hive Metastore | 首版 SSH + spark-submit | 1000 万至 1 亿事件 |

`RuntimeProfile` 至少包含：名称、类型、启用状态、HDFS 地址、Hive JDBC 地址、SSH 主机与端口、提交用户、Spark 主节点、YARN 队列、应用包路径、Landing 路径、时区、默认数据库和凭据引用。密码不明文存储，配置也不出现 `node01` 常量。

切换环境时必须执行连通性检查：文件系统写入、Hive 查询、Spark 提交、指标库查询四项全部通过后，才把新环境设为 ACTIVE。已有运行中的批次不随环境切换，仍绑定创建时的 `runtime_profile_id`。

node01 至 node03 只是 REMOTE_CLUSTER 的一个实例，可用于学习、性能对比和答辩展示。单机模式同样能完成采集、数仓、Spark 和页面流程，只是不提供真正的多机容错；云端或真实多机环境则可替换连接配置继续使用。

## 3.4 存储与查询职责

| 组件 | 首版职责 | 是否权威数据 | 页面是否直接依赖 |
|---|---|---:|---:|
| Landing/HDFS或本地文件 | 保存采集原始文件和重放依据 | 是，针对原始事件 | 否 |
| Hive ODS/DWD/DWS/ADS | 保存完整历史、分层数仓和已计算指标 | 是 | 管理页面和复杂分析使用 |
| MySQL 指标库 | 保存当前发布的高频 ADS 指标快照 | 否，可由 Hive 重建 | 是，首版默认 |
| Doris | 第二阶段替代或并行承担指标服务 | 否 | 第二阶段可选 |
| ClickHouse | 只定义适配接口和配置类型 | 否 | 首版不实现 |

系统不会根据“数据量大小”随机选择 MySQL 或 Hive。固定看板和普通 AI 查询始终访问当前配置的 `MetricStore`；首版为 MySQL。复杂临时分析明确提交 Spark/Hive 异步任务。MySQL 故障时页面显示指标服务不可用，不自动把所有查询切到 Hive；只有管理员可以为白名单查询临时启用只读 Hive 应急模式，防止突发全表扫描拖垮集群。

## 3.5 系统运行机制

系统不是由使用者登录虚拟机手工运行脚本，而是由 Spring Boot 作为统一控制中心。首版内置固定调度流程，深度分析每日执行，核心指标每小时执行；第二阶段用 DolphinScheduler 替换调度实现，但保留相同任务定义和状态模型。

### 3.5.1 自动运行模式

```text
1 自动生成器按照场景、速率和随机种子调用商城业务 Service
2 商城在同一事务中写业务表和 event_outbox
3 OutboxPublisher 生成 JSON 日志，Flume 断点采集到 Landing
4 调度器创建带幂等键的 PipelineRun，记录环境、业务时间和数据版本
5 ODS 装载并校验 schema_version；未知版本进入 quarantine
6 JobSubmitter 提交 DWD 清洗、DWS 聚合和 ADS 生成任务
7 质量中心核对记录数、唯一性、金额、枚举值和异常波动
8 生成状态为 VERIFYING 的指标快照
9 校验通过后原 ACTIVE 变为 ARCHIVED，新快照原子切换为 ACTIVE
10 MetricPublisher 把高频指标写入 MySQL，前端刷新版本号
11 AI 可基于同一快照形成摘要和建议草稿，但不阻塞发布
```

### 3.5.2 页面一键演示模式

管理员在“演示控制台”选择经营场景、日期、用户数、商品数、目标订单量、速率、随机种子和脏数据比例，点击“生成并分析”。系统依次执行生成、采集确认、ODS、DWD、DWS、ADS、质量检查和发布。页面以步骤条显示状态、记录数、耗时、`trace_id` 和失败原因，并可从失败阶段重试。

### 3.5.3 普通用户使用模式

普通运营人员不需要理解 HDFS、Hive、Spark、Flume 或 Schema。首页直接回答五个问题：经营情况怎样、哪里出现异常、可能原因是什么、建议采取什么行动、过去决策是否有效。用户通过日期、店铺、渠道和分类筛选固定看板，也可以在当前页面点击“AI 分析”。技术细节只在数据工程人员与管理员页面展示。

### 3.5.4 AI 辅助运行模式

```text
固定看板：查询已发布指标 → 规则检测异常 → AI解释证据 → 输出建议草稿
自然语言：理解问题 → 选择指标/Schema → 生成SQL → 本地校验
          → 在指标库执行，复杂任务转Spark/Hive → AI解释真实结果
报告生成：读取指定快照 → 模板组织数字和图表 → AI只撰写文字
决策辅助：指标异常 → 候选原因 → 建议行动 → 人工审核创建任务
          → 到期读取后续快照 → 计算效果 → AI生成复盘草稿
```

### 3.5.5 降级与故障隔离

- AI 不可用：固定看板、采集、流水线、报表数字和人工决策继续运行；隐藏 AI 解释并提示稍后重试。
- Flume 暂停：商城继续把事件写入本地滚动日志，恢复后从检查点继续采集；确认 Landing 接收前不清理源日志。
- Spark 任务失败：保留上一个 ACTIVE 指标快照，从失败阶段重跑，不重复成功阶段。
- MySQL 指标库失败：不自动切 Hive；修复后从当前 ACTIVE Hive ADS 快照重新发布。
- 模拟商城失败：不影响历史数仓和分析平台；分析平台失败也不影响商城下单。两者独立进程、独立数据库。

## 5.2 数据接入与管理模块

### 5.2.1 功能内容

- 在独立的模拟商城完成浏览、收藏、加购、下单、支付、取消和退款；
- 在演示控制台配置规模、时间、速度、随机种子、经营场景和脏数据比例；
- 启动或停止 Java 数据生成器，形成具有关联关系的用户、商品、库存、订单和行为数据；
- 通过事务 Outbox 将所有业务变化转换为统一 JSON 事件；
- 通过 Flume 持续采集滚动日志并写入当前环境的 Landing 区；
- 保留 CSV 或 JSON 手动上传作为小数据测试和故障备用方式；
- 校验字段数量、数据类型、必要字段、文件时间和采集批次；
- 创建或刷新 ODS 外部表分区；
- 查看采集批次、来源、数据量、延迟、状态和错误样例；
- 对失败批次执行重新采集或重新导入。

### 5.2.2 最小商城界面

商城不是另一个大型毕业设计，而是本系统的可控业务数据源和演示入口。它与分析平台位于同一代码仓库，但采用独立 Spring Boot 应用、独立数据库和独立进程。商城只需要实现商品首页、分类筛选、商品详情、购物车、结算下单、订单列表和退款申请；不实现真实支付、物流、客服、优惠券中心等非核心功能。

商品数据必须足够丰富：建议设置 8 至 12 个一级分类、每类 5 至 15 个二级分类、500 至 5000 个商品，价格采用分段或对数正态分布，库存、毛利率、品牌和上下架状态存在差异。不同分类设置不同的浏览、收藏、加购、购买和退款倾向，确保后续分析能观察到结构差异。

商城前端的人工操作与自动生成器必须调用同一个 `MallBusinessService`。禁止生成器直接向订单表插入结果，否则会绕过库存扣减、金额计算、状态流转和事件记录，导致演示数据与真实业务逻辑不一致。

### 5.2.3 Java 场景化数据生成器

数据生成器不是简单随机拼接字段，而是通过用户偏好、商品热度、时间周期和经营事件共同决定行为。建议作为 `mall-simulator` 中的独立模块运行，并复用商城 Service。

生成内容包括：

- 用户：注册时间、性别、年龄段、城市和会员等级；
- 商品：分类、价格、上下架状态和库存；
- 行为：view、favorite、cart_add、cart_remove、search，写入业务事件；
- 交易：order_created、paid、cancelled、refunded，写入 MySQL 并产生事件；
- 库存：stock_reserved、stock_released、stock_changed；
- 业务关联：行为引用已存在的用户和商品，购买行为可以按设定概率生成订单。

生成器应支持以下参数：

| 参数 | 示例 | 作用 |
|---|---:|---|
| userCount | 10000 | 初始用户数量 |
| productCount | 5000 | 商品数量 |
| eventsPerSecond | 100 | 每秒行为事件数量 |
| baseConversionRate | 0.02 | 浏览到支付的基础概率 |
| startTime、endTime | 指定日期范围 | 生成历史测试数据 |
| randomSeed | 20260905 | 保证同一配置可以复现 |
| dirtyDataRate | 0.001 | 生成少量空值、重复或非法记录用于质量测试 |
| scenario | normal、promotion、refund_rise | 选择可解释的经营场景 |

建议生成算法如下：

1. 用户活跃度从分层分布抽样，例如高、中、低活跃用户比例为 15%、35%、50%；
2. 商品曝光权重采用 Zipf 分布或“头部 20% 获得约 80% 曝光”的近似分布，制造长尾现象；
3. 小时流量系数采用预设 24 小时曲线，晚间和周末权重较高；
4. 用户选择商品的权重为 `商品热度 × 分类偏好 × 价格接受度 × 场景系数`，归一化后抽样；
5. 行为使用有限状态链：浏览后才可能收藏或加购，加购后才可能下单，创建订单后才可能支付、取消或退款；
6. 订单金额由商品成交价、数量、折扣和运费计算，禁止单独随机金额；
7. 相同 `randomSeed + 配置版本` 必须生成可复现数据，便于测试算法和论文实验。

首版内置场景：正常经营、周末增长、促销爆发、新品冷启动、单品爆款、库存不足、价格上涨、整体销量下降、退款率上升、新用户增长和老用户流失。每个场景保存开始时间、结束时间、受影响分类/商品、参数变化和预期指标方向，作为 AI 原因分析的标准答案之一。

### 5.2.4 事务 Outbox 与事件规范

下单等业务事务和 `event_outbox` 必须在同一个 MySQL 事务中提交。后台 `OutboxPublisher` 分页读取未发布事件，写入按小时滚动的 JSON 日志，成功后标记 `published_at`。即使进程中断，未发布记录仍可重新发送；DWD 按 `event_id` 去重，因此允许“至少一次”投递，不要求不切实际的端到端恰好一次。

统一事件信封：

```json
{
  "event_id": "UUID",
  "event_type": "order_paid",
  "event_time": "2026-09-05T20:15:31+08:00",
  "ingest_time": "2026-09-05T20:15:32+08:00",
  "source_system": "mock-mall",
  "schema_version": "1.0",
  "trace_id": "UUID",
  "payload": {}
}
```

`payload` 按事件类型定义 DTO。消费者只处理已支持的版本；未知 `schema_version` 写入隔离目录和 `quarantine_record`，待增加转换器后重新装载。

### 5.2.5 分阶段采集方案

| 阶段 | 数据类型 | 采集工具 | 目标位置 | 说明 |
|---|---|---|---|---|
| 第一阶段 | 用户、商品、库存、订单、支付、退款、行为事件 | Flume Taildir Source | 本地 Landing 或 HDFS Landing | 统一 JSON 事件，先完成一条可靠主链路 |
| 第一阶段备用 | 小规模 CSV/JSON | Spring Boot 上传 | Landing | 黄金数据集、故障验证，不作为主要数据源 |
| 第二阶段 | 用户、商品、订单等结构化表 | DataX 全量/增量 | HDFS/Hive ODS | 增加数据库批量同步能力 |
| 后续阶段 | 实时事件或异构源 | Kafka/SeaTunnel | 流式或批式目标 | 只在首版接口中预留类型 |

Flume Taildir 的 position 文件和源日志位于持久目录。日志必须在 Landing 文件完成、批次校验通过并达到保留期限后才能清理。首版目标是能够暂停 Flume、继续生成数据、恢复 Flume，并证明事件最终进入 ODS 且没有重复计数。

### 5.2.6 支持的数据主题

| 数据主题 | 必要字段 | 建议数据源 |
|---|---|---|
| 用户信息 | user_id、age_group、city_level、member_level、register_time | 模拟商城用户事件 |
| 商品信息 | product_id、category_id、brand_id、price、cost、status | 模拟商城商品事件 |
| 用户行为 | user_id、product_id、session_id、behavior_type、event_time | 模拟商城行为事件 |
| 订单信息 | order_id、user_id、item、quantity、amount、status、event_time | 模拟商城交易事件 |
| 库存信息 | product_id、available_stock、reserved_stock、event_time | 模拟商城库存事件 |

### 5.2.7 数据批次状态

```text
GENERATED -> COLLECTING -> LANDED -> VALIDATING -> ODS_LOADED -> SUCCESS
                 └-> FAILED             └-> QUARANTINED
```

### 5.2.8 增量、迟到与重放设定

- 首版 Flume 持续运行，按 `event_type/dt/hour` 写入 Landing；
- 事件同时保存 `event_time` 与 `ingest_time`，业务统计按前者，链路延迟按后者；
- 24 小时内迟到数据自动重算受影响小时和日期；7 天内由每日补数任务处理；超过 7 天由数据人员审批后补数；
- 所有采集任务保存 start_offset、end_offset、批次号和记录数；
- DWD 使用 `event_id` 去重，重跑时使用临时分区校验后替换正式分区；
- 正式 Spark 任务只读取已标记完成的采集批次。

第二阶段 DataX 增量使用 `update_time + 主键` 作为联合游标，防止相同更新时间的记录丢失。

### 5.2.9 验收标准

能够人工在商城下单，也能由生成器按相同业务规则批量下单；Flume 能把所有主题事件写入当前运行环境的 Landing；暂停并恢复 Flume 后数据不丢失，重复事件不重复计数；未知版本和错误数据不会进入正式 DWD；失败原因可在页面查看并重试。DataX 不属于首版验收条件。

## 5.3 数仓与 Spark 任务模块

### 5.3.1 功能内容

- 展示 ODS、DWD、DWS、ADS 表及其分区；
- 按业务日期执行全链路或单个 Spark Job；
- 展示任务依赖、开始时间、结束时间、耗时、状态和日志地址；
- 支持失败重试和指定日期补数；
- 展示输入记录数、输出记录数和异常记录数；
- 保存 Spark 参数与任务版本。

### 5.3.2 任务依赖

```text
Job01 用户行为清洗 ─┬─> Job03 行为主题聚合 ─┬─> Job07 ADS 指标生成
Job02 订单明细清洗 ─┴─> Job04 交易主题聚合 ─┤
商品与用户维表 ─────────> Job05 商品主题聚合 ─┤
                               Job06 用户画像 ─┘
```

### 5.3.3 调度设定

- 默认调度周期：每日一次；
- 默认业务日期：系统日期减 1 天；
- 失败重试次数：2 次；
- 重试间隔：5 分钟；
- 同一任务和业务日期禁止重复并发运行；
- 补数使用覆盖指定分区，不影响其他日期；
- 任务依赖未成功时，下游任务不得执行。

## 5.4 数据质量模块

### 5.4.1 质量规则

| 规则类型 | 示例 | 处理方式 |
|---|---|---|
| 完整性 | user_id、product_id、behavior_time 不为空 | 隔离错误记录 |
| 唯一性 | behavior_id、order_id 不重复 | 按主键和时间去重 |
| 合法性 | behavior_type 属于 pv、fav、cart、buy | 标记非法枚举 |
| 范围性 | price、amount、quantity 大于等于 0 | 异常记录进入错误表 |
| 一致性 | 订单商品必须存在于商品维表 | 记录无效外键 |
| 波动性 | 当日记录数较近 7 日均值偏离过大 | 触发告警而不直接删除 |
| 对账性 | DWD 支付金额与 DWS 汇总金额一致 | 阻断 ADS 更新 |

### 5.4.2 默认阈值

- 必要字段空值率不超过 0.1%；
- 主键重复率不超过 0.05%；
- 非法行为类型比例为 0；
- 层间金额误差小于 0.01；
- 当日数据量相对近 7 日均值波动超过 50% 时标记异常。

阈值应保存在配置表中并允许管理员修改，论文实验使用固定阈值并记录版本。

## 5.5 用户行为分析模块

### 5.5.1 页面与功能

1. 流量总览：PV、UV、DAU、人均浏览深度；
2. 行为分布：浏览、收藏、加购、购买次数及占比；
3. 用户活跃趋势：按日或小时展示活跃用户和行为量；
4. 转化漏斗：浏览用户、收藏用户、加购用户、购买用户；
5. 留存与复购：次日和 7 日留存、周期复购率；
6. 时段分析：24 小时和星期分布；
7. 明细钻取：从趋势点进入当天用户或行为摘要。

### 5.5.2 筛选条件

时间范围、行为类型、用户等级、城市、商品分类和设备类型。筛选条件必须传递到指标接口，并在图表标题或查询说明中展示当前口径。

### 5.5.3 输出形式

- 指标卡：PV、UV、DAU、购买转化率；
- 折线图：日活与行为趋势；
- 漏斗图：用户级行为转化；
- 堆叠柱状图：行为类型分布；
- 热力图：星期与小时交叉分布；
- 数据表：按日期或分类的指标明细。

### 5.5.4 关键说明

漏斗建议采用“去重用户口径”作为主要口径，并同时保留“行为次数口径”。论文中必须明确二者不能直接混用。

## 5.6 商品与销售分析模块

### 5.6.1 商品分析

- 商品浏览、收藏、加购、购买排行；
- 商品热度综合评分；
- 商品购买转化率；
- 分类渗透率；
- 热销商品 Top N；
- 商品复购率；
- 头部与长尾商品贡献分析。

商品热度默认公式为：

```text
heat_score = pv_count × 1 + fav_count × 3 + cart_count × 4 + buy_count × 8
```

权重保存在配置表中，默认值只用于系统初始化。论文实验可比较不同权重或说明权重来自业务经验。

### 5.6.2 销售分析

- 日、周、月订单量和销售额趋势；
- 客单价与购买用户数；
- 商品分类销售额及占比；
- 地区销售分布；
- 同比或环比变化；
- 异常日期识别和下钻。

### 5.6.3 验收标准

同一时间范围内图表汇总值与 ADS 明细查询一致；Top N 可配置；时间和分类筛选有效；导出的数据包含统计口径和生成时间。

## 5.7 用户画像模块

### 5.7.1 基础标签

- 活跃等级：高、中、低；
- 消费等级：高、中、低；
- 主要兴趣分类；
- 最近活跃时间；
- 最近购买时间；
- 生命周期状态：新用户、活跃用户、沉默用户、流失风险用户。

### 5.7.2 RFM 特征

| 特征 | 含义 | 计算方式 |
|---|---|---|
| R | 最近一次购买间隔 | 观察截止日减最近购买日期 |
| F | 购买频次 | 观察期内有效支付订单数 |
| M | 消费金额 | 观察期内有效支付金额总和 |

基础版本使用分位数对 R、F、M 分箱并形成可解释规则标签。可选增强版本使用 Spark MLlib StandardScaler 和 KMeans 进行聚类，并通过轮廓系数选择 K 值。聚类只作为可选实验，不作为系统按期完成的前置条件。

### 5.7.3 画像结果

用户画像详情页展示用户基础信息、行为趋势、RFM 数值、标签、兴趣分类和最近订单摘要。所有标签同时保存计算日期和规则版本，保证历史可追溯。

## 5.8 智能分析模块

### 5.8.1 主要功能

- 输入自然语言问题；
- 自动识别业务主题、指标和时间条件；
- 选择与问题相关的 ADS 表和指标定义；
- 生成 Hive SQL；
- 展示校验状态、执行 SQL 和查询结果；
- 根据结果生成趋势描述、关键发现和建议；
- 支持用户评价答案正确或错误；
- 保存查询历史并允许重新执行。

### 5.8.2 推荐问题

- 最近 7 天销售额的变化趋势如何？
- 哪些商品的浏览量高但购买转化率低？
- 本月高价值用户主要分布在哪些城市？
- 周末与工作日的购买量有何差异？
- 最近一天的销售额是否明显偏离近 7 日平均水平？

### 5.8.3 输出结构

AI 回答采用固定结构：

1. 结论：只陈述查询数据可以支持的主要发现；
2. 数据依据：列出关键数值、时间范围和统计口径；
3. 可能解释：明确标注为推测，不能冒充因果结论；
4. 建议：给出与发现对应、可执行的运营建议；
5. 证据：展示 SQL、使用表、返回行数、查询时间和提示词版本。

# 6 数据仓库详细设计

## 6.1 分层原则

| 层级 | 作用 | 数据特点 | 主要使用者 |
|---|---|---|---|
| ODS | 保存原始数据 | 尽量保持源格式，按批次和日期分区 | 数据接入、问题追溯 |
| DWD | 形成统一业务明细 | 清洗、去重、维度补充、字段标准化 | Spark 主题计算 |
| DWS | 按业务主题汇总 | 用户、商品、交易等公共粒度 | 多个应用指标复用 |
| ADS | 面向页面和 AI 查询 | 高度聚合、口径固定、字段易理解 | API、可视化、AI 助手 |

## 6.2 ODS 层

ODS 原始数据层已经包含在四层数仓中，并且是所有 Spark 清洗任务的唯一正式入口。Landing 是采集文件的物理落地区，ODS 是在原始文件之上建立的 Hive 表和分区。数据不会从 Flume 或后续 DataX 直接进入 DWD。

```text
商城全主题JSON事件 -> Flume -> Landing/events/{eventType}/dt=.../hour=...
手动验证文件       -> 上传  -> Landing/upload/{batchId}/...
第二阶段结构化表   -> DataX -> Landing/tables/{table}/dt=...
                         ↓ 校验与分区发布
                     Hive ODS 原始层
                         ↓ Spark清洗
                     Hive DWD 明细层
```

ODS 原则上保留源数据字段，只增加 source_system、source_file、ingest_batch_id、ingest_time、dt 等审计字段。错误数据可以先进入 ODS 暂存分区或隔离目录，但只有通过批次校验的数据才允许被下游 DWD 任务读取。

| 表名 | 粒度 | 关键字段 | 分区 |
|---|---|---|---|
| ods_user_event | 一次用户事件一条记录 | event_id、event_type、event_time、schema_version、payload | dt、hour |
| ods_product_event | 一次商品或库存事件一条记录 | event_id、product_id、event_type、payload | dt、hour |
| ods_behavior_event | 一次行为一条记录 | event_id、user_id、product_id、session_id、behavior_type | dt、hour |
| ods_trade_event | 一次订单、支付或退款事件一条记录 | event_id、order_id、event_type、payload | dt、hour |

ODS 表建议采用外部表并保留 source_file、ingest_batch_id、ingest_time 等审计字段。

### 6.2.1 ODS 加载方式

- 首版各主题 ODS 由 Flume 事件目录映射或由统一加载任务解析；
- 第二阶段可增加 DataX 结构化表对应的 ODS 表，与事件 ODS 按来源和版本区分；
- 每个 ODS 分区保存对应批次号和业务日期；
- ODS 数据不进行复杂业务聚合，主要承担原始留存和问题追溯；
- 对源端字段变化进行 Schema 校验，变化未确认前不自动发布分区。

## 6.3 DWD 层

### 6.3.1 dwd_user_behavior_detail

关键字段：behavior_id、user_id、product_id、category_id、behavior_type、event_time、event_date、event_hour、city、source_batch_id、dt。

处理规则：时间统一、枚举映射、空值过滤、重复事件去重、用户与商品维度补充、异常数据进入 dwd_reject_record。

### 6.3.2 dwd_order_detail

关键字段：order_id、user_id、product_id、category_id、quantity、unit_price、pay_amount、order_status、order_time、order_date、city、dt。

处理规则：只把状态符合业务定义的订单计入销售额；退款或取消订单保留明细，但在指标计算时按口径过滤。

### 6.3.3 维度表

- dim_user：用户稳定属性；
- dim_product：商品、分类、价格带和状态；
- dim_date：日期、星期、月份、季度、是否周末；
- dim_region：城市与区域映射；
- dim_metric：指标名称、业务定义、公式、默认时间字段和允许维度。

## 6.4 DWS 层

| 表名 | 粒度 | 核心指标 |
|---|---|---|
| dws_user_behavior_day | 用户和日期 | pv、fav、cart、buy、active_hours |
| dws_behavior_funnel_day | 日期和可选分类 | 各阶段用户数、阶段转化率 |

| dws_region_sale_day | 地区和日期 | buyer_count、order_count、sale_amount |

## 6.5 ADS 层

| 表名 | 服务场景 | 主要字段 |

| ads_operation_overview | 运营大盘 | dt、pv、uv、dau、order_count、sale_amount |

| ads_active_trend | 活跃趋势 | dt、dau、behavior_count |
| ads_hot_product | 热门排行 | dt、product_id、product_name、heat_score、rank_no |

| ads_sale_trend | 销售趋势 | dt、order_count、buyer_count、sale_amount、avg_order_value |
| ads_category_sale | 分类分析 | dt、category_id、sale_count、sale_amount、amount_ratio |

## 6.7 分区与存储设定

- ODS、DWD、DWS 和按日更新的 ADS 表统一使用 dt 分区；

- 生产演示数据不得包含真实姓名、手机号和精确地址。

# 7 Spark 数据处理任务设计

## 7.1 Job01 用户行为清洗

输入 ods_user_behavior，输出 dwd_user_behavior_detail 和错误记录表。主要步骤为 Schema 显式解析、时间转换、枚举校验、空值处理、去重、维度关联和分区写入。

## 7.2 Job02 订单明细清洗

输入 ods_order_info 与商品维表，输出 dwd_order_detail。主要步骤为金额校验、状态标准化、商品信息补充、取消与退款标识生成和日期分区写入。

## 7.3 Job03 用户行为主题聚合

生成 dws_user_behavior_day、dws_behavior_funnel_day 和 dws_product_behavior_day。漏斗按去重用户统计，并在相同时间范围和筛选条件下计算各阶段人数。

## 7.4 Job04 交易主题聚合

生成 dws_trade_day、dws_product_sale_day、dws_region_sale_day 和 dws_user_trade_period，统一有效订单状态和金额口径。

## 7.5 Job05 商品主题分析

计算商品热度、购买转化率、分类渗透率、复购率和长尾贡献率。长尾分析先按商品销量降序排序，再计算累计销量占比和商品占比。

## 7.6 Job06 用户画像生成

计算活跃次数、最近活跃、RFM、主要兴趣分类和生命周期状态，输出 ads_user_profile。规则版本与计算日期必须随结果保存。

## 7.7 Job07 ADS 指标生成

将各 DWS 主题数据加工为页面和 AI 可以直接使用的 ADS 表。ADS 字段使用清晰的英文命名，并在语义表中记录中文名称、单位、聚合方式和适用条件。

## 7.8 Spark 优化方案

| 优化点 | 实施方式 | 对照实验指标 |
|---|---|---|
| 分区裁剪 | 查询和任务强制使用 dt 条件 | 扫描数据量、任务耗时 |
| 列式存储 | Parquet 与 Snappy | 存储空间、读取耗时 |
| 广播连接 | 对小维表使用 broadcast hint | Shuffle Read、任务耗时 |
| 缓存复用 | 重复使用的数据集 cache 后及时释放 | 重算次数、任务耗时 |
| 并行度 | 根据数据量调整 shuffle partitions | Task 数、倾斜程度、耗时 |
| 小文件治理 | 合理 repartition 或 coalesce | 输出文件数、后续查询耗时 |
| 倾斜处理 | 热点键识别、预聚合或加盐 | 最大 Task 耗时与中位数比值 |

## 7.9 运行参数记录

每次性能实验应保存 executor 数、executor cores、executor memory、driver memory、shuffle partitions、输入记录数、输入文件数、输出文件数、总耗时和失败次数。只有记录这些参数，论文中的性能对比才具有可复现性。

# 8 智能分析模型设计

## 8.1 设计原则

1. 大模型只查询 ADS 白名单，不直接扫描 ODS 和 DWD；
2. 指标含义来自语义层，不由模型临时猜测；
3. SQL 必须先解析和校验，再执行；
4. 查询结果是回答的唯一数据证据；
5. 推测和事实分开表达；
6. 失败过程可重试、可记录、可人工检查。

## 8.2 业务语义层

语义层是本项目 AI 创新的基础。每个可查询表和字段包含：

- 中文名称和业务说明；
- 数据类型和单位；
- 可用聚合方式；
- 默认时间字段；
- 常见中文别名；
- 允许关联的表和关联键；
- 指标计算公式与过滤条件；
- 正确和错误用法示例。

例如 sale_amount 不只描述为“销售额”，还需注明“仅统计有效支付订单，单位为元，可求和，不可直接平均替代客单价”。这种业务语义比单纯提供建表语句更能减少口径错误。

## 8.3 Schema 选择

基础方案不引入向量数据库，使用以下轻量流程：

1. 将问题中的“销售、用户、商品、转化、地区”等词映射到业务主题；
2. 根据主题选择 1 至 3 张 ADS 表；
3. 根据指标别名选择指标定义；
4. 只把相关表、字段、关联关系和示例放入 Prompt。

可选实验增加 Embedding 检索，与“全量 Schema”和“关键词选择”进行准确率、耗时和令牌消耗对比，但不作为一期上线依赖。

## 8.4 Text-to-SQL 流程

```text
用户问题
  -> 问题规范化
  -> 主题和指标识别
  -> 相关 Schema 与指标定义选择
  -> 少样本示例选择
  -> LLM 生成结构化结果
  -> SQL AST 解析
  -> 表字段和函数白名单校验
  -> EXPLAIN 或小范围试执行
  -> 正式执行
  -> 失败反馈与最多一次修复
  -> 结果解释与证据展示
```

模型输出建议使用 JSON：

```json
{
  "intent": "查询最近7天商品销售排行",
  "metrics": ["sale_amount"],
  "dimensions": ["product_name"],
  "time_range": "最近7天",
  "sql": "SELECT ...",
  "assumptions": []
}
```

## 8.5 Prompt 设计

SQL 生成 Prompt 至少包含角色、任务、方言、数据范围、语义层、指标口径、允许关联、少样本示例、输出格式和安全规则。核心限制如下：

- 只输出一个查询语句；
- 只允许 SELECT 或 WITH 开头的只读查询；
- 只使用给出的表和字段；
- 必须包含时间条件，问题没有时间范围时采用默认近 30 天并写入 assumptions；
- 明细查询自动限制返回行数；
- 不确定时返回 clarification_needed，而不是编造字段；
- 不允许把推测写入 SQL 结果。

## 8.6 SQL 安全校验

### 第一级 字符串预检

拒绝多语句、注释逃逸和明显的 INSERT、UPDATE、DELETE、DROP、ALTER、TRUNCATE、CREATE、LOAD、EXPORT 等关键词。

### 第二级 AST 语法树校验

- 根节点必须为 Select 或只读 With；
- 表必须属于 ADS 白名单；
- 字段必须存在；
- 禁止文件、网络和管理函数；
- 禁止笛卡尔积；
- 禁止访问系统库；
- 强制或重写 LIMIT。

### 第三级 数据库权限

首版 MySQL 指标库使用只读查询账号，只拥有已发布指标表的 SELECT 权限；Hive 应急和复杂分析使用独立只读账号并限制可访问 ADS 数据集。即使应用校验失效，数据库权限仍阻止数据修改和底层明细访问。

### 第四级 资源限制

- 默认最大返回 500 行；
- 绝对最大返回 1000 行；
- 默认查询超时 30 秒；
- 单次查询最多关联 3 张表；
- 查询结果发送给模型前最多保留 200 行，并进行字段脱敏和长度截断。

## 8.7 SQL 自动纠错

SQL 在解析、EXPLAIN 或执行阶段失败时，系统将“原问题、相关 Schema、原 SQL、经过脱敏的错误类型”重新发送给模型，允许最多修复一次。修复后的 SQL 必须重新经过全部安全校验。超过次数后返回明确错误和建议问题，不进行无限循环。

## 8.8 结果解释与证据约束

模型收到的数据包括问题、指标口径、SQL、列名、查询结果、时间范围和总行数。Prompt 明确要求：

- 不得引用结果中不存在的数值；
- 比例和增幅需要给出计算依据；
- 不能仅根据相关性声称因果关系；
- 数据不足时说明不足；
- 将推测放入“可能原因”，将事实放入“数据发现”；
- 每条主要结论关联至少一个结果字段或数值。

## 8.9 多轮上下文边界

一期只支持有限上下文：保存上一轮问题、已确认时间范围和筛选条件，不让模型自主调用任意工具。用户说“再按城市拆分”时，系统将其与上一轮完整问题合并后重新执行标准流程。

## 8.11 Java 调用大模型 API 示例

调用大模型本质上是 Spring Boot 向模型服务发送一次 HTTPS POST 请求。请求头携带 API Key，请求体包含模型、系统提示词和用户问题，响应体中返回模型生成的文本。该部分不要求 Python，也不要求 LangChain。

以下代码用于说明核心调用方式，正式实现时应把 baseUrl、model 和 apiKey 放在 application.yml 或环境变量中，并定义请求响应 DTO 代替 Map：

```java
@Service
public class LlmClient {
    private final WebClient client;
    private final String model;

    public LlmClient(
            @Value("${llm.base-url}") String baseUrl,
            @Value("${llm.api-key}") String apiKey,
            @Value("${llm.model}") String model) {
        this.model = model;
        this.client = WebClient.builder()
                .baseUrl(baseUrl)
                .defaultHeader("Authorization", "Bearer " + apiKey)
                .defaultHeader("Content-Type", "application/json")
                .build();
    }

    public String generateSql(String schema, String question) {
        String systemPrompt = "你是指标查询助手，只能针对给定Schema生成SELECT查询。"
                + "只能使用以下表和字段：\n" + schema;

        Map<String, Object> request = Map.of(
                "model", model,
                "temperature", 0,
                "messages", List.of(
                        Map.of("role", "system", "content", systemPrompt),
                        Map.of("role", "user", "content", question)
                )
        );

        Map<?, ?> response = client.post()
                .uri("/v1/chat/completions")
                .bodyValue(request)
                .retrieve()
                .bodyToMono(Map.class)
                .block(Duration.ofSeconds(30));

        List<?> choices = (List<?>) response.get("choices");
        Map<?, ?> first = (Map<?, ?>) choices.get(0);
        Map<?, ?> message = (Map<?, ?>) first.get("message");
        return String.valueOf(message.get("content"));
    }
}
```

实际业务调用过程为：Controller 接收问题，ApplicationService 组织用例，SemanticService 提供相关指标和表结构，LlmClient 生成 SQL，SqlSafetyService 校验 SQL，MetricStore 首版在 MySQL 指标库执行，复杂请求则创建 Spark/Hive 异步任务，最后基于证据包生成解释。调用模型接口的代码量不大，主要难点和论文价值在语义组织、安全约束、执行反馈、结果核对和决策闭环。

## 8.12 JSqlParser 的作用与示例

JSqlParser 是一个 Java SQL 解析库。它把 SQL 字符串转换为抽象语法树，也就是把“SELECT 哪些字段、FROM 哪些表、WHERE 有什么条件、是否存在 DELETE”等结构拆出来。系统因此不必只靠字符串包含关系判断 SQL 是否安全。

本项目只需要掌握三个用途：判断是否为 SELECT、提取访问表名、检查或补充 LIMIT。概念上类似 Java 编译器先把源代码解析成语法结构，再进行规则检查。

```java
public void validateSql(String sql) throws Exception {
    Statement statement = CCJSqlParserUtil.parse(sql);

    if (!(statement instanceof Select)) {
        throw new IllegalArgumentException("只允许SELECT查询");
    }

    String normalized = statement.toString().toLowerCase(Locale.ROOT);
    Set<String> forbidden = Set.of(
            "insert ", "update ", "delete ", "drop ",
            "alter ", "truncate ", "load ", "create "
    );
    if (forbidden.stream().anyMatch(normalized::contains)) {
        throw new IllegalArgumentException("SQL包含禁止操作");
    }

    // 正式实现继续遍历AST中的Table节点，检查是否都属于ADS白名单。
    // 通过本地校验后，再向目标MetricStore执行EXPLAIN；复杂任务才使用Hive。
}
```

JSqlParser 不是本项目的研究重点，只是 SQL 安全模块的一个工具。若其不能解析目标数据库方言，系统应拒绝语句或交由对应数据库的 EXPLAIN 做补充检查，而不是绕过安全流程。

# 9 创新性设计

## 9.1 创新点一 面向电商数仓语义的 Text-to-SQL

传统做法通常只向大模型提供表结构，模型容易生成不存在的字段或采用错误指标口径。本系统增加业务语义层和指标字典，以主题选择的方式只提供相关 Schema，并加入真实的指标含义、时间字段、允许关联和少样本示例。

可验证内容：比较“仅表结构”“表结构加语义层”“语义层加少样本”三种方案的 SQL 执行正确率和指标口径正确率。

## 9.2 创新点二 多级校验与执行反馈驱动的 SQL 修复

系统不直接执行模型输出，而是使用字符串预检、AST 校验、数据库只读权限、资源限制四层防护，并利用解析或执行错误驱动一次受控修复。

可验证内容：统计危险 SQL 拦截率、首次执行成功率、修复后执行成功率和错误类型分布。

## 9.3 创新点三 带证据链的可信分析报告

系统不仅返回自然语言结论，还展示查询 SQL、指标定义、数据范围、使用表、返回行数和耗时；模型被要求区分数据事实、可能原因和建议。这使回答可以复核，而不是生成无法验证的“正确语气”。

可验证内容：构建事实一致性评分，统计回答中数值与查询结果一致的比例，并通过人工评分比较普通总结 Prompt 与证据约束 Prompt。

## 9.4 创新点四 大数据处理与智能交互的分层解耦

Spark 负责重计算，ADS 负责稳定口径，大模型只进行受控查询和解释。与让大模型直接访问原始明细相比，该结构减少扫描量、控制提示词规模、提高查询稳定性，也体现大数据工程与生成式 AI 的合理分工。

可验证内容：比较查询 DWD 与查询 ADS 时的平均扫描量、平均耗时和 SQL 复杂度。

## 9.5 创新点五 场景驱动的可复现实验数据闭环

系统不是静态导入一份文件，而是由最小商城、事务 Outbox、场景化生成器和 Flume 形成连续数据源。每个场景同时保存参数变化、随机种子和预期指标方向，使“异常产生—数仓加工—算法识别—AI解释—人工决策”能够重复实验。

可验证内容：比较不同随机种子下场景方向稳定性，测试 Flume 中断恢复、事件去重和指标重算，并统计系统对退款上升、库存不足、转化下降等场景的识别率。

## 9.6 创新点六 基于指标快照的人机协同决策闭环

AI 不只回答问题，而是基于已发布指标快照生成带证据的建议草稿；员工审核后设置负责人、期限和目标指标；系统再使用后续快照评价效果。该设计把传统“看板展示”扩展为“发现、解释、行动、复盘”的闭环，同时保留人工责任边界。

可验证内容：统计建议采纳率、任务完成率、目标达成率、建议证据完整率，并以典型经营场景展示决策前后指标变化。效果评价不声称严格因果。

## 9.7 创新点表述边界

论文中不应声称发明新的大模型算法或推荐算法。更准确的表述是“提出并实现了一种面向电商分层数仓的受控智能分析方法”，创新属于系统方法、约束机制和工程验证层面。

# 10 实验与评价方案

## 10.1 数据集设计

主数据集可选淘宝用户行为公开数据，并补充与用户、商品和订单主题一致的模拟维度数据。实验需记录：

- 原始记录数和清洗后记录数；
- 用户数、商品数、分类数和日期范围；
- 各行为类型数量及比例；
- 数据生成或关联规则；
- 训练示例、开发问题和测试问题的隔离方式。

AI 测试问题建议不少于 100 条，覆盖简单筛选、聚合、排序、时间比较、多维分组、两表关联、窗口计算、歧义问题和越权问题。

## 10.2 Spark 性能实验

### 实验一 数据规模扩展

使用 100 万、1000 万、5000 万和可行时的 1 亿条记录运行相同任务，记录总耗时、吞吐量和资源占用，验证系统处理规模扩大后的变化趋势。

### 实验二 优化策略对比

依次比较基础方案、增加分区裁剪、增加 Parquet、增加广播连接、调整并行度后的任务耗时。每组至少运行 3 次，报告平均值和标准差。

### 实验三 单机与集群对比

在相同数据规模下比较本地模式和 YARN 集群模式，说明小数据下集群启动开销和大数据下并行计算优势。

## 10.3 Text-to-SQL 对照实验

| 方案 | Schema | 语义层 | 少样本 | 自动修复 |
|---|---|---|---|---|
| Baseline A | 全量基础表结构 | 无 | 无 | 无 |
| Baseline B | 主题选择表结构 | 无 | 无 | 无 |
| Proposed C | 主题选择 | 有 | 有 | 无 |
| Proposed D | 主题选择 | 有 | 有 | 有一次 |

评价指标：

- Valid SQL：语法可解析比例；
- Execution Accuracy：SQL 可成功执行且结果正确的比例；
- Exact Set Match：结果集合与标准答案一致的比例；
- Metric Accuracy：指标口径正确的比例；
- Safety Pass Rate：危险请求被正确阻止的比例；
- Average Latency：端到端平均耗时；
- Token Cost：平均输入输出令牌数或估算调用成本。

## 10.4 结果解释实验

选择 30 至 50 组查询结果，由人工按照以下维度评分，每项 1 至 5 分：

- 数值事实一致性；
- 统计口径正确性；
- 结论完整性；
- 推测边界清晰度；
- 建议与数据相关性；
- 表达可读性。

比较普通结果总结和证据约束总结，必要时由两名评价者独立评分并计算一致性。

## 10.5 安全测试

测试集至少包括：数据修改、删除表、读取系统表、多语句注入、SQL 注释绕过、超大结果、无时间范围、请求敏感字段、提示词注入和不存在字段等场景。预期所有危险请求被阻止，正常只读查询不被误拦截。

## 10.6 建议验收目标

| 指标 | 建议目标 |
|---|---:|
| 核心 Spark 任务成功率 | 100% |
| DWD 与 DWS 金额对账误差 | 小于 0.01 |
| AI 测试集 SQL 可执行率 | 不低于 90% |
| AI 测试集结果正确率 | 不低于 80% |
| 危险 SQL 拦截率 | 100% |
| 回答数值事实一致率 | 不低于 95% |
| 普通看板查询 P95 | 不高于 2 秒，按实验环境说明 |

这些数值是项目目标，不是预先写好的实验结果。论文必须以实测值替换，并如实分析未达标原因。

# 12 安全与隐私设计

## 12.1 数据安全

- 用户标识在展示和发送给模型前进行脱敏；
- 不保存真实姓名、手机号、身份证和精确地址；
- API 密钥使用环境变量或密钥文件，不写入代码库；
- MySQL 指标查询账号只拥有已发布指标表 SELECT 权限；Hive 应急账号只拥有授权 ADS 数据集 SELECT 权限；
- 数据导出记录操作人、查询条件和时间；
- 日志不记录完整密钥和敏感字段值。

## 12.2 大模型安全

- 系统 Prompt 与用户输入分离；
- 用户输入只能作为问题，不能覆盖安全规则；
- SQL 不从 Markdown 文本中直接截取执行，而从结构化字段读取；
- 模型输出即使声称“已经校验”也必须经过本地校验；
- 错误信息只返回必要内容，避免泄露连接信息和服务器路径；
- 模型供应商、模型名称和调用时间进入审计日志。

| T06 | AI 使用不存在字段 | 校验失败，修复后重新校验或明确返回失败 |
| T07 | 普通运营用户修改 AI 参数 | 返回无权限 |
| T08 | 查询结果为空 | 不编造结论，说明当前条件无数据 |
| T09 | 模型 API 超时 | 返回可重试提示，不影响数仓和其他页面 |
| T10 | DWS 金额与 DWD 不一致 | 质量检查失败并阻止 ADS 更新 |

# 16 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| Hadoop、Hive、Spark 版本不兼容 | 环境无法稳定运行 | 先固定版本矩阵并完成最小链路测试 |
| 数据集只有行为、缺少金额 | 销售分析无法验证 | 使用公开订单数据或按规则生成可追溯模拟订单 |
| 功能过多导致延期 | 核心链路未完成 | 先完成必须项，可选聚类和实时计算最后实施 |
| AI SQL 准确率不稳定 | 演示失败 | 建立固定问题集、低温度、语义层和允许一次修复 |
| AI 费用或网络不可用 | 无法现场演示 | 缓存典型结果，提供可切换兼容模型和降级提示 |
| 分析结论出现幻觉 | 降低可信度 | 证据约束、数值核对、SQL 和口径可见 |
| 参考代码与自主成果边界不清 | 学术规范风险 | 记录来源，重构实现，论文中如实说明借鉴内容 |
| 指标口径前后不一致 | 实验结论无效 | 指标字典作为唯一来源，版本化管理 |

# 20 模拟商城与数据生成算法详细设计

## 20.1 商城核心领域模型

| 实体 | 关键字段 | 关键约束 |
|---|---|---|
| mall_user | user_id、register_time、age_group、city_level、member_level | 只使用模拟属性，不生成真实个人信息 |
| category | category_id、parent_id、level、name | 一级 8 至 12 类，最多三级 |
| product | product_id、category_id、brand_id、price、cost、status | price 不小于 cost；状态可追踪 |
| inventory | product_id、available_qty、reserved_qty、version | 乐观锁，库存不得为负 |
| cart_item | user_id、product_id、quantity、updated_at | 同用户商品唯一 |
| mall_order | order_id、user_id、status、total_amount、created_at | 金额由订单项计算 |
| order_item | order_id、product_id、quantity、unit_price、amount | `amount=quantity×unit_price-discount` |
| payment | payment_id、order_id、amount、status、paid_at | 首版模拟支付，不接真实支付渠道 |
| refund | refund_id、order_id、amount、reason、status | 退款金额不得大于已付金额 |
| event_outbox | event_id、aggregate_type、aggregate_id、event_type、payload、created_at、published_at | event_id 唯一 |

订单状态建议为 `CREATED → PAID → COMPLETED`，旁路允许 `CREATED → CANCELLED`、`PAID/COMPLETED → REFUNDING → REFUNDED`。状态转换集中在领域 Service 校验，Controller 和生成器不得直接更新状态字段。

## 20.2 商品目录生成

商品不能只有几个名称或相同价格。建议先定义分类模板，每个二级分类给出价格下限、价格中位数、价格上限、基础转化率、退款倾向和季节系数。价格可由截断对数正态分布生成：

```text
rawPrice = exp(N(μ_category, σ_category))
price = clamp(rawPrice, minPrice, maxPrice)
cost = price × Uniform(0.45, 0.80)
```

商品基础热度 `base_popularity` 使用 Zipf 权重 `w_i = 1 / rank_i^s`，建议 `s` 在 0.8 至 1.2 之间。这样少量头部商品获得较多访问，大量长尾商品访问较少，能够支撑爆款、长尾和库存分析。

## 20.3 用户与会话生成

用户具有分类偏好向量、价格敏感度、活跃等级和退款倾向。生成器先按活跃等级决定每日会话数，再决定会话发生时间。小时权重数组应保存在配置中，并经过归一化抽样，不把当前系统时间直接当业务时间。

一次会话至少包含一个浏览事件，可按概率继续形成搜索、收藏、加购和订单。推荐使用可解释的有限状态模型：

```text
START → VIEW → {VIEW, FAVORITE, CART, EXIT}
CART  → {VIEW, ORDER_CREATED, CART_REMOVE, EXIT}
ORDER_CREATED → {PAID, CANCELLED}
PAID → {COMPLETED, REFUNDING}
```

转移概率由用户特征、商品特征、场景和时间共同修正。例如：

```text
purchaseScore = baseRate
              × userActivityFactor
              × categoryPreferenceFactor
              × priceAcceptanceFactor
              × scenarioConversionFactor
purchaseProbability = min(max(purchaseScore, 0), 0.95)
```

## 20.4 场景注入与标准答案

每个场景实现 `ScenarioStrategy`，只调整明确参数，不直接伪造最终指标。

```java
public interface ScenarioStrategy {
    ScenarioCode code();
    GenerationFactors factors(ScenarioContext context);
    ExpectedEffect expectedEffect();
}
```

| 场景 | 参数变化 | 预期可观察结果 | 可能业务建议 |
|---|---|---|---|
| PROMOTION | 曝光、折扣、转化同时提高 | PV、订单、销售额上升，客单价可能下降 | 检查毛利和库存，不只看销量 |
| HOT_PRODUCT | 指定商品曝光和偏好提高 | 单品贡献集中、库存覆盖天数下降 | 补货或限制投放 |
| STOCK_SHORTAGE | 头部商品可售库存降低 | 加购高、支付转化下降、缺货事件增加 | 优先补充高贡献商品 |
| PRICE_INCREASE | 指定类目价格提高 | 客单价升、转化可能降 | 比较收入增量与转化损失 |
| REFUND_RISE | 指定商品退款倾向提高 | 净销售额下降、退款率异常 | 检查质量和描述一致性 |
| OLD_USER_CHURN | 老用户会话权重降低 | 活跃老客、复购率下降 | 召回高价值沉默用户 |

`ExpectedEffect` 只用于生成测试标准答案和评价 AI 是否识别方向，不传给 AI 作为作答提示，避免实验数据泄漏。

## 20.5 脏数据注入

脏数据应由独立 `DirtyDataInjector` 在事件序列化前按配置注入，类型包括必填字段缺失、非法枚举、重复 event_id、未来时间、负数量、金额不一致和未知 Schema 版本。每种类型保存期望处理结果：拒绝、隔离、去重或告警。禁止对业务库中的有效订单做不可恢复破坏。

## 20.6 生成器验收

- 相同种子、配置和程序版本生成的核心数据摘要一致；
- 订单总额能由订单项重算，支付和退款不超出订单金额；
- 自动生成和人工下单产生相同格式事件；
- 头部与长尾商品分布、时段曲线和转化链路能在图表中观察；
- 每个场景至少有一组已知方向的指标变化；
- 生成速率可调，停止后不再创建新会话，但已开始事务正常结束。

# 21 数仓、指标服务与算法规格

## 21.1 四层数仓职责

| 层级 | 保存内容 | 是否修改原始含义 | 典型表 |
|---|---|---:|---|
| ODS | 按事件主题原样解析的数据及原始 JSON | 否，只增加采集元数据 | ods_event_log、ods_order_event |
| DWD | 去重、类型统一、状态展开后的明细事实和一致维度 | 是，做标准化 | dwd_behavior_detail、dwd_order_detail |
| DWS | 按用户、商品、分类、渠道、日期汇总的主题宽表 | 是，做可复用聚合 | dws_user_day、dws_product_day |
| ADS | 面向具体页面、报告和决策的应用指标 | 是，固定业务口径 | ads_overview_day、ads_funnel_day |

ODS 必须存在，因为它承担重放、审计、Schema 演进和源数据留存。MySQL 指标库位于 Hive ADS 之后，是服务层缓存/副本，不是第五层数仓，也不能代替 ODS 至 ADS。

## 21.2 时间、金额和去重规范

- 数仓统一使用 Asia/Shanghai 解释业务日期，数据库保存时间戳时同时保留时区约定；
- `event_time` 决定指标归属，`ingest_time` 计算采集延迟；
- 金额使用 `DECIMAL(18,2)`，Java 使用 `BigDecimal`，禁止使用 double 计算对账金额；
- 行为以 `event_id` 去重；订单状态事件以 `event_id` 去重并按事件时间重建最新状态；
- UV、转化率等均按匿名 `user_id` 去重，不能用事件行数替代用户数；
- 分母为 0 时返回 null 并显示“无可计算数据”，不返回 0% 造成误解。

## 21.3 经营基础指标

```text
PV = count(view事件)
UV = count(distinct user_id where behavior_type='view')
DAU = count(distinct user_id where 当日存在任一有效行为)
支付订单数 = count(distinct order_id where final_paid_flag=1)
销售额GMV = sum(paid_amount)
净销售额 = sum(paid_amount) - sum(refund_amount)
客单价 = 销售额GMV / 支付订单数
件单价 = 销售额GMV / 支付商品件数
退款率 = 退款订单数 / 支付订单数
```

同比和环比统一采用 `(current - previous) / previous`。previous 为 0 时不计算比例，只展示绝对差。所有指标返回 `metric_code`、`value`、`unit`、`period`、`comparison_value`、`definition_version` 和 `snapshot_id`。

## 21.4 用户级转化漏斗

漏斗按观察窗口内完成各步骤的去重用户计算，而不是直接用事件数。步骤建议为浏览、收藏或加购、创建订单、支付成功。对于用户 `u`：

```text
view_flag(u)  = 是否浏览
intent_flag(u)= 是否收藏或加购
order_flag(u) = 是否创建订单
pay_flag(u)   = 是否支付成功
```

阶段转化率为后一阶段用户数除以前一阶段用户数；整体购买转化率为支付用户数除以浏览用户数。若需严格顺序漏斗，则 Spark 使用窗口函数按 `user_id, session_id, event_time` 排序，并要求后一事件时间不早于前一事件。首版同时展示“宽松用户漏斗”和“会话顺序漏斗”，页面明确口径。

## 21.5 留存与复购

注册留存采用 Cohort 方法。以用户注册日为 cohort_day，若第 N 天有有效行为，则计入 N 日留存：

```text
N日留存率 = cohort中第N天活跃用户数 / cohort注册用户数
```

复购必须指定观察期：

```text
复购用户 = 观察期内支付订单数 >= 2 的用户
复购率 = 复购用户数 / 观察期内支付用户数
```

取消订单不计购买，完全退款订单在“支付复购率”中仍可计入支付行为，但在“有效复购率”中排除。首版页面默认有效复购率，并允许查看口径说明。

## 21.6 RFM 用户分层

- R：统计截止日减去最近一次有效支付日的天数，越小越好；
- F：观察期内有效支付订单数，越大越好；
- M：观察期内净支付金额，越大越好。

首版不依赖机器学习，使用分位数评分。R 按反向五分位记 1 至 5 分，F/M 按正向五分位记 1 至 5 分。再将各维度与中位分比较，得到重要价值、重要发展、重要保持、重要挽留、一般价值、一般发展、一般保持、一般挽留等八类。分位点和观察期必须随 `metric_definition_version` 保存。

可选实验使用 Spark MLlib KMeans：先对 R/F/M 做 `log1p` 和标准化，通过轮廓系数比较 K=3 至 8。聚类只作为增强实验，不替代规则分层，因为规则分层更稳定且易向运营解释。

## 21.7 商品热度、长尾与贡献度

首版热度分数采用可配置权重并先做对数缩放，避免 PV 数量级完全压制购买：

```text
heat = 1.0×log(1+PV)
     + 2.0×log(1+收藏数)
     + 3.0×log(1+加购数)
     + 5.0×log(1+支付件数)
```

权重是业务设定，不应被描述为训练得到。论文可对不同权重做敏感性实验。商品按销售额降序计算累计贡献比例，识别达到 50%、80%、95% 销售额所需商品占比，用于判断头部集中度和长尾结构。

## 21.8 库存指标

```text
库存周转率 = 观察期销售成本 / 平均库存成本
平均库存成本 = (期初库存成本 + 期末库存成本) / 2
日均销量 = 最近N天支付且未全退商品件数 / N
库存覆盖天数 = 当前可售库存 / 日均销量
缺货率 = 缺货商品数 / 在售商品数
```

如果首版缺少真实采购成本，则使用模拟商品 cost 字段，并在页面标记“模拟成本口径”。日均销量为 0 时库存覆盖天数为空，不显示无限大。

## 21.9 异常检测

首版使用透明、可解释的统计方法，不强行引入复杂深度学习。对于日指标序列，使用过去 7 或 14 个同口径周期的滚动均值和标准差：

```text
z = (x_t - rollingMean) / rollingStd
```

当样本数足够且 `|z| >= 2.5` 时标记候选异常；标准差为 0 时改用绝对变化阈值。对长尾或偏态分布使用 IQR：低于 `Q1-1.5×IQR` 或高于 `Q3+1.5×IQR` 标记异常。规则还应同时检查业务阈值，例如退款率超过 15%、库存覆盖低于 3 天。

异常只是“需要关注的信号”，不是因果结论。系统按商品、分类、渠道、新老用户等维度执行贡献拆解：

```text
维度贡献 = 当前维度值 - 基准维度值
贡献占比 = 维度变化量 / 总变化量
```

只把可由指标支持的相关变化提供给 AI，并明确“可能原因，需人工确认”。

## 21.10 决策效果计算

每条正式决策绑定目标指标、目标方向、基准窗口、执行时间和评价窗口。首版使用前后对比：

```text
baseline = 执行前N个完整周期平均值
actual   = 执行后N个完整周期平均值
improvementRate = (actual - baseline) / abs(baseline)
```

对于“越低越好”的退款率、流失率等指标，效果方向取反。结果分为 `ACHIEVED`、`PARTIALLY_ACHIEVED`、`NOT_ACHIEVED`、`INSUFFICIENT_DATA`。前后对比不能证明严格因果，因此论文应称为“决策效果评价”而不是“因果推断”。增强实验可选择未受影响类目作为对照组，使用差分中的差分思路减少整体趋势影响。

## 21.11 指标快照发布

`metric_snapshot` 状态为 `BUILDING → VERIFYING → ACTIVE`，失败进入 FAILED；旧 ACTIVE 在新版本生效后进入 ARCHIVED。一个环境和业务时间只能有一个 ACTIVE 快照。发布步骤：

1. Spark 写入带 snapshot_id 的临时 ADS 分区；
2. 数据质量执行完整性、唯一性、金额对账和波动检查；
3. `MetricPublisher` 把所需数据写入 MySQL 暂存表；
4. 校验暂存表行数、金额和主键；
5. 在事务中切换 MySQL 当前版本指针；
6. 更新 Hive/平台快照状态；
7. 失败时保留旧 ACTIVE，并清理或标记失败暂存数据。

看板响应必须返回 `snapshotId` 和 `dataUpdatedAt`，报告必须永久绑定生成时的快照，避免同一报告日后数字变化。

# 22 AI 跨模块辅助与决策中心设计

## 22.1 AI 能力矩阵

| 业务模块 | AI 输入 | AI 输出 | 不允许的行为 |
|---|---|---|---|
| 经营概览 | 核心指标、环比、异常列表 | 每日摘要、重点变化、待关注事项 | 编造未查询数字 |
| 销售分析 | 趋势、渠道、分类贡献 | 变化解释和进一步分析问题 | 自动改价 |
| 商品分析 | 热度、转化、退款、库存 | 爆款/滞销解释、候选运营动作 | 自动上下架或补货 |
| 用户分析 | 分层、留存、复购汇总 | 人群特征与触达建议 | 输出个人敏感信息 |
| 转化漏斗 | 各阶段人数与流失 | 主要流失点、验证建议 | 把相关性写成因果 |
| 订单质量 | 取消、退款、异常订单汇总 | 异常模式和排查顺序 | 自动取消或拒绝退款 |
| 数据质量 | 规则失败、样例和血缘 | 影响说明、排查步骤 | 绕过质量规则发布 |
| 报告中心 | 固定快照和模板数据 | 日报、周报文字草稿 | 修改指标数字 |
| 决策中心 | 异常证据、业务目标 | 建议草稿、优先级、目标指标 | 自动创建正式任务或执行业务操作 |

## 22.2 统一证据包

AI 不直接访问商城数据库或任意 Hive 明细。`EvidenceBuilder` 从允许的指标接口构造证据包：

```json
{
  "snapshotId": "S20260905_01",
  "question": "为什么退款率上升？",
  "timeRange": {"start": "2026-08-30", "end": "2026-09-05"},
  "metrics": [],
  "anomalies": [],
  "dimensionContributions": [],
  "definitions": [],
  "limitations": ["当前数据只能说明相关变化，不能证明因果"]
}
```

外部模型默认只接收汇总数据。任何分组人数小于 10 的记录先合并为“其他”或不发送。证据包保存哈希和快照 ID，便于复核模型输出。

## 22.3 结构化输出契约

模型必须返回 JSON，不直接信任 Markdown：

```json
{
  "summary": "",
  "facts": [{"statement": "", "evidenceIds": ["M001"]}],
  "possibleCauses": [{"statement": "", "confidence": "LOW|MEDIUM|HIGH", "evidenceIds": []}],
  "suggestions": [{"title": "", "action": "", "targetMetricCode": "", "risk": "", "priority": ""}],
  "limitations": [],
  "followUpQuestions": []
}
```

本地 `AiOutputValidator` 检查 JSON Schema、数值是否来自证据、证据 ID 是否存在、禁止词和权限。事实没有证据时删除或拒绝；建议没有目标指标时只能显示为一般提示，不能进入决策中心。

## 22.4 Text-to-SQL 的正确位置

Text-to-SQL 只是 AI 能力之一，主要服务于分析员的临时问题。固定看板不调用模型生成 SQL。普通员工的自然语言问题优先映射到已定义指标查询；只有无法由指标模板表达且用户有权限时才进入 SQL 生成。

建议处理链：意图分类 → 主题/指标选择 → Schema 裁剪 → 生成标准 SELECT 子集 → JSqlParser AST 校验 → 表字段白名单 → 自动补充时间和 LIMIT → 数据库 EXPLAIN → 只读执行 → 一次受控修复 → 结果证据化。首版默认查询 MySQL 指标服务；需要完整历史或复杂窗口运算时创建异步 Spark/Hive 分析任务，而不是在 HTTP 请求中等待长任务。

## 22.5 大模型 Java 调用提示

```java
public AiAnalysis analyze(AiUseCase useCase, EvidencePack evidence, UserContext user) {
    permissionService.checkAiAccess(user, evidence.datasetCodes());
    AiRequest request = promptFactory.build(useCase, evidence);
    AiResponse response = aiProvider.complete(request);
    AiAnalysis parsed = outputParser.parse(response.content());
    outputValidator.validate(parsed, evidence, user);
    auditService.record(request, response, evidence.snapshotId());
    return parsed;
}
```

HTTP 客户端设置连接和读取超时，网络、限流和临时服务错误最多重试两次并使用退避；格式、安全、权限和事实校验失败不自动无限重试。保存模型供应商、模型名、温度、Prompt 版本、输入输出令牌、耗时、状态和 trace_id。不要在 Controller 中直接写 Prompt。

## 22.6 决策生命周期

```text
DRAFT（AI或人工草稿）
  → PENDING_REVIEW（提交审核）
  → APPROVED（员工确认负责人、期限和目标）
  → IN_PROGRESS（开始执行）
  → COMPLETED（完成业务动作）
  → EVALUATING（等待评价窗口）
  → EFFECTIVE / PARTIAL / INEFFECTIVE / INSUFFICIENT_DATA

任意审核前状态可 REJECTED；执行中可 CANCELLED，但必须记录原因。
```

正式决策至少包含：来源异常、证据快照、建议内容、责任人、截止时间、目标指标、目标方向、基准值、目标值、评价窗口、风险、审核人和操作日志。AI 只能创建 DRAFT；从 PENDING_REVIEW 到 APPROVED 必须由有权限的员工操作。

## 22.7 决策示例

某商品出现“浏览量增长 40%、加购增长 25%、支付增长 2%、库存覆盖仅 2.1 天”。规则引擎标记转化和库存异常，AI 根据证据提出两个草稿：检查结算环节和补充安全库存。运营人员选择“补充库存”，设负责人、三天期限、目标为“支付转化率不下降且缺货率低于 3%”。完成后系统读取未来三天快照，比较基准窗口，形成效果评价。整个过程保留数字、口径、人员和时间，论文可以展示“发现—解释—决策—评价”闭环，而不仅是聊天截图。

# 23 流水线状态、错误恢复与可观测性

## 23.1 流水线与幂等键

首版固定阶段为：`WAIT_LANDING → LOAD_ODS → BUILD_DWD → BUILD_DWS → BUILD_ADS → QUALITY_CHECK → PUBLISH_METRIC → SUCCESS`。运行幂等键由 `runtimeProfileId + pipelineCode + businessTime + sourceDataVersion` 组成。同一幂等键只能有一个非终态实例；人工重跑增加 `attempt_no`，不创建无关联的新批次。

每阶段记录输入批次、输出分区、开始/结束时间、Spark 外部任务 ID、代码版本、记录数、错误码和 trace_id。恢复时从第一个失败或未完成阶段继续，已经成功且输出校验仍通过的阶段不重复执行。

## 23.2 错误分类

| 错误类别 | 示例 | 自动处理 | 用户操作 |
|---|---|---|---|
| TRANSIENT | 网络闪断、限流、临时连接失败 | 最多重试 2 次 | 重试仍失败后查看连接 |
| CONFIGURATION | Hive地址错误、凭据失效 | 不重试 | 修正配置并重新测试环境 |
| SCHEMA | 未知版本、字段类型不兼容 | 隔离 | 增加映射或转换器 |
| DATA_QUALITY | 金额不平、主键重复过阈值 | 阻止发布 | 查看样例、修复或审批补数 |
| SECURITY | 越权、危险SQL、提示词注入 | 立即拒绝并审计 | 管理员复核安全事件 |
| RESOURCE | Spark内存不足、队列不足 | 不盲目重试 | 调整数据范围或资源参数 |
| AI_FORMAT | 非法JSON、缺少证据 | 拒绝本次AI结果 | 可重新生成，不影响指标 |

统一错误返回：

```json
{
  "code": "PIPELINE_QUALITY_FAILED",
  "message": "金额对账未通过，新指标未发布",
  "traceId": "...",
  "retryable": false,
  "details": {"runId": 123}
}
```

## 23.3 调度频率

- 每小时：装载新增事件、更新核心经营指标和异常检测；
- 每日：完整 DWD/DWS/ADS、RFM、留存、复购、报告和迟到数据补算；
- 手动：黄金数据测试、历史补数、指定分区重跑和演示一键流程；
- 第二阶段：使用 DolphinScheduler 表达相同 DAG，增加失败通知和回填能力。

首版 Spring `@Scheduled` 只负责触发应用服务，不能在定时方法中堆叠全部流程逻辑。需要数据库锁或唯一键保证多实例时不会重复调度。

## 23.4 Trace 关联

入口请求、商城事件、Flume 批次、PipelineRun、Spark Job、快照发布、指标查询、AI 调用和决策均携带或派生同一 `trace_id`。运行中心可以从一个异常指标跳转到对应快照、任务和输入批次；AI 详情可以看到所用证据和快照，但普通员工默认不显示底层路径和 SQL。

## 23.5 首版监控项

| 对象 | 指标 | 告警示例 |
|---|---|---|
| 运行环境 | Hive/HDFS/Spark/指标库连通性 | 连续 3 次探针失败 |
| Flume | 最新事件时间、采集延迟、积压文件数 | 延迟超过 10 分钟 |
| 隔离区 | 新增隔离数、Schema版本 | 出现未知版本 |
| Spark | 成功率、耗时、输入输出记录、重试数 | 小时任务失败或耗时翻倍 |
| 质量 | 失败规则、金额差、重复率 | 核心规则失败 |
| 快照 | 当前版本、发布时间、数据时间 | 超过应更新时间仍未发布 |
| API | P95、错误率、并发 | P95 超过 2 秒持续 5 分钟 |
| AI | 成功率、耗时、令牌、校验拒绝数 | 连续失败但不影响固定页面 |

## 24.5 Spark 作业代码约定

每个作业实现相同入口参数：`--runtimeProfileId`、`--businessDate`、`--inputVersion`、`--outputSnapshotId`、`--attemptNo`。作业只从配置解析后的路径读取，禁止写死节点地址。输出先写临时分区，成功后由发布流程切换。

```scala
trait WarehouseJob {
  def code: String
  def validate(args: JobArgs): Unit
  def run(spark: SparkSession, args: JobArgs): JobResult
}
```

公共工具负责 SparkSession、参数、分区路径、审计计数和异常映射。业务算法放在可测试的纯函数或 Dataset 转换中，不能把全部 SQL 写在一个超长 `main` 方法内。

## 24.7 前端代码约定

前端按业务功能而不是后端表名组织，例如 `views/overview`、`views/sales`、`views/products`、`views/decisions`。API 客户端统一处理 traceId、错误码和登录失效；图表组件只接收页面 DTO，不直接理解 Hive 字段。所有图表显示数据更新时间、统计口径入口、空数据状态和导出来源。

# 25 普通员工页面与报告设计

## 25.1 首页信息层级

首页不展示集群节点和任务命令，按以下顺序组织：

1. 日期、店铺、渠道、分类等全局筛选；
2. 销售额、订单数、支付用户、客单价、退款率等核心指标；
3. 趋势和环比；
4. 异常卡片及受影响范围；
5. AI 对当前证据的简短解释；
6. 可创建的决策建议；
7. 正在执行和近期完成的决策效果。

每个专题页统一为“筛选 → 指标卡 → 趋势/分布 → 异常解释 → 可下钻明细 → AI 分析 → 创建决策”。统一交互能减少普通员工学习成本。

## 25.2 技术页面隔离

运行环境、HDFS 路径、Hive 表、Spark Job、Flume 延迟、Schema 隔离和 SQL 只在管理员或数据工程人员页面展示。普通运营人员可以看到“数据更新时间”和“数据暂不可用”，但不需要理解具体组件。

## 25.3 报告模板

首版实现经营日报、经营周报、订单专题、商品异常、用户运营和决策效果六类固定模板。报告数字、表格和图表由程序根据快照生成，AI 只撰写摘要、可能原因、建议和限制。生成报告时保存快照 ID、指标定义版本、模板版本、AI Prompt 版本和生成者。

## 25.4 可理解的错误提示

技术错误 `HIVE_JDBC_TIMEOUT` 对普通用户显示“数据服务暂未更新，请稍后再试；当前仍展示上一版本数据”，对数据工程人员显示连接、环境和 traceId。禁止把 Java 堆栈、SSH 命令和服务器路径直接暴露给普通用户。

# 29 技术时效性与官方资料依据

## 29.1 选型时效性说明

截至 2026 年 9 月核对官方资料，Flume 官方站点展示的最新发布仍为 2022 年的 1.11.0。它能够完成本项目所需的 Taildir 日志采集，也适合体现传统 Hadoop 采集链路，但更新节奏较慢。因此本项目尊重既定选择，在第一阶段实现 Flume，同时通过 `EventIngestor` 和统一事件格式降低替换成本；后续优先评估 Kafka 或 SeaTunnel，论文中应如实说明教学价值、局限和迁移方案。

DataX 开源项目将同步抽象为 Reader/Writer 插件，适合第二阶段增加 MySQL 到 HDFS/Hive 的离线同步。其核心引擎为 Java，但常用启动入口包含 Python 脚本；使用者主要编写 JSON 任务配置，不需要用 Python 开发本项目后端。接入前要单独验证运行环境、插件版本和安全配置。

Apache Livy 官方文档仍标注为 Apache 孵化项目。它提供 batch/session REST API，适合作为 `JobSubmitter` 的第二种实现，但不是首版依赖。接入时必须验证与实际 Spark/Hadoop 版本的兼容性，并保留 SSH + spark-submit 回退方案。

Apache Doris 官方将其定位为 MPP 实时分析数据库，兼容 MySQL 协议，适合报表、多维分析和用户行为分析。因此第二阶段优先实现 Doris 指标服务具有明确业务理由；但文稿不预先承诺官方宣传中的极限性能，所有性能结论以本项目数据和机器实测为准。
