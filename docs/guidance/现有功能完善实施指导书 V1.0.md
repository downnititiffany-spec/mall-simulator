## 1. 本轮目标与完成标准

目标是让现有系统更容易使用、结果更容易理解、遇到失败后能够恢复，并形成可重复的答辩演示步骤。

本轮围绕已存在的登录、分析页面、来源接入、流水线、运行环境、AI、报告和决策流程开展完善。先走查并复现，再修复；已有实现和测试直接复用。一个检查点已满足时登记“复核符合”，不为制造工作量改代码。

本轮结束应交付：

1. 一份按当前源码、角色及环境标明范围的问题清单，区分缺陷、体验改进、复核符合和外部依赖。
2. 已修复问题的最小改动、针对性验证与可追溯证据。
3. 当前增量版本的业务走查和操作说明；用户确认的视觉审阅单独登记。
4. 未完成事项的具体原因、影响和下一步，不使用一个总完成率覆盖不同证据范围。

**本轮增量通过与原交付签收分开登记。** 新代码、新环境、新报告不自动纳入已签收版本；本指导书不提前承诺 RES 销项或新版本发布。

每个问题使用 `UP-日期-序号`，至少记录：角色、页面、代码版本、RunId、输入/快照、复现步骤、预期与实际、脱敏证据、影响、拟改文件、验证结果。

| 类别 | 判定 | 处理 |
|---|---|---|
| P0 缺陷 | 越权、串源/串快照、旧数据冒充新结果、重复写入或错误成功提示 | 优先止损与最小修复；暂停受影响路径的新增写操作 |

采用单个切片闭环：**复现 → 确认契约 → 最小修改 → 定向验证 → 关联回归 → 动态登记**。每批控制在一个工作包或少量强相关问题，不跨多个页面大规模重构。

### U00：基线与问题盘点

**步骤**：核对分支、HEAD、远端和所有本地改动；读取签收表、动态状态及对应原报告。盘点 12 个现有功能路由、登录页和四角色访问结果，将“已有实现”“历史证据”“本轮实测”分列。运行环境确认从脚本内容、依赖和进程归属开始，不主动启动未知旧栈。

建立三个场景：普通分析人员查看指标并理解结论；有权限人员处理报告/决策；管理员查看来源与任务反馈。先用现有受控数据，确需新增隔离测试数据时核对已有授权、环境和写入范围，不向数据库直接插入指标。

**完成标准**：每个拟修问题都有复现或明确的体验依据；已有功能不被标记为未实现；选出首批最值得处理的问题。若没有发现缺陷，可报告复核符合并进入 U06，无需强行修改。

### U01：登录、角色与导航

**检查与完善**：

1. 登录失败、请求中、登录过期、注销后返回受保护页面时，提示与页面行为一致；不出现循环跳转或敏感内容残留。
2. 菜单、地址直达、浏览器前进/后退和后端鉴权相互匹配。前端守卫仅控制导航，不能作为服务端授权依据。
3. 维持当前角色契约：`admin/data_dev` 可进入运行环境管理；流水线、运维和接入向导当前前端仍为 admin-only。后端 `pipeline:run` 等权限较宽不自动授权扩大页面访问，发现需求差异登记后单独裁决。
4. 无权访问的反馈应可理解并能返回允许页面；不为改善体验放宽角色或 owner 限制。

**代码入口**：`web/src/router.js`、`web/src/api.js`、`web/src/utils/routeAccess.js`、`web/src/views/Login.vue`；后端 `RolePermissions`、`AuthInterceptor` 与对应 Controller。

**验证标准**：覆盖匿名、四角色、失效登录和注销；区分路由检查与直接 API 检查，记录应允许/应拒绝的实际结果。复用角色、登录和路由测试；新增测试针对实际改动。
