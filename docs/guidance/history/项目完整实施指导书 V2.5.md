## 3. 三程序架构裁决

### 3.1 最终边界

| 程序 | 建议名称/端口 | 唯一职责 | 明确禁止 |
|---|---|---|---|
| 分析平台 | `analytics-platform` / 8091 | 数据源配置、采集编排、标准化、Landing、Hive 数仓、Spark 作业、质量、指标发布、看板、AI、决策、运维 | 商城业务增删改；随机造订单；依赖商城数据库或 Java 包 |
| 参考商城 | `reference-mall` / 8090 | 用户、商品、分类、库存、购物车、订单、支付、退款、Outbox 事件 | 分析任务、Spark/Hive、生成场景、直接写分析平台 |
| 模拟数据生成器 | `synthetic-data-generator` / 8092 或 CLI | 固定 seed 的场景生成、负载控制、脏数据策略、运行报告 | 直接操作商城数据库；依赖商城内部 Service/Mapper；写平台业务库；触发平台流水线 |

另外建立中立的 `contract-specs`，保存版本化 JSON Schema、OpenAPI 和清单 Schema。三个程序可以分别根据契约生成或校验数据，但不得通过共享 Java 实体、Mapper 或 Maven 业务依赖耦合。

### 3.2 唯一正常业务路径

```text
模拟数据生成器 --公开 HTTP API--> 参考商城 --Outbox/事件文件--> 数据源连接器
真实商城 -----------------------------------------------> 数据源连接器
数据源连接器 -> HDFS/本地 Landing -> 标准化 -> Hive ODS/DWD/DWS/ADS
             -> 质量门 -> MySQL ACTIVE 指标快照 -> 页面/AI/决策
```

这条路径表达两个关键事实：

- 参考商城只是可替换的数据提供者和演示样例，不是分析平台的一部分。
- 模拟数据生成器只是测试客户端。没有生成器、没有参考商城时，分析平台仍必须能连接其他商城并读取历史 ACTIVE 快照。

### 3.3 生成器的两种模式

#### A. `MALL_API` 模式

用于完整演示。生成器通过 `MallTargetAdapter` 调用商城公开接口完成注册、浏览、加购、下单、支付、取消、退款等行为。禁止调用商城内部类、直接连接商城数据库或修改库存表。

脏数据不得在此模式中绕过商城校验直接写库；需要验证平台隔离能力时，使用 B 模式。

#### B. `CANONICAL_EVENT_FILE` 模式

用于采集、质量、数仓和性能测试。生成器直接输出符合指定契约版本的 JSONL、manifest 和可选脏样本，写入独立测试目录。该模式必须显示 `synthetic=true`，不能被描述为商城端到端测试，也不得直接写 ODS/DWD/ADS/指标库或自动触发流水线。

### 3.4 独立验收

1. 三个程序有独立构建产物、配置、端口、日志和启动命令。
2. 商城工程中不存在 `generator` 包、`GeneratorController` 或生成器页面。
3. 生成器工程不引用商城实体、Mapper、Service、数据源配置，也不能访问商城 JDBC。
4. 分析平台不引用商城/生成器 Java 包、商城表或 `mall.*` 配置键。
5. 分别停止三者：其余程序不会因类加载或数据库依赖崩溃；停止数据源时平台明确显示采集不可用，但历史指标仍可读。
6. 生成器以第二个 MallTargetAdapter 证明目标可替换；分析平台必须另以异构源 B 的配置映射、分层、指标全链证明不写死 mock-mall。两类验收不能互相替代。

#### 4.1.1.1 接口签名（唯一执行签名）

```java
interface MallTargetAdapter {
    /** 本实现负责的 adapter_type：注册表的唯一查找键，比较不区分大小写；取值集合不冻结。 */
    String adapterType();

    /** 对目标做一次真实检查（可联网），返回实测能力判定与过程说明。 */
    TargetCheckResult test(TargetConfig config);

    /** 按当前配置**声明**本适配器支持的能力（不联网）。默认实现"什么都没声明"。 */
    default TargetCapabilities capabilities(TargetConfig config) { return TargetCapabilities.none(); }

    /** 本适配器在各操作上真实使用的 HTTP 方法与路径（供运行流水如实记录）；无 HTTP 语义的操作不给条目。 */
    default Map<String, TargetRoute> operationRoutes(TargetConfig config) { return Map.of(); }

    default ProductPage listProducts(TargetConfig config, ProductQuery query) { throw unsupported("listProducts"); }

    default ExternalUser createSyntheticUser(TargetConfig config, UserCommand command) { throw unsupported("createSyntheticUser"); }

    default void emitBehavior(TargetConfig config, BehaviorCommand command) { throw unsupported("emitBehavior"); }

    default ExternalOrder createOrder(TargetConfig config, OrderCommand command) { throw unsupported("createOrder"); }

    default ExternalOrder pay(TargetConfig config, PayCommand command) { throw unsupported("pay"); }

    default ExternalOrder cancel(TargetConfig config, CancelCommand command) { throw unsupported("cancel"); }

    default ExternalRefund refund(TargetConfig config, RefundCommand command) { throw unsupported("refund"); }

    private MallOperationException unsupported(String operation) {
        return new MallOperationException(operation, "本适配器未实现：" + operation);
    }
}

/** 一次操作的 HTTP 方法与路径模板（如 `/api/v1/mall/orders/{orderId}/pay`）；不含 base_url 与凭据。 */
record TargetRoute(String method, String path) { }

interface EventSink extends AutoCloseable {
    void write(CanonicalEvent event);

    Optional<Artifact> rotateIfNeeded();

    void flush();

    ArtifactManifest closeAndBuildManifest();

    @Override
    default void close() { closeAndBuildManifest(); }
}
```

`TargetConfig`（契约定义，字段名以此为准）：

| 字段 | 类型 | 来自 `generator_target`（§4.2） | 语义 |
|---|---|---|---|
| `id` | `long` | `id` | 目标 ID；一次运行内冻结 |
| `adapterType` | `String` | `adapter_type` | 适配器查找键（见下 1） |
| `baseUrl` | `String` | `base_url` | 商城公开接口基地址；文件模式实现把它当输出目录 |
| `credentialRef` | `String` | `credential_ref` | 凭据**引用**（环境变量名/别名）；值绝不进配置、日志、流水与异常 |
| `configJson` | `String` | `config_json` | 适配器私有配置 JSON（如 `behavior_path` / `reset_path`）；内部结构由适配器自述 |

【追认】`generator_target` 其余五列（`name` / `config_version` / `status` / `test_environment` / `capabilities`）
**不进入** `TargetConfig`，也不参与任何适配器判定：能力判定一律取自 `capabilities(config)`（声明）与
`test(config)`（实测），运营登记的 `capabilities` 列只是台账。

#### 4.1.1.2 实现硬约束

1. **无状态 + 目标作首参 + 唯一登记处**【追认】：适配器实例不持有目标，目标一律作首参传入；`MallTargetAdapterRegistry` 是 `adapter_type → 实现` 的唯一登记处，一个类型只允许一个所有者；未注册与重复注册都必须响亮失败并列出已注册类型。禁止"每个目标一份适配器实例"这种第二所有者。
2. **跨目标状态不得进实例**【新增要求】：目录缓存、外部 ID 映射一类跨目标状态属于运行期/仓储，不得放进适配器实例字段。
3. **做不到就响亮失败**【追认】：未实现或不支持的操作抛 `MallOperationException`（携带操作名），不得返回 `null` 或空对象冒充成功；引擎侧按"整类降级 + 记缺口"处理，绝不把跳过写成成功。
4. **凭据纪律**【追认】：`credentialRef` 只是引用名；取不到凭据时抛异常，日志、流水与异常信息里只允许出现引用**名**（如 `GENERATOR_TARGET_TOKEN`），绝不出现值；契约文本本身也只写引用名。
5. **能力三态**【追认】：判定只有 `SUPPORTED` / `ABSENT` / `UNDETERMINED`；缺键、未知、探测不到一律 `UNDETERMINED`，**不得**把 `UNDETERMINED` 说成 `SUPPORTED`。`capabilities` 是声明（不联网），`test` 是实测；运行预检以声明为准并强制 `product` / `user` / `order` 三项。
6. **路由所有权**【新增要求】：运行流水与运行报告里的 `http_method` / `route` **必须取自 `operationRoutes(config)`**；引擎、报告与页面不得内置任何商城的路由字面量。适配器对自报路由的真实性负责（它就是实际发起请求的一方）；未声明路由的操作只写占位说明。理由：流水里的路由是"我们到底请求了什么"的证据，换一家商城却继续写参考商城的路径等于在证据里说谎（与 D12 同类问题）。
7. **新增一家商城 = 新增一个 Adapter + 登记处加一行**【新增要求】：不得为此修改场景引擎、事件契约、表结构或页面；引擎里不得出现"哪家商城"的分支（`adapter_type` 只用于选实现，不用于业务分支）。
8. **只经公开接口**【追认】：`MALL_API` 模式只允许经商城**公开 REST 接口**；不得直连商城数据库，不得依赖商城 Java 包、业务表名或 `mall.*` 配置键。
9. **运行期单一配置实例**【追认】：一次运行只解析一次 `TargetConfig`，并贯穿探测、预检、派发与流水；同一运行内不得出现第二份目标配置。
10. **金额与精度**【新增要求】：不同商城的金额标度可能不同（元/分），适配器负责换算到与参考商城同口径后再交给引擎；换算系数必须是适配器内的显式常量并有单测覆盖；金额一律 `BigDecimal`，禁止 `double`；对账与校验一律用整数分比较。规范事件的金额口径以已冻结的事件契约与参考商城实现为准，本指导书不另立单位。
11. **契约纪律**【新增要求】：`TargetRoute`、`operationRoutes` 以及 §4.1.1.3 之外的新增字段/方法，必须先改本节再实现（§2.1）。`contract-specs/openapi/generator-api.v1.yaml` 现在把这一区域标为 `x-unspecified`，待 M1-5 收口时按本节同步（含 `TargetCheckResult` 的空对象声明与 `adapter_type` 取值集合）。

#### 4.1.1.3 DTO 最小字段表【追认】

字段名与类型以此表为准；**在已列字段之外新增字段，必须先改本节再实现**。构造校验（非空、范围、枚举白名单）同在契约内。

状态机：`PENDING -> RUNNING -> SUCCESS/FAILED/CANCELLED`。相同 `plan_version + seed + time_window` 应可复现；运行中修改计划不会影响已启动任务。

### 4.3 场景和算法

- 商品抽样：类别先按目标权重抽样，类别内采用 Zipf/长尾分布，避免所有商品热度相同。
- 用户分层：新客、活跃、沉睡、高价值、价格敏感等分群使用可配置比例。
- 时间分布：工作日/周末、小时段和活动峰值使用分段权重；不能简单均匀随机。
- 行为链：浏览→收藏/加购→下单→支付→退款使用条件概率，且订单必须引用已存在用户与商品。
- 金额：使用 `BigDecimal`；商品价格、数量、优惠、实付和退款遵守商城公式。
- 库存：MALL_API 模式只通过商城接口变化；失败必须记入运行报告，不能绕过业务规则。
- 可复现：所有随机源由一个根 seed 派生；并行线程也使用确定性子 seed。
- 异常样本：仅在文件模式注入缺字段、未知枚举、重复 eventId、非法金额、迟到事件和非法状态跳转，并在 manifest 中记录期望隔离数。

## 5. 可更换商城的数据源与连接器

### 5.1 平台统一标识

外部商城不能自行决定平台主键。平台创建稳定源身份（概念 source instance；现有数据库/API 为 source_id/sourceId），它从 Landing manifest 传播到 ODS、DWD、DWS、ADS、指标快照和页面筛选。跨商城去重键为 `(source_id, event_id)`，不能只按 `event_id` 去重。

第一阶段可限制“一次流水线只处理一个 source instance”，但任何表、Java/Scala 常量、配置键和页面不得写死 `mock-mall`。

### 5.2 元数据结构

### 5.4 标准化与映射

采集只负责可靠移动和断点；`EventNormalizer` 负责源事件到 canonical event 的转换：事件类型映射、JSONPath 字段提取、枚举映射、时区转换、金额单位转换和允许的纯函数变换。禁止在映射表达式中执行任意脚本或 SQL。

未知源版本、没有 ACTIVE mapping、必填字段缺失和不允许的转换全部进入 quarantine，并保存 source instance、mapping version、reason code 和原始位置。映射激活必须先用样本 dry-run，并输出接受/隔离/错误计数。

映射的最终真相仍是版本化配置和审核记录，不是大模型对话。P1–P5 先证明人工/配置驱动接入异构源；其后 AI 可以读取字段元数据和脱敏样本，生成 `SourceProfileDraft`、字段映射建议、置信度和待确认问题。低置信度、金额、退款、用户身份、时区等业务语义必须由人确认，AI 草案不能直接变为 ACTIVE mapping。

### 5.5 数据源页面

普通员工在分析平台中看到“数据源”，而不是填写 `runtimeProfileId`。页面包括：商城名称、连接器类型、状态、最后心跳、最近批次、映射版本、测试连接、启停和查看错误。运行环境档案属于管理员配置；数据源选择使用可读名称。

### 5.7 数据结构、算法和接口完成定义

新增源映射版本逻辑记录：source_id、mapping_version、profile_schema_version、target_contract_version、mapping_json、checksum、status、approved_by/at、created_at。唯一键 (source_id,mapping_version)，激活版本不可变；具体物理表使用 §5.2 schema_mapping，迁移号由总控分配。source_instance 是领域概念，当前物理身份复用 source_registry.id / source_id，禁止再建一套同义 source_instance 主表；tenant_id 没有隔离实现前不得宣称多租户完成。

SourceProfileLoader → ProfileValidator → MappingCompiler → EventNormalizer 为四个独立职责。Compiler 只编译白名单路径和纯变换；先以 Set 检查目标碰撞，再按每事件组预编译查找表，运行复杂度约 O(记录数×映射字段数+订单项数×项字段数)。不能每行重新读 profile、访问网络或初始化编译器。

NormalizeResult 至少包含 outcome=ACCEPT/QUARANTINE、canonicalEvent、violations[]、warnings[]、rawReference、sourceId、mappingVersion、mappingChecksum。Violation 含 reasonCode/detailCode、sourcePath/targetPath、rawUri、lineNo、byteOffset；日志不输出原始敏感值。原始 JSON 无 event_id 时使用 raw 文件+offset 追溯，不凭空补 event_id。

批次清单版本化，分开 rawChecksum/rawBytes 与 canonicalChecksum/canonicalBytes，不用同一个 checksum 混指两种文件。inputRecords=acceptedRecords+quarantinedRecords；reasonCounts 是违规条数，可以大于隔离行数；系统 I/O 错误单列 systemErrors 并失败整批，不能伪装成业务隔离。记录 raw/accepted/quarantine URI、sourceId/code、profileVersion、mappingVersion/checksum、contractVersion、事件统计和时间范围。

新增 API（先同步 OpenAPI 后实现）：
- POST /api/v1/sources/{sourceId}/mappings/dry-run：输入 mappingVersion、平台受控 sampleRef、maxRecords（1–100）；禁止任意文件路径或外部 URL。返回 reportId/status/input/accepted/quarantined/systemErrors/reasonCounts/warningCounts/mappingChecksum/fieldCoverage/enumCoverage/capabilityLimitations。
- GET /api/v1/sources/{sourceId}/mappings/dry-runs/{reportId}：只允许有该源权限的用户读取脱敏样本和原因；与现有 sources API 命名冲突时只增兼容路由，不私改已有路径。
- POST /api/v1/sources/{sourceId}/mappings/{version}/activate：管理员/data_dev；需通过该 checksum 的 dry-run、所有关键语义确认、版本状态校验及审计；普通员工不能激活映射。

fieldCoverage 分母=样本事件按目标 required 字段形成的应检查槽位数，分子=通过目标约束的槽位数；可选字段覆盖另列。enumCoverage 分母=样本观测的 (event_type,targetPath,sourceValue) 不同枚举数，分子=已确认有效映射数；空分母返回 null+NOT_APPLICABLE，不能补成100%。画像声明覆盖率单列，不能混用分母。

a 单测：每种字段态、金额 FEN/YUAN/数字文本、时区、冲突、数组、未知枚举/第三态、同输入确定性、恶意路径各有正反例。b 验收：raw 与输入字节一致，规范输出可回溯；崩溃后从 raw 重放，checkpoint 不丢不重、不同 mappingVersion 不覆盖旧产物。c 验收：两源使用相同业务 ID，独立 namespace/快照/指标；仅改 profile 接 B，不改核心 Java/Scala SQL 模板。

## 6. WSL 单节点主环境与可切换运行档案

### 6.1 本版部署裁决

主集成环境是单个 Ubuntu WSL2，不是三台虚拟机：单 NameNode + 单 DataNode（副本 1）、Hive Metastore、Spark local[1]、隔离 MySQL。按需启动 Flume；初期不启动 YARN、Spark standalone master/worker、HiveServer2。Hive JDBC 降级查询任务启用 HiveServer2 时另行验收。

Spark local[1] 只限制计算线程，不限制存储：它仍可从 HDFS 读写 Hive 表。没有 HDFS 的 Windows LOCAL 路径保留为快速开发兼容能力；内存 catalog 的测试只属 E2，不冒充完整 Hive 环境。

单节点不能证明高可用、多机容错、横向扩展或跨节点 shuffle。本机故障仍会同时影响全部服务。WSL 方案是阶段出口调整，不是宣布历史集群缺口已经通过。

### 6.2 软件、版本与资源

| 层 | 选择 | 实施提示 |
|---|---|---|
| 开发界面 | Windows Codex/编辑器/浏览器 | Agent 执行环境逐步切 WSL；只切终端不等于切 Agent |
| Java 后端 | Java 17、现有 Spring Boot、Maven | WSL 安装 Linux 版；不引用 Windows java.exe |
| Spark 作业 | Spark 3.5.1、Scala 2.12 系列、JDK8 API 兼容产物 | 当前 Scala 2.12.19 与发行版 2.12.18 有警告；统一版本另开依赖任务，不顺带升级 Spark |
| 存储 | Hadoop HDFS 3.3.4 单节点 | 与现有客户端对照；副本 1，不展示多副本安全承诺 |
| 元数据 | 独立 Hive Metastore + MySQL | Hive 服务包版本先核对现有兼容矩阵、Spark Hive client 与 Metastore 协议后锁定，禁止直接装最新版 |
| 页面 | Vue3/Vite/ECharts、兼容锁文件的 Node | Linux 重新安装依赖，不复制 Windows node_modules |
| 采集 | Flume、LocalFileConnector | Flume 版本在安装清单中固定；FileChannel 持久化目录单独配置 |

环境任务必须交付 Java17/Java8 两条显式命令路径和兼容矩阵；Spark 使用的 JVM由提交器启动配置指定，不能靠更改全局 JAVA_HOME 影响正在运行的后端。

初始试运行预算：WSL 2 CPU / 4–6 GB 内存、Spark driver 1 GB、local[1]、shuffle partitions 2–4、并发流水线 1。预算不是最低配置保证：先只读检查宿主内存/空闲量/磁盘与现有 .wslconfig，再决定是否调整。禁止覆盖已有配置；WSL 关闭/重启可能影响 Docker 等发行版，执行前确认无其他工作。商城/生成器/Flume 按需启动，停止只针对本任务拥有的进程。

### 6.3 源码迁移与目录所有权

最终 Linux 主开发目录建议 /home/<已核实用户>/projects/GraduationProject；此为待创建目标，不假装已存在。HDFS DataNode、NameNode 元数据、Metastore、Spark scratch、数据库文件分开置于已授权 Linux 数据目录，不放 Git 源码中。大型数据优先 Linux 文件系统，不长期通过 /mnt/d 做密集构建和数仓 I/O。

迁移分六个小任务：
1. 只读盘点主目录及 git worktree list，列出未提交、未跟踪、未推送与独有文件。
2. 备份源码、文稿、必要配置和独有证据，记录 SHA-256；密钥不进 Git。
3. 在 WSL 建独立克隆/开发副本，显式迁入未提交改动；不直接剪切含 worktree 引用的 .git，不自动把所有用户文件提交。
4. Linux 重建 target/node_modules 与缓存；验证行尾、执行位、大小写路径、中文路径和时区。现有 PowerShell 脚本保留，新增对应 bash/跨平台入口，不强删旧脚本。
5. 编译和 55 条隔离全链通过后，用户确认切换唯一主开发目录；旧 Windows 目录只读保留，不两边并发开发。
6. 工作树清理单独申请：当前 m3-jdk8fix 有未提交改动，不能当作冗余直接删。每个新 worktree 必须登记 owner、目的、基线、独有修改和清理条件。

Windows 界面可继续保留，不要求重复安装另一套 AI harness；模型 API 与本地执行工具是两层。项目的 LLM 仍通过受控 API/provider 接入，与 WSL 安装无强依赖。

### 6.4 RuntimeProfile：正交配置，不按标签猜行为

| 字段 | 语义/约束 |
|---|---|
| platformPlacement | WINDOWS_LOCAL / LINUX_LOCAL / CLUSTER_GATEWAY，说明性标签 |
| landingStoreType / landingUri | LOCAL / HDFS 与完整 URI；hdfs:// 不能传 java.nio.Path |
| sparkSubmitterType | LOCAL_PROCESS / SSH |
| clusterManager / sparkMaster | LOCAL=local[1] 默认；YARN=yarn；STANDALONE=spark://；须匹配校验 |
| hiveMetastoreUris | thrift://host:9083；供 Spark catalog，不得填 JDBC URL |

### 6.5 数据流、Flume 与连接器

商城 Outbox 完整事件文件 → 同 WSL spool → Flume Spooling Directory + FileChannel → HDFS raw → FlumeLandingConnector 发现已关闭文件 → raw manifest → EventNormalizer → canonical manifest → ODS/DIM/DWD/DWS/ADS → 质量门 → MySQL ACTIVE → 页面。

首期选“不可再修改、文件名唯一”的 spool 文件；商城导出先写临时目录，flush/close 后原子移入 spool。对 .tmp/正在写入文件不采集；不能同时 tail 与 spool 同一文件。若商城暂留 Windows，必须明确可靠传输到 WSL spool 的过程、checksum 与重试；不假定 Windows 路径可供 Linux 服务直接使用。

HDFS 目录按 sourceCode + 采集时间组织，不依赖不存在的 eventType header。Flume 开启采集时间 header；业务日期由规范化后 event_time 决定。连接器只认已关闭产物，排除 in-use 文件，建立文件级 checksum/offset/manifest。源断点只能在 raw 持久化及批次登记成功后推进；转换可从 raw 重放，不因转换失败回滚成重复搬运。

LandingStorage 至少提供 list/open/create/rename/stat/checksum；本地和 HDFS 使用各自实现。URI 解析由唯一工厂拥有；配置支持但实现缺失必须 NOT_IMPLEMENTED，不能回退本地目录。HdfsLandingStorage 探针在授权根下创建本次 UUID 子目录，完成 write/read/checksum/rename/delete，只清理自己创建的探针。

传输采用 at-least-once；幂等靠源身份、文件断点、manifest 与 (source_id,event_id)，不宣称端到端 exactly-once。未来 DataX/Kafka/CDC 通过同一 SourceConnector 契约扩展。

### 6.6 预检与真实小链

依次验收：版本/磁盘/端口 → HDFS 文件探针 → 独立 Hive 临时库表读写 → Spark count → 一文件 Flume 投递 → 固定 55 条全链 → 同源重跑幂等 → 质量失败保旧 ACTIVE → 页面同快照查询。每步记录目标、配置指纹、结果、错误摘要、日志链接和建议。

每次运行建立唯一 testRunId，隔离 MySQL 元数据/指标库、Hive namespace、HDFS raw/warehouse/staging/export、checkpoint、source/profile、快照作用域。仅新 snapshotId 不足以保证上游隔离。

55 条黄金集必须冻结内容/checksum/事件类型/分区/接受隔离期望及指标 oracle；不能把旧 51 或 52 接受数硬套给新契约。已有异构 B 180 条反例保留，不改期望把失败洗成成功；另建版本化正例。

需要用户提供的仅为无法只读获取或涉及权限的项：宿主资源限制、允许的数据目录、已有库是否可复用及账号引用、是否可以重启 WSL。默认不操作旧 node01–03、不导入覆盖旧数据库、不重新 format 既有 NameNode、不修改系统自启。公开端口仅绑定必要接口，不能为方便暴露数据库到所有网卡。

### 6.7 延后的集群能力

保留 SSH wrapper/参数白名单/known_hosts、真实 applicationId/日志、YARN 队列、Kerberos 凭据引用、同输入跨环境对账等要求。原 M3 作为 DEFERRED 的独立后续里程碑；不阻塞 WSL 产品主线，也不允许删实现掩盖缺口。

版本化 jar 置于配置的授权根/<codeRevision>/<sha256>/，不强制旧 /apps 路径；已有 /graduation 路径不动。多节点验证重新启用时先确认服务资源和权限，再跑 55 条同输入对照与 1,000 条，不自动沿用历史授权执行删除。

官方参考（2026-09-14 查阅）：[WSL 文件系统](https://learn.microsoft.com/en-us/windows/wsl/filesystems)、[WSL 资源配置](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)、[Spark local 模式](https://spark.apache.org/docs/3.5.8/submitting-applications.html)、[Agent 与 WSL](https://learn.chatgpt.com/docs/windows/windows-app)。Spark 运行版本仍按上表，不因参考页为 3.5.8 自动升级。

## 7. 数仓、算法与剩余实现规格

### 7.1 DIM 与交易 DWD

- `dim_date`：由可配置日期区间生成日期、周、月、季度、工作日和节假日标志；生成任务幂等。
- `dim_region`：版本化地区字典，至少覆盖来源商城实际地区；未知值落 `-1/unknown` 并计数。
- `dim_metric`：由 MySQL `metric_definition` 同步，记录 metric_code、名称、单位、聚合方式和口径版本。
- 订单状态机：Java 与 Scala 共享同一份中立契约；非法转换写 `dwd_reject_record`，不能静默接受。
- 订单行校验：`SUM(quantity * unit_price - line_discount) = order_amount`，误差绝对值小于 0.01。
- 退款：按 `refund_id + event_time + ingest_time + event_id` 取最新；累计退款不得超过实付。
- 去重排序：同一业务键按 event_time、ingest_time、event_id 确定唯一结果，保证重跑稳定。

### 7.2 DWS/ADS 与算法

- 漏斗增加渠道和分类粒度。若后阶段人数大于前阶段，保留真实数值并输出“非严格同 cohort 漏斗”说明，禁止用 `min` 截断伪造单调性。
- 新增 `ads_category_sale` 与 `ads_region_sale`；地区指标至少有 sale_amount、net_sale_amount、order_count、buyer_count。
- `ads_sale_trend` 增加 net_sale_amount；repeat_rate 必须实际落表并发布。
- RFM：宽表保存 recency_days、frequency、monetary_amount、R/F/M score、segment、rule_version。M 的时间范围、退款口径和评分方向必须冻结；小样本标为“仅演示”。
- 排行和 NTILE 增加稳定次序键，避免同值重跑漂移。
- 异常检测：至少 14 个历史点才计算；第一版可采用滚动中位数/MAD 或滚动均值/z-score。结果表保存 metric_code、source_instance_id、window、actual、baseline、deviation、threshold、algorithm_version、snapshot_id。算法类必须接入生产指标链，不允许只有孤立类。

### 7.3 质量规则

建立 `quality_rule_definition` 和版本/生效区间，严重度行为如下：BLOCKING/ERROR 阻断发布，WARN/INFO 持久化并展示但不阻断。至少分别实现和验收：

1. Landing JSON 可解析率。
2. ODS event_id 非空和 schema version 支持。
3. DWD 行为字段/枚举合法。
4. 订单行金额公式误差 < 0.01。
5. 退款额 ≤ 实付额。
6. 非法状态跳转。
7. DWS 与 DWD 金额对账。
8. ADS 的 GMV ≥ 净销售 ≥ 0。
9. ADS 的 UV ≤ PV。
10. 支付用户 ≤ 浏览用户；不满足时必须给出口径说明。
11. `ingest_time - event_time` P95 和迟到率。
12. 发布行数一致性与抽样 checksum。

每条 BLOCKING 规则必须有一条“构造失败→流水线失败→不产生新 ACTIVE→旧 ACTIVE 可读”的负向验收。

### 7.3.1 F-88 新旧规则与发布安全

当前 RuleSeverity 的全局 ruleCode 覆盖不是最终完成形态。quality_rule_definition 需含 rule_code、version、source_scope、stage、severity、threshold_json、enabled、effective_from/to、checksum；(scope,rule_code,version) 唯一。一次 run 冻结完整规则版本与指纹，结果记录该版本、实际值、阈值、passed、原始及有效严重度、兼容策略版本。

执行顺序：选择作用域/版本 → 计算指标与阈值判定 → 决定严重度 → 汇总门禁。必填/主键/金额对账失败不能被全局规则码映射降 WARN。原始重复事件仅在确定性去重已证且重复率不超批准阈值时为观察项；超过阈值阻断。EVENT_ID_UNIQUE 历史阈值 0.0005 未经新裁决不修改，测试不得为通过把高重复率直接放行。

历史兼容需 (source_id,rule_code,rule_version 或明确批次范围,compatPolicyVersion)，没有版本且不在批准范围时不得自动降级。保留原始结果字段，不回填历史结论；接口同时展示兼容解释。未知规则码不可盲信传来的 WARN，应停止发布并报未登记规则。

历史 staging 存在可观察；真正的当前输入/输出混快照必须阻断。付款 vs 订单总额、订单项公式、DWD↔DWS 金额是三种独立校验，不能用一个 AMOUNT_RECONCILE 测试替代全部。退款以退款业务标识取最新成功状态再累计，与对应订单实付比较，避免重放累计两次。

每条 BLOCKING/ERROR 验一次：构造失败 → 本次流水线失败 → 不生成新 ACTIVE → 原 ACTIVE 数值/指纹可读且不变。失败必须可定位到 stage/rule，不只显示 RUN_JOB_FAILED。

### 7.4 指标存储

第一版 Hive 全程存在：ODS/DWD/DWS/ADS 均在 Hive。MySQL 不是数仓替代品，而是将常用 ADS 指标发布为 ACTIVE 快照的低延迟服务库。页面、AI 和决策只通过 MetricStore 读取同一快照。

建立 `MetricStoreFactory` 按 `metric_store_type` 选择实现：MySQL 为默认，既有成果继续复用并验收；Hive 为管理员显式降级查询路径，不由系统按数据量随机切换；Doris 为第二阶段首选；ClickHouse 仅接口和能力矩阵，标记 DEFERRED。

默认读当前授权源作用域的 ACTIVE；归档历史快照通过显式入口按 source 权限读取并审计，响应醒目标记 ARCHIVED，不混入默认查询。失败不改变原 ACTIVE；成功发布才原子归档旧 ACTIVE。唯一性按发布作用域（至少 source_id + runtime_profile_id；如再按 businessDate 切分，先与现有快照契约统一）建立数据库约束，不凭全库最新一行选择。

必须提供 ACTIVE 元信息：snapshotId、sourceId、sourceCode、businessDate、version、createdAt、definitionVersion。旧 sourceInstanceId 仅作兼容别名，禁止双身份。Hive 降级仅管理员显式启用，必须固定相同源/日期/口径/快照数据，不能随机按数据量切库。

## 8. 页面、AI、决策和安全

### 8.1 面向普通员工的页面

必须补齐：数据源管理、流水线 stage/job/externalJobId/log/error、总览环比、行为渠道/分类构成、商品库存覆盖天数、销售分类/地区、RFM 金额、决策截止日期、表格分页和稳定排序。页面用业务名称，不暴露 runtimeProfileId、Hive 表名或 Spark 参数。

### 8.2 AI 的产品定位

AI 不是独立页面或单一 Text-to-SQL 功能，而是横向辅助三个业务环节：

1. **分析辅助**：自然语言问数、异常解释、指标归因候选与经营摘要，全部引用同一 ACTIVE snapshot 的证据包。
2. **决策辅助**：基于固定模板生成 DRAFT 建议，补充适用前提、风险、观察窗口和目标指标；人负责审批和执行。
3. **新商城接入与数仓设计辅助**：读取数据库元数据、OpenAPI、JSON/CSV Schema 和少量脱敏样本，提出字段映射、分层表、粒度、主键、质量规则、指标与工作流草案。

现有 `LlmProvider`、`TextToSqlService`、`SemanticCatalog`、`SqlSafetyValidator` 和 `EvidencePackage` 是可复用基础，但“类已存在”不代表真实 LLM、动态语义目录或 AI 建模工作台已经完成。开发 Agent 必须按看板证据如实登记。

### 8.2.1 受控 AI 数仓设计器

AI 接入新商城时不得直接创建库表或执行任意 SQL。平台固定通用核心域：用户、商品、行为、订单、支付、退款；只有不能映射到核心域的信息才进入源扩展区。完整流程如下：

```text
源连接/样本/元数据
  -> 确定性数据画像与脱敏
  -> AI 生成 SourceProfileDraft + WarehouseBlueprint + WorkflowDraft
  -> JSON Schema/命名/必填字段/SQL AST/血缘 DAG/资源预算校验
  -> 人工确认低置信度映射和业务口径
  -> 受控编译器生成 DDL、转换 SQL 和固定类型作业 DAG
  -> sandbox 命名空间用 20–100 条数据 dry-run
  -> 对账、质量检查和证据包
  -> data_dev/admin 审批
  -> 不可变版本发布；失败或回归时回滚到 previous_release
```

状态机为：

```text
DISCOVERING -> DRAFT -> NEEDS_CONFIRMATION -> VALIDATING
-> SANDBOX_RUNNING -> REVIEW -> APPROVED -> DEPLOYED
```

失败终态/旁路状态为 `VALIDATION_FAILED / SANDBOX_FAILED / REJECTED / ROLLED_BACK`。只有 `APPROVED` 能进入部署；部署动作必须二次校验 blueprint checksum、审批人、目标 namespace 和前一 release。

### 8.2.2 AI 建模数据结构

| 对象/表 | 核心字段 | 用途与约束 |
|---|---|---|
| `ai_modeling_session` | session_no、source_id、source_profile_version、status、provider、model、prompt_version、input_fingerprint、created_by、started/finished、error | 一次可追溯建模会话；相同输入指纹可识别重复请求 |
| `source_profile_draft` | session_id、version、draft_json、confidence_summary、questions_json、status、checksum | 源画像草案；不得覆盖历史版本 |
| `mapping_review_item` | draft_id、source_path、target_field、inferred_type、confidence、rationale、status、reviewer、comment | 逐字段人工确认；低置信度默认待确认 |
| `warehouse_blueprint` | blueprint_no、version、canonical_model_version、source_id、blueprint_json、status、checksum、approved_by/at | ODS/DIM/DWD/DWS/ADS 的结构化蓝图 |
| `workflow_definition` | blueprint_id、workflow_code、version、nodes_json、edges_json、status、checksum | 只允许受控节点类型的 DAG |
| `modeling_validation_result` | blueprint_id、check_code、severity、status、message、evidence_json | 规则校验和 sandbox 证据 |
| `workflow_release` | release_no、target_namespace、artifact_uri/checksum、status、deployed_by/at、previous_release_id、rollback_at | 不可变发布与回滚指针 |

结构化中间对象至少包括 `SourceProfileDraft`、`WarehouseBlueprint`、`TableBlueprint`、`ColumnMapping`、`QualityRuleDraft`、`MetricDraft` 和 `WorkflowNodeDraft`。工作流节点白名单只允许 `DISCOVER_SOURCE / LANDING_VALIDATE / ODS_LOAD / DIM_BUILD / DWD_BUILD / DWS_AGG / ADS_BUILD / QUALITY_CHECK / PUBLISH_METRIC`，禁止 AI 生成任意 shell 节点。

### 8.2.3 AI 与规则系统的责任边界

AI 可以提出：类型与主键候选、字段/枚举映射、事实表和维表、粒度、SCD 类型、分区、代理键、质量规则、指标、血缘、资源估算和回滚建议。AI 必须显式提出它无法确定的问题，例如“订单金额是标价还是实付”“退款是否冲减 GMV”“订单状态含义”“匿名用户如何合并”“源时区是什么”。

AI 不得决定或执行：销售/退款/复购公式、破坏性重建、低置信度强制映射、任意 SQL/shell、绕过质量门和审批、直接发布经营动作。确定性系统负责 JSON Schema、命名白名单、字段完整性、类型兼容、SQL AST、无环 DAG、扫描量/资源上限、敏感字段脱敏和危险 DDL 拦截。

### 8.2.4 AI 调用、安全与一致性

- 模板、Mock LLM、真实 LLM 三种路径共享结构化输出 Schema、超时、有限重试、熔断、每日预算和审计。
- 真实调用记录 traceId、provider/model、prompt_version、输入输出 token、耗时、状态、错误类型和费用估算；traceId 用于追踪；幂等键由源/快照/请求内容/模型/提示词版本生成并与结果缓存绑定。提供商不支持幂等时，超时重试可能重复计费，必须记录不确定结果，不能保证零重复费用。
- 样本在发给外部模型前做字段级脱敏和数量上限；列名、注释、样本值都按不可信输入处理，防止 prompt injection。
- Text-to-SQL 继续经过语义目录、AST 白名单、EXPLAIN、扫描/行数/时间限制和只读身份；建模 SQL 只能由受控编译器从已验证蓝图生成。
- Hive、MySQL、API、DOM、AI 必须在同一 snapshotId 下进行五处同值断言；AI 无证据时输出“不足”，不得估算或补零。

### 8.2.5 面向非专业用户的建模向导

页面采用七步向导：选择数据源与样本 → 查看画像 → 审核 AI 字段映射与置信度 → 查看分层表/粒度/血缘蓝图 → 执行规则校验和 sandbox → 查看差异、对账和风险 → 审批、部署或回滚。普通员工可以使用解释和默认值完成草案，但只有 `data_dev/admin` 可以批准部署。

### 8.3 决策

完成五个模板：流量下降、漏斗流失、商品转化、库存风险、用户召回。每个模板包含发现、量化证据、适用前提、建议动作、目标指标、观察窗口、截止日期和风险。效果评估使用等长前后窗口聚合，不得只比较两个端点快照。

必须生成并保存 EFFECTIVE、PARTIAL、INEFFECTIVE、INSUFFICIENT_DATA 四类可达样本。人工草稿来源为 `human`；AI 草稿来源记录模型和证据版本。

### 8.4 安全与审计

- 增加 data_dev 测试角色；前端路由和后端 API 双层鉴权。
- 删除可用默认口令；生产可关闭种子账号并要求首次登录改密。
- Hive/SSH/LLM 凭据统一使用 credential_ref，日志脱敏 password、token、Authorization、key。
- 分开“启动流水线”和“重试”权限。
- 审计环境激活、流水线启动/重试、质量强制处理、快照激活和归档快照读取。

## 9. 并行开发和测试提速

### 9.1 并行泳道

按资源和授权使用“一总控 + 最多三开发泳道”，不默认开启四个重型任务：

- A：三程序拆分、连接器、集群。
- B：数仓、ADS、质量、指标发布。
- C：页面、AI、决策、安全。
- 总控：冻结契约、分任务、控制热点文件、集成和验收。

`PipelineService`、迁移版本号、统一事件契约、前端 router、主配置属于热点文件，同一时间只允许一个 Owner 修改。任何跨泳道字段变化先由总控登记契约任务，其他 Agent 等待契约冻结。

### 9.2 测试分层

| 层级 | 内容 | 执行时机 |
|---|---|---|
| T0 | 受影响类的单测、静态检查、编译 | 每个小任务提交前 |
| T1 | 当前 Maven/Vue/Scala 模块测试，使用内存或 20–100 条数据 | 每个泳道交付前 |
| T2 | 固定 55 条黄金链，WSL HDFS/Metastore/Spark/MySQL 真实全链 | 相关合并批次一次；LOCAL 快测不能替代 |
| T3 | WSL 固定 seed 1,000 条耐久/批次验证；远程集群另列 E4 | WSL 完整小链后一次；多节点当前 DEFERRED |
| T4 | 10 万/100 万条性能 | 性能里程碑/最终验收，不做日常回归 |

不删除已有测试，只把重测试移动到里程碑门。以下变化必须运行 T2：事件契约、分区、金额口径、流水线阶段、发布事务、质量阻断。纯页面样式或单一 DTO 变化不应反复启动全 Spark 链。

开发阶段优先使用固定 seed、覆盖所有事件类型和失败分支的小数据；“缩数据量”不能缩业务场景。每个失败只复跑受影响层，修复后再过当前里程碑门。

### 9.3 AI 建模评测与提速

AIW 日常开发不反复运行大集群。T0/T1 使用三个固定小源：参考商城 A、字段/枚举/ID 均不同的异构源 B、包含歧义和恶意内容的源 C；每源只取 20–100 条脱敏记录。稳定评测集统计字段映射 precision/recall、必填字段召回、枚举覆盖、蓝图规则通过率、编译首过率、sandbox 成功率、人工修正项数、耗时、token 和估算费用。

AI 接入的有效性必须用同一异构源 B 做 A/B 对照：P5 的人工配置接入是基线，AI 辅助接入是实验组，环境、数据和验收脚本相同。没有实测前不得填写“效率提升百分比”。安全集必须覆盖样本/列名 prompt injection、SQL/shell 注入、路径穿越、PII 泄漏、循环 DAG、破坏性 DDL、超预算、超时和模型不可用；模型不可用时允许保存人工草案，但不得伪造 AI 成功。

### 9.4 数据库 IT 防误写门禁

先整改 MetricAdsMySqlIT、MetricPublisherMySqlIT，并扫描所有 *Test/*IT（不能只按命名推断安全）。测试默认关闭外部写入；配置缺失立即拒绝，不提供 analytics_metric 等正式库 fallback。测试前通过实际连接 SELECT DATABASE()/服务实例标识校验隔离白名单，先校验后执行 DDL/DML。账号只授予本次测试数据库必要权限，不能使用 root 或正式写账号。

TestRunContext 至少含 testRunId、serverFingerprint、metaDb、metricDb、hiveNamespace、hdfsRoot、manifestRoot、credentialsRef、startedAt。目标必须全部处于同一登记的隔离范围；单改 JDBC URL 不算隔离。库名含 test 不是安全证明。拒绝正式库的负向测试应 mock 写调用或使用无权限账号，不能先在正式库试写再回滚。

cleanup 使用本次 testRunId/拥有的记录 ID，不能只靠可复用 runtime_profile_id；删除前输出目标清单并验证范围。禁止 TRUNCATE 正式库、删除历史 manifest、递归删除仓库根、format 既有 NameNode。跑前/后记录计数和关键行 checksum/快照指针；行数相等不足以证明零修改。只读 IT 也要核实实际账号权限；binlog 零事件只对覆盖完整、对象明确的观测窗口成立。

### 9.5 轻量回归和证据保全

V25-T01 修 WarehouseNameLiteralGateTest 的注释误命中：优先将历史错误原文移到已保留证据、源码仅引用；如改扫描器须以词法方式排除注释且保留真实 SQL 字面量红例，不能跳过整个文件。
V25-T02 将 IngestionManifestSourceSchemaTest 拆成冻结 legacy/new fixture 的自动化契约测试与明确的运行时巡检。测试依赖固定文件集合，不把新采集文件认作旧文件回填；历史文件不可变以冻结清单+checksum核验。禁止删除真实 40–43.json 让测试变绿。

新增测试 profile 明确 fast / integration-local / integration-wsl / cluster；不能假装这些 profile 已存在。参数 failure.ignore 只为收集结果，汇总失败数大于 0 一律 FAIL。平台已有受限模块测试使用 -pl <module> -am 是否可跑应实测，不沿用“必须永远全 reactor”旧结论。

每次验收独立目录保存 README、命令/退出码、JDK/工具版本、git commit+dirty patch 指纹、jar hash、配置/夹具 hash、结果明细和未测范围；日志脱敏。target 报告只作中间产物，不能作为唯一永久证据。WSL/Windows 使用同一 fixture 比较语义，不比较不相等数据量的性能。

### 9.6 并发与反馈

并行只用于没有共享写点的任务：契约冻结后可分别开发纯映射器、页面组件、独立规则测试；PipelineService、迁移号、统一 Schema、router、RuleSeverity 合入串行。低内存环境默认一个构建/测试工作进程；Spark 重型作业和第二条链绝不同时运行。允许多个 Agent 写不重叠文件，不意味着允许它们各起数据库或 Spark。

每个任务开始登记 owner/范围/依赖/下一反馈时间，活跃工作最长 30 分钟反馈一次；失败立即回报原文和影响。暂停时更新状态，不承诺“后台会继续”。没有用户明确授权时不自动创建新会话、启动长时间监控或提交推送。

## 12. 执行治理与历史裁决迁移

- 本版及 V2.5 看板是唯一新执行入口。旧看板的长台账是历史证据，不再追加“以此为准”。
- M1-1/2/6/7/8/10 等已完成基础保留历史证据，不无故重写；其余 M1/P1/P2 的 REVIEW、DONE_LIMITED 不因改版自动升级。
- M1-12 历史 50 行 checkpoint 副本不删除，不作为映射/WSL 前置；只要归一计数及不重读成立即可保留限定结论。
- B-13 是已勘误的假警报，不安排数据恢复/基准重建。AUTO_INCREMENT 间隙、TABLE_ROWS 估算和文件 mtime 不能单独证明删除或无删除。
- F-99 同名表比较必须带 server/schema/table，读数用 SELECT COUNT 与作用域，不能把 analytics_meta 表当 analytics_metric。
- P5 首期仍用固定异构文件，不要求现在接真实开源商城；真实商城后续通过 Adapter/Profile 接入，不准给核心 SQL 加商城名称分支。
- ODS 演示重建只有在备份、表数/行数/checksum、明确 namespace 和授权范围后才能执行；迁移到 WSL 不自动授权删除旧数仓。
- newFileCount 兼容项必须逐步由 consumableFileCount 接替，含义“至少有一条可采集完整记录的文件数”；DTO/OpenAPI 标旧字段 deprecated，前端只读新字段，过渡期同值。
- synthetic=true 只进入 generation run、产物 manifest 和验收元信息，不新增事件信封字段。
- 每个任务交付应具备：范围、输入输出、代码与测试、失败恢复、证据、下一步。四项状态分别登记“代码提交/测试结果/限定验收/完整验收”，不得以已推送文件数量推导完成度。
- 任何既有指导书要求未在新任务行单列，仍按 §3～§8 和原 269 项逐条登记，不可静默丢弃。V25-R01 负责一对一交叉表，禁止从旧覆盖表的 DONE 直接复制结论。

## 13. V2.2 新增裁决：AI 辅助多商城数仓接入

### 13.1 采用方案

采用“受控 AI 数仓设计器”，不采用“让大模型直接建库、任意生成并执行 SQL”。第一阶段只做源画像、字段/枚举映射建议、置信度和待确认问题；第二阶段再做 ODS/DIM/DWD/DWS/ADS 蓝图、受控 DAG、sandbox、审批、不可变发布和回滚。

### 13.2 与商城无关化主线的关系

- P1–P3 是硬前置：必须先有 source registry、每源 namespace、ODS 保真、代理键和语义注册表，AI 才有稳定目标契约。
- P4 提供按源指标和数据源管理 API/页面，可承载建模向导入口。
- P5 先完成异构源 B 的人工配置接入，形成可比较基线。
- AIW 不阻塞 P1-01，不修改参考商城和生成器边界；参考商城、开源商城和文件夹具都只是可替换数据源。

### 13.3 完成定义

1. 源 B 在不修改平台核心 Java/Scala/SQL 模板的条件下，由 AI 产生结构化草案。
2. 草案经过确定性规则校验；所有低置信度和业务语义问题可在页面逐项确认。
3. 编译器只接受白名单节点和转换，输出物包含 blueprint/version/checksum/lineage。
