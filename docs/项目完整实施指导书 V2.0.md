## 1. 本版必须解决的问题

当前项目已经不再是“只有几段 Spark 脚本”的空壳：独立平台后端、数仓分层、Spark 作业、指标库、前端页面、AI 与决策中心均已有代码基础。但“文件存在”不等于“生产链路已经打通”。现阶段最大风险是：旧商城单体、独立分析平台和新 Spark 链路同时存在，部分页面仍读取旧数据，部分新执行器只在测试中使用，因此界面成功或单元测试通过不能证明真实数据链已经运行。

V2.0 必须把项目收敛为两个边界清晰的程序：

1. **电商订单智能分析平台（毕业设计主体）**：只负责连接数据源、采集、数仓建模、Spark 计算、质量控制、指标服务、可视化、AI 辅助和决策闭环。
2. **模拟商城与随机订单生成器（外部辅助工具）**：只负责模拟商城业务和生成测试事件。它不是分析平台的模块，不是平台运行的前置条件，也不计入平台主程序的核心功能完成度。

本版的最终目标不是立即堆更多功能，而是建立以下可验证闭环：

```text
任意合规数据源
  -> 采集适配器
  -> Landing
  -> Hive ODS
  -> Hive DIM/DWD
  -> Hive DWS/ADS
  -> 数据质量门禁
  -> MySQL 指标快照发布
  -> 普通员工可读看板
  -> AI 解释/安全问数
  -> 人工审批的决策任务
```

## 2. 进度判定规则

后续所有进度只能使用以下四种状态，禁止仅因“有类、有接口、有页面”就写成完成。

| 状态 | 含义 | 最低证据 |
|---|---|---|
| 未开始 | 尚无可执行设计或代码 | 无 |
| 已设计 | 数据结构、接口和验收标准明确，但未实现 | 指导书/接口契约 |
| 组件完成 | 单个组件能运行并通过测试，但未接入完整生产链 | 单元/组件测试、日志 |
| 链路完成 | 真实入口到真实出口打通，失败与恢复也验证过 | runId、jobId、分区、快照、对账和页面证据 |

## 3. 产品边界：主平台与模拟商城必须彻底分离

### 3.1 两个程序的责任

| 维度 | 电商订单智能分析平台 | 模拟商城/随机生成器 |
|---|---|---|
| 身份 | 毕业设计主体 | 外部辅助数据源、演示工具 |
| 目标用户 | 运营、分析人员、管理员、数据开发人员 | 演示者、测试人员 |
| 核心责任 | 接入、治理、数仓、计算、指标、看板、AI、决策 | 商品、库存、购物、订单、支付、退款、事件生成 |
| 数据库 | `analytics_meta`、`analytics_metric`，以及 Hive | 独立 `mock_mall` 业务库 |
| 启动要求 | 可独立启动；没有模拟商城也能分析文件或其他系统数据 | 可独立启动；平台停止不影响下单 |
| 通信方式 | 只消费版本化事件或批量数据 | 只输出版本化事件或供 DataX 读取的业务表 |
| 禁止事项 | 禁止查询商城业务表，禁止控制随机下单内部逻辑 | 禁止包含平台采集、数仓、指标、AI、决策代码 |

最终最好拆为两个 Git 仓库。拆仓前也必须先在当前工作区形成独立构建、独立配置和独立启动边界：

```text
GraduationProject/

│  ├─ platform-common/
│  ├─ connection-ingestion/
│  ├─ warehouse-pipeline/
│  ├─ metric-analysis/
│  ├─ ai-decision/
│  └─ platform-app/
├─ analytics-web/                    # 分析平台前端，由现 web 拆出
├─ spark-jobs/                       # 平台计算作业
├─ warehouse/                        # 平台 Hive DDL
├─ connectors/                       # Flume/DataX/Kafka 模板与插件
└─ external-tools/
   └─ mock-mall/                     # 独立辅助程序，由现 mall-simulator 精简
      ├─ mock-mall-server/
      └─ mock-mall-web/
```

`mall-simulator` 当前仍复制了大量平台代码。按以下规则逐步清理，且只有在 `analytics-server` 对应功能验收通过后再删除旧副本。

| `domain`、`controller/MallController`、`AdminProductController` | 模拟商城 | 保留 |

### 3.4 前端分离

现 `web` 中 `/mall`、`/admin-products` 和生成器控制属于模拟商城；`/overview`、`/behavior`、`/products`、`/rfm`、`/sales`、`/pipeline`、`/ops`、`/decisions`、`/ai` 属于分析平台。

实施时应：

1. 新建独立的 `mock-mall-web`，迁移商城、商品管理、手工下单和随机生成页面。
2. `analytics-web` 删除商城业务 API 封装，不再出现“生成订单”按钮。
3. 分析平台的“数据源”页只能配置和检测一个来源，例如事件目录、Flume、DataX 或 Kafka。
4. 为演示方便，分析平台可显示“打开模拟商城”的外部链接，但不能直接调用模拟商城内部生成服务。
5. 两个前端使用不同端口、不同登录会话和不同构建产物。

### 3.5 唯一允许的集成契约

首期使用 JSON Lines 事件文件，统一外层结构：

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| `event_id` | string | 是 | 来源系统内全局唯一，平台幂等键 |
| `event_type` | string | 是 | 必须属于已发布契约 |
| `event_time` | ISO-8601 string | 是 | 必须含时区，例如 `+08:00` |
| `ingest_time` | ISO-8601 string | 是 | 写出事件时生成 |
| `source_system` | string | 是 | 如 `mock-mall`，不可写死为平台名称 |
| `schema_version` | string | 是 | 首期 `v1`；未知版本进入隔离区 |
| `trace_id` | string | 是 | 串联一次业务动作产生的多条事件 |
| `payload` | object | 是 | 由 `event_type` 决定字段集合 |

首期合法事件为：`user_registered`、`product_created`、`product_updated`、`behavior`、`order_created`、`order_paid`、`order_cancelled`、`refund_created`、`refund_completed`、`stock_reserved`、`stock_released`、`stock_changed`。

平台与模拟商城之间禁止：

- 共享 Java 实体或 Maven 依赖；
- 直接查询 `mock_mall` 数据库；
- 共享事务；
- 用商城表主键替代 `event_id`；
- 通过调用生成器接口来证明采集成功；
- 把模拟商城是否在线作为平台健康检查条件。

## 4. 目标技术栈与占比

| 层次 | 第一阶段 | 用途 | 后续可替换/扩展 |
|---|---|---|---|
| 平台后端 | Java 17、Spring Boot、MyBatis、Flyway | API、编排、配置、权限、审计 | 不需要 Python/FastAPI |
| 平台前端 | Vue 3、Vite、ECharts | 普通员工可操作的页面与图表 | 组件库、微前端非首期重点 |
| 大数据计算 | Scala 2.12、Spark 3.5.1、Spark SQL | 清洗、去重、状态归并、聚合与算法 | Spark on YARN、Livy |
| 数仓 | Hive，Parquet，ODS/DIM/DWD/DWS/ADS | 全量与历史数据的权威存储和计算分层 | Iceberg/Hudi 作为论文展望 |
| Landing | 本地文件或 HDFS | 采集后、进入 ODS 前的不可变落地区 | 对象存储 |
| 采集 | 本地文件首通，Flume 首期插件 | 事件流落地 | DataX、Kafka、CDC |
| 元数据库 | MySQL `analytics_meta` | 运行、批次、质量、权限、AI 与决策元数据 | PostgreSQL 可作为适配器扩展 |
| 指标服务库 | MySQL `analytics_metric` | 为页面/AI 提供低延迟、稳定口径查询 | 第二阶段 Doris；ClickHouse 仅预留接口 |
| AI | Java HTTP 客户端 + OpenAI-compatible 接口 | 解释、问数、异常归因提示、决策草稿 | 本地模型、多供应商路由 |
| 测试 | JUnit、ScalaTest、Vitest、Playwright | 单元、组件、契约与端到端 | Testcontainers |

### 4.1 为什么 Hive 与 MySQL 同时存在

Hive 始终是第一阶段数仓主体，ODS、DIM、DWD、DWS、ADS 全部在 Hive 中。MySQL 不是 Hive 的“自动降级版”，也不根据数据量随机切换。它只是把已经在 Hive ADS 计算完成、页面最常用的小体量指标快照发布出来，作为服务层缓存与查询库。

正确关系是：

```text
Hive：历史明细与所有数仓分层，负责大规模计算和可追溯性
  ↓ 发布经过质量校验的 ADS 结果
MySQL：当前/近期指标快照，负责 Web 与 AI 的低延迟读取
```

当 MySQL 发布失败时，页面继续读取上一个 `ACTIVE` 快照；平台可提供“管理员手工选择 Hive 查询”的故障处理能力，但首期不做自动按数据量切换。

## 5. 总体运行机制

### 5.1 一次日批流水线

1. 用户在平台选择一个已激活的 `RuntimeProfile` 和业务日期。
2. 平台创建 `pipeline_run`，立即返回 `taskId`，后台异步执行。
3. 采集模块扫描来源，按文件字节偏移读取新事件，合法行写 Landing，坏行写 quarantine。
4. Spark ODS 作业把 Landing 事件映射到 4 张 ODS 表。
5. DIM/DWD 作业完成维度快照、事件去重、订单状态重建、行为明细清洗。
6. DWS 作业按用户、商品、地区和日期聚合公共主题宽表。
7. ADS 作业写入本次 `snapshotId` 对应的临时分区。
8. 质量模块核对行数、唯一性、金额、状态、分区和指标边界。
9. 任一阻断规则失败：本次运行标记失败，临时结果不得覆盖正式 ADS，也不得发布 MySQL。
10. 质量通过：将临时结果切换为正式 ADS 分区。
11. 指标发布器读取 Hive ADS，写入 MySQL staging，校验后原子激活新快照并归档旧快照。
12. 看板、AI 和决策中心只读取同一个 `ACTIVE snapshotId`。

### 5.2 失败与重试

- 相同 `runtimeProfile + pipelineCode + businessTime + sourceDataVersion` 生成相同幂等键。
- 数据库唯一约束是最终防线；JVM 内锁只能减少同进程重复请求。
- 重试时跳过已成功且输出证据仍存在的阶段，从第一个失败阶段继续。
- 作业失败必须停止依赖阶段，不能“记录失败后继续跑完整链”。
- 平台重启后要扫描 `PENDING/RUNNING` 实例，查询外部任务状态；无法确认时标为 `UNKNOWN`，由管理员选择恢复或终止。
- 不能通过修改旧运行记录伪装重跑成功；`attempt_no`、阶段记录和作业记录必须保留历史。

## 6. 全局数据规范

### 6.1 标识符

| 标识 | 生成位置 | 用途 |
|---|---|---|
| `eventId` | 来源系统 | 事件幂等、ODS/DWD 去重 |
| `traceId` | 来源系统或平台入口 | 串联请求、日志、事件和 AI 调用 |
| `batchNo` | 采集平台 | 标识一次来源扫描与落地 |
| `pipelineRunId` | 平台元数据库 | 标识一次流水线运行 |
| `externalJobId` | Spark 提交器 | 标识真实本地进程/YARN 应用 |
| `snapshotId` | 流水线发布阶段 | 串联 Hive ADS、MySQL 指标、页面与 AI 证据 |
| `decisionNo` | 决策中心 | 标识一条可审批、执行和评价的决策 |

### 6.2 时间

- 外部事件统一 ISO-8601 带时区；进入 DWD 后统一为 `Asia/Shanghai` 业务时间。
- 所有增量窗口使用左闭右开 `[startTime, endTime)`，防止边界重复或丢失。
- `event_time` 决定业务日期；`ingest_time` 用于计算延迟和判断迟到数据。
- 迟到退款必须触发对应历史交易分区的重算，而不是只算到到达当天。
- 日期分区统一 `yyyyMMdd`；对外 API 使用 `yyyy-MM-dd`，在边界层转换。

### 6.3 金额与比例

- 外部 JSON 金额用十进制字符串，禁止使用浮点数表示货币。
- Hive 和 MySQL 使用 `DECIMAL(18,2)` 保存金额，汇率或比例使用 `DECIMAL`。
- Java 使用 `BigDecimal`；禁止 `double` 参与 GMV、退款或客单价计算。
- 分母为 0 时比例返回 `null` 和“数据不足”，不能返回 0 冒充真实比例。

### 6.4 状态

- 对外状态码和数据库枚举应集中定义，不允许 Controller、Service 和 Spark 各维护一份字符串白名单。
- 状态变化必须是有限状态机；非法跳转返回明确错误，不自动纠正。
- 状态、错误码、规则版本和指标版本都必须可审计。

## 7. 模块总表与依赖规则

| 模块 | 主要输入 | 主要输出 | 核心数据结构 | 核心算法/规则 |
|---|---|---|---|---|
| RuntimeProfile | 用户配置 | 激活环境快照 | `runtime_profile` | 分类型校验、版本化激活 |
| 连接器 | 文件/Flume/DataX/Kafka | 统一事件或批量清单 | `SourceConnector`、manifest | 偏移/水位线、重试 |
| 采集 | 统一事件 | Landing、批次、隔离 | ingestion 四表 | 字节偏移、契约校验 |
| ODS | Landing JSONL | 4 张 ODS | EventEnvelope | 类型路由、字段展开 |
| DIM/DWD | ODS | 5 DIM、3 DWD | 行为/订单事实 | 去重、状态归并、维度补全 |
| DWS | DWD/DIM | 7 张主题宽表 | 日/用户/商品聚合 | distinct、金额汇总、漏斗 |
| ADS | DWS | 10 张应用表 | 指标结果 | 热度、RFM、排行、趋势 |
| 流水线 | 运行请求 | run/stage/job 记录 | 三层执行记录 | DAG、幂等、恢复 |
| 质量 | 各层结果 | 质量报告/阻断 | `data_quality_result` | 完整性、唯一性、一致性 |
| 指标发布 | Hive ADS | MySQL ACTIVE 快照 | snapshot/value/物化表 | staging、对账、原子切换 |
| 看板 | ACTIVE 快照 | 图表、表格、CSV | 统一 ViewModel | 查询分页、维度过滤 |
| AI | 问题/证据包 | 解释、只读 SQL 结果 | EvidencePackage | 模板、AST 白名单、限流 |
| 决策 | 指标异常/人工输入 | 决策任务与评价 | task/evaluation | 状态机、前后对比 |
| 权限审计 | 登录与操作 | 会话、审计记录 | user/session/audit | RBAC、当前用户上下文 |

依赖方向必须为：

```text

  -> ai-decision / metric-analysis / warehouse-pipeline / connection-ingestion
  -> platform-common

warehouse-pipeline -> connection-ingestion + platform-common
metric-analysis    -> platform-common
ai-decision        -> metric-analysis contracts + platform-common
```

## 8. 外部模拟商城与随机订单生成器

本模块是辅助工具，但仍应足够真实，以产生可分析、可重复、可制造异常的数据。它不属于分析平台内部模块。

### 8.1 业务数据结构

| 表/对象 | 关键字段 | 关系与约束 |
|---|---|---|
| `mall_user` | user_id、age_group、city_level、member_level、register_time | 只使用虚构属性，不存真实个人信息 |
| `category` | category_id、parent_id、name、level、status | 至少两级分类；父子不能循环 |
| `product` | product_id、category_id、brand_id、name、price、cost、status | 价格大于等于成本；上下架状态有效 |
| `inventory` | product_id、available_qty、reserved_qty、version | 乐观锁；可售库存不得为负 |
| `cart_item` | user_id、product_id、quantity、selected | 用户与商品唯一组合 |
| `mall_order` | order_id、user_id、total_amount、pay_amount、status、created_at | 状态机驱动，不允许跳态 |
| `order_item` | order_id、product_id、quantity、unit_price、discount、amount | 保存下单时价格快照 |
| `payment` | payment_id、order_id、amount、status、paid_at | 一次成功支付幂等 |
| `refund` | refund_id、order_id、amount、status、completed_at | 累计完成退款不超过已付金额 |
| `event_outbox` | event_id、aggregate_type、aggregate_id、event_type、payload、status | 与业务事务同库提交，发布后标记 |

### 8.2 商品丰富度要求

- 一级分类不少于 8 个，二级分类不少于 16 个。
- 第一版不少于 32 个商品，正式演示建议扩展到 100～300 个商品。
- 每类商品应覆盖低、中、高三个价格带；价格不能均匀随机，应使用截断对数正态分布。
- 品牌、毛利、库存和转化倾向要有差异，确保分类分析和商品排行有意义。
- 商品可包含季节、促销、爆款、长尾、缺货风险等标签，但标签只用于生成参数，不直接作为平台分析结论。

### 8.3 生成配置结构

`GeneratorConfig` 至少包括：

| 字段 | 含义 | 校验 |
|---|---|---|
| `userCount` | 虚拟用户数 | 1～100000；开发默认 100 |
| `productCount` | 参与商品数 | 不超过当前在售商品数 |
| `eventsPerSecond` | 生成速率 | 开发 1～20，压力测试单独配置 |
| `baseConversionRate` | 基准购买转化率 | 0～1 |
| `startTime/endTime` | 模拟业务时间窗口 | 左闭右开，开始早于结束 |
| `randomSeed` | 随机种子 | 相同配置必须生成相同统计结果 |
| `dirtyDataRate` | 脏数据比例 | 开发默认 0；质量测试 0.1%～5% |
| `scenario` | 场景代码 | NORMAL、PROMOTION、STOCKOUT 等固定枚举 |

### 8.4 生成算法

1. **可重复随机**：一次运行只创建一个带 seed 的随机源，不允许各类自行用当前时间初始化。
2. **用户活跃分层**：可按高活跃 15%、中活跃 35%、低活跃 50% 分组，给不同事件权重。
3. **商品长尾分布**：按 `weight(rank)=1/rank^s` 做 Zipf 加权，`s` 建议 0.8～1.2。
4. **价格分布**：使用截断对数正态分布，按分类设置最小值、最大值和中位数。
5. **24 小时流量**：用小时权重模拟早晚峰；所有小时权重归一化后抽样。
6. **行为链**：曝光/浏览后才可收藏、加购、下单；支付和退款从有效订单派生。
7. **订单状态机**：`CREATED -> PAID/CANCELLED -> COMPLETED/REFUNDING -> REFUNDED`，保留部分支付后退款。
8. **场景乘数**：促销提高流量和转化，缺货降低支付，退款场景提高退款率；实际效果应输出预期区间。
9. **脏数据注入**：重复 eventId、缺字段、非法枚举、坏金额、未来时间、未知版本分别可配置，且输出注入统计。

### 8.5 外部输出

模拟商城至少提供两种外部方式：

- Outbox 发布为滚动 JSONL 文件，供 Flume Taildir/Spooling Directory 采集；
- 独立业务库，供未来 DataX 按 `update_time` 增量读取。

每次生成运行输出 `generationRunId`、seed、配置摘要、各事件计数、金额总计、脏数据计数和文件清单。分析平台只看标准事件与来源清单，不读取生成器内部统计作为分析结果。

### 8.6 独立验收

- 停止分析平台，模拟商城仍可下单和生成事件。
- 停止模拟商城，分析平台仍可导入黄金文件、运行数仓和打开历史看板。
- 两者使用不同数据库账号、端口、日志目录、构建命令和发布包。
- 平台源码中搜索不到 `mall_order`、`mock_mall` JDBC 或生成器类依赖。
- 相同 seed 的小样本统计一致；不同 seed 的分布满足设定区间。

## 9. RuntimeProfile：本地、单机和远程集群可切换

### 9.1 数据结构

`runtime_profile` 作为一个不可变运行环境版本，至少保存：环境编码、名称、类型、状态、Landing URI、HDFS URI、Hive 连接或本地 catalog 配置、库名前缀、Spark master、deploy mode、YARN 队列、SSH 信息、spark-submit 路径、作业包 URI、指标存储类型、配置引用、凭据引用、时区和版本。

类型含义：

| 类型 | Landing | Hive/Spark | 作业提交 |
|---|---|---|---|
| `LOCAL` | 本地目录 | 本机 Spark + 嵌入/本地 Hive catalog | 本地进程 |
| `SINGLE_NODE` | 本机或单节点 HDFS | 单节点 Hive/Spark | 本地或 SSH |
| `REMOTE_CLUSTER` | HDFS/对象存储 | 外部 Hive/Spark/YARN | SSH、后续 Livy |

即使是 LOCAL，第一阶段仍然有 Hive 数仓概念。它可以使用本地 warehouse 目录和嵌入 metastore，但不能跳过 ODS/DWD/DWS/ADS。

### 9.2 服务接口

- `createDraft`：创建草稿，不立即影响正在运行的任务。
- `testConnectivity`：分项返回 Landing、Hive、Spark、SSH、指标库状态和耗时。
- `activate`：只有必需项全部通过才激活，新版本生效，旧环境归档或停用。
- `getActive`：流水线启动时读取并复制一份环境快照到运行记录。
- `disable`：有运行中任务时禁止停用。

### 9.3 实现提示

- 删除 `RuntimeProfileServiceImpl` 中 Windows Spark 路径常量；默认值放配置文件，实际值从激活档案读取。
- 凭据字段只存 `credential_ref`，由 `CredentialService` 从环境变量或密钥服务解析。
- `LOCAL` 激活测试不能把 Hive 标为无条件 `SKIPPED`；应创建临时库/表并执行一次读写删除验证。
- 提交器由 `JobSubmitterFactory` 根据档案生成，不能在 `PipelineService` 里写 `if local else ssh`。
- `IngestionService.status()` 与运行接口都必须使用同一个激活档案，禁止状态页显示固定本地路径。

## 10. 数据连接器与采集模块

### 10.1 统一接口

定义 `SourceConnector` 抽象，不要求所有来源一次实现：

```text
connectorCode()
validateConfig(config)
testConnection(config)
discover(window, checkpoint)
collect(item, landingStorage)
commitCheckpoint(result)
```

首期实现 `LocalFileConnector` 和 `FlumeLandingConnector`。DataX、Kafka 只提供接口、配置模型和占位状态，不能在界面标“可用”。

### 10.2 连接器配置数据

| 字段 | 用途 |
|---|---|
| connector_id/code/name | 唯一标识和显示名称 |
| connector_type | LOCAL_FILE/FLUME/DATAX/KAFKA |
| runtime_profile_id | 所属运行环境 |
| config_json | 非敏感配置；需 JSON Schema 校验 |
| credential_ref | 密钥引用 |
| status/version | DRAFT/ACTIVE/DISABLED 与乐观锁版本 |
| last_test_at/test_result | 最近一次连通测试 |

建议新增 `source_connector` 表，而不是把所有采集参数继续塞进 `runtime_profile`。

### 10.3 采集元数据表

| 表 | 关键字段 | 作用 |
|---|---|---|
| `ingestion_batch` | batch_no、source、status、record_count、error_count、quarantine_count、landing_dir、start/end_time | 一次采集批次总览 |
| `ingestion_batch_file` | batch_id、file_path、start_offset、end_offset、record_count、checksum、status | 文件级对账与重放 |
| `file_checkpoint` | connector_id、file_path、next_offset、file_identity、updated_at | 下一次读取位置 |
| `quarantine_record` | batch_id、event_id、schema_version、reason_code、raw_path | 坏行索引 |

当前表需补充 `connector_id`、`checksum`、`file_identity` 和标准化 `reason_code`，避免多个来源使用相同路径时冲突。

### 10.4 本地文件增量算法

1. 使用文件规范路径和文件标识（大小、创建时间或 inode 等等）识别文件。
2. 从 `next_offset` 读取完整行；offset 必须按字节而不是字符记录。
3. 若最后一行未换行，保留为残片，下次继续，不得当作坏行。
4. 每行先解析外层 EventEnvelope，再按 schemaVersion 和 eventType 验证 payload。
5. 合法行追加到本批次不可变 Landing 文件；非法行写隔离文件和索引。
6. Landing 写入、统计和文件明细成功后才推进 checkpoint。
7. 进程崩溃后重跑，依靠 eventId 去重和批次幂等保证至多产生可识别重复，不丢数据。

### 10.5 Flume 首期方案

Flume 负责“将外部滚动事件文件稳定搬运到 Landing”，不负责业务清洗。推荐 Source 使用 Taildir 或 Spooling Directory，Channel 首选 File Channel，Sink 写 HDFS 或本地 Landing。

平台需要管理：配置模板、目标 URI、agent 状态、最近心跳、写入路径和批次发现。平台不必把 Flume 嵌入 JVM；可启动外部进程或只连接已部署 agent。

### 10.6 DataX 后续方案

DataX 适合从商城关系库同步维度和订单快照。增量水位线优先使用：

```text
update_time >= start_time AND update_time < end_time
```

只用 `id > last_max_id` 会遗漏旧行更新。水位线只有在目标落地、行数对账和质量校验都成功后才推进。DataX 数据也必须进入 Landing/ODS，不允许直写 DWD 或 MySQL 指标表。

### 10.7 采集验收

- 正常、重复、坏行、半行、文件追加、文件轮转均有测试。
- 暂停后恢复不丢行；重复行能被识别和统计。
- `record_count + quarantine_count + parse_error_count` 可与来源读取行数对账。
- 每个 Landing 文件都能追溯 connector、batch、source file、offset 和 checksum。

`LandingStorage` 负责不可变原始数据的保存，不承担 Hive 表逻辑。已有 `LocalLandingStorage` 和 `HdfsLandingStorage`，应统一返回 `LandingObject`：URI、size、checksum、recordCount、createdAt、batchNo。


## 12. Hive 数仓数据模型

### 12.1 分层原则

| 层 | 保存内容 | 可否被页面直接读取 |
|---|---|---:|
| Landing | 原始事件文件，不可变 | 否 |
| ODS | 原样结构化、增加审计字段 | 否 |
| DIM | 用户、商品、日期、地区、指标字典 | 否 |
| DWD | 去重、清洗、状态归并后的明细事实 | 否 |
| DWS | 可复用的主题汇总 | 否 |
| ADS | 面向具体分析场景的应用指标 | 仅故障/管理查询；正常页面从指标库读 |

### 12.2 ODS 表

| 表 | 粒度 | 主要字段 | 来源事件 | 分区 |
|---|---|---|---|---|
| `ods_user_event` | 一条用户事件 | envelope + user_id、age_group、city_level、member_level、register_time、source_file、batch_id | user_registered | dt/hour |
| `ods_product_event` | 一条商品事件 | envelope + product/category/brand/price/cost/status | product_created、product_updated | dt/hour |
| `ods_behavior_event` | 一条行为事件 | envelope + user/product/session/behavior/channel | behavior | dt/hour |
| `ods_trade_event` | 一条交易或库存事件 | envelope + order/user/payment/refund/product/amount/status/items | order/refund/stock 系列 | dt/hour |

ODS 算法只做：JSON 解析、类型路由、强制类型转换、审计字段补充和分区写入。业务状态判断、订单金额归并和用户画像不能提前塞到 ODS。

### 12.3 DIM 表

| 表 | 粒度 | 主要字段 | 更新规则 |
|---|---|---|---|
| `dim_user` | 用户×快照日 | user_id、年龄段、城市等级、会员等级、注册时间、source_batch_id | 同 user_id 按 event_time 取最新合法事件 |
| `dim_product` | 商品×快照日 | 商品、分类、品牌、价格、成本、状态、source_batch_id | 只接受商品建档/更新事件，库存事件不能创建商品 |
| `dim_date` | 日期 | 年月日、周、季度、星期、是否周末 | 预生成并覆盖分析日期范围 |
| `dim_region` | 模拟地区/城市等级 | region_code、name、city_level | 静态版本化配置 |
| `dim_metric` | 指标定义 | code、name、formula、grain、time_field、dimensions、version | 从 MySQL `metric_definition` 同步 |

第一版采用每日全量快照维度，论文中说明这是 SCD Type 1/快照折中；若后续需要追踪价格历史，再增加生效时间与失效时间实现 SCD Type 2。

### 12.4 DWD 表

| 表 | 粒度 | 主要字段 | 核心算法 |
|---|---|---|---|
| `dwd_user_behavior_detail` | 去重后一条行为 | behavior_id、user/product/category、type、event_time/hour、city、channel、session、batch | eventId 去重、枚举校验、维度补全 |
| `dwd_order_detail` | 订单×商品 | order/user/product/category、数量、单价、折扣、金额、最终状态、支付/退款/净额、标志 | 订单事件状态归并、items 展开、退款去重 |
| `dwd_reject_record` | 一条拒绝数据 | reject_id、source_table、reason、raw_payload、reject_time | 汇总清洗阶段坏数据 |

#### 订单状态归并

对同一 `order_id`：

1. 先按 `event_id` 去重；同一事件只保留一条。
2. 按 `event_time`、`ingest_time`、`event_id` 稳定排序。
3. 使用有限状态机接受合法跳转，非法跳转进入 reject。
4. `order_created.items` 展开为商品行，并验证行金额和订单总额。
5. `order_paid` 按支付标识去重，确定 `paid_at`、`paid_amount` 和 `final_paid_flag`。
6. `refund_completed` 按 refund_id 取最新完成事件并汇总；退款不得超过实付。
7. `net_paid_amount = paid_amount - refund_amount`。
8. 完全退款设置 `final_refunded_flag=1`；部分退款单独保留退款额，不等同完全退款。

### 12.5 DWS 表

| 表 | 粒度 | 主要内容 |
|---|---|---|
| `dws_user_behavior_day` | 用户×日 | pv、收藏、加购、购买、搜索、活跃小时数 |
| `dws_behavior_funnel_day` | 日×分类×渠道 | 浏览/意向/下单/支付用户数及转化率 |
| `dws_product_behavior_day` | 商品×日 | pv、uv、收藏、加购、支付件数 |
| `dws_product_sale_day` | 商品×日 | 销量、销售额、买家数 |
| `dws_trade_day` | 平台×日 | 支付订单、买家、GMV、退款、净销售、客单价 |
| `dws_user_trade_period` | 用户×观察期 | 最近购买日、有效订单数、消费额、周期 |
| `dws_region_sale_day` | 地区×日 | 买家、订单、销售额 |

所有 count distinct 口径必须在指标字典中明确对象是 user、order 还是 event；DWS 不能混用自然日和到达日。

### 12.6 ADS 表

| 表 | 页面/用途 | 关键字段 |
|---|---|---|
| `ads_operation_overview` | 运营总览 | pv、uv、dau、order_count、sale/net_sale、AOV、refund_rate、snapshot_id |
| `ads_behavior_funnel` | 转化漏斗 | stage、user_count、conversion_rate、overall_buy_rate |
| `ads_active_trend` | 活跃趋势 | dau、behavior_count |
| `ads_hot_product` | 热门商品 | product、heat_score、pv/fav/cart/buy、rank |
| `ads_product_conversion` | 商品转化 | product、pv_users、buy_users、conversion_rate |
| `ads_sale_trend` | 销售趋势 | order_count、buyer_count、sale_amount、net_sale、AOV |
| `ads_category_sale` | 分类结构 | category、sale_count、sale_amount、amount_ratio |
| `ads_region_sale` | 地区结构 | region、buyer/order_count、sale_amount |
| `ads_user_profile` | 用户分群 | R/F/M、value_group、activity、偏好、生命周期、版本 |
| `ads_data_quality` | 质量大盘 | rule、检查数、错误数、错误率、阈值、是否通过 |

当前 Hive DDL 的 `ads_sale_trend` 尚缺 `net_sale_amount`，`ads_region_sale` 尚缺 `order_count`；应与 DWS、MySQL 物化表和页面契约对齐后统一补齐。

## 13. 指标定义与算法

`metric_definition` 是唯一权威。Spark SQL、MySQL 字段、页面文字、AI 语义目录和论文公式都必须引用同一个 `definition_version`。

### 13.1 基础指标

| 指标 | 公式 | 时间字段 | 特殊规则 |
|---|---|---|---|
| PV | `count(behavior_type='view')` | behavior.event_time | 不能统计收藏、加购等全部行为 |
| UV | `count(distinct user_id where view)` | behavior.event_time | 匿名用户需单独定义，首期可排除 |
| DAU | 当日任一有效行为的去重用户数 | behavior.event_time | 明确有效行为集合 |
| 支付订单数 | `count(distinct order_id where final_paid_flag=1)` | paid_at | 取消单不计 |
| GMV | `sum(paid_amount)` | paid_at | 完全退款仍先计入 GMV |
| 净销售额 | `GMV - sum(completed refund amount)` | paid_at/退款回溯 | 可为 0，不应为负 |
| 客单价 | `GMV / 支付订单数` | paid_at | 分母 0 返回 null |
| 退款率 | `发生完成退款的订单数 / 支付订单数` | paid_at | 部分/全部退款都算退款订单 |
| 复购率 | `有效支付订单数>=2的用户 / 支付用户` | 观察期 | 是否排除完全退款需在版本中固定 |

当前已发现两处口径冲突，必须在 R7 开始前修复：

1. 指标字典退款率口径会得到 3/5，而现 ADS SQL 只统计完全退款得到 1/5。应以字典为准；如需要“全额退款率”，新增独立指标，不能偷换 `refund_rate`。
2. 指标字典 PV 只计 view，现某 ADS 计算曾把 14 条全部行为当 PV；应改为 view 行为 7 条，并加回归测试。

### 13.2 漏斗

首期使用宽松漏斗，即各阶段在同一时间窗内按用户去重，不强制同 session 严格依次发生：

```text
view_users   = 浏览用户数
intent_users = 收藏或加购用户数
order_users  = 创建订单用户数
pay_users    = 支付成功用户数

intent_rate = intent_users / view_users
order_rate  = order_users / intent_users
pay_rate    = pay_users / order_users
overall_buy_rate = pay_users / view_users
```

若后一阶段人数因跨期数据大于前一阶段，不应静默截断。应显示数据说明，或为严格漏斗另建算法版本。

### 13.3 商品热度

建议公式：

```text
heat = 1*ln(1+PV) + 2*ln(1+收藏) + 3*ln(1+加购) + 5*ln(1+支付件数)
```

对数可降低爆款量级对排行的绝对支配。权重必须保存在规则版本中；排行使用 `row_number(order by heat desc, buy desc, product_id asc)` 保证确定性。

### 13.4 RFM

观察期建议 30 或 90 天：

- R：截止日距最近有效支付日的天数，越小得分越高；
- F：有效支付订单数，越大得分越高；
- M：净消费金额或 GMV，首期必须选择一种并固定版本；推荐净消费金额。

采用五分位数打分。数据量过小导致分位点重复时，使用带稳定排序的 `ntile(5)`，并在样本少于阈值时标注“仅演示”。按 R/F/M 相对中位数划为八类：重要价值、重要发展、重要保持、重要挽留、一般价值、一般发展、一般保持、一般挽留。

### 13.5 异常检测

第一阶段用可解释统计方法，不必上复杂机器学习：

- 数据量至少 14 个历史点时计算 z-score；
- 非正态或有极端值时优先使用 IQR：低于 `Q1-1.5*IQR` 或高于 `Q3+1.5*IQR`；
- 同时设置业务绝对阈值，避免方差过小导致微小波动报警；
- 异常只代表偏离历史，不等于因果结论。

输出必须含 metricCode、当前值、基线窗口、均值/中位数、偏差、规则版本、严重度和 snapshotId。

## 14. Spark 作业模块

### 14.1 作业注册表

`JobRegistry` 是作业代码到实现的唯一映射。建议将作业分配如下：

| stageCode | jobCode | 目标 |
|---|---|---|
| `INIT_SCHEMA` | `lsi` | 本地/测试 schema 初始化 |
| `LOAD_ODS` | `odl` | Landing→4 ODS |
| `BUILD_DIM` | `dmb` | 用户/商品/日期/地区维度 |
| `BUILD_DWD` | `bdw`、`tds` | 行为明细、订单明细与拒绝表 |
| `BUILD_DWS` | `usw` | 7 张 DWS |
| `BUILD_ADS` | `fna` 等 | 10 张 ADS 临时快照 |

现有 8 个注册作业需在指导实现时逐一写入“输入表、输出表、分区、必要参数、结果统计”，不能靠作业名猜测。

### 14.2 JobArgs

必需参数：jobCode、runtimeProfileId/version、pipelineRunId、stageCode、businessDate、windowStart/windowEnd、landingUri、warehousePrefix、outputSnapshotId、attemptNo。可选参数：sourceBatchId、rebuildPartitions、dryRun。

参数解析必须：未知参数报错、缺必填项报错、日期格式严格校验、日志中屏蔽凭据。

### 14.3 JobResult

每个 Spark 作业最后输出一行机器可解析 JSON：

| 字段 | 含义 |
|---|---|
| status | SUCCESS/FAILED |
| externalJobId | 本地 pid 或 YARN applicationId |
| jobCode/stageCode | 作业与阶段 |
| inputRecords/outputRecords/rejectRecords | 对账计数 |
| outputPartitions | 真实写入分区列表 |
| outputSnapshotId | ADS 快照 |
| startedAt/finishedAt | 时间 |
| logUri | 完整日志位置 |
| errorCode/errorMessage | 标准错误 |

`JobResultParser` 只能解析带固定前缀的最终结果行，不能把普通 Spark 日志误认为结果。

### 14.4 分区幂等协议

当前 SQL 直接覆盖正式分区，尚不能证明“质量失败不污染正式表”。应改成：

1. Spark 写 `{table}__staging/snapshot_id={snapshotId}/dt={dt}` 或临时表分区。
2. 作业结果记录临时路径、行数、checksum/统计摘要。
3. 质量模块只检查临时结果。
4. 全部阻断规则通过后，用 Hive 元数据分区交换或受控 rename 发布到正式分区。
5. 发布动作必须幂等：相同 snapshotId 重试不产生第二份正式数据。
6. 发布失败保留旧正式分区；临时分区标记 FAILED，按保留期清理。

对于不支持原子 rename 的远程对象存储，后续使用“版本路径 + 元数据指针”而非覆盖文件。

## 15. R6 真实流水线详细实施

### 15.1 执行记录数据结构

| 表 | 粒度 | 必要字段 |
|---|---|---|
| `pipeline_run` | 一次业务流水线 | idempotency_key、profile/version、pipeline_code、business_time、source_version、attempt、status、trace_id、error |
| `pipeline_stage_run` | 一次运行的一个阶段 | run_id、stage_code、status、records、started/finished、error |
| `spark_job_run` | 一个真实 Spark 作业 | run_id、stage、job_code、submitter_type、command_digest、external_job_id、input/output、log_uri、status、error |

一个阶段可能包含多个 Spark 作业，因此 `spark_job_run` 才是 externalJobId 的权威来源。`pipeline_stage_run.external_job_id` 应废弃或只保存“作业组 ID”，不能只保存最后一个作业 ID 造成证据丢失。

### 15.2 当前具体问题

- `SparkStageExecutor` 已实现并有测试，但生产 `PipelineService` 尚未注入并调用。
- `PipelineService` 仍直接读取 accepted JSON，在 Java 内用 `MetricCalculator` 计算，并以 `source=local-calculator` 发布。
- DWS/ADS 阶段仍存在占位计数，不能代表 Hive 表实际写入。
- 生产事件白名单仍有旧名称，与 12 类正式事件契约冲突。
- 执行器出现某个作业失败时仍可能继续后续作业，必须改为依赖阶段 fail-fast。
- JVM 重启后的 PENDING/RUNNING 恢复尚不完整。

### 15.3 建议改造顺序

#### R6-9：统一事件契约

- 删除 `PipelineService` 私有旧白名单，调用 `EventContract`/`EventContractValidator` 的统一定义。
- 为 12 种 eventType 建参数化测试，确保 ODS 路由与校验器一致。
- 未知类型统一 `UNKNOWN_EVENT_TYPE`，不得悄悄跳过。

#### R6-10：提交器工厂

- 新增 `JobSubmitterFactory`，输入不可变 RuntimeProfileSnapshot。
- LOCAL 返回 `LocalProcessSparkSubmitter`；REMOTE 返回 `SshSparkSubmitter`；未来 Livy 是新实现。
- 工厂只负责构造，不处理阶段 DAG。
- 每次提交先插入 `spark_job_run=PENDING`，提交成功后立即落 externalJobId。

#### R6-11：生产编排接线

- `PipelineService` 只做状态机与阶段编排，不再解析 JSON 或计算指标。
- 将 `SparkStageExecutor` 注入生产服务。
- 每个阶段从配置表/注册表获取 jobCode 列表。
- 作业失败立即将当前 stage 和 run 标为 FAILED，后续依赖阶段保持 PENDING/SKIPPED。
- 所有状态更新使用独立短事务；外部 Spark 运行期间不能持有数据库长事务。

#### R6-12：真实输出证据

- 计数从 JobResult 和 Hive 分区统计取得，禁止使用固定数或输入数冒充输出数。
- `output_partitions` 推荐单独表或 JSON 字段保存，至少包括表、dt、snapshotId、rowCount、path。
- 日志 URI 必须真实可访问；本地进程日志文件名包含 runId、stage、jobCode、attempt。

#### R6-13：临时分区与质量阻断

- ADS 先写 staging snapshot。
- 质量检查读取 staging。
- 通过后发布 Hive 正式分区，再触发 R7 MySQL 发布。
- 质量失败测试需验证旧正式分区 checksum 和 ACTIVE snapshotId 均未变化。

#### R6-14：恢复

- 应用启动时运行 `PipelineRecoveryService`。
- 对 PENDING：确认没有已提交 job 后重新排队。
- 对 RUNNING：根据 externalJobId 查询进程/YARN；运行中继续监控，已成功补写结果，已失败落错误，不可确认标 UNKNOWN。
- 管理员 API 提供 resume、mark-failed、retry-from-stage，全部记录操作人和原因。

#### R6-15：小规模端到端验收

- 日常开发只用 55 条黄金数据或 100～1000 条事件。
- 单次只跑受影响阶段；未改 Spark SQL 时不重复全链。
- 每个里程碑再跑 1 次完整小链；R9 才做 10 万/100 万级性能。
- 这是优化开发速度的正式策略，不以反复大规模测试替代准确的小测试。

### 15.4 R6 完成条件

只有同时满足以下条件才能标“链路完成”：

- Controller 返回 taskId，查询能看到真实阶段变化。
- 每个 Spark 阶段至少有一个真实 `spark_job_run` 和 externalJobId。
- 生产服务不再引用 `MetricCalculator` 或读取 Landing JSON 算 ADS。
- Hive 中存在本次 snapshotId 的 staging 与正式分区证据。
- 质量失败时不发布正式 ADS/MySQL；重试只重跑失败阶段。
- 重启恢复测试通过。

## 16. 数据质量模块

### 16.1 质量规则结构

建议把规则定义从代码常量升级为 `quality_rule_definition`，至少包含：rule_code、name、layer、target_table、check_type、expression/template、threshold、severity、blocking、version、enabled。`data_quality_result` 保存每次实际运行的 check_count、error_count、error_rate、threshold、passed、detail、runId 和 snapshotId。

### 16.2 分层规则

| 层 | 规则示例 | 算法 | 是否阻断 |
|---|---|---|---:|
| Landing | JSON 可解析率 | parse_error/total | 超阈值阻断 |
| ODS | event_id 非空、schema 受支持 | 条件计数 | 是 |
| ODS | eventId 唯一率 | `count-count(distinct)` | 是 |
| DWD 行为 | user/product/type/time 合法 | 条件计数 | 是 |
| DWD 订单 | 行金额=数量×单价−折扣 | 绝对差小于 0.01 | 是 |
| DWD 订单 | 退款额≤实付额 | 条件计数 | 是 |
| DWD 状态 | 非法状态跳转 | 状态机拒绝数 | 是 |
| DWS | 汇总金额与 DWD 对账 | 差值/源金额 | 是 |
| ADS | GMV≥净销售≥0 | 边界条件 | 是 |
| ADS | UV≤PV、支付用户≤浏览用户 | 业务边界 | 视漏斗口径决定 |
| 发布 | staging 与 Hive ADS 行数一致 | count 对账 | 是 |
| 时效 | ingest_time-event_time | P95 延迟 | 警告/可配置阻断 |

### 16.3 阈值与严重度

- `ERROR/BLOCKING`：失败立即停止发布，例如主键重复、金额不平、退款超额。
- `WARN/NON_BLOCKING`：允许发布但页面显示黄标，例如迟到率略高。
- `INFO`：只记录趋势，例如空分类补为 UNKNOWN 的数量。
- 阈值必须版本化；改变阈值不得改写旧运行结果。

### 16.4 对账公式

采集层：

```text
来源读取行数 = Landing 合法行数 + quarantine 行数 + parse error 行数
```

交易层：

```text
sum(DWD paid_amount by paid_at day) = DWS sale_amount
sum(DWD refund_amount allocated to source order day) = DWS refund_amount
DWS sale_amount - DWS refund_amount = DWS net_sale_amount
```

发布层：

```text
Hive ADS 当前 snapshot 行数 = MySQL staging 当前 snapshot 行数
抽样 key 的字段值与 checksum/合计一致
```

质量检查本身失败或超时也必须视为发布失败，不能 catch 后返回空结果继续。

### 16.5 页面

运维页显示：本次 run、规则名、层次、检查数、错误数、错误率、阈值、严重度、通过与否、样例错误路径。普通运营页只显示数据更新时间和质量状态，不展示复杂 SQL。

## 17. R7 指标服务库与快照发布

### 17.1 三类数据源职责

| 数据源 | 账号权限 | 使用模块 | 事务管理器 |
|---|---|---|---|
| `metaDataSource` | 读写 `analytics_meta` | pipeline、ingestion、profile、auth、AI 日志、decision | `metaTransactionManager` |
| `metricPublishDataSource` | 读写 `analytics_metric` | 仅 MetricPublisher | `metricPublishTransactionManager` |
| `metricReadDataSource` | 只读 `analytics_metric` | 看板、AI SQL、决策取值 | 不允许写事务 |

当前 `PlatformDataSources` 只有主数据源和 metricRead，且指标 mapper 很可能仍绑定主数据源。必须为 metric 包单独配置 `SqlSessionFactory`/mapper 扫描和事务管理器。生产环境若只读指标库缺失，AI 查询必须失败，禁止回退到元数据库。

### 17.2 表所有权

| 数据库 | 应保留的表 |
|---|---|
| `analytics_meta` | ingestion、pipeline、quality、metric_definition、runtime_profile、spark_job_run、auth、AI audit、decision |
| `analytics_metric` | metric_snapshot、metric_value、所有 `ads_*_m` 与 staging 表 |

目前 meta 迁移中也创建了 snapshot/value，而 metric 库又有同名表。先新增兼容迁移明确新写入只进 `analytics_metric`，完成数据迁移和读写切换后再移除重复表；不能直接 drop 导致已有数据丢失。

`MetaFlywayInitializer` 当前只运行 `classpath:db/meta`。需增加独立 Metric Flyway initializer，使用指标发布账号执行 `classpath:db/metric`；两个迁移历史表和启动失败信息要分开。

### 17.3 快照数据结构

`metric_snapshot`：snapshot_id、profile_id、business_time、pipeline_run_id、status、version、definition_version、data_updated_at、published_at、source、failure_reason。

`metric_value`：snapshot_id、metric_code、metric_value、unit、period、dimension_json（可选）、definition_version、updated_at。唯一键应至少考虑 `snapshot_id + metric_code + period + dimensions`；当前只按 snapshot+metric 会挡住多日期/多维度值。

对页面固定宽表建议建立：

| MySQL 表 | 主键建议 | Hive 来源 |
|---|---|---|
| `ads_operation_overview_m` | snapshot_id+dt | ads_operation_overview |
| `ads_sale_trend_m` | snapshot_id+dt | ads_sale_trend |
| `ads_behavior_funnel_m` | snapshot_id+dt+stage | ads_behavior_funnel |
| `ads_active_trend_m` | snapshot_id+dt | ads_active_trend |
| `ads_hot_product_m` | snapshot_id+dt+rank_no | ads_hot_product |
| `ads_product_conversion_m` | snapshot_id+dt+product_id | ads_product_conversion |
| `ads_category_sale_m` | snapshot_id+dt+category_id | ads_category_sale |
| `ads_region_sale_m` | snapshot_id+dt+region | ads_region_sale |
| `ads_user_profile_m` | snapshot_id+dt+user_id | ads_user_profile |
| `ads_data_quality_m` | snapshot_id+dt+rule_code | ads_data_quality |

不要使用 `dt` 单列主键，否则新快照写入会覆盖旧快照，无法失败回滚或审计历史。

### 17.4 发布组件

建议职责拆分：

- `HiveAdsReader`：按正式 Hive snapshotId 和日期读取十张 ADS，返回强类型批次。
- `MetricStagingWriter`：批量写入指标库的 staging/带 snapshotId 正式历史表。
- `MetricPublishValidator`：行数、合计、关键 key、指标版本、空值和时间范围对账。
- `MetricSnapshotActivator`：在一个短事务内将 BUILDING→VERIFYING→ACTIVE，并将旧 ACTIVE→ARCHIVED。
- `MetricPublisher`：编排以上步骤，不计算业务指标。
- `MetricStore`：只读 ACTIVE 快照，不负责发布。

### 17.5 原子发布算法

1. 创建 `metric_snapshot(BUILDING, source='spark-ads')`。
2. 从 Hive 已发布 ADS 分区读取本次 snapshotId。
3. 批量写入所有 MySQL 物化表，所有行都带新 snapshotId。
4. 写 `metric_value` 中的统一核心指标。
5. 状态改为 VERIFYING，执行行数、金额、日期、版本对账。
6. 验证失败：snapshot 标 FAILED，保留旧 ACTIVE；新快照数据可保留审计或延迟清理。
7. 验证成功：在同一 metric 数据库事务中锁定 profile 当前 ACTIVE，将其改 ARCHIVED，再将新快照改 ACTIVE。
8. 看板查询先取一个 ACTIVE snapshotId，再在整个请求内固定使用，避免图表各读到不同快照。

### 17.6 当前代码处理

- `AdsMaterializer` 当前扩展的是 Java 内存指标，而不是 Hive ADS；应退役为兼容代码或改造成上述 Publisher。
- 它捕获“表不存在”后继续的做法必须删除；任何目标表失败都应使发布失败。
- `MySqlMetricStore.publish()` 的事务必须绑定 metricPublishTransactionManager。
- 成功快照的 source 必须是 `spark-ads`，不再接受 `local-calculator`。

### 17.7 存储可替换接口

定义 `MetricStore` 只读接口和 `MetricPublisher` 写入接口，按 `metric_store_type` 选择实现：

- 第一阶段：MySQL 实现完整可用；
- 第二阶段：Doris 实现，包括 Unique Key/Aggregate Key 模型、分区和批量导入；
- 后续：ClickHouse 只保留类型枚举、能力矩阵和接口，不写假实现；
- Hive 仍是数仓权威源，不因切换服务库而取消。

## 18. 分析服务与普通员工看板

### 18.1 数据边界

`AnalysisService` 和 `RfmService` 必须只调用 `MetricStore` 或指标库 mapper。当前读取 `landing/events`、直接查询 `mall_order` 的实现全部属于旧原型，应在 R7 切换后删除。

平台后端源码中出现以下模式应视为验收失败：

- 在分析包中读取 JSON 文件；
- 查询商城业务表；
- Controller 中现场聚合；
- 页面各自定义同名指标公式；
- AI 和图表使用不同 snapshotId。

### 18.2 页面模块

#### 运营总览

数据：PV、UV、DAU、支付订单、GMV、净销售、客单价、退款率、更新时间、质量状态。  
算法：当前值、上一周期值、环比 `(current-previous)/previous`；previous=0 时显示“不可计算”。  
交互：时间范围、环境、导出、查看指标口径；不暴露数据库或 Spark 参数。

#### 用户行为

数据：活跃趋势、行为构成、漏斗、渠道/分类维度。  
决策作用：识别流量下降、意向到下单流失、支付环节流失。  
注意：漏斗口径和观察窗口必须在页面可见。

#### 商品分析

数据：热度排行、商品转化、销量、销售额、库存覆盖天数。

## 19. AI 辅助体系

AI 不是独立装饰模块，而是横向增强分析、解释、问数、异常提示和决策草稿。它不能绕开数仓口径，也不能直接修改业务或批准决策。

### 19.1 四类能力

| 能力 | 输入 | 输出 | AI 的边界 |
|---|---|---|---|
| 指标解释 | EvidencePackage | 面向普通员工的摘要 | 不重新计算数字 |
| 异常归因提示 | 异常+维度分解 | 候选原因和核查步骤 | 只称“可能相关”，不宣称因果 |
| 自然语言问数 | 问题+语义目录 | 受限 SELECT 和结果解释 | 只查指标库白名单 |
| 决策草稿 | 证据+规则建议 | DRAFT task | 不自动审批、不自动执行 |

### 19.2 EvidencePackage

新增不可变结构，建议字段：

| 字段 | 内容 |
|---|---|
| evidenceId | 本次证据包唯一 ID |
| snapshotId | ACTIVE 快照 |
| definitionVersion | 指标口径版本 |
| period/currentPeriod | 当前分析区间 |
| comparisonPeriod | 对比区间 |
| facts | `metricCode,value,unit,period,evidenceRef` 列表 |
| comparisons | 当前/基线/变化量/变化率 |
| dimensions | 分类、渠道、地区、商品贡献 |
| anomalies | 规则、阈值、严重度、偏离值 |
| dataQuality | 质量状态、警告、迟到率 |
| lineage | Hive ADS 表、MySQL 表、pipelineRunId |

AI 生成的每个结论必须引用 evidenceRef；无法从证据包支持的内容不得输出具体数字。

### 19.3 固定模板优先

先由规则模板生成稳定结构：

1. 发生了什么；
2. 与上期相比变化多少；
3. 哪些维度贡献最大；
4. 数据质量是否可信；
5. 可采取哪些核查或行动；
6. 有哪些限制。

LLM 只负责把这些受控字段改写为自然语言。LLM 失败时返回模板结果，因此平台核心分析不依赖外部模型可用性。

### 19.4 自然语言转 SQL 流程

```text
问题分类
 -> 选择白名单主题表和字段
 -> 构造语义目录+示例+时间范围
 -> 模型/规则生成 SQL
 -> AST 安全校验
 -> 自动补 LIMIT/日期条件
 -> EXPLAIN 成本校验
 -> 只读账号执行
 -> 行数截断与结果解释
 -> 全程审计
```

### 19.5 AST 安全规则

当前 `SqlSafetyValidator` 对简单列有校验，但尚不足以覆盖表达式、WHERE、GROUP、ORDER、HAVING 与函数参数。第一阶段建议严格限制为单表 ADS 查询：

- 仅允许一个 `SELECT`；禁止 INSERT/UPDATE/DELETE/DDL/CALL/SET。
- 禁止多语句、注释绕过、子查询、CTE、UNION、JOIN、窗口外表。
- 禁止 `SELECT *`，所有列均须在语义目录白名单。
- 递归遍历 select、where、group、order、having 和函数参数中的每个 Column 节点。
- 函数使用白名单，例如 SUM、AVG、COUNT、MAX、MIN、ROUND。
- 强制真实日期范围，不能仅用 `MAX(dt)` 子查询；语义服务先取得允许的最新日期再作为参数注入。
- 自动添加 `LIMIT`，首期最多 200 行；限制扫描天数，例如 90 天。
- 执行 EXPLAIN，超过预估扫描阈值拒绝。
- JDBC 设置只读、查询超时和最大行数；账号只授予 `analytics_metric` SELECT。

`SemanticCatalog` 的 few-shot 示例必须与校验器规则一致。当前示例若含 `SELECT MAX(dt)` 子查询，应改为参数化日期示例。

### 19.6 AI 审计结构

`ai_query_history` 保存 userId、question、sql、tables、snapshotId、status、rows、elapsed、feedback、error。`ai_call_log` 保存 useCase、provider、model、promptVersion、token、耗时、状态和错误。不得记录数据库密码、完整会话 token 或未脱敏个人信息。

### 19.7 模型供应商适配

`LlmProvider` 保持 Java 接口；首期保留 `MockLlmProvider`、规则回退和 OpenAI-compatible HTTP 实现。密钥从环境/凭据服务读取。设置超时、重试上限、熔断和每日调用预算；同一请求用 traceId 防止多次扣费。

## 20. 决策中心

### 20.1 决策不是 AI 文本收藏夹

一条决策必须包含：证据、要执行的动作、目标指标、负责人、目标值、完成时间、风险、审批人和效果评价。没有目标指标的建议只能作为一般提示，不能进入效果评价。

### 20.2 数据结构补全

`decision_task` 在现有字段上建议补充：baseline_snapshot_id、definition_version、evidence_package_id、approval_note、execution_note。  
`decision_evaluation` 建议补充：baseline_snapshot_id、actual_snapshot_id、window_start、window_end、baseline_period_value、actual_period_value、sample_count、definition_version。

### 20.3 状态机

推荐统一为：

```text
DRAFT -> PENDING_APPROVAL -> APPROVED -> IN_PROGRESS -> COMPLETED -> EVALUATING
      -> REJECTED          -> CANCELLED
EVALUATING -> EFFECTIVE / PARTIAL / INEFFECTIVE / INSUFFICIENT_DATA
```

- AI 只能创建 DRAFT。
- 提交审批前校验 action、owner、target、window 和证据齐全。
- 创建者不能伪造 approvedBy；从 `CurrentUserHolder` 获取。
- REJECTED/CANCELLED 必须写原因。
- 完成不代表有效；完成后等待完整评价窗口再评价。
- 数据不足不得归类为无效。

### 20.4 效果评价算法

不能只拿一个快照点对比。应按等长窗口求平均或合计：

```text
baseline = 决策批准前 N 天目标指标聚合
actual   = 决策完成后、评价窗口 N 天目标指标聚合
```

对 UP 指标：

```text
improvement = (actual - baseline) / abs(baseline)
```

对 DOWN 指标：

```text
improvement = (baseline - actual) / abs(baseline)
```

baseline 为 0 或样本不足时返回 INSUFFICIENT_DATA。结果阈值示例：达到目标为 EFFECTIVE，改善但未达到目标为 PARTIAL，未改善为 INEFFECTIVE。阈值必须可配置并保存版本。

评价只能称“执行前后指标变化”，不能称“该措施导致变化”，因为本项目没有随机对照实验。页面应明确标注非因果评价。

### 20.5 决策模板

| 发现 | 建议动作 | 目标指标 | 主要风险 |
|---|---|---|---|
| 浏览高、加购低 | 优化详情、价格或卖点，进行小范围 A/B | cart_rate | 促销损害毛利 |
| 加购高、支付低 | 排查库存、运费、支付失败 | buy_rate | 只降价掩盖流程问题 |
| 热度高、库存覆盖低 | 补货或降低曝光 | stock_days | 需求预测误差 |
| 退款率异常 | 按商品/分类/原因核查 | refund_rate | 将部分退款和全额退款混淆 |
| 高价值用户活跃下降 | 定向关怀/召回 | repeat_rate/DAU | 过度触达 |

模板只是候选动作，必须由运营人员编辑和审批。

### 23.1 四层测试金字塔

| 层次 | 规模 | 触发时机 | 目标耗时 |

- 改指标口径：跑黄金对账 + 页面/AI 一致性。
- 改配置：跑 RuntimeProfile 连通性矩阵。

1. 使用独立 mock-mall 生成固定 seed 中型数据。
2. Flume 或文件适配器采集到 Landing。
3. 完整运行 ODS→DWD→DWS→ADS→质量→MySQL。
4. 对账事件数、订单数、金额、退款和核心指标。
5. 验证失败恢复、重复运行、服务重启和旧快照保护。
6. 验证所有角色、AI 安全攻击和决策闭环。
7. 在本地和至少一个远程/单节点环境运行同一黄金链。
8. 才执行 10万/100万级性能测试并记录资源、时长、吞吐。
9. 更新 README、部署手册、验收清单、论文图表与截图。

## 27. 扩展路线而非首期负担

### 27.1 Doris 第二阶段

在 MySQL R7 完成后实现 `DorisMetricStore` 与 `DorisMetricPublisher`。重点研究 Unique Key 模型、按日期分区、Hash 分桶、Stream Load、物化视图和并发查询。用同一接口与黄金数据对比 MySQL/Doris 查询延迟和导入吞吐，可形成论文实验章节。

### 27.2 ClickHouse 后续

仅保留 `CLICKHOUSE` 能力声明和接口设计。没有真实适配、测试和部署前，页面不得显示可选。后续可比较 MergeTree、分区键、排序键和聚合查询。

### 27.3 Kafka/实时链路

后续 `KafkaSourceConnector` 使用 topic/partition/offset checkpoint；只有 Landing 或下游提交成功后才提交 offset。若引入 Structured Streaming，要另设实时 ODS/DWD 和幂等 sink，不要把批处理假装实时。

### 27.4 Livy

远程 Spark 可增加 `LivyJobSubmitter`，将提交、状态、日志统一为 REST。它只替换提交器，不改 Pipeline DAG 和 Spark 作业业务逻辑。

可主张的创新性不是“调用了 AI API”，而是以下组合：

1. 可在本地、单机和远程集群之间切换的可配置大数据分析平台；

6. 独立可重复模拟数据源支持正常、业务场景和质量故障实验，但不污染主体系统边界。

## 29. 禁止模式

- 看板或 AI 直接查 Landing、ODS、DWD 或商城业务表。
- 在 Java 中重新计算本应由 Spark/Hive 产生的 ADS 指标。
- 生产 Pipeline 使用固定行数或 `source=local-calculator`。
- 质量失败后仍覆盖正式分区或激活新快照。
- 根据数据量自动随机选择 MySQL 或 Hive。
- 把 mock mall 当作分析平台内部模块或启动依赖。
- 以页面显示 SUCCESS 代替 run/job/partition/snapshot 对账。
- AI SQL 使用写账号或回退到元数据库。
- 通过请求头伪造 userId、approvedBy。
- 所有开发变更都重复跑大规模 Spark。
- 未实现的 Doris、ClickHouse、DataX、Kafka 在页面标记为可用。

## 30. 最终验收清单

### 架构

- [ ] 分析平台与模拟商城是不同进程、数据库、前端和构建产物。

## 31. 下一步唯一优先级

下一步不要先扩展功能，也不要先把目录大规模搬家。先按以下顺序完成：

1. 在文档与 issue 中确认主平台/模拟商城的硬边界；
2. 修复 R6 事件契约并把 `SparkStageExecutor` 真正接入生产 `PipelineService`；
3. 实现 Hive staging、质量阻断和正式分区发布；
4. 用 55 条黄金数据完成一次真实小链；
5. 再进入 R7 三数据源、Hive ADS→MySQL 原子发布和看板切换；
6. R7 验收后清理 `mall-simulator` 中的平台复制代码并拆分前端；
7. 最后完成 R8 AI/权限/决策与 R9 完整验收。

这条顺序的核心是：先让数据链真实可信，再让页面和 AI 消费同一份可信指标；外部模拟商城只为这条链提供可重复测试数据，不参与平台内部计算。
