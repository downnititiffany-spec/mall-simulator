# 电商用户行为分析系统项目整改实施指导书 V1.0

> 适用项目：基于 Spark 大数据平台和智能分析模型的电商用户行为分析系统  
> 对应设计文稿：项目设计文稿 V2.2  
> 文档性质：代码整改任务书、实现参考、验收标准  
> 当前原则：本文只指导修改，不提供完整业务代码；编码由项目开发者完成  
> 创建日期：2026-09-06

## 1. 文档目的

当前项目已经具备商城、自动生成器、Outbox、本地采集、Spark SQL、Vue 页面、AI 查询和决策状态机等代码，但这些能力尚未组成一条不可绕过的真实数据链路。最严重的问题不是页面数量少，而是页面显示的结果可能来自原始 JSON 或商城业务表，而不是 Hive 数仓和已发布的 ADS 快照。

本指导书用于把现有“多个可运行原型”整改成设计文稿要求的程序：普通员工通过 Web 完成数据生成、运行分析、查看指标、获取解释、建立决策和复盘效果；后台真实执行采集、Hive 分层、Spark 计算、质量校验和指标发布。

整改期间禁止继续用“增加一个页面”“增加一个状态名称”代替数据链路实现。每一项功能都必须能回答以下问题：

1. 输入数据来自哪里；
2. 数据经过了哪些表和任务；
3. 哪个组件拥有这份数据；
4. 失败时停在哪一层；
5. 页面展示的是哪个快照；
6. 如何通过测试证明没有绕开数仓。

## 3. 整改后的唯一正确主链路

```text
人工商城操作 / 场景化自动生成器
              │
              ▼
mall_business 业务事务 + event_outbox
              │
              ▼
OutboxPublisher → 滚动 JSON 源日志
              │
              ▼
LOCAL: LocalEventIngestor
SINGLE_NODE / REMOTE_CLUSTER: Flume
              │
              ▼
本地 Landing 或 HDFS Landing
              │
              ▼
Hive ODS：原始事件、版本、批次、源文件
              │
              ▼
Spark DWD：清洗、去重、标准化、交易状态合并
              │
              ▼
Spark DWS：用户、商品、交易、漏斗主题聚合
              │
              ▼
Spark ADS：页面和 AI 所需结果
              │
              ▼
数据质量门 + 快照发布
              │
              ▼
MySQL 指标服务库（首版默认）
              │
              ▼
固定看板 / AI 解释 / 决策中心 / 报告
```

以下路径全部视为错误捷径：

- 看板直接读取 `landing/events`；
- 分析服务直接查询 `mall_order`、`mall_user` 或其他商城业务表；
- Web 流水线只在 Java 内存中计算指标；
- 采集器写入 `landed`，流水线却继续读取源日志；
- 页面用一套 Java 口径，Spark 用另一套 SQL 口径；
- AI 查询商城明细库；
- 只检查阶段名称是 `SUCCESS`，不检查 Hive 表和 Spark 作业证据。

## 4. 整改范围和优先级

| 优先级 | 内容 | 不完成的后果 |
|---|---|---|
| P0 | 拆开商城和分析平台的数据边界 | 无法证明系统可以接入其他商城 |
| P0 | Web 流水线真实提交 Spark/Hive | 项目仍是 Java 本地统计演示 |
| P0 | 采集输出成为 ODS 唯一入口 | Flume、隔离、断点形同虚设 |
| P0 | 补齐订单、支付、退款和维度链路 | 销售、漏斗、RFM 和决策没有可信数据 |
| P0 | 修复 ADS 指标口径 | 页面与 AI 给出互相矛盾的答案 |
| P1 | RuntimeProfile 和环境适配器 | 项目仍与当前机器路径强绑定 |
| P1 | 异步任务、恢复和快照发布 | 大任务阻塞 HTTP，失败后无法可靠恢复 |
| P1 | 质量规则真正阻断发布 | 错误数据仍可替换当前指标 |
| P1 | RBAC、只读账号和 AI SQL 安全 | 审批可伪造，AI 可越权读取明细 |
| P2 | 普通员工页面和 AI 决策入口 | 技术功能存在但业务人员不会使用 |
| P2 | 可复现实验与论文证据 | 测试全绿不能支撑论文结论 |

必须按 P0 → P1 → P2 执行。P0 未通过前，不增加 Doris、DataX、Kafka、实时计算或新的 AI 花哨功能。

旧实现先标记为 `legacy-local-calculator`，在真实链路通过黄金数据验收后再删除。迁移期不要同时让新旧实现对外提供同一路径，否则测试无法判断页面实际使用了哪一套逻辑。

## 7. 数据库边界整改

### 7.1 首版允许共用一个 MySQL 实例，但必须使用三个数据库

| 数据库 | 所有者 | 允许内容 | 禁止内容 |
|---|---|---|---|
| `mall_business` | 商城 | 用户、商品、库存、购物车、订单、退款、Outbox | 平台流水线、AI 审计、指标快照 |
| `analytics_meta` | 分析平台 | 环境、任务、批次、质量、用户权限、AI 审计、决策 | 商城业务交易表 |
| `analytics_metric` | 指标服务 | 已发布快照、指标值、ADS 服务表 | 原始订单和用户明细 |

“独立数据库”不代表必须安装三个 MySQL。首版可以在同一个 MySQL 8.0 实例中建立三个 database/schema，但账号和权限必须隔离。

### 7.2 账号建议

| 账号用途 | 权限 |
|---|---|
| 商城应用账号 | `mall_business` 业务表读写 |
| 平台元数据账号 | `analytics_meta` 读写 |
| 指标发布账号 | `analytics_metric` 暂存表和快照表读写 |
| 指标查询账号 | 仅 `analytics_metric` 已发布 ADS 表 `SELECT` |
| Hive 只读账号 | 仅授权 ADS 数据集，只用于管理员应急和复杂分析 |

不得再给 AI 查询账号授予 `mall_business.*` 或整个 `analytics_meta.*` 的 `SELECT`。不得在只读数据源不可用时自动回退到主写数据源。

### 7.3 迁移步骤

1. 创建三个新的 Flyway migration 集合；
2. 把 `V1__init_mall.sql` 归到商城；
3. 把 ingestion、pipeline、metric、AI、decision、platform user 表归到平台；
4. 把 MySQL ADS 宽表归到指标库；
5. 修改实体和 Mapper 的数据源绑定；
6. 为三个数据源增加独立健康检查；
7. 删除平台服务对商城 `JdbcTemplate` 的注入；
8. 编写架构测试，禁止 `analytics-server` 引用商城 Mapper、Entity 或 JDBC 表名。

### 7.4 完成标准

- 停止商城后，历史看板、AI 查询和决策列表仍可访问；
- 停止分析平台后，商城仍能浏览、下单并继续写 Outbox；
- 在分析平台代码中搜索 `mall_order`、`mall_user`、`mall_product`，结果必须为零；
- 指标只读账号查询商城表必须得到权限拒绝。

## 9. 采集链路整改

### 9.1 目录职责必须统一

```text
source/events/                         OutboxPublisher 写入的源日志
landing/accepted/{batchId}/...         LOCAL 采集校验通过的数据
landing/quarantine/{batchId}/...       坏行、未知版本、契约错误
landing/manifests/{batchId}.json        批次清单
```

REMOTE_CLUSTER 中对应 HDFS URI。后续 ODS 只能读取 `accepted` 或 Flume 的 HDFS 落地区，禁止读取 `source/events`。

### 9.2 修复 LocalFileIngestor 偏移量

当前实现使用 `Files.size()` 得到字节数，却用 `BufferedReader.skip()` 跳过字符数。UTF-8 中文字段可能导致断点偏移错误。

修改要求：

- 使用基于字节偏移的 `FileChannel` 或 `RandomAccessFile`；
- checkpoint 保存字节偏移；
- 仅在一整行成功处理后推进偏移；
- 文件被截断或 inode/file key 变化时创建新版本，不继续使用旧偏移；
- checkpoint 唯一键至少包含 `runtime_profile_id + absolute_source_id + file_identity`，不能只用文件名；
- 数据落地成功和 checkpoint 推进必须具备可恢复顺序；
- 重复投递由 DWD 的 `event_id` 去重兜底。

### 9.3 批次 Manifest

每次采集完成生成清单：

```json
{
  "batchId": 1001,
  "runtimeProfileId": 1,
  "source": "local-file",
  "startedAt": "示例时间",
  "finishedAt": "示例时间",
  "files": 3,
  "acceptedRecords": 10000,
  "quarantinedRecords": 12,
  "acceptedBytes": 1234567,
  "schemaVersions": ["1.0"],
  "checksum": "示例校验值"
}
```

流水线的 `WAIT_LANDING` 必须等待一个状态为 `READY` 的 manifest，而不是判断目录里是否存在任意 JSON 文件。

### 9.4 Flume 配置必须补齐的细节

当前 HDFS 路径使用 `%{eventType}` 和时间占位符，但 Taildir Source 没有自动提供这些 Header。需要完成以下任一方案：

方案一，首版推荐：

- Flume 只按采集日期和小时落入统一 raw 目录；
- 设置 `hdfs.useLocalTimeStamp=true` 或显式时间 Header；
- ODS Spark 作业解析 JSON 中的 `event_type` 和业务时间；
- ODS 再按业务 `dt/hour/event_type` 写表。

方案二：

- 配置可靠的 interceptor，从事件中提取 `eventType`；
- 补充 timestamp Header；
- 为缺失 Header 配置失败通道或隔离目录；
- 用实际 Flume 进程验证路径，而不是只检查配置文件存在。

不建议用复杂正则长期解析完整 JSON。首版统一 raw 目录更容易验证和恢复。

### 9.5 采集验收

1. 生成 1000 条事件；
2. 采集 500 条后停止采集器；
3. 商城继续产生事件；
4. 恢复采集；
5. 最终 accepted 数量与有效源事件一致；
6. 重复投递同一批次，DWD 指标不增加；
7. 注入中文商品名，验证断点无错位；
8. 注入坏 JSON 和未知版本，确认只进入 quarantine；
9. 删除或移动源文件前确认 manifest 已 READY 且超过保留期。

## 10. Hive ODS 整改

### 10.1 ODS 必须接收全部首版主题

现有 `ods_user_event`、`ods_product_event`、`ods_behavior_event`、`ods_trade_event` 可以保留，但 ODS 加载任务必须覆盖：

| 事件类型 | ODS 去向 | 必须保留的核心字段 |
|---|---|---|
| user_created / user_updated | `ods_user_event` | event_id、user_id、画像字段、event_time、schema_version、batch_id |
| product_created / updated / status_changed | `ods_product_event` | product、category、brand、price、cost、status |
| inventory_changed | `ods_product_event` 或独立库存 ODS | product_id、available、reserved、change_type |
| behavior | `ods_behavior_event` | user、product、session、behavior_type、channel |
| order_created / cancelled | `ods_trade_event` | order、user、items、amount、status |
| order_paid | `ods_trade_event` | order、user、pay_amount、paid_at |
| refund_requested / completed | `ods_trade_event` | refund、order、amount、status、completed_at |

ODS 必须保留原始 JSON、源文件、批次号、采集时间和 Schema 版本，不能只保留解析后的业务字段。这样才能重放和审计。

### 10.2 新建或整改 Spark 作业

建议用一个入口 `OdsEventLoadJob`，内部按事件类型写四张 ODS 表。也可以拆成四个 Job，但必须共享统一解析器和错误输出。

任务步骤：

1. 从 `LandingStorage` 解析出的 accepted URI 读取；
2. 使用显式 StructType，不依赖自动推断生产 Schema；
3. 校验 `schema_version`；
4. 校验 `event_id`、`event_type`、`event_time`；
5. 把未知版本写入 ODS 隔离表或 quarantine；
6. 按业务日期和小时分区；
7. 写入临时分区；
8. 对比 manifest 数量；
9. 校验通过后覆盖或切换正式分区；
10. 返回 input、accepted、rejected、output 和分区信息。

### 10.3 ODS 验收

- 首版每一种事件类型至少有一条黄金记录；
- ODS 总输入数 = 各主题成功数 + 隔离数；
- 订单、支付和退款事件不能再被 `event_type='behavior'` 过滤掉；
- 重跑相同 `inputVersion` 后正式分区内容不重复；
- 页面流水线详情能查看 ODS 输入、输出和隔离数量。

- 行为类型白名单；
- UTC/本地时间统一；
- 商品和用户维度关联；
- 缺失维度使用明确的 unknown key，并记录质量告警；
- 重复和非法记录写 `dwd_reject_record`。

### 11.2 用户和商品维度

增加 `DimensionBuildJob`：

- 用户事件生成 `dim_user`；
- 商品和库存事件生成 `dim_product` 或独立库存快照；
- 首版可以采用每日全量快照；
- 每次更新保留生效日期和来源批次；
- 禁止 Spark 直接连接商城数据库补维度。

### 11.3 订单交易明细

增加 `TradeDwdJob`，把创建、支付、取消和退款事件合并为订单级明细。

至少处理以下状态：

```text
CREATED → PAID → COMPLETED
CREATED → CANCELLED
PAID → REFUND_REQUESTED → REFUNDED
```

订单明细中的商品项必须展开为一行一个 `order_id + product_id`，否则无法进行商品销售和分类销售分析。

需要明确：

- `order_amount`：订单优惠后的应付总额；
- `paid_amount`：实际成功支付金额；
- `refund_amount`：已完成退款金额；
- `net_paid_amount = paid_amount - refund_amount`；
- `final_paid_flag`；
- `final_refunded_flag`；
- 部分退款的处理规则；
- 多次退款事件按 refund_id 去重后汇总；
- 迟到支付和退款如何重算历史分区。

### 11.4 DWD 验收

- 同一 `event_id` 重复十次只产生一条有效明细；
- 两件商品的一个订单在订单商品明细中产生两行，但订单数仍为一；
- 取消订单不进入支付订单数和 GMV；
- 已支付后全额退款，GMV 保留支付额，净销售额为零；
- 退款事件迟到一天后，重算原订单业务日并生成新快照；
- DWD 的订单金额能够与商城事件中的金额对账，但分析平台不直接读取商城表。

## 12. DWS 和 ADS 整改

### 12.1 DWS 作业必须真实调用

当前 `DwsSql.tradeDay()` 只是被定义，未进入实际作业链。整改后 `DwsAggregateJob` 至少依次生成：

- `dws_user_behavior_day`；
- `dws_product_behavior_day`；
- `dws_trade_day`；
- `dws_product_sale_day`；
- `dws_behavior_funnel_day`；
- `dws_user_trade_period`；
- `dws_region_sale_day`。

不能再把 `order_users`、`pay_users` 和转化率硬编码为 `0/null`。

### 12.2 漏斗口径

首版采用文稿确认的宽松用户漏斗：

```text
view_users   = 当日发生 view 的去重用户
intent_users = 当日发生 favorite 或 cart_add 的去重用户
order_users  = 当日创建订单的去重用户
pay_users    = 当日成功支付的去重用户
```

阶段转化率：

```text
intent_rate = intent_users / view_users
order_rate  = order_users / intent_users
pay_rate    = pay_users / order_users
overall_buy_rate = pay_users / view_users
```

分母为零返回 `NULL`，不能返回 0 冒充“转化率为零”。各阶段独立去重时，人数不一定严格单调，页面必须显示“宽松口径”说明。

### 12.3 商品热度

热度公式可保留：

```text
heat = 1×ln(1+pv) + 2×ln(1+fav) + 3×ln(1+cart) + 5×ln(1+buy)
```

但 `buy` 必须来自订单商品明细中的有效支付，而不是行为表中的不存在的 `buy` 枚举。商品名称和分类必须关联 `dim_product`，不能继续返回 `商品-{id}` 和空分类。

### 12.4 ADS 输出

第一阶段至少完整生成：

- `ads_operation_overview`；
- `ads_sale_trend`；
- `ads_active_trend`；
- `ads_behavior_funnel`；
- `ads_hot_product`；
- `ads_product_conversion`；
- `ads_user_profile`；
- `ads_data_quality`。

分类销售和地区销售可以在第一条纵向链通过后补充，但不得在页面或 README 中提前标记完成。

### 12.5 指标日期格式

统一规则：

- Hive 分区 `dt` 使用 `yyyyMMdd`，例如 `20260905`；
- API 和 MySQL 指标库使用 SQL `DATE`，例如 `2026-09-05`；
- 转换只发生在发布适配器；
- AI 语义层只看到 SQL `DATE`；
- 禁止同一列有时存八位数字、有时存带连字符日期。

## 13. 流水线编排整改

### 13.1 接口必须异步

### 13.2 七阶段真实含义

| 阶段 | 必须执行的真实动作 | 必须保存的证据 |

### 13.4 重试规则

- 同一幂等键返回原 `taskId`；
- 失败重试增加 `attempt_no`；
- 已成功且输出校验仍有效的阶段不重复执行；
- 临时分区必须包含 runId/snapshotId，避免覆盖旧 ACTIVE；
- 配置错误不自动重试；
- 网络或 Spark 暂时失败可按次数退避重试；
- 质量失败必须人工查看，不自动跳过；

6. 列表查询通过 ApplicationService 完成。

## 14. 数据质量门整改

### 14.1 核心阻断规则

| 规则 | 首版阈值 | 处理 |
|---|---:|---|
| 金额对账差异 | 单笔绝对差 `< 0.01` | 超出即阻断 |
| event_id 去重后重复计数 | 指标中必须为 0 | 去重；异常率过高阻断 |
| 必填字段空值率 | `<= 0.1%` | 超阈值阻断 |
| 非法枚举 | 正式 DWD 为 0 | 进入 reject；超阈值阻断 |
| 未知 Schema 版本 | 正式 DWD 为 0 | 全部隔离，不自动丢弃 |
| ODS 数量守恒 | 输入 = 成功 + 隔离 | 不相等阻断 |
| DWD 与 DWS 核心金额 | 差异 `< 0.01` | 超出即阻断 |
| DWS 与 ADS 核心金额 | 差异 `< 0.01` | 超出即阻断 |

阈值最终应放入质量规则配置表，并记录版本。论文里必须说明哪些规则阻断，哪些只告警。

### 14.2 质量结果必须绑定

- runtimeProfile；
- pipelineRun；
- inputBatch；
- snapshot；
- table/partition；
- ruleVersion；
- sampleErrorUri。

### 14.3 页面要求

运维页显示：规则、检查数、错误数、错误率、阈值、是否阻断、样例和处理建议。普通员工只看到“数据已更新”或“数据质量未通过，继续显示上一版本”。

## 15. MySQL 指标发布整改

### 15.1 Hive 始终是权威来源

MySQL 只保存已发布、高频访问的 ADS 副本。发布流程：

```text
Hive ADS 临时分区完成
→ Hive 质量检查通过
→ 创建 BUILDING 快照
→ 读取指定 snapshotId 的 ADS
→ 写 MySQL staging 表
→ 校验行数、金额和日期
→ 事务切换 active_snapshot
→ 快照变 ACTIVE
→ 旧快照变 ARCHIVED
```

MySQL 发布失败时继续保留旧 ACTIVE，不自动切到 Hive。管理员可以在修复后对同一 Hive ADS 快照重新发布。

### 15.2 修复当前物化错误

- `buyer_count` 必须来自支付用户去重数，不能使用 `uv`；
- 漏斗 `conversion_rate` 必须写真实阶段转化率；
- 每张 ADS 服务表必须带 `snapshot_id`；
- `dt` 使用 DATE；
- 商品表必须带真实名称和分类；
- 发布逻辑不能从 Java `MetricDataset` 猜测缺失字段；
- 同一快照的多张表必须整体成功或整体回滚。

### 15.3 MetricStore 约束

固定看板只能依赖 `MetricStore` 或其上层 QueryService。不得访问：

- Landing；
- Hive ODS/DWD；
- 商城数据库；
- 本地 JSON；
- Mapper 拼装的临时口径。

## 17. AI 模块整改

### 17.1 AI 能力顺序

1. 固定指标解释；
2. 异常原因候选；
3. 行动建议草稿；
4. 报告摘要；
5. 推荐问题模板；
6. 受控 Text-to-SQL；
7. 第二阶段复杂 Spark/Hive 异步分析。

Text-to-SQL 不是 AI 模块的全部，也不应该是普通员工查询固定指标的首选路径。

### 17.2 EvidencePackage

AI 输入不得只有用户问题。建立证据包：

```text
question
userRole
selectedMetrics
metricDefinitions
filters
snapshotId
dataUpdatedAt
resultRows
comparisonWindow
qualityStatus
knownLimitations
```

AI 输出中的每个数值必须能在 `resultRows` 找到。找不到证据的内容只能写成“可能原因”，不能写成事实。

### 17.3 Text-to-SQL 安全整改

首版建议严格限制为单表 SELECT。既然产品需求不需要 JOIN，就直接禁止所有 JOIN、子查询、UNION、CTE 和任意函数扩展，降低风险。

校验顺序：

1. 只允许一条语句；
2. AST 根节点必须是 SELECT；
3. 禁止 JOIN、子查询、UNION、CTE；
4. 递归检查 SELECT、WHERE、GROUP BY、ORDER BY 和函数参数中的每个字段；
5. 检查唯一主表在 ADS 白名单；
6. 检查所有字段属于该表；
7. 强制时间范围；
8. 强制 LIMIT，最大 1000；
9. 在目标 MySQL 指标库执行 `EXPLAIN`；
10. 使用独立只读账号执行并设置超时；
11. 最多进行一次受控修复；
12. 保存完整审计但对页面隐藏敏感配置。

规则回退生成的 SQL 也必须经过同一个校验器，不能因为是内部模板就绕过安全链。

### 17.4 修复语义层矛盾

- 示例 SQL 不得包含校验器禁止的子查询；
- “最新日期”由应用先查询当前 ACTIVE 快照日期，再作为参数写入模板；
- 日期统一为 `yyyy-MM-dd`；
- 商品问题必须有商品 ADS 表，不能用销售摘要替代；
- AI 查询结果必须包含真实 snapshotId，不能长期返回 `unknown`；
- `timeRange` 必须实际参与查询，不能只用于解释文字。

### 17.5 模型不可用

模型不可用时：

- 固定看板继续运行；
- 推荐问题走固定查询模板；
- 页面明确标注“当前使用规则解释”；
- 不生成伪装成模型输出的复杂原因；
- 不影响采集、数仓、发布和人工决策。

## 21. 黄金纵向链路实施教程

这是整改时最先完成的工作。不要同时改全部页面。

### 第一步：准备最小黄金场景

固定 3 个用户、4 个商品和以下事件：

- 浏览 5 次；
- 收藏 2 次；
- 加购 2 次；
- 创建 3 个订单；
- 支付 2 个订单；
- 取消 1 个订单；
- 完成 1 笔退款；
- 插入 1 条重复事件；
- 插入 1 条坏事件。

人工写出预期的 PV、UV、DAU、订单数、支付人数、GMV、退款额、净销售额、客单价和漏斗人数。预期值文件不能调用生产计算代码生成。

### 第二步：只打通数据层

按顺序验证：

```text
Outbox 数量
→ accepted/quarantine 数量
→ ODS 各主题数量
→ DWD 有效和拒绝数量
→ DWS 数值
→ ADS 数值
```

此时不接前端，不接 AI。

### 第三步：发布一个销售 ADS

先只发布：

- 支付订单数；
- 支付人数；
- GMV；
- 退款额；
- 净销售额；
- 客单价。

验证 Hive ADS 与 MySQL 指标库完全一致，再接销售页面。

### 第四步：接一个销售页面

销售页只调用 `SalesAnalysisService`，后者只调用 `MetricStore`。页面显示 snapshotId、更新时间和口径。删除任何原始 JSON 读取后再次验证页面仍可用。

### 第五步：接入 Web 流水线

Web 创建 taskId，后台提交相同 Spark 作业，页面轮询状态。手工停止 Spark 或传错配置，页面必须显示真实失败，而不是七个假 SUCCESS。

### 第六步：扩展其他主题

顺序建议：

1. 漏斗；
2. 商品热度和商品转化；
3. 活跃趋势；
4. RFM 用户分层；
5. AI 证据解释；
6. 决策草稿和效果评价。

## 23. 验收脚本必须如何修改

旧验收只检查返回七个阶段和 `SUCCESS` 不够。新的最终验收必须同时检查：

1. 商城和分析平台是两个进程；
2. 使用不同数据库；
3. 生成器通过商城 Service 产生交易；
4. Outbox 排空；
5. 采集批次存在 READY manifest；
6. Pipeline API 返回 taskId；
7. 每个计算阶段存在非空 externalJobId；
8. Hive ODS 四主题均有数据；
9. DWD 行为、订单、用户和商品均有数据；
10. DWS 交易和漏斗不是硬编码空值；
11. Hive ADS 指标等于黄金答案；
12. MySQL ACTIVE 快照等于 Hive ADS；
13. 页面 API 与 MySQL 快照一致；
14. AI 查询相同指标与页面一致；
15. 质量失败时旧快照不变；
16. 非审核角色批准决策返回 403；
17. AI 只读账号查询商城表被数据库拒绝；
18. 停止模型服务后固定看板仍正常。

验收报告不得把 Mock LLM 的毫秒耗时写成真实模型时延。缓存命中性能和冷查询性能必须分开记录。

## 25. 常见错误和禁止事项
