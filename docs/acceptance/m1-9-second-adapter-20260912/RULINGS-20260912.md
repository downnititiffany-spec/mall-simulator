## 1. D-066（H1 处置）：**改规格**，不登记为残余

**问题**：`ed8c531` 改了三个 DTO 的**值语义**（读不到状态从「造 `UNKNOWN`」改为「落 `null`」），但 `ed8c531` 的变更面 12 个文件**不含指导书**，而指导书是权威顺序第 ② 位、第 251/255 行至今逐字要求 `UNKNOWN` ⇒ **代码与权威规格互相矛盾且无人登记**（缺陷类 D，高）。

**裁决：改规格。** 理由（三条，逐条可辩）：

1. **代码方向与项目硬约束一致，规格才是错的一方**：自造词会让「商城说的是它」与「生成器猜的它」落在同一字段里再也分不开（`ExternalOrder.java:14-20` 的 Javadoc 已逐字写明），属 A 类「不得发明证据」。
2. **登记为残余不消除矛盾**：评审已指出 W1 白名单只查 `= "UNKNOWN"` **是否出现**，**拦不住「规格要求它出现」**⇒ 下一位按指导书实现的人会（正确地）把刚修掉的 `UNKNOWN` 做回来 = **保证复发**。
3. **形式有先例**：同一文件第 260-262 行已用同款 append-only 补记修正过 `ExternalProduct.status` 口径 ⇒ 本项**不是新机制**。

**执行（含一次自我更正，如实记录）**：

1. **首次执行走错了载体**：总控最初直接在 `docs/项目完整实施指导书 V2.3.md` **末尾就地追加**勘误补记（708 → 719 行）。随后实测两条本仓规则后判定**不合规**并**已撤销**：① 指导书 §2.1.1 第 49 行逐字＝「已编号文稿**不得覆盖或在末尾持续追加新阶段内容**；每次需求、架构或执行基线发生**实质变化**，先备份当前文件，再生成一份**结构完整的新版本**」；② 看板 D-048 已把「指导书**不就地改**」立为裁决。本项含**新增实现要求**（第三缺口通道）⇒ 属实质变化 ⇒ 必须新版本。撤销用「按标记截断 ＋ 哈希自证」完成（还原后 sha256 逐字回到写前值 `104E1D61…`），**未使用任何 git 破坏性命令**。

## 2. D-067（H2 处置）：第三缺口通道，**规格先行**，且已实测零契约成本

**问题**：`SecondMallHttpAdapter.readCatalog` 为「报价读不懂」的商品准备了收集通道 `priceUnreadable`，但它**有收集无出口**：只在**整份目录都读不懂**时才抛异常（`:314`），**部分**缺价时该清单随局部变量消失（只在 `:813` 留 debug 痕迹），而被排除的 SKU **不进页、不进引擎缺口行、不进报告**。同函数内两条「读不懂就排除」通道的取证能力**不对称，方向恰好是「少说话」**（A 类「证据静默丢失」）。Javadoc `:782-783` 却承诺「被记进去的商品…**一定会被点名报出来**」。

**裁决：采纳评审的 (b) 方向 —— 给 `ProductPage` 增加第三缺口通道，并先改规格。**

1. **规格先行（硬约束 11）**：随 D-066 的补记一次性写清 `ProductPage` 的**三通道**语义（`unmappedStateWords` 原词／`stateFieldMissing` 字段缺失／**`priceUnreadable` 报价读不懂**），三通道并列上报。**先规格、后代码**。
2. **零契约成本已实测**：两缺口通道在 `contract-specs/*`、`web/*`、`report/*` **零命中**（事实 #7）⇒ 第三通道是**生成器侧词汇**（指导书第 242 行已写明「生成器侧实现词汇，不是跨程序契约」），**本项不动 `contract-specs/**`**。
3. **拒绝**「只把 Javadoc 改小以迁就实现」作为收口 —— 那等于把「证据静默丢失」固化成规范。Javadoc 必须与实现**同时**变为真。
4. **边界**：参考适配器 `ReferenceMallHttpAdapter.java:182` 的缺口恒空属**已知未实现**，本项**不得**声称参考适配器已上报缺口。
