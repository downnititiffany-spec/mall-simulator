## 3. 方法与证据级别

判据一律机器可算、可复跑，分两步：

1. **全仓标签普查（正面控制）**：扫描权威链内的全部 markdown（176 个文件；排除 `.git`/`node_modules`/`target`/
   `.verify` 与 `references/` 下的第三方样例项目），提取 `#{1,4} §?<编号>` 形式的编号标题，统计**每个标签出现在
   多少个文档里**。任何"该标签唯一指向某文档"的主张，必须对**全体文档**成立，而不是只对我最初挑的 5 个候选文档成立。
2. **逐锚点判定**：`R-A` = 该标签在全仓（权威链内）唯一 ⇒ 目标文档确定；`R-B` = 标签不唯一，但用锚点上下文
   （前后 60/90 字符内的反引号 token 与「」『』片段）在候选文档的 `L` / `L+1` 行上做内容命中，**且只有一个候选

## 6. 判据的两次自我更正（如实记录）

1. **"标签唯一 = 65 处"被全仓普查推翻**。第一轮只在 5 个候选文档里比标签，得出 65 处"唯一"，其中包含 §2.4/§2.5/§2.6
   等；扩到全仓后这些标签分别出现于 8/4/4 个文档，唯一性判定缩到 **30 处**。教训与 F-27 同类：**唯一/为零的结论必须在
   全体对象上做正面控制**。
2. **token 打分误命中第三方文档**。第一轮 R-B 有 1 处命中
   `references/sample-projects/text-to-sql/text-to-sql-main/README.md`——那是第三方样例项目，不是本项目权威链。
   已把候选集合限定为权威链（排除 `references/`）并复跑：R-B 由 19 → **18**，误命中消失。**token 打分必须限定在权威文档集合内**，
   否则会把无关文档当目标。

两次更正都发生在**写盘之前**，本轮没有任何契约文件被改。

## 7. 结论：为什么本轮不改写这 258 处锚点

- 258 处里只有 **48 处**能给出可复核的目标（文档 + 行），**210 处**连"指向哪个文档"都无法机械确定；
- 它们的共同病根是**跨文档引用时丢掉了文件名**（例如 `§2.4 L77` 实际指 `docs/contracts/event-contract.md` 的
  items 定义，见 `contract-specs/README.md` 的 Q5 条目），**不是** F-29 所说的统一行号偏移；
- 若按 F-29 的 +1 / +12 / +145 批量改写，会把**不可复核的引用写进契约**——这违反"未实测不写结论"；
- 且 `contract-specs/README.md` 自述「本目录是它们的机器可读投影，不是新的语义来源；两者不一致时以 markdown 文档为准」，
  契约当前状态为 `DRAFT`。锚点是**证据指针**，改错比不改更坏。

因此本轮**不动契约**，把问题登记为 **F-30**，并把处置留给裁决。

## 8. 处置方案（待裁）

- **方案甲（逐条补文件名）**：48 处机械可判定的先补（每个锚点写成「`docs/contracts/event-contract.md` §2.10 L146」），
  210 处人工逐条读锚点上下文与候选文档后补。优点：保留行号精度；代价：210 次人工判定，且**行号会随文档继续演进再次失效**。
- **方案乙（改锚点风格）**：统一为「文档名 + 节号」（可选带行号），并在 `contract-specs/README.md` 写入**新锚点必须带文件名**
  的规则 + 机器校验器（裸锚点计数必须为 0，或等于在册白名单）。优点：一次消除病根、可机器守卫；代价：丢失行号级精度，
  需要一次 `VERSION` 升版与全量替换。
- **建议**：乙为主、甲为过渡——先对 48 处机械可判定的补文件名（有证据、可复核），同时立乙的规则与校验器；210 处在
  规则落地时按"补文件名 + 节号"处理（不必逐条对齐行号）。
