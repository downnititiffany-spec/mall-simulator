## 4. 规格草案（要求，非实现）

> 编号 `P2-05-S*` 是本草案自定编号，**不是既有决策号**；总控裁定后应替换为其正式编号。

### P2-05-S1 重建必须显式、可拒绝

- 重建**不得**是默认行为。必须存在一个显式入口（V2.4 L666 指定由 `INIT_SCHEMA` 审计步骤执行），未携带该显式意图时，`LOAD_ODS` 走**非重建**路径。
- `INSERT OVERWRITE` 的**默认语义必须收紧**：现状「重跑即覆盖」是隐式重建，本行要求把它变为**受守卫的显式动作**。
- **不得静默 DROP**（L666 明文）。

### P2-05-S2 备份清单（Rq-2）

重建前必须产出可核对的清单，至少含：
1. **备份对象**：对应 warehouse 目录（L666 字面）；
2. **表数与行数**（L666 字面）；
3. **checksum**（L666 字面）；
4. 备份位置与可恢复性说明。

**开放点（须裁定）**：清单的**粒度**（整库 / 整层 / 单表 / 单分区）与**载体**（MySQL 表 / 文件 / 两者）。详见 §6 D-2、D-3。
**硬约束**：清单若落 MySQL 新表，需要**迁移号**；迁移号**只由总控分配**（见 §6 D-3）。

### P2-05-S3 限定 namespace（Rq-3）

- 重建作用域**只能**是当前源解析出的前缀（`WarehouseNamespace` 派生的库名集合）。
- 必须**显式复核**：重建目标库名前缀 == 当前源前缀；不等即拒绝。
- 复用既有机制：`JobCommandBuilder.java:123` 已按源下发 `--hiveDatabasePrefix`，`:126` 已并列下发 `--sourceSystem`，二者同源于 `RunSourceIdentity` —— **守卫应基于这两个已下发值做一致性复核**，不新增第二个前缀来源。
- **不得写死 `mock-mall`**（V2.4 L316）。
- 守卫必须能拒绝「前缀缺省落回 `dw`」的情形（与 D-071 的 `不设 DEFAULT` 同向）。

### P2-05-S4 审计（Rq-4）

- 重建全流程（意图、守卫结果、备份清单摘要、执行结果、失败原因）必须留审计。
- **优先复用 `operation_audit_log`**（D-035：不建第二张审计表；P1-03 `SourceAuditActions` 已有先例）。
- 须定义新建重建类**动作码**与**资源类型**；动作码一经冻结不得改名（`PermissionCode.java:15` 既有纪律）。
- 审计写入**失败不得静默**：若审计写不进去，重建应失败而非继续（否则等于无审计）。

### P2-05-S5 失败保旧 ACTIVE（Rq-5）

按 V2.4 L480 的四段式负向验收定义：

**「构造失败 → 流水线失败 → 不产生新 ACTIVE → 旧 ACTIVE 可读」**

- 失败时**不得**产生新 ACTIVE 快照（现状快照层已有此行为，见 R-11 的 `S20260901_38` 先例）。
- **旧 ACTIVE 可读**：必须**构造并验证**，不得默认假设。
- **本行的结构性风险（重要）**：ODS 无暂存隔离（R-02/R-05），一次重建会**原地覆盖** `dt/hour` 分区。
  因此即便快照层「旧 ACTIVE 快照记录仍可读」，其**下层物理数据可能已被覆盖**。
  → 本行必须回答：**「旧 ACTIVE 可读」是指元数据可读，还是端到端可重算可读？** 列入 §6 D-1。
- 未决语义：失败时是**保持旧 ACTIVE 不变**，还是**回滚到备份**？两种语义的证据面不同，必须择一。列入 §6 D-4。

### P2-05-S6 守卫的挂载点

- 建议挂载在既有 `INIT_SCHEMA` 阶段（`SparkStageExecutor.java:44` → `sci`）：它已存在、已被 stage evidence 审计、且位于 `LOAD_ODS` **之前**（`PipelineService.java:206`）。
- **但**：`INIT_SCHEMA` 属 `PipelineService.java`，而 V2.4 L659 与看板规定 `PipelineService` 属**热点文件**，且 C 类小项「不得占用公共契约、DB 迁移号、`PipelineService`、P1–P5 热点文件」。
  → **本行是否获准改 `PipelineService`/`SparkStageExecutor`，是开工的硬前置**。列入 §6 D-5。

## 6. 待裁决清单（**本泳道不自行裁定**）

### D-1（建议号，需总控裁定）「旧 ACTIVE 可读」的语义边界

**事实**：ODS/DWD/DWS 三层**无暂存隔离**，`INSERT OVERWRITE` 原地覆盖 `dt/hour` 分区；只有 ADS 有 `__staging/snapshot_id=S`。
**冲突点**：V2.4 L480 要求「旧 ACTIVE 可读」，但下层物理数据可能已被覆盖。

**须裁定**：「可读」是指
(a) **元数据可读**（`metric_snapshot` 行仍在、状态仍 ACTIVE、API 可返回），还是
(b) **端到端可读**（旧 ACTIVE 的指标值可被重新拉取、且与覆盖前逐值一致）？
若为 (b)，则本行必须同时解决 ODS 的隔离问题，**工程量与范围显著不同**，且可能与 P2-04/P2-06 交叠。

### D-2（建议号，需总控裁定）备份清单的粒度

整库 / 整层 / 单表 / 单分区？
- L666 字面只说「对应 warehouse 目录」+「表数/行数/checksum」，未给粒度。
- 粒度决定备份体积与恢复时间；ODS 为 `(dt, hour)` 分区，分区级备份在技术上最贴近「重建目标」，但 L666 写的是「目录」。
**须裁定**后写入施工单 A1。

### D-3（建议号，需总控裁定）备份清单的载体与**迁移号分配**

**事实**：真库**零**备份/清单类表；`operation_audit_log.before_digest/after_digest` 为 `VARCHAR(512)`，承载力有限。
`analytics-meta` 现存迁移至 **V18**；V18 头注释提到「删列是破坏性 DDL，另立任务，**预期号位 V19**」（该句是 P2-07 对**自己的**后续任务所言，**非**对本行的预留）。

**须裁定**：
1. 清单落 **MySQL 新表**（需新迁移号）还是**文件/仓库目录内清单**（不需迁移号）？
2. 若需新表：**迁移号只由总控分配**。本泳道**只提议、不指派**。可提议的候选是「V18 之后的下一号」，但**以总控分配为准**。
3. 若复用 `operation_audit_log`：512 字符的摘要列是否够放清单摘要，还是需要新列（新列同样是迁移）？

### D-4（建议号，需总控裁定）失败语义：保旧 ACTIVE 还是回滚？

- **保旧**：失败时不动旧 ACTIVE，接受「下层已被部分覆盖」的现状，只保证快照记录层不变。
- **回滚**：失败时从备份恢复被覆盖的 `dt/hour` 分区，使端到端回到失败前状态。

二者证据面完全不同。L480 字面只要求「不产生新 ACTIVE + 旧 ACTIVE 可读」，**未明说回滚**；
而 L666 要求「重建前必须备份……可核对」，**备份的存在暗示可恢复**。两条合读是否推出「必须能回滚」——**须裁定**。

### D-5（建议号，需总控裁定）是否获准改 `PipelineService` / `SparkStageExecutor`

**事实**：V2.4 L659 与看板规定 `PipelineService` 属热点文件；C 类小项「不得占用公共契约、DB 迁移号、`PipelineService`、P1–P5 热点文件」。
但 P2-05 的守卫若挂 `INIT_SCHEMA`，几乎必然触及 `PipelineService`。
**须裁定**：本行是否属 C 类小项？若属，则守卫必须落在 `spark-jobs` 侧（`INIT_SCHEMA` 作业内、`LOAD_ODS` 之前），不得改 Java 侧编排。

### D-6（建议号，需总控裁定）重建类审计动作码的命名与归属

`operation_audit_log.action` 现有域前缀风格为 `DECISION_*` / `USER_*` / `AI_QUERY` / `SOURCE_*`（P1-03）。
重建类动作码应取何名（如 `WAREHOUSE_REBUILD_*`）？资源类型取何值（`SOURCE_REGISTRY`？新增 `WAREHOUSE`？）？
**动作码一经冻结不得改名**（`PermissionCode.java:15` 纪律），故须先裁定再落地。

### D-7（建议号，需总控裁定）V18 已在真库执行这一事实如何登记

本泳道实测 V18 已执行（`installed_rank=17`，`2026-09-12 15:06:05`），而 `V18__source_warehouse_prefix.sql` 头注释自称「本轮未在真库执行」。
两处不一致。**本泳道只记录、不改写历史文档**。请总控决定是否需要一条补记/勘误（按 D-091「差异走补记/勘误 +『以此为准』，不改原文」的既定做法）。

### D-8（建议号，需总控裁定）单源库下的负向验收可行性

V2.4 L480 要求构造「流水线失败」的负向验收。当前真库只有 **1 个源**（`mock-mall`）。
负向验收是否可在单源下完成（构造失败不需第二个源），还是仍受 P2-04 所述的跨源样本限制？
**本行判断**：负向验收**不受**跨源限制（失败可人为构造），但「不得影响其他 source namespace」（L666）这一条**在单源库上不可证伪**。请总控确认这一验收盲区如何登记。
