## 2. 机制的精确解释（为什么「旧 jar 成功 / 新 jar 失败」，变量只有 jar）

`INSERT OVERWRITE TABLE … PARTITION (dt)` **未给分区值**（动态分区）时，Spark **仍把分区列
当作一个必须由 SELECT 提供的列**，且它**必须落在 SELECT 列表的最末位**。

因此本 SQL 的取值列表必须凑满 **23 项**（22 个普通列值 + `dt`）。

### 2.1 旧表（20 列）——`t.dt` 是**第 20 项**，位置**正确**（无错位）
旧表结构 = **19 个普通列 ＋ 动态分区列 `dt`**（共 20 列）。
旧 SELECT = **19 个普通值 ＋ `t.dt`**（共 20 项）。
⇒ `t.dt` 前面已有 **19 个普通字段**，它自己落在**第 20 项**，正好对上分区位。

| 序 | 旧表列 | 旧 SELECT 项 | 类型 | 结果 |
|---|---|---|---|---|
| 1…19 | 19 个普通列 | 19 个普通值（逐列对齐） | 同名同型 | ✅ 正确 |
| **20** | `dt`（动态分区列） | **`t.dt`**（STRING） | STRING→分区 STRING | ✅ **正确落入分区位** |

⇒ **旧形态没有错位，也没有写错值**。run 43 的 SUCCESS 是**正确写入**的产物
（其行数/分区数差异另见 §2.2 口径说明——**不得**用作数据损坏证据）。

> **撤回**：早先版本的本文件写「旧表第 19 列 `final_refunded_flag` 落入 `t.dt` ⇒ 静默写错」，
> **该说法不成立，已删除**。旧 SELECT 的第 19 项是 `t.final_paid_flag`/`t.final_refunded_flag` 本身，
> 第 20 项才是 `t.dt`；旧表第 19 列也恰是 `final_refunded_flag` ⇒ 逐列正确对齐。

### 2.2 新表（23 列）——`t.dt` 仍在第 20 项，但**第 20 个普通列已变成 `user_key`**
新表结构 = **22 个普通列 ＋ 动态分区列 `dt`**（共 23 列），
`user_key`/`product_key`/`category_key` 占第 **20/21/22** 普通列，`dt` 是第 23 列（分区）。

`ccc1dff` 把 3 个代理键 SELECT 项追加在 **`t.dt` 之后**，而 `t.dt` **位置未动**
⇒ 新 SELECT = 19 个普通值 + **`t.dt`（第 20 项）** + 3 个代理键（第 21/22/23 项）。
于是**按位置匹配**时：

| 序 | 新表列 | 实际落在该位的 SELECT 项 | 类型 | 结果 |
|---|---|---|---|---|
| **20** | `user_key` **BIGINT** | **`t.dt`（STRING）** | STRING→BIGINT | ❌ **不可安全转换 ⇒ 阶段失败** |
| 21 | `product_key` BIGINT | `$userSurrogate`（BIGINT） | BIGINT→BIGINT | ⚠️ 类型侥幸安全，但**语义错列** |
| 22 | `category_key` BIGINT | `$productSurrogate`（BIGINT） | BIGINT→BIGINT | ⚠️ 同上 |
| 23 | `dt`（分区） | `p.category_key`（BIGINT） | BIGINT→分区 STRING | ⚠️ 未及诊断即被第 20 列拦下 |

⇒ 报错 `Cannot safely cast user_key "STRING" to "BIGINT"` 的 **STRING 就是 `t.dt`**。
「位置错位」与「代理键」在**第 20 列**相撞，于是错误信息把两者显示在一起——
这正是最初把注意力误导向 `user_key` 表达式的原因。

**口径说明（撤回二）**：run 43（旧 jar，batch 42 / 1,000 行）与 run 47（新 jar，batch 43 / 55 行）
的**输入批次与行数不同** ⇒ 其**行数/分区数差异不得**用于论证旧版数据损坏。
本缺陷在旧 jar 上**根本不触发**（位置正确），故两者之间不存在「旧版静默写错」这回事。

## 3. `user_key` 取值表达式的定型（总控最怀疑的一条 → 实测**不是** STRING）

`TradeDwdJob.orderDetailInsertSql` 里 `user_key` 对应的 SELECT 项原文：

```sql
$userSurrogate AS user_key
-- 其中：
val src            = OdsLoadSql.sourceSystemLiteral(sourceSystem)          // 参数通道，非列
val userSurrogate  = SurrogateKey.toBIGINT(src, "user", "t.user_id")
```

经 `SurrogateKey.toBIGINT`（`SurrogateKey.scala:298`）出口：

```
toBIGINT = nullSafe(keyExpr(src,"user","t.user_id"), s"$src IS NULL", blankGuard(...))
nullSafe = CASE WHEN <guard> THEN CAST(NULL AS BIGINT) ELSE <expr> END
keyExpr  = keyFormula = GREATEST(cast(conv(<clearSignBit>, 16, 10) AS BIGINT), 1)
```

⇒ **`cast(… AS BIGINT)` 在内、`GREATEST` 在外，出口类型 = BIGINT**（这就是 P2-03-m 定型修复要防的形态）。
`clearSignBit` 的中间结果确实是 STRING（`lpad(hex(…),2,'0') || substr(…)`），但它**始终被外层 `cast AS BIGINT` 吞掉**。

**故「`user_key` 表达式被换成 STRING 形态」不成立。** 报错里的 STRING 另有来源 = `t.dt`（§2）。
