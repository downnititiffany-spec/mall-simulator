### 3.1 `spark-jobs/src/main/scala/com/graduation/analytics/sql/SurrogateKey.scala`

```diff
   def nullSafe(expr: String, guards: String*): String = {
     require(guards.nonEmpty, "nullSafe 至少需要一个 guard（无 guard 时不该调用 nullSafe）")
     val cond = guards.mkString(" OR ")
-    s"CASE WHEN $cond THEN NULL ELSE $expr END"
```

- 调用点仅 **2 处**，均在 `SurrogateKey` 内（`toBIGINT` :282、`literalSource` :301），`expr` 均来自

- 另加实测缺陷说明（缺陷 3 / P2-03-m）注释 **21 行**，记录 run 44/45 的报错原文与「显式定型」的修法与理由。

### 3.2 `spark-jobs/src/test/scala/com/graduation/analytics/SurrogateKeyVectorSupport.scala`

```diff
-       |     THEN NULL ELSE ${SurrogateKey.keyFormula(sourceExpr, entity, rawIdExpr)} END""".stripMargin
+       |     THEN CAST(NULL AS BIGINT) ELSE ${SurrogateKey.keyFormula(sourceExpr, entity, rawIdExpr)} END""".stripMargin
```

## 6. 下一步线索 → **已升级为「已实测的根因」**（本节为历史记录，结论见更新块）

> **【2026-09-12 21:26 更新 · 状态：假设 → 已证实】**
> 本节原登记的「假设，未经实测」**已被实测钉死为真根因**，并据此完成 P2-03-m2 修复：
> - **机制**：`INSERT OVERWRITE TABLE … PARTITION (dt)` 未给分区值时，Spark 仍要求 SELECT 提供该列，
>   且它**必须落在 SELECT 最末位**。**`ccc1dff` 之前没有错位**：旧表 = 19 个普通列 ＋ 动态分区列 `dt`，
>   旧 SELECT = 19 个普通值 ＋ `t.dt` ⇒ `t.dt` 前面已有 19 个普通字段，它是**第 20 项**，位置**正确**。
> - **`ccc1dff`(P2-03) 才引入缺陷**：新增 3 个 `BIGINT` 代理键并**追加在 `t.dt` 之后**（`t.dt` 位置未动）
>   ⇒ 按位置匹配时，第 20 个**普通列**已变成 `user_key`(BIGINT) ⇒ STRING 的 `t.dt` 落入其中。
>   STRING→BIGINT **不安全** ⇒ `CANNOT_SAFELY_CAST` ⇒ 阶段失败。
>   报错里的 STRING 就是 **`t.dt`**，不是 `user_key` 表达式。
> - **正确顺序**：19 个数据字段 → `user_key` → `product_key` → `category_key` → `t.dt`（与 DDL 列序一致）。
> - **撤回**：早先本块写的「旧表第 19 列 `final_refunded_flag`(INT) ⇒ STRING→INT 安全 ⇒ run 43 静默写错」
>   **不成立，已删除**：旧形态 `t.dt` 恰好落在分区位，写入是正确的；也**不得**用 run 43 与 run 47 的
>   行数/分区数差异论证数据损坏（两者输入批次不同）。
> - **实验 1**（复刻错位形态：19 个普通值后紧跟 STRING 的 `t.dt`，即 `t.dt` 为**第 20 项**，一次性表）
>   ⇒ **逐字复现**同一报错。
> - **实验 2**（同一 SELECT，**仅** `t.dt` 移到末位）⇒ 写入成功，读回 `EXPERIMENT2_OK 111 222 333 20260901 0`。
> - **m2 修复**后 **run 47 八阶段全绿**，`tdw` in18/out139/rej0，本地快照 `S20260901_47` 已产出。
> - **假设一（`nullSafe` 裸 NULL）＝ 已证伪（hypothesis-1 / FALSIFIED）**：必要但不充分；
>   修复保留的理由**仅限**「改善类型确定性」，**不得**作为根因。

### 6.1 原始线索记录（保留备查）

已排除 `nullSafe`。剩余最可疑点是 `TradeDwdJob.orderDetailInsertSql`（`:136-158`）的
**INSERT 无列名 + 与 DDL 列序的位置约定**：该 SELECT 把 `t.dt` 放在第 19 个取值，
而 DDL 里 `dt` 在**列尾**（第 23）；源码注释自称「位置必须对齐」。若位置不齐，
错位后落进 `user_key`（`BIGINT`）的取值可能是 STRING 列（如 `order_date`/`order_status`），
报错形态与实测**一致**。

当时状态：**假设，未经实测**（验证需把作业生成的 SQL 原文取出，或对比 `OUT_SCHEMA` 与 DDL 的逐列位置）。

**事后核对（订正原始线索的一处猜测）**：错位落进 `user_key` 的**不是** `order_date`/`order_status`，
而是 **`t.dt` 本身**——因为 `t.dt` 在 SELECT 里位于 `final_refunded_flag` 之后、代理键之前。
这一点已由实验 1/2 与 23 行位置对照表钉死。
