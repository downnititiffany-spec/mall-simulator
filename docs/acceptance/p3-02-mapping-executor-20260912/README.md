**硬性要求 1 规定：契约先行，不可跳过。** 先做规格盘点，再**恰好**裁定一种情形：

| 分支 | 条件 | 动作 |

**本轮裁定 = ②。** 依据见 `SPEC-CHANGE-DRAFT.md` §2 的 A1–A10。

### 1.2 为什么是 ② 而不是 ①（不回避的反方论证）

**反方（支持 ①）的最强证据**，本轮已**主动检索到并如实登记**：

- `docs/superpowers/plans/2026-09-11-mall-agnostic-platform-implementation.md:196-199` 有 P3-02 的**逐字规格**：流水线**顺序固定**、转换**白名单**、**六类原因码名**（`UNKNOWN_EVENT_TYPE`/`FIELD_REQUIRED`/`ENUM_UNKNOWN`/`TIME_PARSE`/`AMOUNT_PARSE`/`PROFILE_VERSION`）。
- 同书 `:225` 定义 dry-run 输出项；指导书 V2.4 `:346-350` 授权 `EventNormalizer` 的存在与职责；看板 `:229` 的验收口径「dry-run 覆盖率与**六类原因码**」与计划书**数目吻合**。

⇒ **「映射执行」这件事本身是被规格授权的**，不是无源之水。若只读到这里，会倾向 ①。

**正方（支持 ②）的决定性证据**：**骨架有、执行语法无**。规格定义了「按什么顺序做、允许用哪些变换、失败叫什么名字」，但**没有定义**「一条映射怎么算成功」所需的判据。逐条均有**互相矛盾的既成实例**：

| 缺口 | 决定性事实（原文见 `SPEC-CHANGE-DRAFT.md`） |
|---|---|
| **canonical 骨架无 owner** | 「规范字段是骨架」（设计书 `:122`）＋「`@keep` 表示字段不映射到骨架」（`:148`）⇒ 骨架是判据核心；但**骨架从未被枚举**，三处清单互不相等（契约 62 / 闸门 37 / 设计书 §4.4 是 ODS 9 列） |
| **`timePolicy.field` 命名空间矛盾** | `p1-03-probe-1.v1.json:28` 与 `fixture-b.v1.json:132` 是**源侧**名，`mock-mall.v1.json:117` 是**规范侧**名 ⇒ 三份画像**两种读法**；读错则时间解析全失败 |
| **`@keep` 键名与位置未定义** | 设计书 `:148` 只说「仅保留在 `payload_json`」，**未说键名**（`ext_coupon_code` 是否去前缀？）**未说位置**（信封层字段移入何处？）——而这是 **P3-01-a 断言 I4** 与设计书 **A4 断言**的判据核心 |
| **`missingField`/`nullValue` 旋钮不存在** | `missingField` 全仓 **0 命中**；`unknownField` 4 命中**全是画像 JSON 文本、生产代码 0 读者**；设计书 `:147` 只定义「键不存在」，**JSON `null` 与空串完全无定义** |
| **原因码无一覆盖字段级失败** | 计划书 6 个、D-116 冻结 7 个、P2-02 建议 7–8 个 ⇒ **三处数目与命名都对不上**，且**无码**可表达「字段存在但为 null」「字段类型不符」「时间格式歧义」 |
| **金额类型/单位无载体** | `fixture-b` 金额**全部是「分」**，规范侧不是；`fieldMapping` **没有** scale/unit/type 的位置；闸门对 **JSON 数字直接放行**、对 **JSON `null` 误报「类型异常」** |
| **同目标冲突无规则** | `fixture-b.v1.json` 有 **3 组同目标多源**（`status`×2／`quantity`×2／`amount`×2）；扁平 `fieldMapping` 的 key 不可能重复 ⇒ 重复 value **必然**发生，而规格**一句未提** |

⇒ **定性**：规格**有骨架、无执行语法**。缺口不在「要不要做」，而在「做出来的语义算不算合规」——A1–A10 每一项都会被验收反查，任一项由实施方自行拍定即构成「发明语义」。**故 ②。**
