## 1. D-111 —— 「统一 UTC」的落点（**本行最大未决点，已裁定**）

**冲突**：plan L153-157 要求 `event_time` 「按 source profile 的格式列表依次解析、**最终统一 UTC**」，而冻结契约 **D-053** 要求 `event_time` 保持 `STRING`。

**裁定：两案并存 —— 「原列一字不动 ＋ 追加派生列」，具体如下（不得改写 `event_time`）**

1. **`event_time`（源列）**：**保持 `STRING`、保持写入时的原始表示**。理由：①D-053 是冻结契约（权威 ①）；②原始表示的字节级溯源是 P2-02 全部负例与 C5 基线可复算的前提；③就地改写会同时违反 D-053 与 D-058。**禁止**「就地改成 TIMESTAMP」或「就地改写为 UTC 字符串」。
2. **新增派生列 `event_time_utc`（`STRING`，规范 UTC 表示）**：承载「统一 UTC」诉求。**只加列、不改列、不改既有分区**（沿用本项目既有的**加法扩列**惯例，与 ODS v2 的 D-054/D-056 处理一致）。
3. **分区口径（`dt`/`hour`）保持不变 = 业务时区 `Asia/Shanghai`**。理由：①现状 349 个 landing 文件、2,622,616 个 `event_time` 全为 `+08:00`（泳道 R1 全量扫描，正/负对照齐备）⇒ 业务时区即现状语义；②改成 UTC 分区等于**全量重分区**，越出本行范围且不可逆（属需单独裁决的结构性变更）。但**分区的取值来源必须从「位置切片」改为「由 `event_time_utc` 依业务时区换算」**（消除 `OdsLoadSql.scala:168-169` 的位置切片与 `DwdSql.scala:34` 的解析式两套口径并存）。
4. **源时区的唯一 owner ＝ `source_registry.timezone`**。理由：与 P2-07 已完成的「前缀所有权迁到 `source_registry`」同构（同一个「源级属性归源注册表」原则），且 `runtime_profile.timezone` 实测为**写死值**（`RuntimeProfileServiceImpl.java:72` 强制 `Asia/Shanghai`）⇒ 它不是真源。
   - `runtime_profile.timezone` 降为**运行时副本**（只读派生），实现时不得再作为解析依据。
5. **源时区缺失时的处置**：**显式兜底为 `Asia/Shanghai` 并留痕**（WARN ＋ 审计/DQ 记录），**不静默**、**不阻断**。理由：单源阶段真实值恒为 `+08:00`，阻断无收益；但静默兜底不可接受（「未实测不写结论」的反面）。此条**登记为已知折衷**。
6. **影响面登记**：`iso8601_time` 实测为 **1 处定义 ＋ 8 处 `$ref`**（覆盖 `event_time`/`ingest_time`/`register_time`/退款 `created_at`/`paid_at`/`cancelled_at`/订单 `created_at`/`completed_at`）⇒ 本行影响面是 **8 个时间字段**，不是只有 `event_time`；施工单须逐个字段写明是否同时产出 UTC 派生列。
7. **不得声称**：在 `event_time_utc` 未实现、未取证前，**不得**写「已统一 UTC」。
