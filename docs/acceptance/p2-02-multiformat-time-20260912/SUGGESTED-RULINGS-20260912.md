## D-101 `event_time`「最终统一 UTC」与冻结裁决 D-053（保持 `STRING`）如何相容

**问题**：plan L156 要求「`event_time` … 最终统一 UTC」，而 D-053 裁决 `event_time` 保持 `STRING`、D-058 裁决"只加不改"。二者字面冲突。

**选项**

| 选项 | 内容 |
|------|------|
| P-A | 就地改写 `event_time` 为 UTC 串（如 `…Z`／`+00:00`） |
| P-B | `event_time` 原样保留；**追加**派生列（如 `event_time_utc`）承载 UTC |
| P-C | 只校验 + 记录命中偏移，**不做换算**（最省，但不满足 plan L156 字面） |

**影响**
- P-A：改变既有 2,622,616 行的**可见取值**；下游以"源本地时间"为直觉的读数与既有夹具期望需全部重算；`dt`/`hour` 若维持源业务日则必须另存原值 ⇒ 有信息丢失风险；且与 D-053／D-058 冲突。
- P-B：满足 D-053／D-058／D-059；但需追加裁决"**哪一列是权威时刻**"（否则会新造出双 owner）。
- P-C：最小改动；但 plan 的 UTC 要求**落空**，须在看板明确记为"未实现"。

**本草案倾向**：P-B。**理由**：唯一同时满足冻结契约与 plan 的方案。
**不裁决的后果**：A2／A3 无法定接口（归一结果放哪一列），施工单只能停摆。

## D-102 `timePolicy.formats` 的取值语法与消费语义

**问题**：`formats` 今天**只被检查键是否存在**（`SourceProfileValidator.java:35-44`），内部完全不校验；且**没有任何生产代码读取它**（token 扫描 `timePolicy`：8 命中 = 1 键名 + 7 测试／夹具）。设计 §4.2 夹具里给的 3 个取值**混用两种词汇体系**（`ISO_OFFSET_DATE_TIME`／`EPOCH_MILLIS` 是 Java 风格 token，`yyyy-MM-dd HH:mm:ss` 是 pattern 字符串）。

**必须回答的 4 个子问题**

| 子问题 | 选项 | 影响 |
|--------|------|------|
| a. 元素允许什么 | ① 仅受控 token 闭集 ② 仅显式 pattern ③ 二者混用 | 影响校验器复杂度与"非法配置"失败态 |
| b. 是否要求首项自带绝对时刻（带偏移／epoch） | ① 要求 ② 不要求 | 不要求则"源时区缺失"只能在**运行期**逐行暴露，无法在配置期发现 |
| c. 顺序语义 | ① 从左到右、首个成功即用 ② 最长匹配优先 ③ 未定义 | 直接影响 **C1 的期望值**能否唯一确定 |
| d. 属契约还是运行时配置 | ① 契约级（版本化 + 评审） ② 运行时配置（可改不留痕） | 若②，则「源改了时间格式」这件事**不会留下证据**，与设计 §4.2 L149「画像文件受版本化与评审」矛盾 |

**本草案倾向**：a①（P2-02 只接受闭集，自由 pattern 延后）、b①、c①、d①。
**不裁决的后果**：C1「多格式接受」判据的期望值**无法唯一确定**（"依次解析"没有可判定的语义）⇒ 该项验收不可能客观。

## D-103 `dt`／`hour` 分区口径 + 源时区的唯一 owner

**问题 A（分区口径）**：分区 `dt`/`hour` 今天由**位置切片**得出（`OdsLoadSql.scala:168-169`），等价于"源字符串前 10 位 + 第 12-13 位"。若将来出现 `2026-08-31T17:00:00Z`，其 `Asia/Shanghai` 语义是 `2026-09-01 01:00`，而位置切片会给出 `dt=20260831`／`hour=17` ⇒ **业务日与小时双双错位**。

| 选项 | 影响 |
|------|------|
| ① 保持**源时区业务日** | 既有 55／1000 夹具期望与全部历史读数不变；UTC 时刻放派生列 ⇒ 与 D-101 的 P-B 自洽 |
| ② 改为 **UTC 日** | 全部既有 `dt` 分区语义位移；跨日边界行会换分区 ⇒ C7 基线必破 |
| ③ 位置切片不动，只加校验 | 风险仍在（非 `+08:00` 输入仍错分区） |

**问题 B（源时区 owner）**：今天有 **4 个可写点**（真库 `source_registry.timezone` varchar(64)、`runtime_profile.timezone` varchar(32)、`SparkSessionFactory.scala:14` 写死 `Asia/Shanghai`、`RuntimeProfileServiceImpl.java:72` 兜底 `Asia/Shanghai`）。

| 选项 | 影响 |
|------|------|
| ① `source_registry.timezone` 唯一权威 | 与"按源解析"同向；`runtime_profile` 降级为环境默认 |
| ② `runtime_profile.timezone` 唯一权威 | 与"按运行环境"同向；但换源时可能沿用旧值（D-037 已指出 `runtime_profile.source_id` 会被改写，是既有踩坑点） |
| ③ 维持 4 个可写点 | 就是今天的双 owner 状态 ⇒ 建议否决 |

**本草案倾向**：A①（保持源时区业务日）+ B①（`source_registry.timezone` 唯一权威，且 `SparkSessionFactory` 的写死值**只**用于 Spark 内部类型转换，**不参与业务语义**）。
**不裁决的后果**：A3 的分区派生无法定口径；且"统一 UTC"落地后必然产生**跨日错位**，属静默数据错误。

## D-104 ODS 装载的**静默丢弃**如何处置

**问题**：`OdsLoadSql.scala:181` 用 `WHERE … event_id IS NOT NULL AND event_time IS NOT NULL` 把坏行**静默丢弃**——不报错、不留痕、不进 quarantine、不进 DQ。plan L157 明列三类应「进入 quarantine」（未知版本／无法解析时间／缺 eventId）。

| 选项 | 影响 |
|------|------|
| ① 改为进入 quarantine（留痕） | 与 plan L157 字面一致；但**改变既有行为**（今天这些行是"消失"的），会影响既有链路行数读数 ⇒ C7 需重新基线 |
| ② 保留丢弃，但补记 DQ 计数（批次级） | 不改行级行为；但"哪一行被丢了"仍不可查 |
| ③ 改为进入 `dwd_reject_record` | 与"landing 解析"环节错位（该表语义是 DWD 清洗拒绝） |

**本草案倾向**：①。**理由**：静默丢弃是**四通道之外的第五种处置**，且是唯一不留痕的一种；plan L157 与看板 L221 都要求"负例"可查。
**不裁决的后果**：坏时间负例（C2）**无法验收**——行被丢了，没有可断言的隔离记录。

## D-105 四个通道的边界 + 死 SQL `rejectedSelect()` 的处置

**问题 A**：今天存在四条彼此不同的通道（`quarantine_record` 行级自由文本／`data_quality_result` 批次级规则／`dwd_reject_record` DWD 清洗／ODS `WHERE` 静默丢弃）。边界未成文。

## D-106 新增原因码的**确切集合**

**问题**：规格 §3.2 建议 5 个新码（`TIME_PARSE_FAILED`、`TIME_ZONE_UNDETERMINED`、`TIME_FORMAT_NOT_ALLOWED`、`MISSING_EVENT_ID`、`TIME_AMBIGUOUS_LOCAL`），其中两个存疑。

| 子问题 | 选项 | 影响 |
|--------|------|------|
| a. `TIME_FORMAT_NOT_ALLOWED` 是否单列 | ① 单列 ② 并入 `TIME_PARSE_FAILED` | 单列能把"数据脏"与"画像滞后"分开（运维动作完全不同）；代价是多一个码 |

**本草案倾向**：a①（单列）、b②（复用，不新增）、c②（延后）。
**不裁决的后果**：C2「坏时间负例（逐码）」**无法列出断言清单**。

## D-108 quarantine 的结构化字段 + 时间类 DQ 规则

**问题 A（结构化字段）**：plan L157 要求「保留**原因码**和**原位置**」。「原位置」今天只有 `raw_path`（隔离文件路径），**无行号、无源文件**。而 `Violation.lineNo` **已存在**（`EventContractValidator.java:30`），却在调用点被写死为 `check(text, 0)` ⇒ **行号被丢弃**。

| 选项 | 影响 |
|------|------|
| ① 新增 `reason_code VARCHAR(64) NULL`（加法列，历史 `NULL` = 未知） | 需 Flyway 迁移 ⇒ **属 D-092 停止条件，必须总控放行** |
| ② 不改表，把码塞进 `reason` 前缀（如 `[TIME_PARSE_FAILED] …`） | 不用迁移；但**结构化程度低**、且污染自由文本可读性 |
| ③ 不改表也不改文本 | 违反 plan L157 |

**问题 B（时间类 DQ 规则）**：`data_quality_result` 今天 **0 条时间相关** `rule_code`。指导书 §7.3 规则 #11 要求 `ingest_time - event_time` 的 P95 与迟到率（它**隐含要求时间可解析**）。

| 选项 | 影响 |
|------|------|
| ① 新增 `TIME_PARSE_FAILED_RATE`（ERROR，记录）与 `LATE_EVENT_RATE`（WARN） | 与既有 15+ 规则同构；须遵守 §7.3 L480「BLOCKING 规则须有失败负向验收」 |
| ② 不加，只做行级 quarantine | 失去"这批还能不能发"的判断 |

**本草案倾向**：A①（加法列，且**不改写历史**）、B①。

## D-109 源时区与 `source_system` 是否同通道注入

**问题**：D-056 已裁 `source_system` 由 `spark-submit --extra` 注入。而 P2-02 需要**按源**取时区。若两者走**不同**通道，会出现「源标识正确、时区缺失」的错配；更糟的是该错配会被**误报**成 `TIME_ZONE_UNDETERMINED`（把配置缺报成数据问题）。

| 选项 | 影响 |
|------|------|
| ① 源时区复用 `--extra` 同一通道 | 两者同源同生共死，不可能错配；代价是需扩 `--extra` 的载荷（**改 CLI 参数结构 ⇒ 注意 D-092 停止条件**） |
| ② 源时区由作业自行读 DB | 需在 Spark 侧引入 DB 读；与"作业不读元数据库"的既有边界可能冲突 |
| ③ 源时区写死在作业参数里 | 与"按源"矛盾 |

**本草案倾向**：①，并**明确它是否触碰 D-092 的「改既有 CLI 入参名」停止条件**（若只是**新增**一个 `--extra` 键而非改名，建议判为不触碰；**但需总控认定**）。
**不裁决的后果**：A3 无法确定源时区的取得方式 ⇒ 无法开工。
