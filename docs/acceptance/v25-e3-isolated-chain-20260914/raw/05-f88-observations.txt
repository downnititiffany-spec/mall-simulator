结论：存在**判定路径**（可达、语义明确），但**类型化异常是死代码**（声明了、全仓无人 throw）；本轮 26 行**未触发**。

    · RuleSeverity.java:160  default -> UNREGISTERED；:62 `UNREGISTERED = BLOCKING`（保守默认，宁可阻断不停机静默放行）
    · RuleSeverity.java:366-370 RuleVerdict.unregistered(...) 的说明即「未登记规则码：按保守默认阻断，须先登记规则版本（§7.3.1 line 524：不得盲信传来的 WARN）」

观察 3：data_quality_result 的 severity 落地成什么？
────────────────────────────────────────────────────────────────────────
结论（本轮 26 行实测）：落库的是**平台归一化后的有效档位**，不是作业/规则的字面量；
      **条件观察项的两个分支都真实出现了**：通过 ⇒ 落 WARN，未通过 ⇒ 升为 BLOCKING；
      也存在「WARN 且 passed=0」的行（观察项未通过但不阻断）。
      因此不能把这一列当作「声明档位」来统计，也不能把「severity=BLOCKING」直接读成「声明为阻断」。

实测分布（raw/22b-isolated-meta-evidence-run2.txt:115-137「data_quality_result 严重度落地分布」）：
    BLOCKING 23 行 / WARN 3 行 / ERROR 0 / INFO 0 / UNREGISTERED 0
    三条 WARN 行（全在 run 2）：
      id=7  LANDING     EVENT_ID_UNIQUE                WARN passed=1  detail「event_id 重复率=0.000000（未超批准阈值，观察项） OK
                                                                   [阈值判定通过 ⇒ 观察项，不阻断（确定性去重已证且重复率未超批准阈值）]」
      id=10 ADS_STAGING ADS_STAGING_SNAPSHOT_ISOLATION  WARN passed=0  detail「存在其它快照暂存分区（不阻断发布，pub 将按引用关系清理）…」
      id=13 PUBLISH     PUB_DQ_EVENT_ID_UNIQUE          WARN passed=1  detail「观察项：重复 event_id 比率，不阻断发布」
    对照 run 1 同一规则码的相反分支：
      id=3  LANDING     EVENT_ID_UNIQUE                BLOCKING passed=0 detail「event_id 重复率=0.010989（超批准阈值，阻断） FAILED
                                                                   [阈值判定未通过 ⇒ 由观察项升为阻断（§7.3.1 line 522「超过阈值阻断」）]」
    ⇒ 同一 rule_code=running 同一定义，落库档位随 passed 变化（WARN↔BLOCKING）—— 这是**设计意图**，
      QualityChecker.java:186-189 的 javadoc 明写「同一规则码在通过/未通过两种情况下落库的严重度可以不同，这是设计意图，不是不一致」。
    ⇒ 但也有真缺陷面：**列名 `severity` 同时承担两种语义**（声明档位 / 有效档位），且 V19/V20 才补的
      `effective_severity` 正说明「有效档位应与声明档位分列」。当前 14 列版本下，做统计的人极易把 id=7 的 WARN
      读成「声明 WARN」，把 id=3 的 BLOCKING 读成「声明 BLOCKING」——两个结论都不对。属**可裁决的语义缺陷**。
