## 4. 草案指出的现状缺口（转述，待实施车道实测确认）

1. **ODS 12 公共列缺 4**：`raw_event_type`/`landing_file`/`payload_json`/`payload_hash`。全仓检索三词只命中 `docs/**`，`spark-jobs/src`、`analytics-server/*/src`、`warehouse/ddl`、`contract-specs` **零命中** ⇒ 计划书 L79 是目前唯一权威 ⇒ **没有任何机器可读的 ODS v2 列所有者**。
2. **payload 是"解析后重写"**：`EventOdsLoadJob.scala:37` 用闭合 `StructType` 读 JSON，模板一律 `payload.<f> AS payload_<f>` ⇒ **没有任何列保存原始对象字符串**，逐字节保真今天不可能成立。
3. **额外字段确实在丢**（键普查）：`available_qty`(9 行)/`quantity`(9 行)/`reserved_qty`(8 行) 在数据里有、schema 里没有——而这三个键**正是契约要求的字段**（`canonical-event.v1.schema.json` L764/774/778/802/812/816/848/853）⇒ 性质是"契约内字段一致性缺口"，不只是额外字段问题。反向：schema 声明的 `available`/`reserved` 在契约与真实数据中**都不存在**。
4. **`source_system` 由行内取值**（`OdsLoadSql.scala:96-97`）⇒ 与计划书 L150「由平台注册表注入而非信任外部值」冲突；`source_file` 是常量字面量 `'landing'` 且被测试断言为"正确"＝**常量冒充事实**。
5. **列集有两个所有者**：`warehouse/ddl/00-ods.sql` 与 `LocalSchemaInitJob.scala:43-82`，逐列相同；真实链路跑的是后者 ⇒ 只改一处会造成本地/集群分叉。
6. **ODS 今天没有任何去重**；去重在 DWD 且键是 `event_id` 单键（计划书要求 `(source_system, event_id)`）；`dwd_reject_record.raw_payload` 恒 NULL。
7. **`items` 类型不一致**：契约声明为数组，真实数据全为字符串 ⇒ `EventContractValidator.java:124-134` 的子项金额校验**静默跳过**。

## 5. 最关键的 3 条断言（草案 §5 摘要）

- **A2 逐字节保真（独立 oracle）**：输入夹具第 1 行 → ODS 的 `payload_json` 与"非 Spark 工具原样截取 payload 对象字节"的 SHA-256 相等，且 `payload_hash` 等于该值；**语义等价但字节不同的负例必须变红**（如 `"1.50"`→`"1.5"`）。
- **A3 额外字段不丢**：新建夹具（含契约与画像都没有的 `coupon_code`）→ `payload_json` 中可见，且 `warehouse/ddl/**` 哈希逐字节不变；**改动前同输入必红**（正向对照）。
- **A4 契约内字段回归**：stock/product 行 → `available_qty`/`quantity`/`reserved_qty` 可见且值逐字节一致，计数必须 == 9/9/8；改动前 100% 不可见（已实测）。
